模型权重加载成功，只说明固定参数放得下。真正接入用户后，每个活跃序列还会留下自己的上下文状态。显存预算中的这部分会随请求变化：它就是 <Term id="kv-cache" />。

## 先数一个 token 保存多少数据

对于普通全注意力 Transformer，假设有 $L$ 层、每层 $H_{kv}$ 个 K/V 头、每个头维度 $d$，每元素占 $s$ 字节。每 token 的缓存数据量约为：

$$B_{token}=2LH_{kv}ds$$

系数 2 代表 K 和 V。若有 N 个等长活跃序列，每个保留 T 个 token，则 $B=2LH_{kv}dsTN$。变长时应把 TN 替换为各序列保留 token 数之和。

例如 32 层、8 个 KV heads、维度 128、BF16 每元素 2 字节：每 token 131,072 字节，即 128 KiB。单序列 8,192 token 约 1 GiB，8 个这样的序列约 8 GiB。这里使用二进制 GiB，不要与十进制 GB 混用。

## 缓存中到底是什么

普通自回归生成中，每推进一个位置，对应 K/V 会进入后续上下文。实现中的缓存槽位分配时机和 token 计数可能存在一步差异，容量规划要以引擎实际定义为准。

## 为什么实际占用不等于公式

公式只数理想 K/V 元素。实际引擎还需要分页块、对齐、元数据和临时缓冲。总显存还包括权重、激活、执行图、通信缓冲以及其他进程。降低 KV <Term id="dtype" label="dtype" /> 也不保证总显存减半，因为只有 KV 那一项变了。

滑动窗口注意力可能只保留限定范围；混合模型不同层的缓存形态可能不同；<Term id="tp" label="TP" /> 对 KV 的分片或复制又受头数与实现约束。不能把公式作为所有模型的万能计算器。

## 分页解决的是组织方式

设每页容纳 4 个 token，一个长度 10 的序列需要 3 页，最后一页只用了 2 个位置。逻辑连续的序列可以映射到不连续的物理块，避免为了未来长度预留巨大连续空间，也方便复用与回收。

分页并没有消除每 token 的 K/V 本身，也没有让碎片变成零。页过大可能增加末页浪费；页过小又增加管理开销。PagedAttention 的关键是让注意力计算适配这种块映射，而不是简单调用操作系统换页。

你应同时看活跃序列、缓存占用、排队和抢占，而不是只看显存总量。引擎可能提前预分配内存池，因此 `nvidia-smi` 中占用不变不代表 KV 使用量不变。下一节会区分预留容量、已用块和能够复用的块。

## 把分页表真正走一遍

仍用每页 4 个 token 的小例子。序列 A 的逻辑页 0、1、2，可以分别对应物理块 7、2、9。读取第 9 个 token（从 0 开始编号是位置 8）时，先算逻辑页 `8 // 4 = 2` 和页内偏移 `8 % 4 = 0`，再查到物理块 9 的偏移 0。逻辑上相邻，不要求物理地址相邻。

若新 token 进入位置 10，它仍落在逻辑页 2 的偏移 2，不必申请新页；位置 12 才需要逻辑页 3。注意力 kernel 根据块表读取历史 K/V。代价是间接寻址和块管理，收益是按实际增长分配，不用为最大上下文一次性预留连续大块。

假如序列 B 与 A 共享已经完成的前 8 个 token，可以让两者的前两项页表引用相同物理块。块的引用计数从 1 变成 2；A 结束只减到 1，不能立即回收。两者后来分叉时，已有的只读前缀可继续共享，待写入块是否需要复制取决于实现的共享粒度与写时复制规则。不能在仍被 B 使用时覆盖这些字节。

## 从显存预算倒推能够接多少请求

设一张设备提供给实验的总预算为 80 GiB，示例中权重、激活与运行时等占 48 GiB，另外留 8 GiB 的波动余量，那么可用于 KV 的教学预算是 24 GiB。这些数字用于算例，不是某个模型的真实配置。

按前面的每 token 128 KiB，24 GiB 可容纳 196,608 个保留 token。若每请求要保留 8,192 个 token，理想上限是 24 个这样的请求；若平均 2,048 个，看起来可容纳 96 个。但不能只用平均值接满：长尾输入、正在增长的输出、页碎片和引擎调度都可能提前触发限制。

这里算的是同一设备上的 KV 数据预算。并行部署中，需要明确哪些头被分片、哪些被复制，以及最紧张设备的负载。把全模型总 KV 直接除以 GPU 数，可能得到过于乐观的结论。

## 看见 OOM，先分清是哪一种不足

加载模型时失败，优先看权重与加载峰值；运行途中失败，要结合活跃 token、临时激活、执行图、通信缓冲和其他进程。引擎显示 KV 块耗尽却没有系统级 OOM，也可能只是它管理的缓存池达到上限，需要排队、抢占或拒绝新工作。

一个合理的检查次序是：确认模型和精度 → 记录单请求基线 → 限定输入输出长度 → 分批增加并发 → 对齐引擎 KV 使用和设备总显存。每次只改一项；修改 `gpu-memory-utilization` 会改变预算分配，却不会凭空增加设备容量。
