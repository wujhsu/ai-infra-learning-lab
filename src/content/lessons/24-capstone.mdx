最后一个项目不追求组件最多，而是让每个组件有明确职责、每个结论有证据。你将把同一套负载从单服务带到工作组，再加入观测与发布控制。

## 第一阶段：建立可信基线

固定 vLLM 镜像、模型 revision、输入输出长度和 <Term id="gpu" label="GPU" /> 配置。完成健康检查、流式客户端、负载生成、指标快照和冷/热启动记录。用相同负载重复测试，确认波动范围。

交付 `environment.json`、启动配置、原始 JSONL 测量记录和一页解释。报告 <Term id="ttft" label="TTFT" /> 或首内容口径，不混用；失败请求单独计数，不能静默丢弃。

## 第二阶段：扩展协作与资源管理

先验证多卡 <Term id="allreduce" label="AllReduce" />，再运行多卡模型；再进入多节点，验证 rank 发现、网络与全组预检。随后将工作负载纳入 Kubernetes/<Term id="lws" label="LWS" />，最后单独验证 <Term id="dra" label="DRA" /> 的设备选择与节点准备。

每增加一层都保留上一个可运行版本。否则出现故障时，无法判断是模型、通信、容器、调度还是设备驱动引入的问题。

## 第三阶段：观察并恢复

接入请求、引擎、<Term id="pod" label="Pod" />、节点和 GPU 的关联信息，完成三个诊断场景：长输入、KV 压力、受控坏版本。<Term id="canary" label="Canary" /> 在路由层切换稳定与候选服务，LWS 管理各自模型组，避免控制器所有权冲突。

回滚后确认新流量路由、在途请求和残留资源。Agent 仅在有足够证据时提出修复，修改通过评审与测试后进入下一次发布。

## 每项验收都对应可观察结果

| 验收项 | 需要提交的证据 |
|---|---|
| 服务能正确回答 | 请求参数、响应、模型与软件版本 |
| 性能结论成立 | 原始样本、负载分布、统计方法与比较条件 |
| 多卡通信正确 | rank 数、输入、预期与实际归约结果 |
| 调度与准备可解释 | Claim、Pod、驱动状态和事件 |
| 预检能阻止坏组 | 失败 rank、日志、退出码和组内结果 |
| 回滚有效 | 实际路由比例、分析状态、恢复后的指标 |

## 写一份真正有用的复盘

按照“我原本以为 → 测量看到了什么 → 为什么发生 → 我改了什么 → 还没有验证什么”组织。明确列出失败尝试，它们能帮助你理解边界。

不要把所有指标都写成改善。如果缩短首 token 的方案增加了显存或降低了吞吐，把代价写出来。工程判断的价值就在于知道为了哪个目标做了什么交换。

## 完成之后怎样继续深入

若通信成了瓶颈，进入 <Term id="nccl" label="NCCL" /> 同步与 KernelAgent；若多后端适配复杂，进入 PyTorch Generalization；若拓扑约束不清晰，进入 DRA 高级专题。上午 Keynote 则用于回顾生态位置，不需要记住所有项目名称。

你最终应能独立画出请求路径、解释主要状态、选择观测方法，并提出一个可验证的优化或恢复方案。这比“成功启动过所有组件”更接近掌握。
