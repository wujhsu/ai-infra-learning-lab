两个人都向模型提交同一份长文档，只在末尾提出不同问题。前半段 token 完全相同，模型为它们计算的历史 K/V 是否可以共享？这就是前缀缓存最直接的应用。

## 什么才算相同前缀

匹配依据通常是实际 token 序列及影响计算的必要上下文，而不是肉眼看起来相似的文字。系统提示、chat template、模型 revision、适配器或多模态输入不同，都可能改变可复用结果。

设请求 A 是 `[a,b,c,d,x]`，请求 B 是 `[a,b,c,d,y]`。前四个位置可能复用，末尾分别处理。如果 B 改成 `[a,b,z,d,y]`，不能直接把第四个位置当作原来的 d：因果表示依赖此前上下文。

## 块与前缀链

实现通常以块为单位管理，完整块更容易参与共享。一个块的身份可能依赖之前块的身份，因此“块里文字相同”未必足够。最后一个未满块如何处理，以及不同 attention 类型的支持，必须对照引擎版本。

前缀缓存主要节省可复用输入的计算，不会自动消除新 token 的生成，也不保证网络加载免费。vLLM 官方 APC 文档明确讨论其适用范围与限制。

## 命中率至少有两种口径

按请求算命中：100 个请求里 90 个有任意复用，命中率 90%。按 token 或字节算命中：实际省下多少输入工作量？一个只命中 16 token 的长请求，与命中 16,000 token 的请求，不能只用“都命中”一笔带过。

进一步还需要看命中后的时间收益和缓存占用。命中很高但每次跨网络搬运巨大 KV，可能无法达到预期 <Term id="ttft" label="TTFT" />。

## 怎样设计不自欺的 A/B 实验

准备三个负载：完全相同长前缀、相同长度但不同内容、前缀中段改变。分别在开启与关闭缓存的条件下测量。每组记录冷缓存与热缓存，随机交错顺序，保持并发和输出长度一致。

比较 TTFT、输入计算量、缓存查询与命中、显存和吞吐。不要用“第二次比第一次快”就断言缓存起作用，第二次也可能只是完成了编译热身。

## 多租户边界也是正确性的一部分

复用状态时要明确模型、适配器及租户隔离边界。不能为了提高命中，把本来不应该共享的上下文混在一起。具体隔离能力应来自引擎支持与服务设计，不在客户端自行拼凑一个不完整的缓存键。
