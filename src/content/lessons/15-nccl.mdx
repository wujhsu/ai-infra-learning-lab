传统执行方式可以先收齐一整块输入，再启动计算。但如果前半块已经到达，计算却仍在等后半块，系统就失去了重叠机会。<Term id="nccl" label="NCCL" /> Device API 让自定义 <Term id="gpu" label="GPU" /> kernel 直接组合通信原语，尝试缩小这样的等待。

## 先看对象各管什么

Device communicator 提供通信上下文与能力；window 指定注册的内存范围；team 决定参与的 rank 子集；coop 决定共同执行操作的线程范围。team 和 coop 都是“组”，但前者组 rank，后者组线程，不能混淆。

<Slide id="advanced-nccl-14" minute="四个对象把参与者、内存、线程协作与 transport capability 分开。Host 先声明资源和能力，device kernel 接收相应句柄。" />

## Symmetric memory 不要求地址数值相同

两个进程虚拟地址可以不同，只要注册窗口具有可对应的布局与偏移，就能根据 peer 和 offset 定位相应数据。地址看起来一样也不自动代表是同一块可访问物理内存。

<Slide id="advanced-nccl-20" />

<Term id="lsa" /> 用于具备 load/store 可达性的对端内存路径；Multimem 还要求相应硬件多播能力；<Term id="gin" /> 允许 GPU 发起网络通信。它们是不同能力，实验前必须查询支持条件。

## 从完整缓冲区到 tile

tile 是大张量中的一个计算/传输小块。以 <Term id="moe" label="MoE" /> 为例，某块 dispatch 完成后就可以开始该块计算，同时后续块继续到达。收益来自阶段重叠，而不是简单地把某次复制命令换了名字。

若 n 块每块传输 t、计算 c，完全串行约为 `n(t+c)`；理想双阶段流水线约为 `t+c+(n−1)max(t,c)`。第一块需要填充，最后一块需要排空，不能直接把时间写成 `max(nt,nc)` 后忽略边界。

## 同步是正确性的组成部分

开始读某块之前，要确认写入数据已经对消费者可见。消费者结束前，生产者不能重用仍被读取的缓冲。设备上的操作发起、源缓冲可重用、远端数据可消费，可能是不同事件。

注册和创建 communicator 通常在热循环外摊销，但其生命周期必须覆盖实际工作。过早注销 window 或释放设备内存会破坏正在进行的传输。

## 版本不能混用

官方 NCCL 文档说明 Device API 从 2.28 开始提供，GIN 从 2.28.7 开始提供；后续版本增加能力并存在编译/运行时兼容条件。本教材进阶实验固定 2.31.2 并记录 CUDA 与硬件条件，不把会议中的 API 片段直接拼到任意系统上。

## 一个三块数据的纸上时间表

设每块传输 3 ms、计算 5 ms，共三块。串行要 `3 × (3+5)=24 ms`。一种带单槽交接的教学流水线如下：

| 数据块 | 传输区间 | 计算区间 |
|---|---|---|
| 0 | 0–3 ms | 3–8 ms |
| 1 | 5–8 ms | 8–13 ms |
| 2 | 10–13 ms | 13–18 ms |

总时间 18 ms，与 `3+5+2×5` 一致。为什么传输不是一直连续？这个简化模型只按瓶颈节奏交接，空闲时间提醒我们：流水线不等于每个资源时时满载。增加更多缓冲可以改变中间排程，但不会自动突破同一阶段的吞吐上限。

若把计算从 5 ms 加快到 1 ms，瓶颈转到每块 3 ms 的通信。继续优化计算的收益会变小。这也是演示让你同时调两个阶段的原因：先找最长依赖路径，再决定优化对象。

## 双缓冲并不能替代所有权协议

生产者写缓冲 A 的时候，消费者可以读取缓冲 B；下一轮交换角色。这叫双缓冲。但在交换前仍要确认两件事：B 的消费已结束，A 的新数据已可见。单纯使用两个指针，既不能保证远端写完成，也不能保证消费者不读到旧轮次数据。

可以把每个槽位想成三个状态：可写 → 数据就绪 → 消费中 → 可写。真实实现中的 signal、计数器、epoch 和 barrier 用于建立这些关系。下面只是协议伪代码，不对应某个具体 NCCL API：

```text
生产者：等待 slot 可重用 → 写入第 k 轮数据 → 发布第 k 轮就绪
消费者：等待第 k 轮就绪 → 读取并计算 → 发布第 k 轮消费完成
```

必须带轮次概念，否则上轮遗留的“已就绪”标记可能被本轮误读。还要检查所有参与线程是否按 API 要求合作调用，不能只让一部分线程进入要求集体参与的操作。

## 怎样证明真的发生了重叠

先通过小输入与参考实现比较，确保重叠前后结果一致；再预热并测稳态。设备时间线中应该能看到目标通信与计算的时间区间重叠，而不是只看主机发起函数相邻。最后比较端到端耗时，因为两个区间重叠也可能互相争用带宽，使总耗时反而变长。

实验至少保留串行、仅调整分块、分块加重叠三组结果，固定数据尺寸、精度和拓扑。若小块变多后变慢，检查启动、同步、尾块和管理成本；若拓扑改变后收益消失，检查实际 transport 与带宽路径。不要把某个融合 kernel 的单点加速比直接当成整个推理服务的加速比。
