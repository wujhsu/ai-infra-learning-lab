第一个部署的目标不是“越大越好”，而是建立一个可重复的起点：知道运行的模型、软件版本、资源条件和请求参数，并能保存响应与观测结果。

## 先分清四个版本

服务镜像决定 vLLM 与其依赖；模型 revision 决定权重和配置；<Term id="gpu" label="GPU" /> 驱动影响设备兼容性；启动参数决定并行方式和资源预算。只记录“用了 vLLM”不足以复现实验。

本教材将 vLLM 服务实验固定到 `v0.29.0`。模型使用一个小型公开模型作为起点，模型仓库 revision 需要在实验准备阶段解析成具体 commit，并记录到环境文件中。标签与模型名称都可能变化，内容 hash 更适合长期复查。

## 启动容器时每个参数都应该有目的

```bash
docker run --rm --name inference-lab --gpus all \
  -p 127.0.0.1:8000:8000 --shm-size 2g \
  -v "$PWD/model-cache:/root/.cache/huggingface" \
  vllm/vllm-openai:v0.29.0 \
  Qwen/Qwen2.5-0.5B-Instruct \
  --served-model-name lab-model \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.8
```

`--gpus all` 让容器可访问设备，但模型并行度仍由引擎配置决定。端口只绑定本机是为了这个单机实验。模型缓存卷避免每次重建重新下载。`--max-model-len` 限制可接受序列长度；`--gpu-memory-utilization` 是引擎内存预算参数，并不是 GPU 实际忙碌比例。

这段命令用于解释结构。执行正式实验时使用实验包的 `serve.sh`，它还要求固定 `MODEL_REVISION` 并保存镜像信息。

## 从最小请求验证开始

```bash
curl http://127.0.0.1:8000/v1/models
curl http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"lab-model","messages":[{"role":"user","content":"用一句话解释缓存"}],"max_tokens":64,"temperature":0,"stream":true}'
```

第一条确认服务可访问并查看对外模型名称。第二条请求流式输出。`temperature=0` 减少采样随机性，但不保证不同硬件、后端或执行批次之间完全逐位一致。

## 成功响应之后还要检查什么

读取 `/metrics`，观察是否存在请求与引擎相关指标。保存启动日志中的软件版本、可用 KV 预算和模型配置。指标名称可能随版本变化，先读当前端点的 HELP 与 TYPE，再写查询。

不要把模型下载、冷启动、编译热身和稳定服务混成一个耗时。冷启动本身值得测，但要单独成组记录。

## 常见失败的定位顺序

| 现象 | 优先检查 | 不应直接得出的结论 |
|---|---|---|
| 容器看不到 GPU | runtime、驱动、设备暴露 | vLLM 模型不支持 |
| 启动时 OOM | 权重、长度预算、并行度、其他进程 | 一定是 KV Cache 泄漏 |
| HTTP 404/模型找不到 | 接口路径、served model name | GPU 不健康 |
| 长时间没有响应 | 加载日志、队列、引擎状态 | 一定是网络慢 |

接下来我们会让这个服务承担多个负载，而每次只改一个变量。这样才能把“快了”变成有证据的解释。
