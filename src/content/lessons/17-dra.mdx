传统设备请求往往先问“要几个”。<Term id="dra" /> 进一步允许询问“设备有什么属性、如何访问、是否准备好”。理解 DRA，最有效的方法是沿一次请求走完生命周期。

## 四类对象各自表达什么

**ResourceSlice** 是驱动发布的设备库存与属性。**DeviceClass** 提供设备选择规则。<Term id="claim" /> 表达请求并承载分配结果。**ResourceClaimTemplate** 用于为工作负载生成相应声明。

它们不是四份重复配置：库存由设备提供方维护，请求由使用方表达，类别连接两者。对象存在也不代表分配成功；有分配结果也不代表节点准备已完成。

## 跟着一次请求走

驱动先发布设备。用户创建或引用 Claim。调度过程结合节点约束和设备选择条件作出分配与绑定。节点 kubelet 需要时调用驱动准备资源；驱动可借助 <Term id="cdi" label="CDI" />（Container Device Interface，容器设备接口）描述设备如何进入容器。容器结束后还涉及解除准备与回收。

## 一个最小声明的形状

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceClaim
metadata:
  name: example-gpu
spec:
  devices:
    requests:
      - name: gpu
        exactly:
          deviceClassName: example-gpu-class
          allocationMode: ExactCount
          count: 1
```

`example-gpu-class` 是说明用途的名字，必须替换为驱动真实提供的 <Term id="deviceclass" label="DeviceClass" />。完整实验会先枚举类别并用 API Server dry-run 校验。仅验证 YAML 能被解析，不能证明驱动有能力完成分配。

## 失败应该看哪一层

Claim 没有分配：查库存、类别规则、节点约束与资源竞争。<Term id="pod" label="Pod" /> 已绑定但容器进不去：查 kubelet、驱动 prepare 和设备注入。运行后设备异常：查驱动状态和工作负载恢复策略。不要在不同阶段重复删除 Pod，导致证据丢失。

## 核心能力与高级功能分开核对

会议讲义同时出现 1.36、1.37 和 1.38 计划。实验以 Kubernetes 1.37 作为声明基线，高级拓扑、派生属性和驱动扩展逐项核对 feature gate；后续版本计划只放进进阶说明。

DRA 解决了表达与协作机制，但仍需要驱动提供准确库存、稳定状态和正确设备准备。集群规模变大后，<Term id="resourceslice" label="ResourceSlice" /> 与状态更新频率也会影响控制面负载。

## Pod 怎样真正引用这个声明

仅创建上面的 Claim，还没有告诉哪个容器要使用它。下面的片段建立两层名字关联：Pod 中的 `resources` 指向现存 Claim `example-gpu`，容器再引用 Pod 范围内名为 `gpu` 的条目。

```yaml
spec:
  resourceClaims:
    - name: gpu
      resourceClaimName: example-gpu
  containers:
    - name: app
      image: your-verified-gpu-image
      resources:
        claims:
          - name: gpu
```

这是字段关系片段，不是可直接提交的完整 Pod；镜像也必须替换。Claim 请求里的 `gpu`、Pod resourceClaims 的 `gpu` 和对象名 `example-gpu` 各有自己的作用域。名字相同不意味着这些对象自动连上，显式引用才建立关系。

若工作负载每个副本都需要独立声明，ResourceClaimTemplate 可以用于生成声明；若显式复用现存 Claim，则必须理解其消费者和分配语义。不要因为两个 Pod 都写了同一个名字，就假设驱动支持任意并发共享一张卡。

## 为什么设备选择和节点调度要一起考虑

设节点 A 有足够显存，但缺少可用 CPU；节点 B 的 CPU 足够，但设备不满足请求。分别选择“最佳 GPU”和“最佳节点”后再拼起来，会得到无法运行的组合。调度过程必须找到同时满足 Pod 普通资源、节点约束和设备要求的候选。

另一种情况是资源被其他请求占用。即使几秒前的库存面板显示存在一张设备，当前 Claim 也未必能拿到它。库存、已分配状态和节点准备状态的更新发生在不同组件间；需要检查实际对象与事件，不能只依赖某一张历史截图。

这解释了为什么 DRA 需要 Kubernetes 调度器与驱动合作，而不是仅在容器启动后运行一条 `nvidia-smi`。后者最多证明某个运行环境能够看到设备，不能替代之前的选择与资源协调。

## 沿对象读故障，而不是沿猜测重启

| 观察 | 下一步检查 | 不能据此得出的结论 |
|---|---|---|
| 查不到预期 ResourceSlice | 驱动运行、发布权限、所在 pool 与节点信息 | 集群中物理上没有 GPU |
| Claim 一直未分配 | 真实 DeviceClass、选择条件、其他约束和竞争 | 一定是容器镜像问题 |
| Claim 已分配、Pod 启动卡住 | 节点事件、kubelet 与驱动准备日志 | 分配成功就一定能访问设备 |
| 容器运行但设备不可用 | CDI/运行时、驱动健康与容器实际权限 | 删除 Claim 就一定能修复 |

`kubectl describe` 用于先读事件，`kubectl get ... -o yaml` 用于核对期望与状态。涉及已被工作负载使用的 Claim 时，先理解消费者与清理关系；不要为了“清零状态”丢掉排障证据。

## 最后再问：这个需求是否需要 DRA

如果需求只是独占一张兼容 GPU，现有 device plugin 可能已经足够。需要更丰富属性选择、明确设备生命周期或实际驱动支持的高级配置时，DRA 才提供新的表达空间。选择依据是工作负载要求、集群版本与驱动成熟度，而不是仅因为 API 更新。
