写下 `y = x * 2 + 1`，看起来只有一个表达式，但底层可能发生多次 <Term id="gpu" label="GPU" /> 工作提交。高级代码短，不等于执行路径短；同样，代码行数多也不一定慢。

## 从算子到 kernel

PyTorch 中的算子表达张量操作的语义，例如乘法、加法和矩阵乘法。底层实现可能调用硬件库或生成 <Term id="kernel" />。一个算子可以由多个 kernel 实现，多个算子也可能被融合进一个 kernel。

Eager 模式通常随着 Python 执行逐步调度操作。`torch.compile` 尝试捕获可编译部分，通过后端进行优化。编译不意味着所有 Python 逻辑都能无条件变成一个 GPU kernel：动态行为、图中断、形状变化都会影响实际路径。

## 一个可观察的表达式

```python
import torch

def pointwise(x):
    return torch.relu(x * 2 + 1)

x = torch.randn(1024, 1024, device='cuda')
compiled = torch.compile(pointwise)
expected = pointwise(x)
actual = compiled(x)
torch.testing.assert_close(actual, expected)
```

这段代码先检查正确性。首次调用 `compiled` 可能包括编译，因此不能拿它与已经热身的 eager 单次运行直接比较。不同 shape 或输入类型还可能触发重新编译。

## GPU 执行通常是异步的

CPU 提交工作后可能立即继续。若用 Python 时钟只围住一个调用，测到的可能主要是提交时间，而不是 GPU 完成时间。使用 CUDA events 或在计时边界同步，才能把完成等待包含进去。

```python
# 独立计时示意；性能实验还需多次重复与统计。
for _ in range(10):
    compiled(x)
torch.cuda.synchronize()
start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
start.record()
for _ in range(100):
    compiled(x)
end.record()
end.synchronize()
print('平均 GPU 时间(ms):', start.elapsed_time(end) / 100)
```

这仍不包含完整服务端排队、Python 业务处理和网络时间。计时口径必须跟你的问题一致。

## 与框架通用化的联系

GPU 不是唯一加速器。PyTorch 的统一入口尝试把设备管理等公共行为抽象出来，但某些 kernel 和 profiler 仍然属于具体硬件。统一 API 让上层代码更易维护，不代表不同后端支持完全相同，也不代表性能可直接迁移。进阶专题会进一步拆解这条边界。
