当用户说“今天比昨天慢”，你需要先知道慢在哪里、影响多少请求，以及能否找到同一次请求的相关证据。一个数字、一条日志、一张 trace 图分别提供不同视角。

## 三种信号不是互相替代

**Metrics** 是按标签与时间聚合的度量，适合观察趋势和报警。**Logs** 是离散事件记录，适合解释失败上下文。<Term id="trace" /> 描述一次执行的阶段和关联，适合看时间花在哪里。

| 想知道什么 | 优先信号 | 还需要什么 |
|---|---|---|
| 最近五分钟是否整体变慢 | 延迟分布指标 | 请求量和长度分布 |
| 一个请求卡在哪个阶段 | Trace | 完整传播与采样条件 |
| 某个 worker 为什么退出 | 日志与事件 | rank、Pod、节点关联 |
| GPU 忙但产出下降 | 引擎与硬件指标 | 时间窗口和负载解释 |

## Counter、Gauge、Histogram 的区别

Counter 是累计值，通常看一段时间内增长率；进程重启会重置。Gauge 是某时刻的值，例如队列长度。Histogram 将观测值累计进桶中，可用于估计分位数。

如果把累计 token 数直接画成速度，曲线会一直上升却回答不了吞吐。应该按时间计算增量。队列长度则应保留当前状态，不能当作永久累计计数。

## 从 SLO 决定该收什么

<Term id="slo" /> 必须说明观察对象、窗口、成功条件和排除规则。例如实验中定义“某个固定负载下，95% 请求首内容延迟小于 2 秒”，同时记录错误与取消。这里的 2 秒是练习目标，不是通用标准。

不要只统计成功请求：如果慢请求都超时退出，剩下请求的延迟可能变好，用户体验却更差。失败、超时和取消应有独立计数。

## 标签带来可检索性，也带来成本

模型、引擎实例、<Term id="pod" label="Pod" /> 和 <Term id="gpu" label="GPU" /> 标识有助于定位。但把每个 request ID 或完整 prompt 放进指标标签，会导致高基数和存储压力。请求级标识更适合 trace 或日志，敏感输入也不应默认采集。

## 统一语义要固定版本

OpenTelemetry 提供 span、属性和指标的共同约定。GenAI 规范仍在演进并已迁移到独立仓库；不能把会议上的一个字段名当成永久 API。应用侧、引擎侧和采集器的版本及属性映射要记录在同一份契约中。

## 一份最小观测清单

先收请求数、错误数、排队、首 token/首内容、后续输出、输入与输出量、KV 使用和抢占。再接入 CPU、网络与 GPU 指标。每增加一个面板，都写出它能验证的假设；无法解释用途的面板暂时不加。

后续实验同时保留原始 `/metrics` 快照、查询表达式和时间窗口，使图表结论可复查。
