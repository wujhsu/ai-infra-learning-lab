看到一个很慢的请求和一张很忙的 <Term id="gpu" label="GPU" /> 图表，不能直接断言后者导致前者。两条证据需要同一时间范围、同一实例映射，以及能解释机制的中间环节。

## 先建立请求级关联

网关创建或接收 trace context，并向下游传播。引擎生成代表排队、<Term id="prefill" label="Prefill" /> 或执行等阶段的 span 时，应保留父子或关联关系。`traceparent` 是常见的上下文传播格式，但只有各层实际支持并正确接入，链路才完整。

<Slide id="llm-observability-11" />

一条客户端请求也可能产生重试、拆分或异步工作，不能假设天然是一条线性父子树。span links 可以表达某些非树形关联；具体采用方式应跟随实际 instrumentation。

## 再建立资源级关联

从服务实例映射到 <Term id="pod" label="Pod" />、节点和 GPU UUID。GPU 序号 0 在不同容器或节点中可能指向不同物理设备，长期关联更适合使用稳定设备标识。容器重启后，Pod UID、进程和时间范围也可能变化。

<Diagram id="correlation" caption="请求级追踪与设备级指标通过实例、设备标识和时间窗口关联；共享资源的消耗不能强行精确归属。" />

## GPU 指标通常不是请求专属数据

连续批处理中，多请求共享一次 kernel 或一段设备执行。GPU utilization、<Term id="hbm" label="HBM" /> 活动和网络吞吐往往是时间窗口聚合值。它们能支持“这个时间段设备处于什么状态”，却未必能支持“这个请求消耗了多少 GPU 时间”的精确归因。

如果没有真实设备级追踪支持，不要制造一个看起来很完整的 per-request GPU span。诚实的空白比错误精度更有用。

## 用同一时间窗口问问题

请求 10:00:03 到 10:00:05 慢，硬件图表若按一分钟聚合，短暂尖峰可能被稀释。不同机器时钟偏差也会让事件顺序看起来错乱。收集器抓取周期、trace 采样率和时间同步都影响可见性。

观察缺失不等于没有发生：低采样 trace 可能漏掉故障，指标 scrape 失败也可能让曲线断裂。排障笔记应记录这些限制。

## 把现象串成可验证链

例如：用户 <Term id="ttft" label="TTFT" /> 上升 → 对应 span 的 queue wait 增加 → 同时引擎 KV 使用接近上限且发生抢占 → 检查活跃请求长度分布变化。最后一步需要负载数据支撑，不能因为两个曲线同时上升就直接宣告根因。

<Slide id="llm-observability-15" minute="讲义的诊断范式是现象、trace 阶段、相邻层指标、根因与调优动作。地图和标签只有进入具体检查步骤，才能变成排障能力。" />

## 留下一份可复查记录

每次调查保存症状、时间窗、受影响对象、候选假设、证据、反证和下一步。改变参数后重复相同负载，确认目标指标改善且没有把问题转移到错误率或其他请求上。

## 先统一时间，不要先拼仪表盘

客户端记录适合使用单调时钟计算同一次请求内部的间隔，避免系统时间校准造成负时长。跨机器对齐则需要墙上时钟和时间同步。二者用途不同：一个回答“经过多久”，另一个帮助回答“与其他机器的哪个时间段对应”。

例如客户端记录某请求 12:00:00 发起、12:00:02 收到首内容；服务器时钟却快 300 ms。若直接用两个机器的绝对时间相减，就会把时钟偏差误当网络或处理开销。记录时钟来源与估计偏差，必要时只比较各自可靠的局部区间。

## 把一条慢请求写成证据表

下面是用于练习归因的假设数据，不是本站运行结果：

| 层次 | 假设观察 | 它支持什么 |
|---|---|---|
| 客户端 | 首内容 2.0 s，之后输出平稳 | 首响应阶段需要调查 |
| 请求 trace | queue span 1.5 s，Prefill 0.3 s | 大部分可见延迟发生在计算前 |
| 引擎同窗口 | 等待请求增加，KV 使用率接近上限 | 缓存容量可能限制接纳 |
| 设备同窗口 | GPU busy 并非始终很高 | “计算单元全部跑满”不是唯一解释 |
| 负载记录 | 长上下文请求比例明显提高 | 提供一个可实验验证的上游变化 |

这一组合支持“长上下文占用 KV，使接纳受限并增加排队”的候选链。还需要反证：若限制上下文长度后队列没有改善，或 KV 曲线来自另一实例，假设就不能成立。链路中的每一步都应能够被一个观察或实验否定。

## 关联字段应放在哪里

trace ID 适合在日志中定位单次请求；服务版本、实例和设备标识适合建立资源关联。Prometheus 常规指标标签应控制取值数量，不要将任意用户输入、完整请求 ID 或不断变化的 prompt 作为标签。否则每个新值都可能创建新的时间序列，增加内存、存储和查询负担。

一个可行的关系是：指标发现异常窗口 → 在窗口内选取代表性 trace → 从相关日志补充错误细节 → 用实例/设备映射读取硬件指标。它不要求把所有数据塞进同一种存储，也不要求所有请求都永久全量记录。

## 采样会改变你能回答的问题

如果仅保留一小部分 trace，恰好没采到错误请求并不说明错误不存在。按延迟或错误选择保留的策略又会改变样本分布，不能拿它直接推算全体请求比例。指标和采样 trace 应互相补充，报告中保留采样规则。

GenAI 相关语义约定仍需按所使用版本核对：字段命名变化会影响查询和仪表盘。升级采集链时，先在一组固定请求上检查 context 传播、字段、时间单位和缺失值，再把新版本扩到完整系统。
