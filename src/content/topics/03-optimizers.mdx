优化器负责根据梯度更新模型参数。即使矩阵计算很快，优化器对大量参数与状态的读取和写回仍可能占用可观时间。因此这个五分钟场次可以展开成一个很好的性能与数值专题。

## AdamW 保存了什么

除参数和梯度外，AdamW 维护一阶、二阶矩等历史状态。每次更新涉及缩放、加法、平方和归一化等操作。若每一步分别运行，可能产生很多 kernel launch 和中间显存读写。

<Slide id="speedy-optimizers-2" />

## foreach 与 fused 不是同义词

foreach 批量处理多个 tensor 上的同一种操作，减少逐 tensor 调用；fused 路径还能合并同一更新链中的多个步骤，减少中间结果写回。横向与纵向是理解两者的方向。

<Slide id="speedy-optimizers-3" /><Slide id="speedy-optimizers-5" />

支持条件受设备、<Term id="dtype" label="dtype" /> 和版本影响，不能只把 `fused=True` 加到所有优化器上。内存峰值、编译与图捕获兼容性也要测试。

## 状态精度下降能省多少

如果原先两个状态 tensor 使用 FP32，改为 BF16，其自身字节数约减半。但模型参数、梯度、激活和其他缓冲没有随之全部减半，所以总训练显存不会机械下降 50%。

<Slide id="speedy-optimizers-7" />

数值范围与有效精度是不同概念。BF16 保留较大的指数范围，但有效位较少；更新很小或长期累积时，误差可能影响收敛。只比较 step 时间不足以证明替换正确。

## Functional API 把责任交给谁

面向对象优化器通常管理参数组和状态。functional 接口显式接收参数、梯度和状态，更便于自定义，但状态创建、dtype、checkpoint 和参数对齐都需要调用方处理。

<Slide id="speedy-optimizers-11" />

内部 `_functional` 等路径不能未经说明就当稳定公共接口。实验优先比较公开 AdamW 的 single/foreach/fused 路径；讲义中的内部 API 用于理解设计，不直接做生产依赖。

## 一份有意义的比较

固定模型、数据批次、种子、学习率和训练步数；分别测 step 时间、峰值显存和损失曲线，再检查任务指标。每个配置初始化独立状态，避免把上一次训练结果带进下一组。

Muon 涉及矩阵更新的算法变化，不能与单纯融合混成一个开关。要比较它，需另设优化超参数与收敛评价，本教材把它列为延伸阅读。
