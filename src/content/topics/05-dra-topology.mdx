“<Term id="gpu" label="GPU" /> 与 <Term id="nic" label="NIC" /> 在同一个 <Term id="numa" label="NUMA" />”听起来简单，但两个驱动可能使用不同属性名称与表达方式。调度系统需要共同语义，才能比较来自不同资源提供方的信息。

## 拓扑为什么不能只靠设备数量

两套分配都包含一张 GPU 和一张 NIC，路径却可能不同。额外的 CPU 插槽或 <Term id="pcie" label="PCIe" /> 层级会影响延迟和带宽。更复杂的平台还有 <Term id="nvlink" label="NVLink" /> fabric、分区和跨节点设备域。

<Slide id="kubernetes-dra-12" />

拓扑约束缩小候选集合，可能提高单任务效率，也可能降低可调度性。硬约束与偏好应根据真实需求选择，避免把所有“可能更快”的条件都写成必须满足。

## 属性必须具有可比较含义

一个驱动发布 `numa`，另一个叫 `numaNode`，名称与类型还可能不同。派生属性思路用表达式转成共同维度，再施加匹配约束。CEL（Common Expression Language）是用于表达选择/计算逻辑的语言，不是任意执行脚本。

这些页涉及特定 <Term id="keps" label="KEP" /> 与 feature gate。核心 <Term id="dra" label="DRA" /> 可用，不代表所有高级功能都默认开启。实验应先读取目标版本功能表，再确认驱动确实发布了预期属性。

## ComputeDomain 的生命周期

讲义讨论 NVIDIA 驱动管理或主机预置 IMEX 等方式。前者把更多生命周期绑定到工作负载，后者可能降低启动延迟但增加预置容量与清理责任。ComputeDomain 不是普通 GPU/NIC 共置的必需概念，而是特定平台进阶能力。

## 规模问题来自状态写入方式

许多 daemon 同时写同一对象可能制造冲突与热点。拆分状态对象、降低更新频率或让协调器汇总，都是控制面设计取舍。对象模型语义正确，不意味着大规模更新自动高效。

评估时记录设备数、<Term id="resourceslice" label="ResourceSlice" /> 数、更新频率、API Server 压力、冲突重试和启动延迟。不能只展示一份成功调度的 YAML 就宣称“支持大规模”。

## 版本表怎样维护

把已发布稳定能力、默认启用的 Beta、默认关闭的 Alpha、未合入提案分开。对每个实验记录 Kubernetes、driver、chart、feature gates 和实际 API schema。1.38 计划保留为会议背景，不加入 1.37 的可执行路径。
