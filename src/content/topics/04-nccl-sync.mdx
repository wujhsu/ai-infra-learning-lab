融合 kernel 最危险的错误往往不是“算错加法”，而是某个线程提前读了尚未可见的数据，或生产者重用了消费者仍在读取的缓冲。同步协议必须先于性能优化设计。

## 分清四个时刻

操作已发起、源数据可以重用、数据已到达远端、消费者可以读取，这些时刻并不总是同一个。具体接口只保证文档声明的完成层级，不能用名字猜测。

<Term id="gin" /> 的传输与 signal/counter 协议需要配合；<Term id="lsa" /> 的普通 load/store 也不能代替跨 rank 的可见性和阶段同步。

<Slide id="advanced-nccl-32" />

## 两 rank 归约的所有权

每个 rank 先写好本地输入，再共同确认输入可读；随后读取 peer 并计算输出；最后确认消费完成，才能进入可能覆盖输入的下一轮。若输入与输出原地重叠，更需要检查是否有 rank 提前覆盖其他 rank 尚未读取的数据。

<Slide id="advanced-nccl-21" />

课程中的练习图是协议框架，不是可直接复制的完整生产实现。具体 barrier、线程参与范围和内存 fence 要依据 2.31.2 API 与示例源码核对。

## 对称性是布局约定

<Slide id="advanced-nccl-27" />

window offset 对应同一逻辑数据位置，虚拟地址数值可能不同。每个 rank 注册大小或布局不一致，会使“相同偏移”指向不同含义的数据。创建/注册通常也是 collective setup，需要全体参与者遵守协议。

## 缓冲生命周期如何记录

为每个 buffer 写出分配、注册、生产、传输、消费、复用、注销、释放八个阶段，标明哪个 stream 和哪些 rank 使用它。复用与释放都应等待所有相关操作完成。

在单步正确后再循环多轮。很多竞态只在复用时出现，单轮结果正确不能证明长期安全。增加数据校验、不同消息大小和重复次数，记录首次不一致的 rank 与阶段。

## 性能测试不能隐藏正确性

先通过参考结果验证，再开启计时。遇到不稳定结果，不应只挑选“没出错的最快轮次”。使用 sanitizers 或调试工具时，也要说明工具覆盖范围与对时间的影响。

进阶实验从本地归档源码的固定 commit 出发，保留原历史，不自动复制整个嵌套仓库到公开站。实验包记录代码来源和硬件条件，未实际运行的部分明确标注。
