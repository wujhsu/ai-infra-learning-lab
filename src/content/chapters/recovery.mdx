分布式作业出事时的第一份现场往往有误导性：所有 <Term id="rank"/> 同时报 <Term id="nccl"/> 超时，而真正退出的可能只有一个进程——其余人只是在集合通信的会合点等不到伙伴，把等待报成了超时。这提醒我们，分布式训练的故障与恢复都要放在"多个参与者、一条时间线"的框架里看。

保存与恢复这件事，单机版已经在 <a href={asset('read/checkpoints-finetuning/')}>checkpoints-finetuning 章</a>讲透了：什么状态跨步存活、检查点装哪些键、"写完了"何时才等于"可恢复"、判据是恢复后的下一步与不中断基线一致。本章不重复那份清单，而是回答它没有回答的问题——当状态不再由一个进程独占，而是切成 N 份、散在 N 台机器上时，同样的三问会多出什么。

## 这一章解决什么问题

把单机的结论原样搬进集群，会在三个地方失效。每个失效点对应本章的一问：

1. **分片一致性**。单机只有一份文件，"保存于第 1000 步"天然描述全部状态。分布式检查点是 N 份分片文件，"第 1000 步"必须是一个全体达成的快照：N 份分片必须属于同一步的同一次全局快照。只要有一份是旧的，拼起来的就不是任何时刻真实存在过的模型——而加载多半不会报错。
2. **成员变更**。保存时的 world size 是 4，重启时只剩 2 张卡。每个 rank 一个文件的朴素布局在这里直接失效：第 3、4 份分片没有进程来认领，前两份又不完整。参数能否重排、按什么语义重排，决定了"少几张卡接着训"是常规操作还是重新开始。
3. **数据与进度**。权重和优化器之外，跨步存活的还有数据进度与随机数状态——单机是一份，分布式是 N 份，而且必须彼此对齐：各 rank 的 dataloader 游标、各自的随机流，任何一份错乱都有具体而非抽象的症状。

三问背后是同一个转变：单机的恢复问题是"装了什么"，分布式的恢复问题是"N 份东西怎样才能构成同一个时刻"。回答它要同时给出机制（谁来担保 N 份属于同一步）、语义（成员变了哪些目标自动保持、哪些要重答）和账目（为这份可靠付出多少吞吐）。

本章的证据来自 `labs/distributed/checkpoint_check.py`——它在 2 个 CPU 进程上把"保存→恢复→续走"和"从不中断"两条路径走到严格相等，由 CI 运行并有 `docs/runs/dcp-cpu.json` 作证；更大规模的故障注入（杀节点、换 world size 的真实重启）未在本环境运行，属于本章陈述"已设计、未执行"的部分，与 CPU 路径的证据地位不同。

本章属于工程线项目 distributed-training 的收尾：前面各章解决了多卡怎样一致地算，本章解决多卡怎样在故障与成员来去之间保持同一个训练时刻。

## 机制讲解：分布式恢复比单机多出的三样

### 一、分片一致性：N 份分片必须来自同一步

先看分布式检查点长什么样。以 <Term id="fsdp"/> 为例，参数、梯度、优化器状态都按 rank 切片：保存时每个进程把自己持有的那一片写成自己的文件，目录里落 N 份分片加一份元数据。DDP 则相反——每个 rank 各存一份完整副本，N 份互为镜像。

危险藏在这条时间里：保存不是瞬时的。把一次出错的重启画成时间线：

```text
T0   各 rank 在 step 1000 达成快照，开始写各自的分片文件
T1   rank 0/1/2 写完
T2   rank 3 所在节点写出错退出，目录里它名下的文件仍是 step 960 的残留
T3   作业重新调度，加载方按目录读取：3 份来自 step 1000，1 份来自 step 960
```

逐条推演 T3 之后的后果：

1. **加载不报错**。分片文件的形状、数据类型、张量名全部匹配——它们本来就是同一个模型切出来的，差的只是版本。所有文件级校验通过。
2. **参数成了马赛克**。FSDP 下每个参数都被切成 N 段，混用意味着每个参数的大部分行来自第 1000 步、某几行来自第 960 步。这不是一个加了噪声的模型，而是一个从未在任何训练轨迹上存在过的缝合体：旧的那几行系统地落后 40 次更新。
3. **优化器矩跟着错位**。AdamW 为每个参数元素维护两份矩。旧分片里的矩与旧分片里的参数是配套的，于是错位呈现"局部自洽、全局矛盾"的形态：每个切片内部像一次正常的旧恢复，合起来没有一条一致的轨迹。
4. **下一次更新方向不属于任何真实模型**。梯度在这份混合权重上前向计算，逐元素的矩按错位的历史缩放，<Term id="optimizer"/> 的更新量既不是第 1000 步该走的，也不是第 960 步该走的。
5. **症状是损失跳一个台阶，然后照常训练**。不崩溃、不 NaN，模型从此沿一条偏掉的轨迹走下去——和单机丢优化器状态一样，是"不报错但悄悄变差"的失败，只是病根从"漏了一项状态"变成了"混了两个版本"。

DDP 的变体更糟：各 rank 拿到的是不同版本的**完整**参数，两个进程从此在两个不同的模型上算梯度，AllReduce 平均出来的更新不对应任何一个模型；而 DDP 只同步梯度、不同步参数，版本差一旦引入，永久存在。

防线只有一条：**把"内容写完"和"版本存在"分开，由一个全局标记作证**。这正是 <Term id="artifact"/> 制品语义在检查点上的落点。DCP 的做法是全部分片落盘之后，由协调者最后写一份 `.metadata` 账本；加载方只认 `.metadata` 指向的版本——账本不在，这个版本就不存在。晚到或残留的旧分片因此失去被误读的机会。两条配套纪律：分片先写进带版本号的独立目录（或临时位置），写完才发布标记；目录里永远保留上一个已确认完整的版本，新保存失败时退一步，而不是退到残片。

还有一层主动体检：让每个分片在元数据里声明自己的 step，加载方断言 N 份的 step 全等——混版本这种"不会喊"的病，只能靠元数据主动去查，不能指望它自己暴露。

与单机章的提交协议对照着看最清楚：**临时位置 → 完整性标记 → 发布**三步在这里逐字适用，变化只有两处——标记的作者从进程换成协调者，标记的管辖范围从一份文件换成 N 份分片。协议本身没有变复杂，变的是"谁有权宣布完成"。

### 二、成员变更：world size 变了，参数怎么重排

4 份分片重分到 2 个进程，问题等价于：新进程 0 要读旧分片 0 和 1 的内容，新进程 1 读旧分片 2 和 3 的。朴素布局（"rank i 的状态在文件 i"）表达不了这件事——文件名绑死了旧成员关系。

DCP 天然支持，原因在它存的不是"谁的文件"，而是"哪个张量的哪些字节区间在哪个文件"。`.metadata` 记录每个张量被切成哪些 chunk、每个 chunk 的 offset 与 length 落在哪个分片文件里；加载时按**当前的** world size 重新规划读哪些区间。拿一个一维张量把账摆出来：

```text
一维张量 W（1024 个元素），保存时 world size = 4：
  文件 s0: W[0:256]      文件 s1: W[256:512]
  文件 s2: W[512:768]    文件 s3: W[768:1024]

重启时 world size = 2，新的读计划：
  进程 0：s0 全部 + s1 全部   → 持有 W[0:512]
  进程 1：s2 全部 + s3 全部   → 持有 W[512:1024]

若按"rank i 读文件 i"的朴素布局：s2/s3 无人认领，s0/s1 只覆盖一半参数
```

分片布局是账本里的一张表，不是写死在目录结构里的身份，所以"从 4 份重分到 2 份"只是一次不同的读计划。这也是教科书时代的 per-rank `torch.save` 在大模型时代被淘汰的根本原因：它把成员身份焊进了存储格式。

重排是免费的，语义不是。world size 从 4 变 2，至少三件事要显式重答：

- **全局有效批次**。4 卡每卡 B=8 是全局 32；2 卡同配置只剩 16。梯度噪声近似翻倍，损失曲线的形态随之变化。
- **学习率与调度**。批次减半后学习率是否按 sqrt 规则之类的惯例补偿、调度器步数怎么映射，是重启时的决定，不是账本能代答的。
- **数据再划分**。采样器要按 2 份重新切分剩余样本，dataloader 游标在新布局下的含义要重新对齐。

支持弹性进程数量，不意味着训练目标自动保持不变——这正是代码走读一节里 `scope` 字段写明 "same world size" 的原因：本章的严格判据覆盖到同布局恢复为止，重分片的正确性是另一组要单独验证的语义。

### 三、数据与进度：一张分布式恢复清单

权重与优化器之外，跨步存活的状态在分布式下逐份翻倍。下面的清单把每一项和它丢失时的具体症状配成对——症状列才是这张表存在的理由，它把"要记得存"从提醒变成可核对的故障对照：

| 清单项 | 分布式下谁持有 | 丢失或错乱的具体症状 |
|---|---|---|
| 参数分片 | 每 rank 一片 | 元数据找不到分片文件，加载当场报错——最"友好"的失败 |
| 优化器状态分片 | 每 rank 一片 | 头几步一切正常，第一次更新后与基线分岔，损失曲线一个台阶，且不会自愈 |
| 训练步数 | 通常随元数据 | 恢复后多训若干步：同一数据过度重复学习；学习率按步调度则整体错位 |
| 学习率调度器 | 每 rank 一份 | 从头调度，学习率突跳回初值，损失先升后缓降 |
| dataloader 进度（epoch 与样本游标） | 每 rank 一份 | 从 epoch 头重放：部分样本二次学习，训练损失虚低、验证指标停滞 |
| 随机数状态 | 每 rank 一套（CPU 流与 CUDA 生成器是分开的两份） | 各 rank 的 shuffle 顺序错乱：可能采到彼此重复的样本，"数据并行"悄悄变成"重复并行" |
| 分片布局元数据 | 全局一份 | world size 变化后无法重排，只能按原布局重启 |
| 进程组与环境 | 所有 rank | 集合通信组不成形，卡在 init 或第一个 collective |

读这张表要分清两类病：**丢**会喊（缺文件、缺元数据，当场报错），**错**不喊（版本混用、游标错位、随机流错乱，只在训练质量上显形）。分片一致性一节治的是"错"，这张表治的是"丢"；工程上先保证不丢，再保证不错。

随机数一行值得再拆一层：分布式采样器通常由一个主种子派生每个 epoch 的 shuffle，再按 rank 加偏移切分。丢掉主种子后，各 rank 的偏移仍然"整齐"地错着——训练照常、指标缓慢变差，比彻底乱掉更难察觉。这也是为什么随机状态要作为一等公民进检查点，而不是"反正初始化已经不用它了"的遗留物。

单机章的方法在这里原样适用，只是主语换成了"逐 rank"：**问"什么跨步存活、谁持有它"，存活者进检查点，持有者各自存自己那份，全局标记最后发布**。梯度照旧不进——它每步清零重算，只活一步，存它只是把上一圈的尸体装进文件。

这张表还配套一个工程惯例：恢复路径要有自己的自动化判据。保存清单每次改动，就跑一遍分岔对照——症状列正是断言该抓的东西。单机章的 `test_checkpoint_resume_preserves_next_updates` 做的是这件事，本章的 `checkpoint_check.py` 是它的分布式版。

## 故障模式与策略：停顿的账与丢失的账

恢复策略前先校正一个视角：报超时的 rank 多半不是出事的 rank。同步训练里所有人都要在 collective 上会合，一个进程先退出或变慢，其余人的第一症状就是超时。所以排查先对齐时间线——记录每个 rank 的全局序号、节点、设备、step 与最近一次成功的阶段，按时间找**最早**异常，同时容忍各节点时钟误差；把日志最后一行当根因，等于把回声当成声源。会合失败的另一常见来源是工作量不均：某个 rank 的输入有效长度更大、数据准备更慢、被同节点其他负载争抢，都会让它"变慢"而不是"坏了"——用相同形状的固定数据对照，就能把"硬件慢"和"活重"分开。

重试也要分型：网络抖动、节点掉电，重新调度后可恢复；数据格式错误、不支持的配置，重复启动只是重复失败。先分类，再决定重试、隔离节点还是停止。重启前还有一笔清理账：上一轮残留的进程若还在占卡占通信组，新一轮会在完全不同的地方莫名其妙地卡住——任务平台的旧进程回收必须幂等。

真正要算的是两笔对拉的账。

**停顿的账**：假设每 30 分钟的训练进度触发一次同步保存，保存期间全集群停 5 分钟：

```text
周期墙钟 = 30 min 计算 + 5 min 停顿 = 35 min
有效吞吐 = 30 / 35 ≈ 85.7%，损失约 14.3%
等价说法：每 30 分钟训练要多付 5 分钟，时间开销 +16.7%
集群放大：64 卡作业每次停顿 = 64 × 5 = 320 卡·分钟，全部蒸发
```

**丢失的账**：故障落在两次保存之间时，平均损失半个间隔的计算——30 分钟间隔的期望损失是 15 分钟 × 全集群。两笔账往相反方向拉，把不同间隔摆在一起看：

| 保存间隔（每次停 5 min） | 每周期墙钟 | 有效吞吐 | 每次故障期望丢失 |
|---|---|---|---|
| 10 min | 15 min | 66.7% | 5 min × 全集群 |
| 30 min | 35 min | 85.7% | 15 min × 全集群 |
| 60 min | 65 min | 92.3% | 30 min × 全集群 |

间隔缩到 10 分钟，丢失账降到 5 分钟，停顿账却把有效吞吐拖到三分之二。最优频率取决于故障率、单次保存耗时与恢复时间，没有普适常数——这张表的正确读法不是"选 30 分钟"，而是把两列代入自己的故障率与保存耗时：把账算出来，选择就从"感觉"变成了取舍。

把停顿账压下去的主流做法是**异步分层保存**：先把状态从 GPU 搬进 CPU 的固定内存（秒级、不停训练），再由后台线程慢慢写对象存储（分钟级、与训练重叠）：

| | 同步保存 | 分层异步 |
|---|---|---|
| 训练停顿 | 每次一个完整保存周期 | 搬运到 host 内存的秒级 |
| 故障丢失 | 上次保存之后的计算 | 多丢最近一两个仍在写盘的版本 |
| 主机内存 | 不驻留 | 整份状态要在 host RAM 驻留片刻，大模型受主机内存限制 |
| 带宽争用 | 集中在停顿窗口 | 后台写盘与数据加载长期争网卡与存储带宽 |

还有一条不能让步的：全局完成标记必须在内容真正落到对象存储**之后**发布，否则"看起来异步存好了"比不存更危险——异步把"写完"和"存好"的距离拉长了，标记是唯一弥合它的东西。

弹性训练（如 torchrun 的 elastic 模式）解决的是最后一环：节点失联后不整个作业重来，而是 rampdown 到更少的 rank，按上一节的 reshape 语义从检查点重分片加载、继续训——配合成员变更一节里"批次语义要显式重答"的警告使用。

## 代码走读：checkpoint_check 为什么能验证恢复

`labs/distributed/checkpoint_check.py` 把单机章的"分岔对照"实验搬进 2 个进程。运行方式是 `torchrun --standalone --nproc-per-node=2`：gloo 后端、90 秒超时、CPU 设备——选这条最朴素的路径，是为了让"恢复等价"这个语义问题在没有 NCCL 和 GPU 噪声的环境里被 CI 反复执行，证据落在 `docs/runs/dcp-cpu.json`。

实验设计是：同一条命令下，A 路径连续走两步；B 路径走一步、保存、新起模型加载、再走一步。判据是 B 的第二步做完后参数与 A **完全相等**。核心十四行：

```python
    step(model,opt)
    ms,osd=get_state_dict(model,opt)
    state={'model':ms,'optimizer':osd,'step':torch.tensor(1)}
    dcp.save(state,checkpoint_id=a.directory)
    step(model,opt)
    expected=[v.detach().clone() for v in model.parameters()]
    torch.manual_seed(99);restored=DDP(TinyLM());restored_opt=torch.optim.AdamW(restored.parameters(),lr=.01)
    ms,osd=get_state_dict(restored,restored_opt)
    loaded={'model':ms,'optimizer':osd,'step':torch.tensor(0)}
    dcp.load(loaded,checkpoint_id=a.directory)
    set_state_dict(restored,restored_opt,model_state_dict=loaded['model'],optim_state_dict=loaded['optimizer'])
    step(restored,restored_opt)
    error=max((a-b).abs().max().item() for a,b in zip(expected,restored.parameters()))
    assert loaded['step'].item()==1 and error<1e-7,(loaded['step'],error)
```

逐行看每一步在实验设计里的角色：

- `step(model,opt)`：基线走到第 1 步——保存点。两个 rank 输入相同、梯度经 AllReduce 平均后仍相同，所以每个 rank 都能独立地对基线断言，打印各自的记录。
- `get_state_dict(model,opt)`：从 <Term id="ddp"/> 包装下抽出干净的参数名（剥掉 `module.` 前缀）与优化器状态，连同 `step` 打包成三键 state——对照上一节的恢复清单，能点名的恰好是同布局恢复所需的全部三项。
- `dcp.save(...)`：每个 rank 写自己的分片，全部落盘后协调者发布 `.metadata`——分片一致性一节的协议在这里执行，`checkpoint_id` 指定的目录就是"带版本的独立目录"。
- 第二个 `step(model,opt)` 与 `expected=...clone()`：基线**不停**，原地走到第 2 步并把参数克隆成独立副本。克隆是把"基线答案"冻结下来，之后的任何操作都动不了这份参照。到这里 A 路径完毕。
- `torch.manual_seed(99)`：故意换一个种子初始化 `restored`——这是实验最聪明的一行。新模型的参数与基线毫无关系，接下来若 `dcp.load` 静默失效、模型还是随机初始化，error 会是 O(1) 量级而不是 0。随机初值在这里充当"加载真的发生了"的对照。
- `loaded={...,'step':torch.tensor(0)}`：DCP 是**就地**加载——先造好结构正确的容器，再往里填数。`step` 故意填错误值 0：加载后它必须变成 1，这一个断言同时验证了非张量状态也随检查点走了。
- `dcp.load` 与 `set_state_dict`：前者按 `.metadata` 把分片读进容器（同 world size 下每个 rank 读回自己那部分），后者把值装回模型与优化器对象——先结构、后数值、再状态，顺序与单机版相同。
- `step(restored,restored_opt)`：判决动作。恢复的成败不由"加载没报错"判定，由恢复后**走出的下一步**判定。
- `error=max(...)` 与 `assert`：对全部参数取最大绝对差压成一个数，断言它小于 1e-7，且步数为 1——两个条件分别钉住数值状态与进度状态。

为什么敢要求精确相等（证据文件里实得 `next_step_max_error: 0.0`）？因为两条路径是**同一个确定性函数在同样输入上的两次求值**，逐条数出确定性从哪来：

- 输入固定：两 rank 用同一句 x/y，没有数据管线；
- 没有随机消费者：无 dropout，种子 99 的初始化被加载整体覆盖，从未参与计算；
- 执行确定：CPU 上 gloo 后端、脚本开头 `torch.set_num_threads(1)` 压掉多线程归约顺序的抖动；
- 状态完备：跨步存活的只有参数、优化器状态、步数三样，三样全在检查点里，同 world size 逐份读回。

输入相同、状态相同、函数确定，输出应当逐位相同——1e-7 只是浮点噪声的护栏，本不该用到。这个判据的严格性是双向的：清单里任何一项漏存，0.0 立刻保不住；反过来，脚本输出里的 `scope` 字段也老实写明了边界——固定数据、无 dropout、同 world size。它**没有**测弹性重分片；换 GPU 与 NCCL、非确定性 kernel、真实数据管线后，逐位相等不再可预期，判据必须降档为"数值近似"或"训练质量等价"，并把降档声明出来——比较标准本身也是恢复语义的一部分。

## 动手：分岔会在哪里显形

先做一个不用跑代码的推演，把"随机数状态"从清单里单独拎出来刑讯：

**题**：恢复时漏掉 rng 状态（不存、不恢复各 rank 的随机流），从恢复后的哪一步起能观察到与基线的分岔？分三层想：本 lab 的配置；把 TinyLM 换成带 dropout 的同构模型；模型仍无 dropout、但数据加载器每个 epoch 用 rng 重新 shuffle。

<details>
<summary>展开核对</summary>

分岔出现在**恢复后第一个消费随机数的算子**上，所以三层答案各不相同：

- **本 lab**：永远观察不到。固定的一句输入、无 dropout，从保存到对照走完，没有任何算子消费随机数——`manual_seed(99)` 的随机初始化也被 `dcp.load` 整体覆盖，从未参与计算。漏掉 rng，`next_step_max_error` 仍是 0.0。这不是判据的漏洞，而是判据的前提：正因为随机流不参与，0.0 才敢要求。
- **带 dropout**：恢复后的第一次前向就要采样 dropout 掩码，两条路径的掩码不同，**同一步的损失就已经不同**；这一次 `optimizer.step()` 之后，参数分岔可见。症状最早出现在第一个随机消费者处，而不是"训练一段时间后"。
- **只有数据 shuffle**：当前 epoch 内每个 rank 按既定顺序读完，与基线完全一致；**下一个 epoch 的第一个 batch** 起，采样顺序分岔，输入不同导致损失与更新从此走岔。

结论：rng 丢失不是"立刻坏"，而是"在第一个随机消费者处坏"——这就是清单表里它对应的症状要写具体场景、而不是笼统写"训练变差"的原因。

</details>

推演完跑实验，按顺序看三处：

1. 两个进程各打印一条 JSON 记录，`next_step_max_error` 应为 0，`scope` 字段声明了它成立的前提；
2. 做一次破坏性验证：把 state 里的 `'optimizer'` 键删掉再跑，看 0.0 怎么碎掉——症状应与清单表的预言一致（加载仍成功、第一次更新后分岔），而不是报错；
3. 摸一下 scope 的边界：把 `--nproc-per-node` 改成 1 再跑，记录实际行为——这是把"same world size"这条边界亲手按一遍，体会哪些保证在边界内、哪些不在。
