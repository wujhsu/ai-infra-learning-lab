## 这一章解决什么问题

从极小模型训练开始，我们就记录 loss、step 与耗时；从首次推理服务开始，我们记录 TTFT、输出 token 和请求错误。这些记录散落在各个实验里，各答各的问题。本章要解决的是把它们接成一条证据链：某一批请求为什么慢——是排队、模型计算、通信，还是节点异常？

先把一句最常见的报警用语拆开："今天变慢了"。这句话单独看是句废话，因为它缺三个要素：

- **对象**：哪个服务、哪个接口、哪个口径的"慢"？TTFT 和 TPOT 是两个不同的慢。
- **基线**：和什么比？昨天同时段的分布、上周的 p95，还是发布前的一次压测？没有基线，"慢"只是感觉。
- **维度**：慢在哪类信号上？延迟、吞吐、质量、饱和度是四类不同的问题，各自有不同的第一指标。

四类信号各答一个问题：**延迟**答"多久"（TTFT、TPOT、总时长）；**吞吐**答"多少"（每秒输出 token、每秒请求数）；**质量**答"好不好"（答案正确率、输出长度分布的漂移）；**饱和度**答"还有多少余量"（队列长度、KV 水位、GPU 利用率与显存）。听到症状先映射到信号类别，才知道该打开哪张图：

| 你听到的症状 | 先看哪类信号 | 第一个该看的指标 |
|---|---|---|
| "首字要等很久" | 延迟 | 客户端口径的 TTFT 分布，再拆排队 / prefill / 网络 |
| "一个字一个字往外蹦" | 延迟 | TPOT / token 间隔分布，decode 每步耗时 |
| "一到高峰就堆请求" | 吞吐 + 饱和度 | 每秒输出 token、并发数、队列长度、KV 水位 |
| "回答质量变差、答非所问" | 质量 | 输出长度分布、失败率、抽样评估 |
| "偶发报错或卡死" | 饱和度 + 错误 | 按错误码分组的失败计数、OOM 计数 |

这张表是本章的导航图。往下三节分别展开三种证据——指标、追踪、日志——各自擅长回答什么、会在哪里骗人；再往下走读本仓库那个二十来行的观测栈；最后用一道排查设计题收束。

先交代证据边界：**本章的观测栈（Prometheus、OTLP Collector、Jaeger）需要 Docker 与真实服务，本环境未运行**。文中所有毫秒数字都是标注过的算例（假设输入），作用是建立排查框架，不是实测成绩；走读对象是配置文件与脚本本身，它们的口径已逐行复核。

排查之外还有留证。一次异常记录至少包含：起止时间、受影响请求范围、模型与镜像身份、输入输出长度分布、实例和设备身份、原始指标窗口、相关日志与追踪，以及期间是否发生发布或资源变更。所有结论标明来自观察还是推断——这就是后面章节反复要用的"最小证据包"。

## 机制讲解：指标、追踪与日志各看到什么

三种信号不是三选一，而是同一个系统的三种分辨率。[OpenTelemetry 信号](https://opentelemetry.io/docs/concepts/signals/)把它们定义为指标、日志、追踪三类，各自有明确的能与不能。

### 指标分三层，每层都有会骗人的读数

<Term id="metrics" /> 把大量事件聚合成随时间变化的数值，适合回答"何时开始异常、影响多大"，但通常不保留每个请求的完整过程。对推理服务，指标至少分三层，混着看是多数误诊的起点：

| 层 | 代表指标 | 回答什么 | 一个会骗人的读数 |
|---|---|---|---|
| 系统层 | GPU 利用率、显存占用、功耗温度、网络带宽 | 机器忙不忙、还有多少余量 | 利用率 100% 却在等内存搬运（下详） |
| 服务层 | TTFT、TPOT、队列长度、在途请求数、KV 水位 | 引擎各阶段的耗时与拥堵 | 队列为 0，TTFT 却仍在涨 |
| 业务层 | token/s、成功率、输出长度分布、评估分 | 用户体验与产出是否达标 | token/s 持平，答案质量已经掉了 |

**系统层的骗术：利用率统计的是"驻留"，不是"有效计算"。** GPU 利用率的口径是采样窗口内有 kernel 驻留在 SM 上，它不区分这个 kernel 在做乘加，还是在等数据从显存搬运过来。decode 阶段是小 batch、低算术强度的典型 memory-bound 场景：每个 token 只搬一小段权重和 KV，计算单元大部分周期在等数据——利用率满格、每秒产出的 token 却上不去。讲者那句"GPU utilization 90% 可能只是等待或 memory-bound"说的就是这个。诊断动作是跨层对照：利用率高 + 业务层 token/s 低，怀疑带宽受限，方向是增大 batch 或查 kernel 效率，而不是加机器。显存占用高同理是容量现象，不能当作计算饱和的证据。

**服务层的骗术：队列指标有自己的起点定义。** "队列为 0 但 TTFT 涨"至少有两种解释。其一，引擎口径的队列只统计已进入调度器的请求——堵在网关、限流层或连接池上的排队，这个指标看不见。其二，没有新请求排队不代表没人等：已在批次里的长 prefill 会推迟其他请求的 decode 回合，"队列空"和"没人被挡"是两回事。比较不同引擎的"排队时间"前，先确认各自从哪个事件起算。

**业务层的骗术：token/s 没写分母就没有意义。** 分母是单请求 decode 时间、整个实验的墙钟时间，还是 GPU 活动时间，三个数可以差好几倍。训练吞吐同理：样本、有效 token、含 padding 的 token 是三个口径。质量也是信号：换过量化版本后 token/s 不变、抽样答案质量下滑，只有质量类指标拦得住这种"性能没退化的退化"。

最后是聚合方式的骗术。两个请求耗时 10 ms 和 990 ms，平均值 500 ms，无法描述两种完全不同的体验；直方图把观察值放进桶，可聚合分布、估计分位数，桶边界决定估计精度。本章开头问题在这里有了答案骨架：**分位数不是可线性合并的统计量**，把各实例的 p99 求平均当作全服务 p99 是错的——正确做法在下面。

<aside class="concept-note">
<strong>易混点：为什么实例 p99 不能平均成服务 p99</strong>


p99 由分布形状决定，不是由各实例 p99 的数值决定。两个实例各处理 100 个请求，A 的 p99 是 100 ms、B 的 p99 是 900 ms，合并后 200 个请求的整体 p99 落在哪，取决于两批样本如何交错，通常既不等于 500 ms 也不靠近它；流量悬殊时更糟——1 小时 1 个请求的实例和 1 秒 100 个请求的实例在"平均"里同权。正确路径是合并可聚合的分布数据再整体估计：直方图的桶计数（Prometheus 里 `_bucket` 序列）是可加的，先跨实例求和，再对合并后的分布算分位数；`summary` 的分位数则不可跨实例合并。[Prometheus 直方图说明](https://prometheus.io/docs/practices/histograms/)


</aside>

指标还有一个设计期就要付的约束：<Term id="cardinality" />。模型版本、实例和有限的错误类型通常可管理；把每个 request_id、完整 prompt 或任意用户输入作为标签，会制造不断增长的时间序列，存储与查询成本随之失控。请求级身份更适合放进日志与追踪；指标保留有限维度，必要时用 exemplar 从一个直方图桶指向一条代表性追踪，把两类信号缝起来。

### 追踪：一条请求的时间线

<Term id="trace" /> 把一次请求拆成相关联的时间段；<Term id="span" /> 是其中一个有起止时间与属性的操作，如网关处理、引擎排队或模型执行。指标告诉你"TTFT 在 14:00 开始涨"，追踪告诉你"这批请求的 120 ms 花在了哪一段"。

先给一组假设毫秒，把一个流式请求画成时间线（算例，非实测；输出 64 个 token）：

```
t=0     HTTP 请求发出（客户端计时起点，traceparent 已在头部）
t=12    ├── tokenize ── 6 ms ──┤ 模板拼接与分词
t=18    ├────── queue ────── 120 ms ──────┤ 等批次位置与 KV 预算
t=138   ├── prefill ── 58 ms ──┤ 处理整段输入，首个 token 产生
t=196   ├─ decode ─ TPOT 24 ms × 63 ──┤ 剩余 token 逐个生成，SSE 持续写回
t=210   ← 客户端读到首个非空正文（TTFT，客户端口径）
t=1722  ← 最后一个数据块与 [DONE]
```

把关键量算出来，口径跟着数字走：

| 量 | 算式 | 结果 |
|---|---|---|
| 服务端口径 TTFT（首 token 产生） | 12 + 6 + 120 + 58 | **196 ms** |
| 客户端口径 TTFT（首个非空正文） | 196 + 14（输出处理与网络） | **210 ms** |
| 排队占服务端 TTFT 的比例 | 120 ÷ 196 | ≈ 61% |
| 总时长（64 token） | 196 + 24 × 63 + 14 | **1722 ms** |

这张表立刻给出一个反直觉结论：即使把 prefill 从 58 ms 优化到 29 ms，若同期队列从 120 ms 涨到 200 ms，客户端 TTFT 反而从 210 ms 升到 261 ms——**优化了计算，用户却更慢了**。没有分段追踪，这两种变化会互相抵消在同一个 TTFT 数字里，谁也看不见。

跨组件对表之前，还有两件事必须先钉死。一是口径：客户端收到 HTTP 响应头、首个 SSE 数据事件、首个非空正文、服务端产生第一个模型 token，是四个不同时刻，各有各的名字；<a href={asset('read/serving/')}>serving 章</a>的 `measure_stream.py` 用的是"首个非空正文"。二是时钟：跨机器相减得到的段耗时，精度受时钟同步限制；同一进程内的 span 相减才可靠。

span 除了起止时间，还携带属性（attributes）：模型名、实例、输入长度分桶、停止原因这些低基数字段。属性是追踪里做筛选的维度——"只看输入超过 2048 token 的请求的首段耗时"这类问题，靠属性回答。属性同样受基数纪律约束：放 request_id 可以（每条 trace 本来就是独立的），放任意用户输入就不行。

**W3C traceparent：把客户端测量与服务端 span 缝起来的那一行头部。** 标准格式是 `00-{trace_id}-{parent_id}-{flags}`：版本 00，trace_id 为 32 个十六进制字符，parent_id 为 16 个，flags 里 `01` 表示采样。仓库里的 `labs/observability/trace_request.py` 只用标准库就完成了这件事——`secrets.token_hex(16)` 生成 32 位十六进制 trace_id，`token_hex(8)` 生成 16 位 parent_id，拼成 `00-…-…-01` 放进请求头部。服务端引擎的追踪 SDK 读到这个头部后，它创建的每个 span 都挂到同一个 trace_id 上，parent 指向这个客户端从未导出的"远程父 span"。于是拿着脚本打印的 trace_id 去 Jaeger 搜索，就能看到这条请求在服务端的完整链路；客户端自己测的 `client_seconds` 打印在终端，作为不在图上的旁证，与图中服务端 span 的时长相减，差值约等于网络与客户端开销。完整走读在下一节。

追踪也有它的边界。采样后未见到某种失败，不能证明失败不存在——采样是取舍，不是证明。追踪也不能自动测得每个 GPU kernel 对某个请求的精确贡献：GPU 侧的归因靠 span 时间窗与设备标签去关联对应的指标区间，是推断而不是直接测量。

### 日志：从字符串到可聚合的字段

<Term id="logs" /> 保存离散事件：某个 rank 在某节点出现超时，以及当时的配置与错误栈。它擅长回答"那次到底发生了什么"，但有一个工程前提——**字段化**。

为什么 `grep "timeout"` 输给指标？看一个把日志变指标的例子。假设训练日志里散落着：

```text
[2026-09-14 03:12:04] rank 1 nccl timeout after 30000ms, retrying
[2026-09-14 03:12:06] rank 4 nccl timeout after 30000ms, retrying
[2026-09-14 03:13:40] rank 1 nccl timeout after 30000ms, retrying
```

想回答"超时是否集中在特定 rank、是否随 step 加剧、每小时多少条"，你得写正则解析时间戳和 rank，还要扛住多行堆栈、格式改版、时区漂移——每次换问题重写一次，且数出的结果无法稳定复算。把同样的信息写成结构化字段就变了性质：

```json
{"ts":"2026-09-14T03:12:04Z","event":"nccl_timeout","rank":1,"world_size":8,"step":1204,"duration_ms":30000}
```

按 `(event, rank)` 分桶计数，日志就变成了指标：可以画每分钟超时数的曲线、按 rank 聚合看是否单点故障、挂上阈值告警；每条日志再带一个 trace_id 字段，就能从指标异常跳回具体链路。规则可以一句话记住：**grep 产生一次性的答案，字段产生可复算的证据**。

边界同样要说：不应把提示全文、用户身份与敏感数据默认写入日志——结构化让检索更强，也让泄露更彻底。

## 代码走读：二十行配置搭出的观测栈

`labs/observability/` 里有两个 compose 文件，一个管指标、一个管链路，合计不到四十行。本章观测栈未在本环境运行，走读针对配置与脚本口径。

先看组件职责表——谁拿什么数据、给谁看：

| 组件 | 来自 | 拿什么数据 | 给谁看 |
|---|---|---|---|
| prometheus | `compose.yaml` | 每 5 s 抓取 `inference-lab:8000` 的 `/metrics`（vLLM 暴露的服务层指标） | Prometheus 自带 UI；生产栈中通常再接 Grafana 做统一面板 |
| collector | `tracing.compose.yaml` | 4317（gRPC）/ 4318（HTTP）上收到的 OTLP span | 转发给 jaeger |
| jaeger | `tracing.compose.yaml` | collector 转发的 span，存于内存 | Jaeger UI（`127.0.0.1:16686`） |

Grafana 不在本实验里：它只做可视化，不产数据；教学栈用 Prometheus 与 Jaeger 自带的界面已经够用，生产栈再把它接到这两个数据源上。

### collector.yaml：receivers → processors → exporters 的管道

Collector 的心智模型是一条管道：**接收**（哪些协议、哪个端口）、**加工**（批处理、采样、脱敏）、**导出**（送到哪个后端）。逐段看这 20 行：

```yaml
receivers:
  otlp:
    protocols:
      grpc: {endpoint: 0.0.0.0:4317}
      http: {endpoint: 0.0.0.0:4318}
processors:
  batch: {}
exporters:
  otlp/jaeger:
    endpoint: jaeger:4317
    tls: {insecure: true}
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlp/jaeger]
```

（原文件为多行写法，此处压缩仅省篇幅，字段一一对应。）

- **receivers.otlp**：同时开 gRPC 4317 与 HTTP 4318，监听 `0.0.0.0`——容器内任意来源可投递。任何说 OTLP 的 SDK（包括 vLLM 内置的追踪导出）都能直接把 span 送进来。
- **processors.batch**：空配置即全用默认值，语义是"攒一批再发"。逐条转发每条 span 都要一次网络往返；攒批用少量延迟换吞吐，是观测基础设施里最常见的一笔折中。
- **exporters.otlp/jaeger**：再走一段 OTLP 发给 `jaeger:4317`——容器名即服务发现；`tls.insecure: true` 说明这段是内网明文，出了信任边界就要换 TLS。
- **service.pipelines**：只声明了 `traces` 一条管道。这个实验不收指标与日志——Prometheus 走自己的拉取模型，根本不经过 Collector。

**采样：这份配置没有采样，为什么生产默认不是 100%？** 注意 `processors` 里没有 sampling——所有收到的 span 100% 转发，实验栈这是刻意的：流量是手发的几条，全量才能看到完整教学链路。生产不能这么算。一笔账（算例）：100 请求/秒 × 每请求 8 个 span × 压缩后每 span 约 1 KB ≈ 0.8 MB/s，一天约 70 GB 入存储，后端还要为每条 span 建索引，查询先于写入变慢。所以生产默认加采样：头部采样按 trace_id 哈希决定去留，实现最简单；尾部采样（tail sampling）看完整个 trace 再决定——错误的一律保留、正常的抽 1%——代价是 Collector 必须缓住完整链路。采样率的本质是用"看不到的部分"换"看得住的整体"。

### prometheus.yml 与 compose.yaml：拉的模型

```yaml
global:
  scrape_interval: 5s
scrape_configs:
  - job_name: vllm-lab
    static_configs:
      - targets: ['inference-lab:8000']
```

三行各有一个决定。`scrape_interval: 5s`：教学选 5 秒是为了快速看到曲线变化，生产常用 15–30 s——抓取本身也是负载，指标端点每秒被打满就得不偿失。`job_name: vllm-lab`：所有抓到的序列都带 `job` 标签，多服务混布时靠它分流。`targets: inference-lab:8000`：目标容器名来自 <a href={asset('read/serving/')}>serving 章</a>`serve.sh` 里 `--name inference-lab` 的命名，两个 compose 文件都挂在名为 `ai-infra-lab` 的 external 网络上，容器名即可互解。

`compose.yaml` 本体只有 prometheus 一个服务：挂载配置只读、端口只绑 `127.0.0.1:9090`、`extra_hosts` 把 `host.docker.internal` 指向宿主机网关——想抓宿主机上的进程时不用改网络模型。指标来源的分工也在这里定下：vLLM 的 `/metrics` 给出引擎内部视角（排队、KV 水位、各阶段直方图），客户端口径（含网络与代理）仍由 `measure_stream.py` 这类脚本测量；两者相减才能定位"慢在引擎还是慢在路上"。

### tracing.compose.yaml 与 trace_request.py：链路的接线

`tracing.compose.yaml` 第一行注释就写了边界：**独立本地 trace 实验，数据在内存里，关停即失——导出证据再关机**。jaeger 只暴露 UI 端口 16686，collector 暴露 4317/4318，全部只绑回环地址；`depends_on: [jaeger]` 只保证启动顺序，不保证 jaeger 已就绪。

`trace_request.py` 的口径值得逐行对齐，它证明**传播追踪上下文不需要引入任何观测库**：

- `trace_id = secrets.token_hex(16)`——16 字节随机数，打印成 32 个十六进制字符，正好是 W3C 规定的 trace_id 宽度；`parent_id = token_hex(8)` 同理得 16 个字符。
- 头部 `'traceparent': f'00-{trace_id}-{parent_id}-01'`——版本 00，flags `01` 请求采样。请求是真实的 `/v1/chat/completions` 调用，正文与计时和普通客户端无异。
- 脚本 docstring 与输出 `note` 都声明：**不虚构网关或 GPU span，也不导出自己的 parent span**。所以在 Jaeger 里按 trace_id 搜到的是服务端链路，客户端那段只存在于终端打印的 `client_seconds` 里——拿它与图中服务端 span 总长相减，差值就是网络与客户端开销的估计。
- 服务端接线在 `serve.sh`：设了 `TRACE_ENDPOINT` 才追加 `--otlp-traces-endpoint` 与 `OTEL_SERVICE_NAME=vllm-lab`——引擎的 SDK 从请求头部读 traceparent，把服务端 span 挂到该 trace 上，经 OTLP 发给 collector。

这条链路完整跑通需要 Docker、真实引擎与 GPU，本环境未运行；`trace_request.py` 的头部格式与打印逻辑可离线复核。在具备条件的机器上，接线顺序是（顺序错一步，最常见的症状是 Jaeger 里搜不到 trace_id）：

```bash
docker network create ai-infra-lab                     # 两个 compose 都挂在它上面
docker compose -f labs/observability/tracing.compose.yaml up -d   # 先起 jaeger + collector
cd labs/serving && TRACE_ENDPOINT=http://127.0.0.1:4318 ./serve.sh # 再起带 trace 导出的引擎
python labs/observability/trace_request.py --url http://127.0.0.1:8000
# 拿输出里的 trace_id，打开 http://127.0.0.1:16686 搜索
```

两个易错点：collector 未就绪时引擎的导出会静默重试（span 延迟到达，别急着判定失败）；Jaeger 数据在内存里，`docker compose down` 之前先把要留的 trace 导出成文件，关停即失。

## 动手：设计一次"TTFT 突涨"的三步排查

不需要起栈，这是一道纸面设计题。背景：周一早上，用户反馈首字变慢，你手上有的证据源是——客户端测量（`measure_stream.py` 风格的 JSONL）、引擎 `/metrics`、Jaeger 里的 trace、结构化日志。请写下三步排查，每步回答"先看哪个维度、各自排除什么"：

1. **第一步，定对象与基线，只看延迟的分布。** 写出你会先取的两个数，以及各排除掉哪类"假故障"。
2. **第二步，拆延迟的分量。** 说明用什么相减定位到排队 / prefill / 网络中的哪一段，每一段涨分别指向什么。
3. **第三步，才下探系统层。** 写出什么条件下才轮到看 GPU 利用率与显存，以及看到什么算证据、什么算干扰。

<details>
<summary>对答案</summary>

**第一步**：取客户端口径 TTFT 的当前分布与上周同时段基线（同一模型 revision、同一镜像 digest 下比较，否则对象都没钉死）；同时取同期请求量与输入长度分布——排除"今天输入特别长"和"流量高峰"这两个不是故障的变化。中位数与 p95 一起看：中位数涨是普遍变慢，只涨 p95 是尾部问题，排查路径不同。

**第二步**：用引擎口径 TTFT 与客户端口径相减。差值变大，问题在网络或中间层（代理缓冲了流式响应是最常见的假性 TTFT 放大），引擎侧不变可证引擎无辜；引擎口径涨，再看排队与 prefill：队列长度、在途请求数、KV 水位上涨，指向容量或调度放行慢（并发上来了，或 KV 池满导致请求滞留）；队列不动而 prefill 变长，指向输入分布变化或 prefill 效率下降（长输入请求、前缀缓存失效）。每一步都对一条 trace 抽样验证数字：排队段的毫秒数应与指标方向一致。

**第三步**：只有当分量定位到"引擎计算段变慢"时，GPU 指标才上场。利用率高且业务层 token/s 低——memory-bound 的干扰信号，不是"算得忙"的证据；显存贴上限且伴随抢占或重算计数上涨——KV 紧张在拖慢调度；利用率低——供数不足或有别的负载在共享设备。利用率本身在这道题里始终不是起点，也不是结论。

贯穿三步的纪律：每步先写下一个可证伪的预测（"如果假设 A 成立，队列长度应该涨"），再去取数验证——预测错了就排除一个方向，这才是"缩小范围"的含义，而不是背一句"慢就看 GPU"。
