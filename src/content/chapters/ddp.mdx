两张 GPU 各训练一份模型，结束后简单挑一份参数，并不自动等于“训练速度翻倍”。要让它们共同完成同一个训练目标，必须定义数据如何分配、梯度如何合并，以及参数什么时候更新。

## 每个 rank 先有相同的模型

<Term id="ddp"/> 让各进程持有模型副本。通常从相同参数出发，各自处理不同数据，反向计算局部梯度，再按规定通信。若所有进程最终使用相同梯度与优化器状态更新，参数就能保持一致。

这解释了 DDP 的主要内存特征：每个进程仍有一份模型及训练状态。它主要扩展数据处理能力，并不是直接把一个装不下的模型分到多张卡上。

## 局部平均怎样组成全局平均？

假设四条样本的梯度分别为 1、3、5、7，全局平均为 4。rank 0 处理前两条，局部平均为 2；rank 1 处理后两条，局部平均为 6；再平均得到 4。

若两边样本数不同，不能无条件平均两个局部平均。语言模型中还要考虑有效目标 token 数不同：四条序列的长度或被忽略目标数不同，按“序列平均”与按“token 平均”可能是不同目标。

因此先写出你真正优化的损失，再推导每个 rank 的归一化与通信缩放。看到 AllReduce SUM 也不能直接推出最终用了求和梯度，框架可能在其他位置做缩放。

## 反向还没全部结束，通信就能开始

后面的层先完成梯度计算，较早的层还在反向。DDP 把梯度组织成 bucket，达到就绪条件后通信，与尚未完成的反向重叠。

<Diagram id="ddp" caption="数据并行的一次更新：不同样本产生局部梯度，就绪 bucket 通信，各副本使用一致更新依据" />

bucket 大小改变通信启动时机与消息数量。参数使用路径不同、未使用参数、动态分支等还会影响就绪与同步行为。源码阅读会追踪 DDP 前后向准备与 reducer，而不是把所有同步简化成训练循环末尾的一行。

## 数据不能意外重复

把同一个普通 DataLoader 放到每个 rank，不代表各 rank 自动获得不同样本。需要适当的分布式采样或显式分片，并在每个 epoch 按规则更新随机顺序。

如果所有进程重复读取同一批数据，你可能看到多卡都很忙，但并没有按预期增加有效数据处理量。日志应记录每 rank 的样本身份、有效 token 数和更新步数。

## 梯度累积怎样与通信配合？

如果每个微批次都同步，累积可能产生许多额外通信。DDP 的 `no_sync` 允许在选定微批次暂缓同步，最后一轮再完成所需合并。相关上下文应按接口要求包住对应前向与反向，不是只在 backward 周围随意加开关。

归一化规则仍需正确。梯度累积次数、rank 数、每批有效 token 的变化，都会影响全局目标。最后不足一个完整累积组的尾批次也需要处理，不能固定除以原计划次数。

## 用一个可运行对照验证理解

项目提供 CPU/Gloo 的两进程教学检查，以及 GPU/NCCL 运行方式。它们验证数据并行与同步的语义；CPU 结果不代表 GPU 通信性能。

```bash
torchrun --standalone --nproc-per-node=2 labs/distributed/ddp_check.py
```

脚本从同样的初始参数比较单进程全批次与两进程分批更新，并验证各 rank 参数一致。只有“程序跑完”不足以证明归一化正确，所以要有单进程参考。

## 扩展效率为什么小于理想值？

通信、数据加载、调度不均、重复同步和每卡微批次太小都可能限制扩展。如果总批次固定，增加卡数会减少每卡工作，通信占比可能上升；如果每卡批次固定，总批次变大，又需要重新考虑训练目标和收敛。

报告吞吐时同时记录批次策略与质量指标。训练得更快但需要更多步才能达到目标，也不一定降低总成本。
