两张 GPU 各训练一份模型，结束后任挑一份参数——这不自动等于“训练速度翻倍”：你拿到的可能是两份各自为政、互不一致的参数。要让它们共同完成同一个训练目标，必须把三件事规定清楚：数据怎么分、梯度怎么合并、参数什么时候更新。任何一条规定错掉，多卡训练都能“看起来正常”地跑完，产出的却不是你想要的模型。

本章把这三件事合成一条可检验的契约，再用一个 CPU 上就能跑的对照实验验证它：单进程吃下全部 4 条样本走一步更新，与两个进程各吃 2 条、梯度同步后各走一步，得到的参数应当相同。真实运行的结论是：相同——两种路径的最大参数误差为 1.4901161193847656e-08，一个浮点舍入量级的数。本章先讲清契约，再算清这笔浮点账，然后逐行读产生这个数的脚本，最后请你预测一个改动会让它发生什么。

## 这一章解决什么问题

问题一句话：多份模型副本，怎样学成“同一份”参数？

“同一份”不是修辞，是可以逐位检查的数值命题——训练结束后，各 <Term id="rank"/> 的每个参数都相等。它之所以可能，靠的是一条闭环契约：

1. **同一起点**：所有进程从逐位相同的初始参数与优化器状态出发；
2. **各算各的**：每个进程对自己的数据分片做前向与反向，得到局部<Term id="gradient"/>；
3. **梯度合并**：用 <Term id="allreduce"/> 把各进程的局部梯度合成同一份全局梯度，每个进程拿到相同结果；
4. **各自更新**：每个进程用这份相同的梯度和同样的优化器规则独立执行 step。

“优化器状态也从同一起点”不是多余的话。本实验用 SGD、状态为空，起点天然相同；换成 Adam，每个参数还各带一份跨步累积的统计，两边统计一旦不同步，即使梯度相同，更新也会分岔——这也是后面“为什么不每步直接平均参数”的答案的一半。

这是一条能自我维持的闭环：第 1 步成立、第 3 步给出逐位相同的梯度，第 4 步就保持参数一致；下一步又从同样的起点出发，一致性一旦建立就持续保持。反过来，每一环断裂都对应一类真实故障：

| 断裂的环节 | 现象 | 为什么难发现 |
|---|---|---|
| 数据没有真正分片 | 每个进程重复读同一批样本 | 每张卡都很忙，吞吐数字也翻倍，但有效样本量没变 |
| 梯度没有合并 | 各进程沿不同方向更新 | 不报错；参数从第二步起分道扬镳，最后挑哪份都不对 |
| 合并了但归一化不对 | 全组同步到一个错误目标 | 一致性检查照样通过；同步的是“错得整齐”的梯度 |

表里第一行就是本章开头自检题的场景：两卡吞吐更高，但每张卡都用了同一批样本——先验证采样分片、各 rank 样本身份、有效 token 数与全局损失定义，再评价吞吐。

这条契约同时划定了 DDP 的能力边界。<Term id="ddp"/> 让每个进程持有一份完整模型与训练状态——<a href={asset('read/training-memory/')}>training-memory 章</a>数过的训练态四类额外住户（梯度、优化器状态、前向激活、混合精度主权重副本），每个进程都有一整份。所以 DDP 扩展的是数据处理能力，不解决“一份模型装不下一张卡”；把状态切开存是 <Term id="fsdp"/> 的主题，也是下一章的内容。

本章的证据来自一次真实运行：macOS、Python 3.12.14、torch 2.14.0、CPU 上的 Gloo 后端、world_size 2，2026-09-13；命令与结论记录在 `docs/runs/ddp-cpu.json`。读法是：先契约，再浮点账，再代码走读，最后一个预测题。

## 机制讲解：一条契约与一笔浮点账

先把契约放回时间轴，看一次更新在两个 rank 上怎样发生：

1. 两个 rank 从逐位相同的参数出发，各取自己的样本分片；
2. 各自前向，各自得到本分片的平均损失；
3. 各自 backward——靠后的层先算完梯度，就绪的 bucket 先通信，与仍在继续的反向重叠；
4. `backward()` 返回时，每个 rank 的 `.grad` 都已是全局平均梯度；
5. 各自 `optimizer.step()`，两边参数更新一致；
6. 回到第 1 步——一致性自我维持。

**局部平均怎样拼回全局平均。** 用整数把第 4 拍之前的数学算一遍。设全局批次 4 条样本对某个参数的梯度分别是 1、3、5、7。单进程路径：全局平均 (1+3+5+7)/4 = 4。两进程路径：rank 0 处理前两条，局部平均 (1+3)/2 = 2；rank 1 处理后两条，局部平均 (5+7)/2 = 6；DDP 把两个局部梯度合并成跨进程平均，(2+6)/2 = 4。两条路径恒等，因为“局部和各除以 2、再平均”在代数上就是“总和除以 4”。DDP 的合并语义正是如此：对梯度做 AllReduce 求和后按进程数缩放——通信算子上写的是 SUM，默认得到的是平均。等式成立的条件只有一个：每个进程的样本数相同。

**条件不满足时，平均会静默地错。** 改成 3+1 分片：rank 0 处理前三条，局部平均 (1+3+5)/3 = 3；rank 1 只处理 7，局部平均 7；再平均 (3+7)/2 = 5 ≠ 4，而且没有任何报错。补救是加权合并：(3×3+1×7)/4 = 4，按各进程样本数配权。

真实语言模型训练里这不是玩具问题：各 rank 分到的序列长度不同、被忽略的目标位置不同，每步的有效目标 token 数天然不相等。设序列 A 有 3 个有效目标、平均损失 $L_A$，序列 B 只有 1 个、损失 $L_B$：按序列平均是 $(L_A+L_B)/2$，按 token 平均是 $(3L_A+L_B)/4$，是两个不同的优化目标，正确的缩放也随之不同。所以工程顺序应当是：先写下你真正优化的全局损失，再反推每个 rank 的局部损失怎样缩放、通信端怎样合并。反过来从“我看到 AllReduce 是 SUM”去猜训练目标，是猜不出来的——缩放可能发生在损失端，也可能在 reducer 端。

**两份“相同”的梯度差多少：1.4901161193847656e-08 的账。** 上面的恒等在实数里成立，在 fp32 里只是“几乎”。两条路径做的是同一个平均，但浮点加法不满足结合律：加法的分组不同、除法发生的时机不同、AllReduce 环内求和又是另一条顺序，每一步的舍入就不同。具体到本实验：

| | 基线（单进程） | DDP（2 rank） |
|---|---|---|
| 前向 | 4 条样本一次前向 | 每 rank 2 条各自前向 |
| 损失平均 | 12 个位置一次平均 | 每 rank 6 个位置先平均 |
| 梯度合并 | 一次归约直接得全局平均 | AllReduce 求和，再除以进程数 |
| 数学结果 | (1/12)·Σ₁₂ | (1/2)·[(1/6)·Σ_A+(1/6)·Σ_B] = (1/12)·(Σ_A+Σ_B) |
| 浮点结果 | 一条舍入路径 | 另一条舍入路径 |

量级估算（只对数量级负责，不逐位复推）：fp32 的机器精度 ε = 2⁻²³ ≈ 1.2×10⁻⁷，每次加法舍入的相对误差以 u = ε/2 ≈ 6×10⁻⁸ 为界。聚合涉及十几次加法，各项量级记为 G，两条路径的梯度差上界约为“项数 × u × G”，即 10⁻⁷·G 量级；G ≈ 0.1–1 时，绝对差落在 10⁻⁸–10⁻⁷ 之间。

再乘上学习率 0.01，参数更新量的差约 10⁻¹⁰–10⁻⁹——已经小于参数本身的一格表示精度。最后一层是量化：参数必须落回 fp32 网格，多数参数舍入到同一个数，恰好跨过舍入分界线的参数相差整整一格（一格 ULP）。实测最大参数误差 1.4901161193847656e-08 恰好等于 2⁻²⁶——正是数值落在 [0.125, 0.25) 区间的参数的一格 ULP，而本模型宽度 32 的线性层初始幅度约 ±0.177，正在这一档。这笔账读出的结论：最坏处差一格，没有一处开始发散；误差是舍入的量化，不是逻辑差异的信号。

这也解释了脚本为什么用容差断言而不是逐位相等：`torch.testing.assert_close(a, b, atol=2e-6, rtol=2e-5)` 比实测误差宽约两个数量级，足以容纳上面的舍入量级；又远小于真正的逻辑错误（忘记除以进程数、分片重叠、梯度没同步）会造成的偏差，错了必然打红。

把容差和实测对一下数：atol=2e-6 约为实测误差 1.49e-08 的 134 倍——不是拍脑袋的宽，而是恰好落在“容纳舍入、拦住逻辑错误”之间的量级。若有一天断言开始失败而误差只涨到 1e-6 量级，先查环境（线程数、后端、torch 版本）再查逻辑；涨到 1e-2 量级，几乎一定是归一化或分片错了。

复现性也一样有账可算：同环境重跑（单线程、固定种子、固定数据）应当逐位复现同一个数；换到 GPU 与 NCCL、并行归约之后，具体的数会变，量级不会——所以断言写成量级判断，而不是把 1.49e-08 硬编码成期望值。

**梯度什么时候真正开始通信：bucket 与 reducer。** 时间轴第 3 拍展开就是这一节。反向从输出层往输入层推进，靠后的层先算完梯度；DDP 把参数梯度预先编成若干 bucket（通信分组），某个 bucket 内的梯度全部就绪，就立刻发起这一桶的 AllReduce，与仍在继续的反向计算重叠。不是 `optimizer.step()`，也不必等整个 backward 结束。

桶的大小是时机旋钮：桶太碎，通信次数多、每次启动开销占比大；桶太大，要等更多梯度就绪才能开始，重叠窗口变小。影响就绪语义的还有别的情形——参数本轮未被使用（各 rank 走了不同分支）、梯度累积用 `no_sync()` 暂缓前几个微批次的同步（上下文要按接口要求包住对应的 forward 和 backward，不是只在 backward 边上挂开关）。这些机制在源码里怎样落位，是下一节要衔接的走读篇的主题；通信在硬件上怎样搬运，是 <a href={asset('read/nccl/')}>nccl 章</a>的内容。

<Diagram id="ddp" caption="数据并行的一次更新：不同样本产生局部梯度，就绪 bucket 通信，各副本使用一致更新依据" />

**契约正确，效率也不是线性翻倍。** 通信占据步时的一部分，还有数据加载、各 rank 快慢不均的互相等待、每卡微批次太小导致的算力吃不满。扩展方式还分两种：总批次固定时，加卡减少每卡工作，通信占比上升；每卡批次固定时，加卡增大总批次，训练目标与收敛行为随之改变。

所以报告吞吐要连同批次策略和质量指标一起报——训练更快但需要更多步才达标，总成本不一定更低。

## 代码走读：ddp_check.py 的对照设计

实验设计一句话：把契约的两条路径放进同一份代码，让它们对同一批数据各走一步，再逐参数比较。基线和 DDP 同进程同居，环境、种子、数据张量完全相同，唯一的差别就是执行路径本身——这比两个脚本、两次运行、靠文件中转的对照干净得多。

`labs/distributed/ddp_check.py` 由 torchrun 启动（`--standalone --nproc-per-node=2` 注入 rank、world size 等环境变量；进程组本身是 <a href={asset('read/collectives/')}>collectives 章</a>的内容），CPU 默认走 Gloo，`LAB_DEVICE=cuda` 时切到 GPU 与 NCCL。准备段有三件事值得先记：`torch.set_num_threads(1)` 把每个进程固定为单线程，求和顺序确定、数字可逐位对照；`torch.manual_seed(7)` 让两个进程构造出同样的初始参数；进程组带 90 秒超时，卡住就失败而不是一直挂着。

还有一个身份细节：`rank` 是通信组里的进程编号，`LOCAL_RANK` 是同一台机器内的编号，脚本用后者在 GPU 模式下选中本进程的卡（`torch.cuda.set_device(local)`）。两者在小实验里恰好相等，多机多卡时会分家——rank 是全局身份，LOCAL_RANK 决定你用哪块设备。

核心是三段。第一段（第 20–28 行）建立基线，并让基线吃下全局批次：

```python
model=TinyLM().to(device)
baseline=copy.deepcopy(model)
ddp=DDP(model,device_ids=[local] if use_cuda else None)
x=torch.tensor([[0,1,2],[0,2,1],[1,3,4],[2,4,3]],device=device)
y=torch.tensor([[1,2,3],[2,1,4],[3,4,5],[4,3,6]],device=device)
opt_a=torch.optim.SGD(baseline.parameters(),lr=.01)
opt_b=torch.optim.SGD(ddp.parameters(),lr=.01)
full_loss=torch.nn.functional.cross_entropy(baseline(x)[0].reshape(-1,7),y.reshape(-1))
full_loss.backward();opt_a.step()
```

逐行对照：

- `model=TinyLM().to(device)`：种子 7 之下，两个进程各自构造出逐位相同的初始参数——契约第 1 步的起点。规模小，靠种子就够；一般情形 DDP 构造时还会把 rank 0 的参数与缓冲广播给全组，把“同一起点”从约定变成机制。
- `baseline=copy.deepcopy(model)`：在 DDP 包装之前拍下冻结副本。此后它只作为单进程参考存在，不受任何分布式逻辑影响——对照组必须这样隔离。
- `ddp=DDP(model, device_ids=...)`：DDP 包装的是同一个模块，不复制参数，只接管它的梯度路径（CPU 上 `device_ids=None`，GPU 上传本地卡号）。因此后文比较 `model.parameters()`，比较的就是 DDP 训练出的那份参数；`opt_b` 优化的 `ddp.parameters()` 也是同一组张量。
- `x` / `y`：4 条长度 3 的样本，`y` 是每行右移一位的下一 token 目标——tiny-training 章的同款构造，词表 7。这四条就是全部教学批次，两条路径吃的必须是同一批。
- `opt_a`：基线的 SGD。
- `opt_b`：DDP 路径的 SGD。两个优化器学习率同为 0.01——契约第 4 步要求“同样的更新规则”，从优化器构造这一行就开始保证；一个 SGD 一个 Adam，后面的比较就失去意义。
- `full_loss=...`：基线一次吃全部 4 条。`baseline(x)[0]` 取 logits（第二个返回值的各层 K/V 训练用不上），`reshape(-1,7)` 把输出摊平成 4×3=12 个位置。
- 同一行里的 `cross_entropy` 默认取平均——12 个位置各算一次交叉熵再平均，这一行就是“全局批次平均损失”。
- `full_loss.backward(); opt_a.step()`：单进程路径一步走完。没有 zero_grad，因为优化器全新、`.grad` 尚不存在，只走一步。

第二段（第 29–31 行）是 DDP 路径，各 rank 只吃自己的分片：

```python
indices=torch.arange(rank,4,world,device=device)
local_loss=torch.nn.functional.cross_entropy(ddp(x[indices])[0].reshape(-1,7),y[indices].reshape(-1))
local_loss.backward();opt_b.step()
```

- `indices=torch.arange(rank,4,world)`：交错分片。world=2 时 rank 0 拿样本 [0,2]、rank 1 拿 [1,3]——不重叠、全覆盖、各 2 条。连续切还是交错不影响数学，但必须显式：把同一个普通 DataLoader 原样放进每个进程不会自动分片，重复读同一批数据就是故障表的第一行，而且每张卡都很忙，很难从吞吐数字看出来。
- `local_loss=...`：本 rank 只对自己的 2 条样本、6 个位置取平均——局部平均损失。
- `local_loss.backward(); opt_b.step()`：backward 触发上一节的整笔账——reducer 对就绪的 bucket 发起 AllReduce 并按进程数缩放，`backward()` 返回时每个 rank 的 `.grad` 都已是全局平均梯度；step 各 rank 独立执行同样的 SGD 更新，契约第 4 步。

第三段（第 32–34 行）是对照本身：

```python
error=max((a-b).abs().max().item() for a,b in zip(baseline.parameters(),model.parameters()))
for a,b in zip(baseline.parameters(),model.parameters()):
    torch.testing.assert_close(a,b,atol=2e-6,rtol=2e-5)
```

- `error=max(...)`：先算出“两条路径参数的最大绝对差”——证据文件里 `max_parameter_error` 的来源。zip 的一侧是 `baseline.parameters()`，另一侧是 `model.parameters()`（DDP 包装的原模块）。
- `assert_close(a, b, atol=2e-6, rtol=2e-5)`：真正的判据，通过才打印 JSON。
- 打印里的 `'matches_global_batch': true` 是通过路径中的常量：下判据的是断言，量化证据是 `error` 这个数。读多卡日志要能区分“声明”与“判据”。
- `samples` 字段让每个 rank 自报处理了哪些样本编号：先证明“我处理的是哪几条数据”，误差数字才有解释权——多卡日志的基本纪律。
- `finally` 里的 `dist.destroy_process_group()` 在退出前拆掉通信组，即使中途抛错也会执行。

断言通过后程序打印的键，逐个对照：

- `rank` / `world`：本进程的通信组身份与组大小；
- `device`：本 rank 用的设备，证据记录里是 cpu；
- `samples`：本 rank 分到的样本编号，分片的直接证据；
- `max_parameter_error`：两条路径的最大参数误差，证据记录里是 1.4901161193847656e-08；
- `matches_global_batch`：通过断言后的声明——判据在断言，不在这一格。

`local_loss.backward()` 与配套的源码走读篇 <a href={asset('code/ddp-reducer/')}>《梯度什么时候开始跨 rank 同步？》</a>直接相接。那篇从 PyTorch v2.14.0 `distributed.py` 的 forward 入口往下追：DDP 在 `_pre_forward`/`_post_forward` 里做反向准备、构建 reducer，把通信挂进 autograd hook，完整逻辑在 C++ reducer 里而不在 Python 文件；桶在反向中逐个就绪、逐个通信，`optimizer.step()` 消费的是已同步完的梯度。

它的开篇问题也一并带走：为什么不干脆每次 `optimizer.step()` 之后把各 rank 的参数平均一下来代替 DDP？——那是另一条算法路径；优化器带动量或 Adam 统计时，与“先同步梯度、再各自一致更新”并不等价。

把你的数字与证据记录逐项对照（`docs/runs/ddp-cpu.json` 原文）：

```json

  "date": "2026-09-13",
  "python": "3.12.14",
  "torch": "2.14.0",

  "world_size": 2,
```

跑不出来时按顺序排查：`torchrun` 不存在说明环境没激活；两个进程卡住不动，先看 `--standalone` 的 rendezvous 端口是否被占用；报错退出则读最先抛错的那个 rank 的栈，其余 rank 多半只是等它超时。

跑通之后，先预测再验证：把 `--nproc-per-node` 改成 3，会发生什么？

<details>
<summary>先自己推一遍，再展开</summary>

脚本会拒绝启动，而不是给出错误结果。第 19 行的护栏先于一切计算生效：

```python
if 4%world:raise ValueError('world size must divide the four-sample teaching batch')
```

world=3 时 4%3=1，三个进程各自抛出同一个 ValueError，torchrun 以非零码退出。

为什么把“不整除”当成启动错误，而不是让它继续跑？4 条样本分给 3 个进程只能是 2+1+1（按脚本的交错分片，rank 0 拿 [0,3]、rank 1 拿 [1]、rank 2 拿 [2]），而机制一节算过：局部样本数不相等时，“平均再平均”不再等于全局平均。用数字看——设四条样本的梯度为 1、2、4、8，全局平均 (1+2+4+8)/4 = 3.75：

| rank | 样本编号 | 局部平均 |
|---|---|---|
| 0 | [0,3] | (1+8)/2 = 4.5 |
| 1 | [1] | 2 |
| 2 | [2] | 4 |
| 平均的平均 | — | (4.5+2+4)/3 = 3.5 ≠ 3.75 |

此时若让 DDP 照常同步，各 rank 会“一致地”走向一个错误目标——参数一致性照样成立，错误反而更隐蔽。要让不相等的分片保持等价，必须按各 rank 的样本数（更准确地说是有效目标 token 数）加权合并，这正是真实 LM 训练里损失归一化要显式解决的问题。护栏把“静默的错误归一化”提前成“响亮的启动失败”：对照实验的前提一旦破坏，结论就不再成立。

预测完动手验证：把命令改成 `--nproc-per-node=3` 真跑一遍，应当以非零码退出，错误信息正是护栏那一行。

顺带两问：world=4 能过护栏吗？能——每 rank 恰好 1 条样本，“平均再平均”的链条仍然成立。world=1 呢？也能——退化为单进程，AllReduce 变成空操作，对照依旧成立。

</details>
