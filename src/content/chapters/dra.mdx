前一章的任务已经获得预算，现在它需要一张具有指定显存属性的 GPU。传统的整数扩展资源擅长表达“几张”，但更丰富的设备属性、请求约束与分配结果需要清楚的数据接口。<Term id="dra" /> 将这些关系表达为 Kubernetes 对象，并把分配决定与节点侧准备连接起来。

先建立边界：DRA 不是 GPU 驱动本身，也不会替模型计算显存需求。它提供设备发现、请求与分配框架；驱动负责报告真实设备并落实所支持的配置。

## 四个对象分别回答什么

<Term id="resource-slice" /> 描述驱动发布的设备库存，例如设备属于哪个池、哪些节点可访问、有哪些属性。<Term id="device-class" /> 表达一类设备的选择规则与相关配置。<Term id="resource-claim" /> 是工作负载对设备的具体请求，并记录分配结果。ResourceClaimTemplate 则用于按模板生成声明，避免手工为每个 Pod 编写独立对象。

可以把它们放回当前例子：库存说“GPU A 有 24 GiB，GPU B 有 48 GiB”；类别规定这是某个驱动管理的 GPU；声明要求“至少 32 GiB”；调度与分配流程在可达、可用且满足其他约束的候选中找到设备。属性名称、单位和表达式以驱动定义为准，不能猜一个字段名称就认为所有厂商都支持。

## 从创建到容器可用

<Diagram id="dra-flow" caption="基本路径：库存与请求进入调度，分配结果再被节点侧兑现。这里省略高级功能门与驱动可选优化。" />

创建引用声明的 Pod 后，系统要找到满足 Pod 放置条件与设备要求的组合。分配结果写入 ResourceClaim；Pod 被安排到可访问该资源的节点；kubelet 与相应驱动协调节点准备，把容器需要的设备访问配置落实。基本流程及版本差异以官方文档为准。[DRA 工作流程](https://kubernetes.io/docs/concepts/resource-management/dynamic-resource-allocation/how-dra-works/)

“Claim 已分配”只证明控制面做出了选择，不能证明节点设备准备成功。驱动调用失败、设备状态变化、运行时配置错误，都可能发生在后面。因此，排障必须沿生命周期逐步查看，不能只搜索某一条 GPU 报错。

## 一个请求要检查哪些状态

```bash
kubectl get deviceclasses
kubectl get resourceslices
kubectl -n inference-lab get resourceclaims
kubectl -n inference-lab describe resourceclaim CLAIM_NAME
kubectl -n inference-lab describe pod POD_NAME
```

前两条检查库存与类别是否存在；第三、四条检查请求和分配结果；最后一条查看 Pod 事件。名称由实际创建结果替换。若库存正确但声明未分配，查请求条件、可达节点和占用；若已分配但 Pod 无法启动，继续查节点驱动及 kubelet 事件。

在实验前记录 Kubernetes 版本、DRA 驱动镜像、资源 API 版本与功能门。核心 API 稳定不代表所有高级子功能都已稳定或默认开启。比如设备绑定条件与容量共享等能力有各自版本状态，不应从会议路线图直接推断本集群可用。

## 释放不是删除一个名字那么简单

当工作负载结束，系统需要完成节点侧清理，并在声明生命周期允许时释放分配。独立声明可以有不同于单个 Pod 的寿命；从模板产生的声明有其所有者关系。删除 Pod 之后是否还能看到声明，要结合创建方式判断。

真正的回收验收应提交另一个符合条件的请求，确认设备能再次分配并使用，同时检查旧消费者已经不能继续访问不属于它的资源。节点失联、驱动重启和重复清理调用都需要处理；因此，驱动操作的幂等性与状态恢复是可靠性问题的一部分。
