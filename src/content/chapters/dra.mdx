<a href={asset('read/scheduling/')}>scheduling 章</a>结束时，任务拿到了入场券：配额批了、准入过了，Pod 可以创建。但入场券上还没有座位号——这个 Pod 究竟用**哪几张卡**，一个字都没写。<Term id="dra" />（动态资源分配，Dynamic Resource Allocation）就是 Kubernetes 回答这个问题的方式：把"设备分配"从数数变成一场带属性、带约束、带结果的对话。

先立边界，本章结尾也适用：DRA 不是 GPU 驱动本身，也不会替模型计算显存需求。它提供设备发现、请求与分配的框架；驱动负责报告真实设备并落实所支持的配置。

## 这一章解决什么问题

"这台机器有 8 张 GPU"——这句话在调度层几乎不携带信息。对一次真实的训练或推理任务，它至少缺三样东西：

- **哪 8 张**：设备是有身份的个体，不是可互换的豆子。分到 GPU-0 和 GPU-3，与分到分属两个互连域的卡，是两种完全不同的分配。
- **健康吗**：8 张里可能有 1 张正带着 ECC 错误降频运行，或已被驱动标记下架。库存数字看不见这些。
- **拓扑近吗**：<a href={asset('read/topology/')}>互连拓扑一章</a>算过账：同一个 NVSwitch 域内两卡之间每向 450 GB/s，跨出域只剩网卡级带宽。8 张卡内部有快线有慢线，"8"这个总数把它们抹平了。

传统的设备插件模型恰好只能表达"8"。它的工作方式是：第三方设备插件以节点守护进程的形式向 kubelet 注册 `nvidia.com/gpu` 这类扩展资源并上报数量；调度器在过滤与打分时只看到"节点上有 8 个"；真正决定把哪些具体设备 ID 交给容器的，是节点内的插件实现。这个分工留下两个结构性问题。第一，**请求的表达上限是一个整数**——你可以说"给我 4 个"，说不出"给我 4 张互相 NVLink 互联、每张至少 48 GiB、都要健康的卡"。第二，**决策权分裂**：控制面只按计数选节点，发卡的策略藏在节点内的插件里，请求方既看不见也约束不了。

DRA 的答案是声明式的：请求方描述**要什么**（属性与约束），而不是**拿哪些 ID**。系统在驱动发布的库存里找一个满足全部条件的设备组合，把结果记录成 API 对象。于是上面三样缺失的东西都有了落点：身份落在库存对象里，健康落在设备状态里，拓扑落在可筛选的属性里。

本章按四步走：先算一次设备请求要过的**三层账**（健康、容量、拓扑）；再沿 ResourceClaim 的**生命周期**走一遍（申请→驱动分配→kubelet 挂载）；然后把"同域"这行约束换算成 topology 章的**收益账**；最后逐段走读 lab 清单，并把交互演示的每个旋钮对号入座。读完的检验标准：看着一份设备表，能逐层写出谁被刷掉、为什么，以及"已分配"之后还差哪几步容器才真正用得上卡。

## 机制讲解：从"给 4 个 ID"到"按约束选 4 张卡"

### DRA 用四个对象把库存、规则、请求、结果拆开

<Term id="resource-slice" />（ResourceSlice，资源切片）是驱动发布的**库存**：这个资源池里有哪些设备、设备属于哪个节点或池、各有哪些属性——显存容量、NUMA 归属、互连域，属性名和单位都由驱动定义。<Term id="device-class" />（DeviceClass，设备类别）是管理员定义的**选择规则**与配套配置：凡按这个类别发起的请求，都按同一套规则筛选设备、附带同一套驱动参数。<Term id="resource-claim" />（ResourceClaim，资源声明）是工作负载的**请求**，同时是**分配结果的记录**——claim 被分配后，`status` 里写的就是选中的具体设备。第四个对象 ResourceClaimTemplate 让 Job、StatefulSet 这类控制器按模板为每个 Pod 生成声明，声明的寿命既可以跟随 Pod，也可以独立存在。

放回例子：库存说"GPU-A 有 24 GiB、在 NUMA 1；GPU-B 有 48 GiB、在 NUMA 0"；类别规定"这是某驱动管理的 GPU，按这些规则选"；声明要求"至少 32 GiB"；分配流程在可达、可用、满足约束的候选中找到 GPU-B 并写回声明。要注意属性名称、单位和匹配表达式以驱动定义为准——不能猜一个字段名就认定所有厂商的驱动都支持它。

对比设备插件模型，变化不只是"多了一些对象"。把两个模型放在同一张表上：

| 维度 | 设备插件模型 | DRA |
| --- | --- | --- |
| 请求表达 | 一个整数（`nvidia.com/gpu: 4`） | 属性与约束（"4 张、每张 ≥48 GiB、同域"） |
| 库存形态 | 节点上的计数器 | ResourceSlice：逐设备、带属性的对象 |
| 决策位置 | 节点内插件（黑盒），控制面只数数 | 带规则的分配流程，结果写入 claim status |
| 健康表达 | 插件下架设备让计数减一 | 设备状态是库存对象的一个字段，可被选择器引用 |
| 拓扑表达 | 无标准通道 | 属性与约束可筛选，成组约束由分配逻辑凑 |
| 结果可见性 | 容器里的设备 ID（事后才知道） | 分配结果是 API 资源，可 `kubectl get`、可审计 |

健康一行值得多说一句，因为它常被低估。设备插件模型里，插件发现坏卡可以把它从上报列表里摘掉，计数减一——新请求不会再拿到它，但**已持有这张卡的 Pod** 只能靠自身重启退出。DRA 同样依赖驱动报告设备状态，但状态落在库存对象上：调度与分配读取它，排障时 `kubectl get resourceslices` 就能看见"哪张卡、什么属性、什么状态"，而不是从一个总量里猜差额。

### 筛选的三层账：健康、容量、拓扑

现在把"找一个满足条件的设备组合"拆开。任何实现——从站内演示的三行代码到真实的 CEL 选择器——都要过同样三层账。以下是本章交互演示背后的设备表，也是后面所有算例的库存：

| 设备 | 显存 | NUMA 域 | 健康状态 |
| --- | --- | --- | --- |
| GPU-0 | 80 GiB | 0 | 健康 |
| GPU-1 | 24 GiB | 1 | 健康 |
| GPU-2 | 80 GiB | 1 | 故障（已下架） |

演示的筛选逻辑浓缩在一个函数里：`selectDevices(memory, sameNuma)` 返回**同时**满足"健康、显存 ≥ memory、（若要求同域）NUMA 为 0"的设备。三层账逐层看：

**第一层：健康。**GPU-2 有 80 GiB，容量条件对任何请求都绰绰有余——但它不健康，任何请求第一个刷掉的就是它。这直接回答了演示的预测问题："显存足够的设备，为什么仍可能不符合请求？"健康是按设备维度的否决，一票即出局，与其他条件多好无关。

**第二层：容量。**请求 16 GiB：GPU-0（80 ≥ 16）与 GPU-1（24 ≥ 16）都通过，`selectDevices(16, false)` 返回 `[GPU-0, GPU-1]`，两个候选。请求 48 GiB：GPU-1 的 24 GiB < 48，被刷掉，`selectDevices(48, false)` 只剩 `[GPU-0]`。注意这两句话的差别——"集群还有卡"与"有满足你约束的卡"不是一回事。scheduling 章的准入管的是预算够不够，这一层管的是库存形状与请求形状匹不匹配。

**第三层：拓扑。**勾选"与 NIC 的 NUMA 0 共置"后，NUMA 不为 0 的设备再被刷掉——GPU-1（NUMA 1）出局。这个开关模拟的是真实诉求：推理进程的 GPU 与承接流量的网卡最好在同一 NUMA 侧，否则每次跨机传输前后两端都要先绕一段 CPU 间互连（topology 章的 NUMA 一节算过这笔小账）。

**全军覆没的情形。**`selectDevices(100, false)` 返回空数组：没有任何一张卡 ≥ 100 GiB。请求会停在"无候选"，Pod 挂在 Pending——但这次的 Pending 不是配额不足，是库存里根本没有那个形状。演示里勾选"模拟容量不足"后请求变为 96 GiB，同一行代码给出同样的空结果。两者的修法完全不同：配额不够找管理员加预算，形状不匹配要么改请求，要么等库存变化（新节点上线、坏卡修复）。

演示是一个小候选集的机制模型，不复制 Kubernetes 的完整调度算法、并发冲突处理或全部 API。它用于让你区分过滤、选择和准备这三个不同阶段，不能用演示输出预测生产调度顺序。真实 DRA 的选择器写法更丰富（DeviceClass 与声明里可用 CEL 表达式组合属性条件），"同域 4 卡"这类**成组**约束还要由拓扑感知的分配逻辑在候选集上凑组合——单卡合格不等于组能凑齐，动手环节会专门练这道题。

### ResourceClaim 的生命周期：申请、驱动分配、kubelet 挂载

<Diagram id="dra-flow" caption="基本路径：库存与请求进入调度，分配结果再被节点侧兑现。这里省略高级功能门与驱动可选优化。" />

筛选只是生命周期的一环。站内的源码走读任务<a href={asset('code/dra-lifecycle/')}>《设备选择怎样走到节点准备？》</a>（固定 Kubernetes v1.36.0）逐步追了这条路径，这里按它的结论复述，给不马上读源码的读者对齐图景：

1. **申请。**Pod 创建时引用 claim（直接引用名字，或经 ResourceClaimTemplate 生成）。claim 此时未分配，Pod 不可运行。
2. **调度器筛选与暂存。**调度框架的 DynamicResources 插件在 `Filter` 阶段对每个候选节点回答"这个 Pod 引用的 claim 在此节点上能否分配"——读的是 ResourceSlice 库存与 DeviceClass 规则，做的就是上一节的三层账。`Reserve` 暂存选择，`PreBind` 提交，分配结果（具体设备列表）写入 claim 的 status。这一段全部发生在控制面。
3. **节点准备。**Pod 绑定到节点后，kubelet 的 DRA 管理器在 `PrepareResources` 里沿 Pod 的声明引用找到分配与驱动信息，调用节点侧驱动插件准备资源；成功后容器运行时按 CDI 规格把设备访问注入容器。硬件相关的准备（挂载、配置 GPU 实例这类）由驱动完成。
4. **使用与回收。**工作负载结束，kubelet 走 `UnprepareResources` 清理节点侧状态；声明的生命周期规则再决定何时释放。回收的验收不是看 delete 调用，而是提交另一个符合条件的请求，确认设备能再次分配、旧消费者已不能访问。

三个必须钉死的边界，每个都对应一类真实故障。第一，`Filter` 通过不等于驱动已经把 GPU 交给容器——它只是调度阶段的一个控制面判断，节点侧准备在后面，仍可能失败。第二，"claim 已分配"只证明控制面做出了选择，不能证明节点准备成功：驱动调用失败、设备状态变化、运行时配置错误都发生在第 3 步。这正是本章开头的问题——**ResourceClaim 已分配但容器用不上卡，下一步查的是节点侧**：Pod 事件、节点可达性、kubelet 与驱动的准备结果。第三，`Reserve` 不是永久设备准备，并发调度下还有冲突与撤销要处理。

沿这条链的检查命令，按生命周期对号：

```bash
kubectl get deviceclasses
kubectl get resourceslices
kubectl -n inference-lab get resourceclaims
kubectl -n inference-lab describe resourceclaim CLAIM_NAME
kubectl -n inference-lab describe pod POD_NAME
```

前两条查库存与规则是否存在；第三、四条查请求状态与分配结果；最后一条看 Pod 事件——节点侧的失败会停在这里。若库存正确但声明未分配，查请求条件、可达节点和占用；若已分配但 Pod 无法启动，继续查节点驱动与 kubelet 事件。基本流程与版本差异以[官方 DRA 文档](https://kubernetes.io/docs/concepts/resource-management/dynamic-resource-allocation/how-dra-works/)为准。

版本口径值得单独记：核心 API 进入 `resource.k8s.io/v1` 不代表所有高级子功能都已稳定或默认开启。设备绑定条件、容量共享这类能力各有自己的版本状态，不应从会议路线图直接推断本集群可用。实验前记录 Kubernetes 版本、DRA 驱动镜像、资源 API 版本与功能门。

### 释放与故障：声明寿命、幂等性与恢复

生命周期的第 4 步比"删掉一个名字"复杂。独立创建的声明可以有长于单个 Pod 的寿命；从模板生成的声明则跟随所有者关系——删除 Pod 之后声明还在不在，要结合创建方式判断，不能一律假定"Pod 没了资源就回来了"。

回收这一侧有三个真实故障点。**清理路径是另一条代码路径**（源码篇的 `UnprepareResources`），不是分配的逆函数自动倒放；它有自己的失败模式。**重复调用必须安全**：节点失联后恢复、驱动重启、清理与重新分配交错，都会让 prepare/unprepare 被调用不止一次——驱动操作的幂等性因此是可靠性问题的一部分，不是实现细节。**节点重启要能恢复本地状态**，否则分不清"没准备过"和"准备了但记录丢了"。

所以验收释放也要像验收分配一样走证据链：提交另一个符合条件的请求，确认设备能再次分配并使用，同时确认旧消费者已经不能访问不属于它的资源。两个检查都过了，才算回收完成。

### 拓扑约束值多少钱：把 topology 章的账接过来

第三层账刷人是要付代价的——约束越紧，可行集越小。那为什么还要写"NVLink 互联的 4 卡"这行约束？因为它的收益不是优化项，是数量级项。<a href={asset('read/topology/')}>互连拓扑一章</a>对同一个 8 卡 ring AllReduce 算过完整账，这里直接引结论，不重推：

- 并行组在**同一 NVSwitch 域内**：环上每条边都是 NVLink，每层通信的带宽项 ≈ **3.9 ms**（每向 450 GB/s）。
- 并行组**跨两个域**（经慢层互联，最优排列）：过桥 rank 的全部出向流量都落在慢线上，带宽项 ≈ **70 ms**（每向 25 GB/s）——18 倍差距，且这是排列最优后的结果；环排交错还要再差 4 倍（280 ms）。

同一个张量并行模型每层都通信，80 层就是每步 0.3 s 对 5.6 s 的差别。所以在声明里多写一行拓扑约束，等价于把每层通信的分母从 25 GB/s 换成 450 GB/s——传统设备插件模型里，这行约束**没有地方可写**；DRA 让它变成请求的一等公民。反过来，这也是调度要在"通信代价"与"装不装得下"之间权衡的原因：把所有紧密组挤进一个域可能容量不够或 Pending，把账算清楚再决定约束写到多紧。

## 代码走读：dra.yaml 与演示旋钮

配套 lab 是 `labs/kubernetes/dra.yaml`，一个文件里两份对象，用 `---` 分隔。逐段走读。

第一段，ResourceClaim——请求本体：

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceClaim
metadata: {name: gpu-lab, namespace: inference-lab}
spec:
  devices:
    requests:
      - name: gpu
        exactly:
          deviceClassName: example-gpu-class
          allocationMode: ExactCount
          count: 1
```

三个读点。`deviceClassName` 指向 DeviceClass——类别是管理员随驱动安装创建的，不是工作负载发明的；`example-gpu-class` 是占位符，必须替换为所装驱动注册的真实类名，这是 lab 注释里第一行就警告的事。`allocationMode: ExactCount` 加 `count: 1` 表示"恰好 1 张"——这里仍是一个整数，但与设备插件的区别在于：**筛选规则与属性条件写在类别与选择器里**，不是只能数数。示例保持最小；真实的约束（显存下限、拓扑要求）会以选择器表达式的形式出现在类别或声明中。

第二段，Pod——消费方：

```yaml
apiVersion: v1
kind: Pod
metadata: {name: dra-consumer, namespace: inference-lab}
spec:
  restartPolicy: Never
  resourceClaims:
    - name: gpu
      resourceClaimName: gpu-lab
  containers:
    - name: inspect
      image: vllm/vllm-openai:v0.29.0
      command: [sh, -c, 'nvidia-smi && sleep 60']
      resources:
        claims: [{name: gpu}]
```

`spec.resourceClaims` 把 claim 接进 Pod；`containers[].resources.claims` 让容器声明自己消费哪份——两边通过 `name: gpu` 对上。inspect 容器跑 `nvidia-smi` 不是凑数：它是生命周期第 5 步"容器可使用"的直接检查——分配、准备全部成功之后，容器里应当能看见那张卡。`restartPolicy: Never` 让验证完就退出，方便观察回收。

这份清单不满足条件时会停在哪，取决于哪层失败：类名不存在或无候选，claim 未分配、Pod Pending（三层账或规则问题）；已分配但容器报错，则查节点侧准备（生命周期第 3 步）。

交互演示的旋钮与模型逐一对应：

| 演示旋钮 | 模型参数 | 效果 |
| --- | --- | --- |
| 请求至少 48 GiB（开/关） | `memory` = 48 / 16 | 开：GPU-1 被容量层刷掉，候选只剩 GPU-0；关：`[GPU-0, GPU-1]` 两候选 |
| 与 NIC 的 NUMA 0 共置 | `sameNuma` | 拓扑层生效：NUMA 1 的 GPU-1 再被刷掉 |
| 模拟容量不足：请求 96 GiB | `memory` = 96 | 覆盖前一个开关，无候选——"全军覆没" |
| 五个相位按钮 | 生命周期步 | 库存发布 → 筛选候选 → 分配与绑定 → 节点准备 → 容器可使用 |

相位按钮的第 3、4 步之间正是上一节钉死的边界：分配与绑定完成后、节点准备完成前，设备"已属于你"但容器还用不上。演示选择候选时取排序后的第一个（`matching[0]`，本例恒为 GPU-0）；真实调度还要综合节点约束、亲和性与已有占用，顺序不可由此预测。

建议按预测—验证的顺序把演示走三遍，每遍先写下预期候选数再动手：

1. 默认状态（16 GiB、不共置）：预测两个候选，分配落到 GPU-0；被排除的是 GPU-2——先确认自己会把它归到健康层而不是容量层。
2. 打开 48 GiB：预测候选减为一个——GPU-1 这次的出局原因换成了容量层，同一条"被排除"的视觉状态背后是不同的账。
3. 勾选容量不足（96 GiB）：预测零候选，相位按钮走到"筛选候选"就停下——对照上一节"全军覆没"的两种修法，想清楚哪一种该找管理员、哪一种该改请求。

三遍走完的标准：不看正文，能对三张卡分别说出"它被哪层刷掉、或者为什么没被刷掉却也可能进不了结果"。
