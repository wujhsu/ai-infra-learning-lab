## 这一章解决什么问题

上一章，我们在 CPU 上把两层小模型的训练循环完整跑通了：损失一路降到 0.00087 量级，生成命中目标。现在把同样的代码想象放到真实模型、真实 <Term id="gpu"/> 上——最先撞上的常常不是算不快，而是两种更笨拙的失败。

第一种是“装不下”。训练或加载时报内存不足，错误信息里那句"Tried to allocate …"说的正是容量账里的一个分项：此刻想新分配的那块放不下了。第二种是“看起来有空闲却很慢”。利用率不高、批次也不大，吞吐却上不去——很多时候是数据搬运拖住了计算，而不是计算本身不够快。

这两种现象都不是玄学，而是可以列式计算的账。本章把它们拆成两个问题：

- **容量账**：运行时到底有哪些数据住进了设备内存，各占多少字节，各随什么增长？
- **带宽账**：这些字节在存储层次之间搬运，每秒能搬多少、搬一次要多久？

路线如下。先给三类住户各算一笔账：真实规模用 Qwen3-0.6B，对照规模用我们已跑熟的 TinyLM——同一个公式，两种尺度。然后把容量与带宽分开：同一份权重，从显存读一遍和从主存搬一遍，时间差多少倍。再进代码走读，确认参数在 forward 之前就已占好内存、派生状态何时才到。最后把这些方法组装成一次练习：算一遍你自己显卡的账。

住户分三类，生命周期完全不同——权重（常驻的一份）、激活（每批用完即弃的耗材）、KV（生成时每请求持续增长的账）。用后端做类比：权重像进程启动时加载的只读配置，加载一次、所有请求共享；激活像处理单个请求时的临时对象，请求结束即可回收；KV 像按会话隔离的 session 状态，随会话变长、随并发变多。

有一个后果值得先点破：训练与推理的显存账本不同。训练要为反向保留激活、为更新保存梯度与优化器状态；推理没有这些，但生成服务要为每个请求保留 KV。所以不能拿模型文件大小推断训练需要多少内存，也不能把一份 KV 当作整个模型的占用。

读完的检验标准：不看正文，能说出三类住户各自“随什么增长”——权重不随任何运行参数增长，激活随 batch×seq 相乘增长，KV 随并发×上下文增长。本章开头的引导问题（参数量不变，序列变长为什么会内存不足）的答案，就藏在这三句话里。

## 机制讲解：显存的三类住户

先明确“住在哪里”。GPU 侧的设备内存——数据中心卡常见的是 <Term id="hbm"/>——是三类住户共同的预算池。

下面各算一笔账。真实规模用 Qwen3-0.6B（模型卡：28 层、16 个查询头、8 个 KV 头、hidden size 1024，约 6 亿参数，以下按 6×10⁸ 取整做算例）；对照规模用教学模型 TinyLM（2 层、宽度 32、词表 7、上下文上限 32）。所有数字都是容量算术，不是测量。

### 权重：常驻的那一份

权重在加载时一次写入，之后只读。字节数就是三因子相乘：参数个数 × 每参数字节（由 <Term id="dtype"/> 决定）。

Qwen3-0.6B 按 fp16 或 bf16（每参数 2 字节）保存：6×10⁸ × 2 B = 1.2×10⁹ 字节 = 1.2 GB，按二进制口径约 1.12 GiB。推理服务无论同时接多少请求，这一份是共享的。参数量是广告数字，这行乘法才是工程数字。

训练时这份账立刻膨胀。按一套常见的混合精度配置算：

- 反向需要与权重同形状的梯度：fp16，再 1.12 GiB。
- AdamW 为每个参数维护一阶矩、二阶矩两个 fp32 统计：各 6×10⁸ × 4 B = 2.24 GiB。

合计 1.12 + 1.12 + 2.24 + 2.24 = 6.72 GiB——每参数字节从 2 变成 12，正好是推理权重的 6 倍。注意这是按指定表示方式算的示例，不是所有混合精度实现的固定账本；有的实现还保留 fp32 主权重，账更大。

对照 TinyLM：参数可以逐张量数出来，一张表就能装下。

| 张量 | 参数个数 | 备注 |
| --- | --- | --- |
| token 嵌入表 | 7×32 = 224 | |
| 位置表 | 32×32 = 1,024 | |
| 每个 Block | 12,576 | qkv 投影 3,072、输出投影 1,024、两个 LayerNorm 各 64、MLP 两个带偏置线性层共 8,352 |
| 末层 LayerNorm | 64 | |
| 输出头 | 32×7 = 224 | |

两个 Block 共 25,152 个，加上表里的其余各项，合计 26,688 个参数。PyTorch 默认 fp32 下 26,688 × 4 B = 106,752 字节，约 104 KiB——这份账稍后在代码走读里用一行代码原样验出。

Qwen3-0.6B 的 1.2 GB 权重约是它的 1.1 万倍。但下一笔账会看到，“参数多一万倍”并不等于“运行时各数据的比例不变”。

### 激活：随 batch 与序列长度相乘的耗材

<Term id="activation"/> 是前向计算产生的中间张量。梯度一章算过一笔关键账：反向传播要读取正向的中间值，所以训练不能随手丢掉它们——激活在训练里是“要留给反向用的耗材”，推理（no_grad 下）才是用完即弃。

它的大小是一个乘法：**批次数 B × 序列长度 T × 每位置宽度 × 每元素字节 × 保留的份数**。B 和 T 地位相同：batch 翻倍或序列翻倍，激活都翻倍。这就是“参数量不变，序列变长仍会内存不足”的第一个来源。

用 TinyLM 实算一次，B=8、T=32（共 256 个位置，fp32）。每个 Block 里挑四种有代表性的中间量：

| 中间量 | 形状 | 字节 |
| --- | --- | --- |
| norm1 输出 | [8, 32, 32] | 32 KiB |
| qkv 投影输出 | [8, 32, 96] | 96 KiB |
| 注意力概率 | [8, 2, 32, 32] | 64 KiB |
| MLP 中间层 | [8, 32, 128] | 128 KiB |

每层小计约 320 KiB，两层约 640 KiB，再加上嵌入输出等零头——只数这四种张量，就已超过全部权重（104 KiB）的六倍。要说明的是，autograd 实际保留哪些张量取决于各算子的实现，这张表数的是“哪些形状会出现在账上”，量级结论不依赖精确清单。在教学模型上，一个中等批次的激活就能压过权重；真实模型上同理，只是所有数同乘一个倍数。

推理的激活账小得多：no_grad 下不为反向保留，中间量随用随丢，峰值大约由最宽的那一层决定。但 Prefill 处理长提示词时，上表这些形状仍会一次性出现——长输入的推理同样要过一遍激活的乘法，只是不留到反向。

Qwen3-0.6B 上再算一行。每 token 的残差流一份是 hidden 1024 × 2 B = 2 KiB；批次共 B×T = 4,096 个 token、28 层，每层只保留这一份，就是 4,096 × 28 × 2 KiB = 224 MiB。

这还不是全部：上表那种注意力概率矩阵的形状含 T×T，随序列长度平方增长——序列从 4,096 拉到 8,192，残差流那份翻倍，注意力概率那份翻四倍。序列长度同时出现在两条增长曲线里，参数量哪一条都管不着。

### KV：随并发与上下文增长的账

推理侧的主角。生成服务为每个请求保留 <Term id="kv-cache"/>，KV 复用一章已经算过这笔账：28 层、8 个 KV 头、头宽 128、fp16，每 token 每请求 2 × 28 × 8 × 128 个数 × 2 字节 = 114,688 字节，即 112 KiB——这组配置正是 Qwen3-0.6B 的注意力结构。

接着往下乘：上下文跑满 4,096 是 112 KiB × 4,096 = 448 MiB；8 路并发就是 3.5 GiB，约是同一模型权重（1.12 GiB）的 3 倍。

权重是所有请求共享的一份，KV 是每请求一份、随并发线性放大、随上下文线性增长。并发再往上加，先耗尽的是 KV 预算而不是权重——这是推理容量压力的主要算术来源，也是后面量化 KV、分页管理这些主题的动机。

一个提醒：演示固定用 32 层、8 个 KV 头、头宽 128 的示例配置，每 token 是 128 KiB，与正文 28 层的 112 KiB 不同。公式不变，配置一换结果就变——真实工程要从实际加载的模型配置读数，这正是 KV 分配一章展开的话题。

TinyLM 的 KV 账小到几乎看不见：2(K/V) × 2(层) × 2(头) × 16(头宽) × 4 B = 每 token 512 字节，上下文上限 32，全程最多 16 KiB。同一个公式，在教学模型上是可以忽略的零头，在真实模型上是账本主角。

尺度变化会改变瓶颈，但改变不了账本的记法。

### 三笔账放在一起

把三笔账并排放在一张表里，本章开头的引导问题就只剩查表：序列变长时，哪些行会动、哪些行不动。

| 住户 | 何时分配 | 何时可释放 | 随什么增长 | 上文的算例 |
| --- | --- | --- | --- | --- |
| 权重 | 模型构造、搬上设备 | 进程结束 | 参数量 × 每参数字节 | 1.12 GiB（共享一份） |
| 激活 | 前向计算中逐个产生 | 训练：反向用过之后；推理：当前层用完 | B × T × 宽度 × 层数 | 224 MiB（4,096 token） |
| KV | 每请求随生成追加 | 请求结束 | 并发 × 上下文 | 3.5 GiB（8 路 × 4,096） |

训练还要在这张表之外再记两行：梯度（与权重同形，反向时分配）和优化器状态（首次更新时分配）。它们的行为像权重（常驻、随参数量增长），但到达时间晚一拍——这个时间差，代码走读一节会亲眼看到。

最后划一条边界：这张表数的是数据本身的字节数，是容量的下界。实测的显存面板还会叠加碎片、对齐、通信缓冲与运行库开销。容量算术回答“数据要放多少”，不回答“监控里会显示多少”——两者对不上时，先查差额属于哪一类，而不是怀疑算术。

## 机制讲解：容量、带宽与 Roofline 下界

容量账算完“放多少”，现在算“搬多快”。先分清三个量：容量回答能放多少字节；<Term id="bandwidth"/> 回答每秒能搬多少字节；延迟回答从发起到完成要等多久。一个仓库可以很大但门很窄——容量够而传输慢的直觉就在这里。

数据在 CPU 和 GPU 之间也不是同一块可以无成本随意读取的存储。CPU 通常负责数据读取、程序控制和发起工作，GPU 执行大量并行数值运算；数据要经过支持的传输路径，或者使用具体平台的统一内存机制——后者也不等于没有迁移成本。

GPU 内部还有层次：较大的设备内存、缓存、线程块可共享的存储，以及线程使用的寄存器。越靠近执行单元，通常容量越小，访问代价和使用规则也不同。

不要把这些层次都叫“显存”，否则看 kernel 优化时会分不清数据到底在哪儿。本章的账只记设备内存这一层；哪些可复用数据该留在设备内存、哪些转去主存或更冷的层，是后面分层缓存一章的主题。

现在做本章的关键算例：**同一份 1.2 GB 权重，从两个不同位置读一遍，各要多久？**

- 已经在 HBM 里：以 H100 SXM 的 HBM3 规格带宽约 3.35 TB/s 计，1.2×10⁹ ÷ 3.35×10¹² ≈ 0.00036 秒，约 **0.36 毫秒**。
- 还在 CPU 主存里，经 <Term id="pcie"/> 搬上卡：PCIe 5.0 ×16 单向规格约 64 GB/s，1.2×10⁹ ÷ 64×10⁹ ≈ 0.019 秒，约 **19 毫秒**。

同样的字节，路径不同，差约 52 倍（3,350 ÷ 64 ≈ 52）。为什么推理服务要把权重常驻在 GPU 而不是放在主存里随用随取、为什么“把数据放到离计算近的地方”值钱，算术来源就是这一行除法。

搬运的频率和方向也要进账，方向有行话：主存到设备叫 H2D（Host to Device），设备到主存叫 D2H。权重只在加载时 H2D 一次；输入批次每个训练步都 H2D；输出（loss 或候选得分）每步 D2H 回主存。用 TinyLM 数一遍（B=8、T=32）：输入是 int64 的 token ID，[8, 32] × 8 B = 每步 2,048 字节；logits 是 [8, 32, 7] 的 fp32，每步 7,168 字节出卡；权重 106,752 字节只在开始搬一次。每步流动的是小头，一次搬定的是大头——所以“权重放得近”比“输入搬得快”重要得多。

两个边界：这是用规格峰值做的除法，不是实测——有效带宽通常低于规格，还叠加启动、同步、排队开销；更小的数字同理，搬 4 GB、有效带宽 20 GB/s，仅传输部分就约 0.2 秒。

算这类账时先统一口径：GB 使用十进制 10⁹ 字节，GiB 使用二进制 2³⁰ 字节。同一个原始字节数，用 GB 表示会比用 GiB 表示的数字大——本章的 1.2 GB 与 1.12 GiB 就是同一份权重。

互连规格还有一个易踩的口径：PCIe 5.0 ×16 的 64 GB/s 是单向值，双向合计再翻倍；单次搬运只能按单向算。术语卡里“标称双向总带宽不是单次传输的有效带宽”说的就是这类差别。

### 带宽还是算力：一个决定时间下界的除法

最后把搬运和计算放在同一杆秤上。设某段计算需要 F 次浮点运算、搬运 B 字节，设备在这个任务下的有效算力为 P 次运算/秒、有效带宽为 W 字节/秒。理想情况下也至少受到两种时间限制：

$$T\geq\max(F/P,\ B/W)$$

F/B 叫算术强度：每搬一字节做多少运算。这个用计算峰值和内存带宽共同估计性能上限的框架叫 <Term id="roofline"/>。拿两个形状相同、性格相反的算子做对照（数字取公开规格的常见值：H100 SXM fp16 稠密峰值约 989 TFLOP/s，HBM3 约 3.35 TB/s；每个数输入只读一次、输出写一次，这是理想化假设）：

- **矩阵乘** [1024,1024] × [1024,1024]（fp16）：F = 2×1024³ ≈ 2.15 GFLOP；B = 3 个矩阵 × 1024² × 2 B ≈ 6.3 MB。算术强度约 341 FLOP/B。时间下界取 max(2.17 µs, 1.88 µs)——两项接近，略偏算力一侧。
- **逐元素加** c = a + b，同样的两个输入矩阵：F = 1024² ≈ 1.0 MFLOP，只有矩阵乘的约 1/2000；B 同样约 6.3 MB，一个字节都没少。算术强度约 0.17 FLOP/B。时间下界就是搬运项 1.88 µs——计算项约 1 纳秒，完全不重要。

同样的 6.3 MB 数据量，一个把算力吃满，一个把带宽吃满，分界只由算术强度决定，不由数据量决定。分界点在 P/W ≈ 989/3.35 ≈ 295 FLOP/B：强度高于它，时间由算力说了算；低于它，由带宽说了算。

后面通过批处理、分块和融合增加数据复用，正是在改变 F/B 这个比值——融合的本质是让逐元素算子的中间量不必写回设备内存，B 降下去，强度就升上来。它也能预判生成阶段的形态：Decode 每步只算一个新 token，却要读回全部历史 KV——每字节对应的运算量很小，天然落在带宽一侧。

两点边界照旧：这个下界假设真正经过该层存储的数据已算对，也不表示现实中能完美重叠；有效性能不是厂商峰值，实际运行还受形状、调度与同步影响。

## 代码走读：参数在 forward 之前就已占好内存

三类住户里最“安静”的是权重：它们不等到 forward 才出现，而是在模型构造那一刻就分配好了。这件事可以在自己的代码里指认，也可以一路追进 PyTorch 源码——站内的源码阅读任务<a href={asset('code/model-forward/')}>《参数怎样进入前向与梯度？》</a>就是这条路径，本节先走到它的门口。

先看 TinyLM。`labs/tiny_model/model.py` 的 `TinyLM.__init__` 里每写一行模块，存储就当场落位：

```python
self.token_embedding = nn.Embedding(cfg.vocab_size, cfg.width)     # 7×32 = 224 个元素
self.position_embedding = nn.Embedding(cfg.max_context, cfg.width) # 32×32 = 1,024 个元素
self.blocks = nn.ModuleList([Block(cfg) for _ in range(cfg.layers)])
```

`Block.__init__` 同理：`nn.Linear(cfg.width, 3 * cfg.width, bias=False)` 构造完成的瞬间，32×96 = 3,072 个元素的 weight 张量就已存在。`TinyLM(Config())` 执行完，26,688 个参数的存储各就各位（CPU 上在主存）；之后的 `forward` 只是读取这些已存在的张量参与运算，不新建任何参数。权重是“先占好、再反复读”的数据。

再往上追一层（基于 v2.14.0 源码阅读）：`nn.Linear(in, out)` 在构造时按 `[out_features, in_features]` 建好 weight（可选 bias），`Linear.forward` 把输入、weight 和 bias 交给 functional linear——参数在这里成为算子输入。源码阅读任务正是从这个入口往下追到“参数成为算子输入”的边界。TinyLM 的 `qkv`、`out`、`mlp` 用的都是同一个构造规则，所以数账代码对所有层通用。在仓库根目录跑：

```python
import sys; sys.path.insert(0, 'labs/tiny_model')
from model import TinyLM
m = TinyLM()
print(sum(p.numel() for p in m.parameters()))                  # 26688
print(sum(p.numel() * p.element_size() for p in m.parameters()))  # 106752
```

两个打印值正是前面手算的数：参数个数与 fp32 字节数。`numel()` 数元素，`element_size()` 报每元素字节——权重账的三因子，这段代码里就差一个参数个数没乘。

这段代码只数参数数据，不包含梯度、激活、缓存或分配器预留。测 GPU 时还要区分已分配给张量的数据与框架保留以供复用的内存；两者不同不意味着一定泄漏。

账本里另外两类住户是“按需到”的。`.to('cuda')` 把已构造好的参数按 dtype 逐字节搬进显存（TinyLM 的 106,752 字节也要走这条搬运路径，搬完主存那份释放）。梯度张量在第一次 backward 时按参数形状分配。AdamW 的两个统计在第一次 `optimizer.step()` 时才惰性建立——`load_checkpoint` 里 `torch.optim.AdamW(model.parameters(), lr=0.01)` 执行完时，还没有任何优化器状态。

所以训练的显存占用是分三步涨到峰值的：构造时占权重，第一次反向后加梯度，第一次更新后再加优化器状态——正好是上一节那笔 6.72 GiB 训练账的到达顺序。

一个实用检查动作由此而来：记录加载模型前、加载后、前向后、反向后、更新后的内存状态，把每一段增加与数据生命周期对应，而不是看到显存高就只调小批次。

这段到达顺序也回收了梯度一章的结论：优化器状态必须随检查点一起保存、随恢复一起加载。`load_checkpoint` 里 `optimizer.load_state_dict(...)` 恢复的，正是那笔“首次更新后才存在”的状态——漏掉它，后续更新就走样。

## 动手：算一遍自己显卡的账

准备：查出一张卡的显存容量与带宽规格（自己手头的，或任选一张公开规格卡），并把口径统一。以下设定：Qwen3-0.6B 约 6 亿参数、fp16；可用显存按二进制 GiB 记。

1. 把设备的可用显存总量记为 C GiB，同时查出显存带宽规格和 PCIe 代际与宽度。
2. 算推理权重：6×10⁸ × 2 B 等于多少字节？换成 GiB 是多少，占 C 的比例是多少？
3. 算 8 路并发、上下文各 4,096 的 KV 总量（每 token 每请求 112 KiB）。
4. 把权重与 KV 加起来，剩多少 GiB 给激活、临时量与运行库？判断推理放不放得下。
5. 换成训练账：fp16 梯度加两个 fp32 优化器统计，这张卡还训练得动吗？
6. 带宽账：这份权重从主存经 PCIe 5.0 ×16（约 64 GB/s）搬上卡要多久？换成 PCIe 4.0 ×16（约 32 GB/s）呢？
7. 把第 4、5 步的结论各写成一行的容量判断：“这张卡对 0.6B：推理放得下 X 路并发；训练放不下/勉强”。

先全部手算，再展开核对（示例按 C = 8 GiB）：

<details>
<summary>展开核对</summary>

```text
第 2 步：6×10⁸ × 2 B = 1.2×10⁹ B ≈ 1.12 GiB，占 8 GiB 的约 14%
第 3 步：112 KiB × 4096 = 448 MiB/请求；8 路 = 3,584 MiB = 3.5 GiB
第 4 步：1.12 + 3.5 = 4.62 GiB，剩约 3.4 GiB——8 路并发的推理放得下
第 5 步：1.12(权重) + 1.12(梯度) + 2.24×2(AdamW 两份 fp32) = 6.72 GiB，
        只剩约 1.3 GiB；B×T = 4096 的激活光残差流一份就要 224 MiB，
        还有注意力概率与 MLP 中间量——训练非常紧张
第 6 步：1.2 GB ÷ 64 GB/s ≈ 19 ms；÷ 32 GB/s ≈ 38 ms
```

同一张卡“推理轻松、训练放不下”的算术来源就在第 4、5 步的对比里。规格做除法得到的都是下界估计：有效带宽通常低于规格，实际只会更慢。

规格去哪查：Linux 上 `nvidia-smi` 报显存总量与当前 PCIe 链路代际和宽度；带宽峰值在厂商的规格页。本项目的 CPU 环境没有独立显存——统一内存由系统按需分配，这正是练习允许“借一张公开规格的卡纸面完成”的原因：容量算术不依赖手头真有那张卡。

</details>

最后把方法带走：换任何一张卡、任何一个模型，做法不变——先查实际配置（参数量、层数、KV 头数、dtype、上下文上限），再按三类住户分别列乘法，最后与容量和带宽规格相除。把每步的算式和结果记成一张小表，这是后续章节反复使用的“容量算例”格式。数字会换，账本不会。
