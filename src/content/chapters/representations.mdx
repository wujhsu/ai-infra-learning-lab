## 这一章解决什么问题

上一章，我们把“北京是中国的”变成 `[0,1,2,3]`，再用一个没有打开的 `model(context_ids)` 给候选打分。这一章打开它的第一层，回答一个更基本的问题：**模型内部处理的，为什么不是这四个编号本身？**

编号只是词表中的身份。ID 2 与 ID 3 相差 1，没有理由意味着“中国”和“的”只差一点点词义。如果直接把 ID 当数值参与计算，编号怎么安排就会错误地决定意义——就像把数据库自增主键当业务字段去做加减，主键的分配顺序会伪装成业务规律。

所以模型需要另一种表示：每个 token 对应一组可以参与运算的数值，而且这些数值能在训练中调整。本章沿一条固定的路线走：**先查表（ID 变向量），再乘矩阵（向量变新向量），全程用形状跟踪数据，最后数一数字节。** 所有数字都来自项目里的教学数据文件 `src/data/toy-model.json`，标注为教学设定——它们是手工填写的，不是训练结果。

## 机制讲解：从 ID 查到向量

<Term id="vector"/> 是按固定顺序排列的一组数字。`[1,0]` 是一个二维向量：“二维”指有两个分量，不要求你想象几何空间。第一个分量是 1，第二个是 0。

为什么不给每个 token 只配一个数？一个数的表达空间太有限：七个 token、每人一个数，几乎所有“词义组合”都挤在同一条直线上。给每个 token 一组数字，后续计算才能用不同组合去区分和表示输入的特征。真实模型的分量数通常是几千；我们缩到两个，是为了每一步都能手算。

但不要给这两个坐标贴上“城市程度”“国家程度”这类固定标签。真实模型学到的表示通常不能逐项翻译成人话。**数值能支持后续任务，不代表每个数都有一个可直接命名的语义。**

<span id="embedding"></span>
有了向量，就可以给整张词表配数字。下面这张表来自 `toy-model.json` 的 `embeddings` 字段（教学设定，共 7 行、每行 2 个数）：

| ID | token | 向量（ toy-model.json 第 id 行） |
|---|---|---|
| 0 | 北京 | `[1,0]` |
| 1 | 是 | `[0,1]` |
| 2 | 中国 | `[1,1]` |
| 3 | 的 | `[0,2]` |
| 4 | 首都 | `[2,0]` |
| 5 | 。 | `[0,0]` |
| 6 | 结束标记 | `[0,0]` |

整张表叫嵌入表；按 ID 从中查出向量，叫 <Term id="embedding"/>。查表规则说出来很平淡：

```text
输入 ID 2  → 取表中第 2 行 → 得到 [1,1]
输入 ID 0  → 取表中第 0 行 → 得到 [1,0]
```

注意这不是对数字 2 做任何自然语言计算，而是**用编号去选择一张参数表中的一行**。写过后端的人可以这样理解：它就是 `embedding_table[id]`——数组下标访问，O(1)，连哈希都没有。

词表与嵌入表分工不同：<Term id="vocabulary"/> 负责“哪个 token 是哪个编号”，嵌入表负责“这个编号对应怎样的数值表示”。换一套编号体系而不同时改对应关系，就会查错行。

这张嵌入表本身就是上一章所说的 <Term id="parameters" context="这里具体指嵌入表中的数值。真实模型在训练时可以更新这些数；普通推理时根据输入 ID 读取相应行。"/>：收到新请求时不是临时为每个词随机造一组数，而是读这张已经确定的表。

两个细节值得记下。其一，ID 5 与 ID 6 的行完全相同——这意味着这个极小示例无法仅靠初始向量区分“。”和结束标记，这是教学设定的限制，不是嵌入机制的缺陷。其二，查表只依赖 ID 本身：同一个 ID，无论出现在什么上下文里，查出的初始向量都一样。记住这一点，本章结尾和下一章都会用到它。

## 机制讲解：亲手完成一次矩阵乘法

查表只是起点。模型还会用权重矩阵转换这些数字。我们不编新数字，直接取 `toy-model.json` 里的 `wv` 字段——它是下一章 Attention 会用到的 V 投影矩阵（教学设定）：

```text
wv = [ [2, 0],
       [0, 1] ]
```

为了看清规则，先只拿“中国”的一行 `x = [1,1]`。计算 `y = x·wv` 时，**拿 x 与 wv 的每一列配对，逐项相乘再相加**：

```text
y 的第 1 个数 = x 第 1 个数 × wv 第 1 列第 1 行 + x 第 2 个数 × wv 第 1 列第 2 行
             = 1×2 + 1×0 = 2
y 的第 2 个数 = 1×0 + 1×1 = 1
所以 y = [2, 1]
```

每个输出数都是“先乘再加”。这个过程叫 <Term id="matmul"/>。它不是把两个矩阵相同位置的元素逐个相乘——那种运算也存在，但在代码里是另一个操作，结果完全不同。

把输入的四行分别做同样的事（输入 X 就是上一节查出的四行）：

| token | 输入行 x | 输出行 x·wv |
|---|---|---|
| 北京 | `[1,0]` | `[2,0]` |
| 是 | `[0,1]` | `[0,1]` |
| 中国 | `[1,1]` | `[2,1]` |
| 的 | `[0,2]` | `[0,2]` |

这个特定的 wv 恰好把第一个分量乘 2、保留第二个分量。真实权重会更复杂，会混合不同分量，而不只是放大其中一项——先用简单数字学会追踪规则，再扩大规模。

同一份文件里还有 `wq` 与 `wk`。`wq` 是单位矩阵 `[[1,0],[0,1]]`，所以任何向量乘它都不变：“是”的 `[0,1]` 乘 `wq` 仍是 `[0,1]`。下一章 Attention 配图里“是”的 Q 就标注为 `[0,1]`，来源正是这里。真实模型的 wq 不会是单位矩阵；教学设定成单位矩阵，是为了让下一章的每一步也能手算。

用 Python 标准库核对一次四行的结果：

```python
X = [[1, 0], [0, 1], [1, 1], [0, 2]]   # toy-model.json 的 embeddings 前 4 行
W = [[2, 0], [0, 1]]                    # toy-model.json 的 wv

Y = [
    [sum(row[k] * W[k][j] for k in range(2))
     for j in range(2)]
    for row in X
]
print(Y)
# 预期：[[2, 0], [0, 1], [2, 1], [0, 2]]
```

最外层循环逐行处理输入；`j` 选择输出列；`k` 完成“逐项相乘再相加”。如果你写过后端，这些循环都很普通。GPU 的作用之一，是让规模大得多的同类运算高效执行；数学规则不会因为搬到 GPU 上就换一套。

<aside class="concept-note">
<strong>把这个规则概括为公式</strong>


若 `X` 的形状是 `[n,d]`，`W` 的形状是 `[d,m]`，则 `Y=XW` 的形状是 `[n,m]`。

- `n`：位置数，也就是行数。
- `d`：每行的输入分量数，必须与 W 的行数一致。
- `m`：每行的输出分量数，由 W 的列数决定。

$$Y_{ij}=\sum_{k=1}^{d}X_{ik}W_{kj}$$

`i` 选择输入的哪一行，`j` 选择输出的哪一列，`k` 依次经过参与相乘的输入分量。本例 `[4,2]` 乘 `[2,2]` 得 `[4,2]`：每行取两个输入分量，算出两个输出分量，重复四行。这些数值没有物理单位；维度表示元素个数，不是米或秒。


</aside>

## 机制讲解：用形状跟踪每一步

把查出的四行排在一起：

```text
X = [ [1, 0],   ← 位置 0：“北京”
      [0, 1],   ← 位置 1：“是”
      [1, 1],   ← 位置 2：“中国”
      [0, 2] ]  ← 位置 3：“的”
```

4 行、2 列，形状是 `[4,2]`：第一维数位置，第二维数每个位置的分量，总共 `4 × 2 = 8` 个数。**形状描述怎样组织数据，真正存的值是那八个数。** 这种带形状的数字数组叫 <Term id="tensor" context="当前的张量 X 是四行两列：每行对应一个输入位置，每列对应表示中的一个分量。"/>，中文叫张量；向量是一维张量，矩阵是二维张量。你不需要先学张量代数才能读懂这里的代码。

如果同时处理两条长度为 4 的输入，就多出一个维度，写成 `[2,4,2]`：两条序列、每条四个位置、每个位置两个分量，共 `2 × 4 × 2 = 16` 个数。后面看到三维、四维数组，先问每一维在数什么。

形状可以当断点用：在每个阶段打出形状，就能知道数据有没有走错。先跟踪本章的教学模型（矩阵均为 `[2,2]`）：

| 阶段 | 数据来源 | 形状 |
|---|---|---|
| 输入 ID | 分词结果 | `[4]` |
| 查嵌入表 | `embeddings[id]` 逐行取出 | `[4,2]` |
| Q 投影 | 每行 × `wq` | `[4,2]` |
| K 投影 | 每行 × `wk` | `[4,2]` |
| V 投影 | 每行 × `wv` | `[4,2]` |

投影不改变形状，只改变数值——`[2,2]` 的方阵进多少分量就出多少分量。再跟踪一遍真实代码 `labs/tiny_model/model.py` 的 `forward`（配置：`width=32`、`heads=2`、`vocab_size=7`，输入 1 条序列、4 个位置）：

| 代码位置 | 发生什么 | 形状 |
|---|---|---|
| `ids` 进函数 | 一条序列、4 个位置 | `[1,4]` |
| `token_embedding(ids)` | 查表，每位置 32 个分量 | `[1,4,32]` |
| `+ position_embedding(positions)` | 逐位置加位置向量 | `[1,4,32]` |
| `qkv` 线性层 | 一次算出 Q/K/V 拼接 | `[1,4,96]` |
| `chunk(3)` 后拆头 | 三份各 `[1,4,32]` → `[1,2,4,16]` | 3 × `[1,2,4,16]` |
| `q @ k.transpose(-2,-1)` | 位置两两算分 | `[1,2,4,4]` |
| 权重 `@ v` 后并回 | 混合各位置信息 | `[1,4,32]` |
| `head` 线性层 | 投到 7 个候选的得分 | `[1,4,7]` |

现在不必看懂每一行——只要接受一件事：**从 `[1,4]` 到 `[1,4,7]`，每一步的形状变化都对应一次明确的数组操作**。`96 = 3 × 32` 是 Q/K/V 拼在一起；`16 = 32 ÷ 2` 是把宽度拆给两个注意力头；这些乘除法你在本章已经全部手算过一遍，只是数字更大。

<aside class="concept-note">
<strong>关键区别：为什么不能把 [4,2] 随便改成 [2,4]？</strong>


两者都是八个数，但含义不同。我们约定一行对应一个位置；改成两行四列，就成了两个位置、每个四个分量。某些代码允许重新排列形状，但语义是否仍正确，要由算法决定。元素数量相等，不保证可以互换使用。


</aside>

## 机制讲解：dtype 与数值范围

形状告诉你有多少个数，<Term id="dtype"/> 告诉你每个数用几个字节、能表示哪些值。两者相乘才是真实的字节数：`X` 的 8 个数按 fp32（4 字节）存是 `8 × 4 = 32` 字节；按 fp16 或 bf16（2 字节）存是 16 字节。字节数直接决定显存占用和数据搬运时间。

三种常见格式的一段式记法（符号位 + 指数位 + 尾数位）：

| 格式 | 位分配 | 字节 | 数值范围 | 特点 |
|---|---|---|---|---|
| FP32 | 1 + 8 + 23 | 4 | 约 ±3.4×10³⁸ | 范围大、精度高、最贵 |
| FP16 | 1 + 5 + 10 | 2 | 约 ±65504 | 省一半，但范围小 |
| BF16 | 1 + 8 + 7 | 2 | 约 ±3.4×10³⁸ | FP32 的范围，FP16 的字节 |

那为什么不是“精度越高越好”？因为代价与风险都不在精度这一侧：

- **容量与带宽翻倍。** 权重、激活、KV 缓存的字节数全部随 dtype 翻倍。上面 `X` 从 16 字节变 32 字节只是教学数字；把同样的比例应用到整张卡的显存预算，就是“能放下 7B 还是 14B”的差别。
- **FP16 会溢出。** 上限约 65504，训练中大梯度或大激活一旦超过它，数值变成 `inf`，后续计算全部失效。BF16 的做法是保留 FP32 的 8 位指数（范围不变），砍尾数（精度降低）——用“数得没那么细”换“数得没那么宽的区间不会炸”。
- **很多计算并不需要那么多位。** 语言模型推理对小幅数值误差不敏感，主流推理引擎因此默认跑 BF16 或 FP16；再往下省字节还有一套系统方法，称为 <Term id="quantization"/>，后面有专门一章。

注意表格里的教训：FP16 与 BF16 同为 2 字节，范围却差了三十多个数量级。**相同字节数不代表相同数值范围或精度**，比较 dtype 时必须同时看这两项。

用 TinyLM 的真实参数量感受一下：`token_embedding` 有 `7 × 32 = 224` 个数，fp32 存是 `224 × 4 = 896` 字节，bf16 存是 448 字节。数字很小，但乘法结构与大模型完全一致。

## 机制讲解：为什么一层不够

回头看矩阵乘法那一节：它对每行独立执行。把前面的“北京”换成别的 token，“的”这一行仍是 `[0,2]`，乘 `wv` 后仍是 `[0,2]`。**只做这种逐行转换，当前位置就没有从其他位置获得任何信息。**

语言理解显然需要上下文：同一个词出现在不同句子里，所指对象或作用可能不同。需要一种操作把前面位置的信息带到当前位置——下一章的 Attention 就负责这种跨位置的信息汇总。

在常见的 Transformer 语言模型中，一层也不等于只乘一次矩阵。可以把一层理解为一段有固定结构的数值处理流程：一部分用 Attention 汇总其他位置的信息，另一部分对各位置的表示继续加工。这样的层反复堆叠，后一层读取前一层的结果；`model.py` 里 `layers=2`，真实模型通常是几十层。

逐位置加工的部分常叫前馈网络或 MLP，包含矩阵运算和非线性操作——“非线性”意味着整个过程不能压成一次固定矩阵乘法。层中还常见残差连接（把进入某段计算前的表示加回输出，给已有信息留一条直接路径）与归一化（按规定方式调整数值尺度）。本章的小矩阵没有模拟一个完整的真实层。

```text
输入 ID
  ↓ 查嵌入表，并按模型设计处理位置信息
初始数值表示
  ↓ 多层处理：跨位置汇总 + 逐位置加工
结合上下文的数值表示
  ↓ 输出投影：转换为词表中各候选的得分
最后位置的候选得分
  ↓ 使用上一章的选择规则
下一个 token ID
```

输入经过计算而产生的数值叫 <Term id="hidden-state"/>，也常称激活。它与参数的分工要分清：参数是运算读取的配置，中间表示是本次输入通过运算后产生的数据。`X·wv` 里，`wv` 是参数，结果 `Y` 是这次计算产生的表示——换一段输入，`Y` 变，`wv` 不变。

从输入沿着这些步骤算到输出，叫一次 <Term id="forward"/>。基本生成循环会反复调用前向计算；后面加入缓存后，每轮送入模型的数值范围会变，但“先计算表示，再决定下一个 token”的依赖还在。

<span id="training"></span>
## 训练改变权重，推理使用权重

<Term id="training"/> 时，模型把自己的输出与训练目标比较，再按学习算法调整参数。真实嵌入表和投影矩阵里的数值，就是这样逐步得到的。本章的数值直接手工填写——`toy-model.json` 文件自己就标着“同一份手工构造的教学数据；不是训练后的语言模型”——所以不应期待它们已经“知道北京是首都”。

推理时，一般只读取训练完成的参数，根据当前输入计算结果。对话变长会改变输入和中间表示，却不会让模型参数自动吸收这段对话。以后讨论“Agent 记忆”时，必须分清写入上下文、保存外部记录与更新模型参数这三种行为。

回到后端视角做一个有限对照：模型权重像服务加载的一份固定数值配置，输入 ID 像这次请求的输入，中间表示像处理过程中产生的临时数据。这个比喻有助于区分生命周期，但并不意味着模型是规则配置系统。

## 代码走读：embedding 在 TinyLM 里是哪几行

`labs/tiny_model/model.py` 里的 TinyLM 是本项目能真实运行的最小语言模型。它初始化与使用嵌入表的全部代码，节选如下（省略号为本章省去的行）：

```python
class TinyLM(nn.Module):
    def __init__(self, cfg=Config()):
        super().__init__()
        ...
        self.token_embedding = nn.Embedding(cfg.vocab_size, cfg.width)
        self.position_embedding = nn.Embedding(cfg.max_context, cfg.width)
        ...

    def forward(self, ids, cache=None):
        ...
        positions = torch.arange(past, past + ids.shape[1], device=ids.device)
        x = self.token_embedding(ids) + self.position_embedding(positions)
        ...
```

逐行对照本章内容：

- `nn.Embedding(cfg.vocab_size, cfg.width)` 就是“造一张 `vocab_size × width` 的表”。默认配置下是 `7 × 32`，所以 **token 嵌入表的参数量 = 7 × 32 = 224 个数**——没有别的魔法，参数量就是表的大小。
- 还有一张位置表：`nn.Embedding(cfg.max_context, cfg.width)`，即 `32 × 32 = 1024` 个数。注意它反而比词嵌入表大：因为 TinyLM 词表只有 7，而真实模型词表通常是十万量级，届时词嵌入表会反过来占绝对大头。做一个纯教学算例（整数自选，不代表任何具体模型）：词表 150,000、维度 4,096，仅词嵌入表就是 `150,000 × 4,096 = 614,400,000` 个数，约 6.1 亿——fp32 下约 2.3 GB，这就是“参数量 = vocab × dim”在真实规模上的分量。
- `forward` 里的 `self.token_embedding(ids)` 就是本章第一节的查表：`ids` 形状 `[1,4]` 进去，出来 `[1,4,32]`。与手算的 `[4] → [4,2]` 是同一件事，只是分量从 2 换成 32。
- 那个 `+` 是位置信息：每个位置的 token 向量加上对应位置的向量。本章的教学小模型省略了这一步，这是简化之一；TinyLM 用一行加法补上了它。

也就是说，你在纸上对 2 维向量做的每一步，在真实代码里都有对应的一行——只是维度变成了 32、768 或 4096，并且交给矩阵库批量执行。

## 动手：纸笔与一行代码

准备：打开 `src/data/toy-model.json`，或直接在仓库根目录跑下面的一行命令。先手算，再用命令核对。

1. **查两行再相加。** 查出 ID 2 与 ID 4 的嵌入向量，逐分量相加。这个“两行相加”正是 TinyLM 里 token 向量加位置向量的操作形式。

   ```bash
   python3 -c "import json; e=json.load(open('src/data/toy-model.json'))['embeddings']; print([a+b for a,b in zip(e[2], e[4])])"
   ```

2. **用 wv 乘“首都”。** 取 ID 4 的向量，乘 `wv`，手算两个输出数。算完记下答案——下一章 KV 缓存配图里“首都”的 V 就用它。

   ```bash
   python3 -c "import json; m=json.load(open('src/data/toy-model.json')); v=m['embeddings'][4]; w=m['wv']; print([sum(v[i]*w[i][j] for i in range(2)) for j in range(2)])"
   ```

3. **改一行，推演影响。** 把“北京”的向量临时改成 `[3,0]`，其他行与 `wv` 不变。四行 `x·wv` 的输出哪些会变？这说明了什么？

4. **数参数。** 若把 TinyLM 的 `width` 从 32 改成 64（其他不变），`token_embedding` 与 `position_embedding` 各有多少个参数？

<details>
<summary>展开参考答案</summary>


**1.** `[1,1] + [2,0] = [3,1]`。逐分量相加，长度不变。

**2.** `[2,0] × wv`：第 1 个数 `2×2 + 0×0 = 4`，第 2 个数 `2×0 + 0×1 = 0`，得 `[4,0]`。这就是缓存章节图中“首都”的 V——数字全部来自同一份 `toy-model.json`。

**3.** 只有第 0 行从 `[2,0]` 变成 `[6,0]`（`3×2 + 0×0 = 6`，`3×0 + 0×1 = 0`）；其他行不变，因为每行独立与 wv 相乘。逐行独立意味着还没有任何上下文信息交换——下一章引入的 Attention 会让前文的变化影响当前行的结果。

**4.** token 表 `7 × 64 = 448`；位置表 `32 × 64 = 2048`。参数量只跟两张表的“行 × 列”有关，与其他配置无关。
