前面三篇分别在单机执行、并行训练与推理服务里算清了主要的取舍账。进入平台篇，第一个问题不是"多快"，而是"还是不是同一个实验"：把启动命令原样交给另一位同事，或隔一周自己重跑，输出与速度都不同——而双方都坚称自己用的是"同一个 Qwen"。这句话缺少的信息，就是本章的全部内容。

"同一个 Qwen"是一根指针的指针：`Qwen/Qwen3-0.6B` 指向仓库默认分支的当前提交，而默认分支随时间前进；`vllm/vllm-openai:v0.29.0` 指向 registry 里同名的 tag，而 tag 可以被重新构建和覆盖。两句话都为真，指向的内容却都变了。<Term id="artifact" />（制品）把运行产物当作可发布、可验证、可追踪版本的对象来管理——本章把前面各章零散出现过的"钉住版本"动作收拢成一张完整的地图：身份有几个层级、一份模型制品由哪些字段组成、它们放在哪层存储上、以及用什么机制保证"写完了"等于"可恢复"。

路线四步：先看每个松动的身份各自怎样咬人；再建立身份层级与制品字段清单，算一笔扩容洪峰的复现下界账，并对照三层存储的语义差异；然后逐行读把身份钉进文件的两个脚本；最后亲手写一张"今天回答变差"的制品排查单。本章数字均为教学算例，机制与算式可复算；制品构建本身未在集群运行。

## 这一章解决什么问题

先承认一条诱人的捷径：只记"容器 tag + 模型名"，其余交给默认值。这条捷径在单机、当天、同一人手里通常走得通；它失效的方式不是报错，而是每个松动的身份在不同时刻各咬一口：

| 松动的身份 | 咬人的具体场景 |
|---|---|
| 只记模型名 | 仓库默认分支前进：同名模型一周后权重、分词器或配置已不同，你毫无感知 |
| 只记镜像 tag | tag 被重推覆盖：扩容的新节点拉到新镜像，与老节点行为不同，而 `docker ps` 里 tag 一模一样 |
| 没记 digest | "我们用的就是那个版本"无法验证：没有任何记录能把运行中的实例与某一份字节对上号 |
| 分词器与权重不同步 | 同样文字换一组 token ID：输入长度、KV 占用、输出风格一起漂，且不报错 |
| 没记驱动与硬件 | 容器内 CUDA 版本看着正常，宿主驱动跑不动这个构建；两批"相同"的机器行为不同 |
| 没记评估口径 | "变差了"三个字无法与上周比较：尺子本身没被钉住 |

这些咬痕落在同一个部位：**复现**。前面各章其实已经各自钉过身份——<a href={asset('read/serving/')}>服务章</a>在测量前先钉 revision 与镜像，<a href={asset('read/checkpoints-finetuning/')}>检查点章</a>用"写临时、后标记"的协议发布版本。本章把这些动作统一起来，回答三个问题：身份分几层，每层的可变性由谁保证？一份能复现的模型制品，字段清单有多长？这些制品放在哪层存储上，每层的语义承诺是什么？

## 机制讲解：身份的层级、制品的字段与存储的形态

### 身份的四级：名字、tag、revision、digest

把"版本"这个词拆开，其实是四种可变性完全不同的东西：

| 层级 | 例子 | 谁能改它 | 早晚拉到同一内容？ |
|---|---|---|---|
| 名字 | `Qwen/Qwen3-0.6B` | 仓库所有者，随时（默认分支前进） | 否——它指向默认分支的当前提交 |
| tag | `vllm-openai:v0.29.0` | 发布者，可重推覆盖 | 否——同名 tag 重新构建后内容即变 |
| revision | `c1899de…47ca`（40 位十六进制） | 没有人——git 提交哈希由内容算出 | 是——钉住仓库某一提交的全部文件 |
| digest | `sha256:…`（镜像清单哈希） | 没有人——由镜像字节算出 | 是——pull by digest 精确到字节 |

前两级是**可变指针**，后两级是**内容寻址**——差别可以用一次两级解引用看清楚。只说模型名时，实际发生的是：

```text
你说 "用 Qwen3-0.6B"   → 解析为默认分支 main 的当前 HEAD
周一: main = c1899de…   → 权重 A + tokenizer A + config A
周四: main 前进          → 同一个名字，解出权重 B + tokenizer B，一字未改
```

tag 会漂移不是理论风险，写一个具体场景：周五夜间，registry 里 `v0.29.0` 因安全修复被重新构建并覆盖推送；周六自动扩容的新节点拉到新 digest，存量节点仍跑旧字节。同一个 Service 背后的两副本，引擎行为已经不同，而 `docker ps` 与启动日志里的 tag 一模一样——不报错、不显眼、行为漂移，这是可变指针最咬人的形态。digest 则把身份交给内容本身：哈希由字节算出，改一个字节就不再是这个 digest，`pull @sha256:…` 永远拿到同一份内容。

表格之外还有第四个内容寻址身份：**源码 commit**。它描述程序，模型 revision 描述模型仓库内容，镜像 digest 描述容器内容——三者各管一层，不可互相替代：知道 revision 推不出程序版本，知道 commit 推不出镜像里装了什么。三者能合并的前提是把源码 `COPY` 进镜像（后面 Dockerfile 走读会看到），此时镜像 digest 一并覆盖程序与环境。

名字与 tag 的存在有其理由：人需要可读的指针做日常选择。正确的分工是**用 tag 选、用 digest 记**——对话与文档里说 v0.29.0，部署与审计记录 digest；需要绝对钉死时直接按 digest 拉取：`docker pull vllm/vllm-openai@sha256:…`，registry 只会返回这一份字节。本库 `serve.sh` 的做法就是 pull tag 之后立刻 `docker image inspect` 把实际 digest 落进 `image-digests.json`。

revision 与 digest 还各有一条不显眼的边界。revision 钉住的是"仓库那个提交的全部文件"——权重、config、tokenizer、特殊 token 表、模板整套取自同一提交，这正是它比"分别去下各个文件"强的地方；但它不校验你下载到本地的字节，传输损坏或磁盘问题仍要靠摘要检查兜底。digest 钉住的是镜像清单，镜像内的用户态库再完整，驱动接口仍要宿主机配合——容器带得走程序，带不走内核驱动。

于是身份清单还要加上第五层：**环境**。GPU 型号、驱动版本、CUDA 用户态与驱动的兼容组合，不属于任何制品，却决定同一份制品能否运行。健康路径是三步：宿主机上检查设备与驱动，容器内跑一个最小张量计算，最后才加载模型——若最小计算都失败，直接调 vLLM 的批次参数只会把问题搅在一起。记录 GPU 型号、驱动、镜像 digest、启动参数与错误日志，故障才可重现。这也解释了后面代码走读里那个刺眼的 `hardware_verified: false`。

### 一份模型制品由什么组成

训练与发布的产出从来不只是"一个权重文件"。按字段清单过一遍，每一项都有丢了之后的专属症状：

| 字段 | 它固定什么 | 丢了或不配套会怎样 |
|---|---|---|
| 权重（safetensors，钉 revision） | 参数本身 | 同名仓库默认分支更新：权重悄悄换了，日志里看不出差别 |
| config.json | 结构、精度、上下文上限 | 结构对不上：加载直接失败（好症状，当场暴露）；只差 max_position_embeddings：长输入行为悄悄变 |
| tokenizer | 文字与 token ID 的映射 | 见下文两副面孔 |
| 特殊 token 表 | im_start 等保留标记的 ID | 模板渲染出的标记查不到或错位：输出夹带未闭合标记，回答"看起来坏了" |
| 聊天模板与推理参数 | 提示怎样拼装（`enable_thinking` 等开关） | 同一权重换模板：质量骤降，而权重与镜像全没变——排查时最容易漏的一项 |
| 评估身份 | 判定好坏的尺子（评测集版本、口径、基线数字） | 尺子换了读数自然变；没有它，一切质量对比都不可证 |

tokenizer 不配套有两副面孔。**词表尺寸与权重不配**：查表越界，启动时直接报错——这是好症状，问题当场暴露。**配套错位但尺寸恰好兼容**：不报错，同样一句话被切成另一组 token ID，prompt token 数漂移、KV 占用变化、边界行为（大小写、数字、空格）全变——所有测量与质量对比悄然失效。前者是崩溃，后者是中毒；排查后者耗时百倍，所以"tokenizer 与权重取同一 revision"必须是机械保证，不能靠人记得。训练侧的清单还要再加两行：数据身份（数据集版本与预处理代码——权重只对配套的数据分布有意义）与恢复身份（优化器状态、随机状态、并行布局，<a href={asset('read/checkpoints-finetuning/')}>检查点章</a>展开过）。

把清单落成一份最小的记录文件（本库服务实验的形态）：

```json
{
  "model": "Qwen/Qwen3-0.6B",
  "revision": "c1899de289a04d12100db370d81485cdf75e47ca",
  "engine": "vllm/vllm-openai:v0.29.0",
  "served_name": "lab-model",
  "max_model_len": 4096,
  "chat_template_kwargs": {"enable_thinking": false},
  "verification": "GPU environment pending"
}
```

七个键各管一行身份：模型与 revision 钉权重；engine 记引擎，tag 便于人读，实际拉取后还要补记 digest；served_name 是对外名字；max_model_len 是口径（输入加输出的总上限）；chat_template_kwargs 钉模板开关；最后一项 `verification` 是诚实位——这份清单还没有在真实 GPU 环境验证过，谁验证谁改。[模型卡](https://huggingface.co/Qwen/Qwen3-0.6B)说明使用入口，下载时让 tokenizer 与模型取同一 revision，正是这张表的机械落实。生产形态在这份清单之外还要挂上评估身份：发布决策引用的是"这组身份加这份评估"，而不是某个文件名。

本库自己的运行记录就是这个习惯的最小实践：`docs/runs/` 下每份 JSON 都记录日期、工具链版本（python 3.12.14、torch 2.14.0）、command、结果，再加一句 scope/limitation——例如 DDP 的 CPU 记录写明 `max_parameter_error` 约 1.49e-08，同时声明"不是 GPU 性能结果"。诚实的边界声明与身份本身同属制品：没有它，数字会被引用到不成立的场合。

### 复现的下界：一次扩容洪峰的账

制品放在哪里不只是"存得下"的问题，先算一笔能复现的账。权重在启动时是一次性大对象顺序读：设扩容把副本数从 1 加到 8，每个副本各拉 4 GiB 权重，源端（registry 或模型缓存）有效总吞吐只有 1 GiB/s。传输总量的下界：

```text
总量 = 8 × 4 GiB = 32 GiB
下界 = 32 GiB ÷ 1 GiB/s = 32 s
```

数字刻意配整，方便复算。单副本独享链路只要 4 s——**不能把单副本的 4 秒当成全组的就绪时间**。下界抬不动的部分才是调度能动的：同样 32 s，可以铺成两条时间线（教学算例，设加载加初始化另需 L=20 s）：

| 时间线 | 源端占用 | 每副本完成 | 全组就绪 | 首批请求可用 |
|---|---|---|---|---|
| 同时扩容（8 路齐拉） | 1 GiB/s 持续 32 s，打满 | 32 s（每路公平分得 128 MiB/s） | 32+20 = 52 s | 52 s |
| 两波错峰（4+4） | 1 GiB/s 持续 16 s + 16 s | 第一波 16 s，第二波 32 s | 32+20 = 52 s | 16+20 = **36 s** |

读出三条结论：

- **总量下界不随调度改变。** 错峰没有少传一个字节，全组就绪都是 52 s；变的是就绪分布——首批请求提前 16 s 有模型可用，且链路在两波之间有喘息，不必与在线流量对撞整整 32 秒。
- **峰值与故障形态改变。** 同时扩容把 8 份需求叠进同一窗口：源端一次抖动，8 个副本同时失败、同时重试，连重试都是同步的；错峰天然把失败与重试打散。
- **真正能降总量的是缓存，而缓存只认不可变身份。** 第二个副本拉同一 digest 可以从共享缓存就近命中，源端只剩首个 32 s；tag 是可变指针，缓存不敢做主——每次都要回源核对，核对完还可能拿到新内容。钉 digest 不只是审计习惯，它直接买回洪峰里的重复传输。

这笔账是容量估算口径：32 s 只是传输，其上还有校验、加载、初始化，四段对不同副本可以重叠；规划时先按"总量 ÷ 源端吞吐"立下界，再按时间线分配谁等待。

还有一笔容易漏的：**一个新节点要拉的不止权重**。镜像本身动辄数 GiB，设再占 6 GiB，8 个新副本的真实窗口是 8 × (4+6) = 80 GiB，同一源端下界 80 s；而镜像这 6 GiB 恰恰是最能被缓存救回的部分——层缓存按 digest 命中，节点上已有同 digest 的层就完全不重传。可变身份让缓存失效，洪峰就原价重付：身份层级与容量账在这里接上了头。同样的逻辑落在重启策略上：拉取策略配成"总是拉"加可变 tag，每次重启都按新 tag 回源核对、可能整份重付；钉 digest 后第二次拉取只剩校验，传输近零。

### 三层存储：访问形态与一致性语义

下界账里的"源端"在真实系统里是三层存储之一，三层的语义承诺并不相同：

| 存储层 | 访问形态 | 元数据与一致性 | 典型失败 |
|---|---|---|---|
| 对象存储 | HTTP PUT/GET 整对象；吞吐高，适合大对象分发与版本化 | 无目录、无 rename 原语；"改名"是 COPY 加 DELETE 两个独立请求 | 把"发起了 COPY"当"已提交"：目标键没建成，旧版本却已清理 |
| 共享文件系统 | POSIX 挂载，open/read/write 与本地路径无差别 | 元数据服务是集中热点；海量小文件的 stat/open 风暴先打满元数据服务，再表现为延迟尖刺 | 吞吐没满、延迟飙高——瓶颈在元数据不在带宽 |
| 本地 NVMe | 延迟最低、带宽独占、无网络参与 | 数据寿命绑定节点：节点故障或 Pod 重建（emptyDir）即消失 | 检查点只写本地，换一个节点就丢 |

访问形态要和数据对上。训练与推理系统里至少有三类形状不同的数据：

| 数据 | 访问形状 | 最贴合的一层 |
|---|---|---|
| 训练数据 | 海量小文件，按批次随机读，要 shuffle、解压与缓存 | 共享 FS 或预处理打包后的对象存储；小文件直挂对象存储会被请求数放大 |
| 模型权重 | 启动时一次性大对象顺序读，读完驻留显存 | 对象存储加分发缓存；上节的洪峰账就是它的账 |
| 检查点 | 多分片加清单的一致落盘，恢复时按布局重读 | 写提交协议的那一层；本地 NVMe 只配做暂存 |

让一层存储同时服务三种形状，必然有一侧吃亏——这也是上一节容量账要分层算的原因。

其中最容易踩坑的是把本地文件系统的直觉搬上对象存储，写一个具体失败：**rename 语义不等于原子提交**。本地协议依赖一条 POSIX 承诺——同一文件系统内的 `rename(2)` 是原子的：写临时文件、写完改到最终名，读者要么看到旧版本要么看到新版本，永不看到半份。把这套协议原样搬上对象存储：

1. 训练进程把 20 GiB 检查点分片与清单写入临时键，开始"改名"：对每个对象发起 COPY 到最终键，再删临时键；
2. COPY 是逐对象、可失败的两个独立请求，没有事务包裹。第 4 个分片 COPY 到一半，进程被杀（或配额打满）；
3. 此刻最终键下已有 3 个分片，临时键下还剩一半——目录列举"看起来有"一个版本；
4. 读取端只检查"最终键前缀非空"就认定版本已提交，加载了一份截断的权重。

教训不是"对象存储不可靠"，而是**提交协议要按存储系统的原语重新设计**：内容先全部落定为不可变对象，最后写一个小的完整性标记（清单加摘要），读者只认标记——标记不存在，这个版本就不存在。标记里带摘要有双重理由：部分实现对目录列举与跨区读是最终一致的，标记键刚写完的瞬间，别的节点可能还看不到它，读端必须校验内容本身而不是信任"目录里有"；摘要也让"存在"升级为"存在且完整"。这正是检查点章"写临时、全量落定、最后标记"的三步协议；跨到分布式，标记还必须由协调者在全部分片到齐后统一写。共享 FS 与本地盘各有自己的原子性与寿命语义，但原则同一条：把"写完了"从动词的过去式，变成一个有明确定义的协议状态。

## 代码走读：把身份钉进文件的两个闸门

前面是语义；现在看本库怎样把语义压进可执行的检查。两个脚本一前一后：`prepare.py` 定义身份，`render-lws.py` 在生成集群清单时强制校验——身份只在一处出现，其余环节全是引用与闸门。

### prepare.py 逐行：定义与自检

脚本十行，两个实质动作，各写一个文件；docstring 第一句就声明 "Does not launch a GPU"——它可以在任何机器上运行和测试。

```python
# labs/serving/prepare.py
MODEL='Qwen/Qwen3-0.6B'
revision='c1899de289a04d12100db370d81485cdf75e47ca'  # Official model revision checked 2026-09-13
if len(revision)!=40 or any(c not in '0123456789abcdef' for c in revision):raise ValueError('Invalid revision')
```

- 第 4–7 行：三个身份（模型、revision、镜像）以常量写死，revision 行尾注释记录核对日期。不设命令行参数是有意的——身份是实验的前提，不是每次运行可调的选项。
- 第 6 行是一道自检，两个条件合成一句话：**恰好 40 个字符，且每个都是小写十六进制**。40 是 git 提交哈希（SHA-1）的完整长度；短哈希、分支名（`main`）、tag 名（`v2.5`）、大写串，任何一种"看起来像"的手滑都在这里抛 `ValueError`。为什么不接受短哈希？HF 的 ref 参数同时接受分支名与提交号，只有完整 40 位才无歧义地钉住一个提交，不给碰撞和漂移留缝。
- 第 8–9 行写出的两个文件各司其职：

| 文件 | 键 | 谁读它 |
|---|---|---|
| `experiment.env` | `MODEL` / `MODEL_REVISION` / `IMAGE` | `serve.sh` 直接 source，转成 `--revision` 与容器参数 |
| `environment.json` | `model` / `revision` / `image` / `hardware_verified: false` | 人与后续章节：身份记录加运行状态 |

- `hardware_verified: false` 是整份记录里最重要的一个键——**诚实位**。它把"定义了身份"与"验证了兼容"分成两件事，承认前者不蕴含后者；谁在哪台机器上把三步就绪检查跑通，谁才有资格把它改成 true。分两个文件不是重复：`.env` 是 shell 可直接消费的键值对，JSON 多出运行状态字段供后续引用——消费端的完整走读在<a href={asset('read/serving/')}>服务章</a>。
- 最后一行 `print` 写完即提示下一步（`bash labs/serving/serve.sh`）。脚本边界同样清楚：`prepare.py` 管到"身份落档"为止，起不起服务、在哪台机器起，是下一段脚本的事——两个诚实声明（不碰 GPU、硬件未验证）都长在这个边界上。

### render-lws.py：40 位十六进制是一道闸

生成 Kubernetes 清单的脚本把同一套校验又立了一遍，但方向相反——`prepare.py` 防自己写错，这里防**别人随手填**：

```python
# labs/kubernetes/render-lws.py
p.add_argument('--model-revision',required=True)
if not re.fullmatch('[0-9a-f]{40}',a.model_revision):p.error('Use the exact Hugging Face commit from prepare.py')
```

`--model-revision` 是必填参数，且必须精确匹配 40 位小写十六进制。集群清单是出了名的手改重灾区：把 `main`、短哈希或版本号当 revision 填进去，肉眼审查几乎必然放过——正则不放。报错信息也别有用心：不解释怎么拼一个"像样的"值，直接指向 `prepare.py`——**身份只有一个事实来源**，不要在第二个地方发明它。

通过闸门之后，身份以引用的形式流动，全程没有第二处手写版本号：`experiment.env` 里的 revision → render 参数 → Pod 环境变量 `MODEL_REVISION` → 启动命令 `vllm serve … --revision "$MODEL_REVISION"`。生成的清单里每个副本加载的都是同一个提交；"tokenizer 与权重同 revision"因此成为机械结果——按同一提交取全套文件，不靠人记得。脚本 docstring 同样声明硬件执行未验证：闸门管得住字符串，管不住驱动，那仍是诚实位的领地。

### 训练侧的同构做法：Dockerfile 与运行记录

推理侧钉身份，训练侧同构。`labs/kubernetes/training.Dockerfile` 四行实质内容：基镜像 `python:3.12.14-slim` 钉到补丁号（对照 `python:3-slim` 这类浮动 tag 的漂移面）；依赖由 `requirements.txt` 钉精确版本（`torch==2.14.0`、`numpy==2.4.3`）、`--no-cache-dir` 安装；`COPY labs/tiny_model` 把程序本体收进镜像——这一步之后"程序版本"被镜像吸收，镜像身份同时覆盖代码与环境；`CMD` 固定入口与输出路径，输出落在 `/results`，进集群后应是挂载的持久卷，下一章展开。要挑剔的话：基镜像仍是 tag，真正不可变的形态是 digest——本库在 tag 这一级停住是教学取舍，生产发布应再钉一格。三个诚实位连成一线：`prepare.py` 的 docstring、`environment.json` 的 `hardware_verified`、`docs/runs/` 每份记录的 scope 声明——本库的每一份制品都自带"它证明了什么、没证明什么"。

## 动手：给"今天回答变差"写一张制品排查单

场景：周一早上，用户反馈"模型回答变差"，值班同学说"周末什么都没改"。服务在线、健康检查通过、延迟正常。

你的第一个动作不是调任何参数，而是把运行中的实例与基线记录逐项比对——**在证明"没变"之前，一切"变差"先按"有东西变了"处理**。本章的身份层级与记录文件，就是这张排查单的全部素材。

写出这张排查单：

1. 列出你计划核对的 5 个身份：是哪五个，按什么顺序；
2. 每个身份一行：查什么、用什么命令、什么结果判定"变了"；
3. 说明每项比对所用的**基线记录**从哪来——没有基线，比对无从谈起；
4. 最后回答：如果五项全部一致，下一步查什么？
5. 排查单跑通之后，反向用它：新版本上线前，哪几项应该自动核对而不是等人来查？

先自己写，再展开对照。提示：命令只需要 docker、curl、nvidia-smi 和仓库里的记录文件。

<details>
<summary>参考排查单（先自己写，再对照）</summary>

**① 模型 revision（权重身份）。** 查运行实例实际加载的提交：`docker exec <容器> printenv MODEL_REVISION`，与 `labs/serving/environment.json`、启动日志里 vLLM 打印的 revision 行三方比对。判定：三处互不一致，说明有环节绕过了 prepare.py；一致但不等于基线的 `c1899de…47ca`，权重已经换了——"没改任何东西"到此证伪。

**② 镜像 digest（引擎身份）。** tag 相同不代表内容相同：`docker images --digests vllm/vllm-openai`，与 `serve.sh` 落档的 `image-digests.json` 及基线记录比对。判定：tag 同、digest 异，说明 tag 被覆盖重推，引擎行为已变——这是"周末什么都没改"最经典的反例：改发生在 registry 那头。

**③ tokenizer 配套（分词身份）。** 用探针测"同样文字切成几个 token"：发一条固定提示（temperature 0、max_tokens 给小值），读响应里的 `usage.prompt_tokens`，与基线 JSONL 中同一提示的记录比对。判定：同一文字、token 数不同，分词变了——revision 漂移的影子症状；若输出还夹带未闭合的特殊标记（如裸的 `<|im_start|>`），是特殊 token 表错位的直接证据。

**④ 模板与推理参数（口径身份）。** 查请求构造：`chat_template_kwargs`（`enable_thinking`）、system prompt、`max_model_len`、采样参数，与基线测量记录比对——服务实验的每行 JSONL 都带完整请求配置。判定：任何一项与基线不同，则权重没变、尺子没动，但**被测物的输入变了**。权重镜像全对而质量骤降时，最容易漏的就是这一项。

**⑤ 驱动与硬件（环境身份）。** `nvidia-smi --query-gpu=name,driver_version --format=csv`，与首次验证（`hardware_verified` 改 true 那次）留档的记录比对。判定：驱动版本变了，内核选择与数值行为可能全变；GPU 型号变了（比如调度到了另一批节点），连"同一台机器"这个前提都没了。

**基线的来源**贯穿五项：environment.json 与 image-digests.json 是服务侧的身份落档，首次验证时的启动日志与 nvidia-smi 输出是环境基线，测量期的 JSONL 是口径基线——它们都是本章说的"制品"，平时不落档，故障时就无处比对。

**五项全一致时**，查第六项：**评估身份**——"变差"这个判断所用的样本与口径，和上周是不是同一把尺子（评测集版本、指标定义、对比基线）。尺子漂了，读数自然变。再往后就不是制品问题而是变更与发布问题：灰度期间什么算成功、回滚时旧请求怎么办，在<a href={asset('read/delivery/')}>交付章</a>展开——那里的每一次发布决策，引用的正是本章这种"身份加评估"的关联记录。

**第 5 问（反向用排查单）。** 能机器核对就不要留给人：①②④ 是纯字符串与记录比对，启动时由脚本自动核对（`experiment.env` 与运行实例的三方一致性、digest 与落档一致），不一致直接拒绝起服务——`render-lws.py` 的正则闸门就是同一个思路；③ 的 token 数探针可以并入就绪检查；⑤ 的 nvidia-smi 输出应在首次验证时留档、每次部署比对。人的注意力留给只有人能判断的部分：评估身份与"变差"的语义。

</details>

这张排查单背后，是同一条链路在系统里的流动：训练任务产出制品身份与评估报告，服务加载该身份，每个请求的观测关联当前服务版本，回滚选择之前已验证的制品与配置。"今天回答变差"因此能定位到具体变化，而不是猜测哪台机器上有什么文件。下一章把进程、存储请求与服务入口交给 Kubernetes 表达成可管理的对象；对象系统不会替你验证模型质量，但它给这套身份与生命周期一个清楚的边界。
