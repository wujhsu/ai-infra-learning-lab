上一章的引擎已经能在请求结束后释放 KV。现在来了第二个用户，输入仍然以同一段很长的系统说明开头。重新算这段说明没有改变数学结果，却又花了一次 Prefill 时间。直觉的解法是"把算好的留下来"。但"留下来"立即引出三个问题：留在哪里、留给谁、什么时候必须扔掉。这三个问题的不同答案，就构成了本章的三级缓存。

先限定讨论对象：我们复用的是同一模型对**完全一致的 token 前缀**产生的中间结果。文本看起来相似、语义相同，都不够。模型看到的输入 ID、位置和参与计算的权重必须兼容。

## 这一章解决什么问题

把"缓存"这个词拆开，本章实际上在管理三个不同作用域的对象：

1. **请求级 KV**（上一章的主角）：缓存**当前请求**生成过程中的历史 K/V。拥有者是这个请求本身；请求结束（生成完、被取消或超时）就确定性释放。它回答的问题是"本轮 Decode 不要重算上一轮的历史"。
2. **会话级缓存**：一个 Agent 会话在两轮请求之间有空隙——等工具返回、等用户输入。这段时间里，该会话已算出的 KV 可以留在 GPU，或被换到 CPU 等更大的层，下一轮直接接回。它失效于两个条件：会话结束（END，确定性释放），或容量压力下被逐出（之后靠重算恢复）。
3. **前缀级缓存**：以块为单位、按**前缀身份**跨请求共享。两个毫不相干的会话，只要以同一段系统说明开头，就能共享那段前缀的块。它没有明确的"结束"事件，失效主要来自容量逐出；前缀身份不匹配则根本不会命中。

三级回答的是同一个问题的三个尺度：**谁还会再用这段 K/V，值得为它付出多少容量**。用本章的教学数字（每 token 约 1 MiB 的 KV）把三个尺度各算一笔：

- **请求级**：一个 4,500 token 的请求，KV 约 4.5 GB。它必须完整存在，否则连生成都进行不下去——这是不可妥协的底线容量。
- **前缀级**：4,000 token 的系统说明只存**一份**约 4 GB。100 个并发会话都用它时，前缀缓存把"100 份 × 4 GB"压成"1 份 × 4 GB"——省下的是两个数量级的显存。
- **会话级**：100 个并发 Agent 会话，各自还有几百 token 的私有历史，每会话约 0.5 GB 就是 50 GB——单张 80 GB 的卡放不下模型加这笔账。会话缓存必须决定谁留 GPU、谁换 CPU、谁直接放弃。

这也正是本章开头问题的答案：同一会话保留了全部文本，不必一直保留其 GPU KV——文本是可以存进数据库的业务状态，可以重算；KV 是有容量成本的派生计算状态。是否保留，取决于复用概率、搬运成本和重算成本的比较，而不是"聊天记录还在不在"。

接下来先把三个机制各自的时间账算清楚，再讨论它们怎样组合、各自住在哪里。

## 机制讲解：前缀缓存省的是哪段时间

### 哪些块可以共享

把一个块暂定为 4 个 token。请求 A 是 `[0,1,2,3,4,5]`，请求 B 是 `[0,1,2,3,6]`。它们前四个位置相同，因此在同一权重、同一位置规则和同一执行配置下，前四个位置每层的 K/V 可以共用。A 的后两个位置和 B 的最后一个位置分开存。

如果 B 改成 `[0,1,7,3,6]`，不能因为第四个 ID 又相同，就继续共用第四个位置。这个位置的表示已经通过前面的层利用了第三个位置；它的 K/V 也可能变化。缓存键必须描述完整的前缀依赖，而不只是当前块里有哪些 token。

把这件事做成可检查的机制，就是**块身份链**：每个块的身份由"前一块的身份 + 本块内容"共同决定，像链条一样从第一个块伸到最后一个块。用 `∅` 表示链的起点，上面两个请求的身份链是：

| 块号 | A = `[0,1,2,3] [4,5]` | B = `[0,1,2,3] [6]` | B′ = `[0,1,7,3] [6]` |
| --- | --- | --- | --- |
| 1 | `∅+[0,1,2,3]` | `∅+[0,1,2,3]`，与 A 同 | `∅+[0,1,7,3]`，与 A 不同 |
| 2 | `块1+[4,5]` | `块1+[6]` | `块1′+[6]` |

A 与 B 的第 1 块身份相同，可以共享；第 2 块身份立刻分开。B′ 的第 1 块从第三个 token 起就断了链——后面每一块的 K/V 都只能自己算。**身份链让"能共享到哪里"变成一个可以在写入前判定的比较**，而不是靠文本相似度猜。

### 命中的时间账：一张 TTFT 对比表

命中到底省了什么？用一组教学假设的数字把账摆出来。设：

- 共同前缀 4,000 token（一段系统说明加少量历史），其 KV 体积 4 GB（约每 token 1 MiB 的教学设定）；
- 每个请求的新问题部分 500 token；
- Prefill 计算速率 0.25 ms/token，于是重算整个前缀要 `4000 × 0.25 = 1000 ms`，新问题部分 `500 × 0.25 = 125 ms`；
- 命中时前缀 KV 从 CPU 层加载回 GPU：有效带宽 8 GB/s，另有 20 ms 的查找、排队与元数据开销；
- 排队与首 token 采样等固定开销 80 ms，命中与否都一样。

| 项目 | 未命中（冷请求） | 命中 |
| --- | --- | --- |
| 共同前缀 4,000 token | 重算 1,000 ms | 加载 KV `4/8×1000+20 = 520 ms` |
| 新问题 500 token 的 Prefill | 125 ms | 125 ms |
| 排队、采样等固定开销 | 80 ms | 80 ms |
| **TTFT** | **1,205 ms** | **725 ms** |

命中省下的 480 ms 恰好就是 `重算 1,000 ms − 加载 520 ms`。这正是站内模拟器 `cacheBenefit(4, 8, 1000, 20)` 的结果：`loadMs = 520`，`savingMs = 480`。上面这张表里的每个数，都可以在下面的模拟器里直接验证。

### 命中不省什么

命中 4,000 个前缀 token，不代表服务可以直接返回答案。新问题仍要计算；新生成位置仍要计算 Q/K/V、读取历史 K/V、执行其他层并采样。注意表里"新问题 125 ms"那一行命中与未命中完全相同——Prefix Cache 主要减少重复 Prefill，**不会消除长历史对 Decode 的读取成本**。每生成一个 token，注意力都要读全部可见历史的 K/V：前缀 4,000 token 加本轮新增，意味着 Decode 每一步的注意力要扫过四千多行历史——历史越长，单步越慢，这与是否命中无关。上一章时间账里"Decode 单步读取成本随可见历史增长"的那一项，前缀缓存一格都省不掉；它只把这笔账推迟到生成阶段，而不取消。

还有一张账容易被忽略：**未命中的代价不是零，是全价**。开了前缀缓存后，引擎要维护块身份表、做引用计数、在逐出时更新元数据——这些是每个请求都要付的小额固定税。命中率高的流量里它微不足道；如果共同前缀只占输入的 10%，命中省下的可能还不够付这笔税。缓存策略的收益上限由流量分布决定，机制只决定你能拿到上限的几成。

还要区分"存在缓存"与"能立即使用"。块可能已经被其他活动请求引用；也可能在 GPU 池里可直接寻址；也可能被移到 CPU 内存或远端。调度器必须把缓存可用性、计算预算和本轮 KV 容量一起考虑。

## 机制讲解：命中也可能更慢

上面那张表成立的前提，是"加载 520 ms 比重算 1,000 ms 便宜"。这个前提会失效。把同一份 4 GB 的前缀 KV 放到一个有效带宽只有 1 GB/s 的慢层上：

`cacheBenefit(4, 1, 1000, 20)`：`loadMs = 4/1×1000+20 = 4020 ms`，`savingMs = 1000−4020 = −3020 ms`，`worthwhile = false`。

命中了，却比重新算多花 3,020 ms。判据就是模拟器里那一个比较：**值得用缓存，当且仅当 `loadMs < recomputeMs`**，即

```text
sizeGB / bandwidth × 1000 + overheadMs  <  recomputeMs
```

注意两件事。第一，判据是严格小于：`cacheBenefit(4, 4, 1020, 20)` 给出 `loadMs = 1020`，恰好等于重算的 1,020 ms，`worthwhile` 仍是 `false`——打平不算划算，加载路径还占着本来能服务别人的带宽。第二，这些数值是教学设定：实际有效带宽必须从端到端路径测量，CPU 分配、PCIe、网络、存储和 GPU 等待都可能参与其中，压缩还会增加编解码成本。

判据里唯一能被基础设施改动拉动的量是带宽。把 4 GB 前缀、重算 1,000 ms、开销 20 ms 固定，扫一遍有效带宽：

| 有效带宽 | `loadMs` | 相对重算 1,000 ms | `worthwhile` |
| --- | --- | --- | --- |
| 1 GB/s | 4,020 ms | 多花 3,020 ms | 否 |
| 2 GB/s | 2,020 ms | 多花 1,020 ms | 否 |
| 4 GB/s | 1,020 ms | 多花 20 ms | 否 |
| 8 GB/s | 520 ms | 节省 480 ms | 是 |
| 16 GB/s | 270 ms | 节省 730 ms | 是 |

盈亏平衡点在 `4 GB × 1000 / (1000 − 20) ≈ 4.08 GB/s`——本组数字下，加载层必须提供约 4 GB/s 以上的有效带宽，命中才开始赚钱。**"要不要分层缓存"因此不是策略问题，而是这台机器的带宽测量题**；同一份代码，换一条 PCIe、换一个远端存储，结论可以翻转。

把模拟器里的带宽滑块从 8 拖到 1，看"相对重算节省"翻成"相对重算多花"，就是在重演上面的算例。两个值得带着的问题去拖：固定重算 1,000 ms，带宽从多少开始结论翻转？再把 KV 体积翻倍，翻转点移动的方向和你预期的一致吗？——体积越大，搬运的账越重，盈亏平衡带宽越高。

还有一个延迟之外的角度：即使加载在时间上不划算，命中仍然省下了 GPU 的计算占用——1,000 ms 的重算占的是 GPU，4,020 ms 的加载占的主要是搬运路径。在算力饱和而带宽空闲的机器上，"省时间"和"省算力"会给出相反的结论。选哪个目标，取决于瓶颈在哪。

## 机制讲解：会话缓存与 END 释放

一个 Agent 可能先读取说明，生成工具调用，等待工具数秒，再把工具结果接回上下文。等待期间 GPU 并不计算这个请求，但如果所有会话都长时间保留 KV，显存会被不活跃的上下文占据。会话缓存的核心问题就是：**两轮之间的 KV 由谁保、保到什么时候**。

站内模拟器把这件事写成了一条策略。访问序列为

```text
root → middle → tail → other → root → middle → tail → END → other
```

其中 root/middle/tail 是同一个会话的三个块，END 表示该会话结束。`cachePolicy(step, 'session')` 的行为是：走到 END 时，把缓存里属于这个会话的块（root/middle/tail）**全部移出**，END 本身既不算命中也不算未命中。这是"会话结束是确定性释放"的直接实现——释放的时机由生命周期事件决定，而不是等容量满了碰巧逐出。

用序列走到第 7 步（END 刚处理完）验证：`cachePolicy(7, 'session')` 返回 `cache = []`、命中 2 次；而 `cachePolicy(7, 'prefix')`（不响应 END）此时缓存里仍留着 root/middle/tail 三块。同样走到第 7 步，两种策略历史命中数相同，差别全在 END 之后：会话策略把 3 块容量还了回去。

把 session 策略逐步走一遍（容量 3；满时先逐出 tail，与 prefix 策略相同）：

| 步 | 访问 | 结果 | 缓存（右端最新） |
| --- | --- | --- | --- |
| 0 | root | 未命中 | `[root]` |
| 1 | middle | 未命中 | `[root, middle]` |
| 2 | tail | 未命中 | `[root, middle, tail]` |
| 3 | other | 未命中，满；逐出 tail | `[root, middle, other]` |
| 4 | root | 命中，移到最新端 | `[middle, other, root]` |
| 5 | middle | 命中，移到最新端 | `[other, root, middle]` |
| 6 | tail | 未命中，满；tail 不在缓存，逐出最旧 | `[root, middle, tail]` |
| 7 | END | 释放本会话三块，不计命中/未命中 | `[]` |
| 8 | other | 未命中 | `[other]` |

这张表把"会话缓存"的两半拼完整了：第 0–6 步它就是一台带前缀优先逐出的普通缓存，靠命中率吃饭；第 7 步生命周期事件接管，确定性清空；第 8 步之后从零开始。对照模拟器里把策略切到"前缀优先＋会话结束释放"、拖动访问序列位置，可以逐行核对这张表。

但释放是有代价的赌注。再走一步到第 8 步（访问 other）：`cachePolicy(8, 'session')` 的缓存是 `['other']`，只占 1 块；`cachePolicy(8, 'prefix')` 是 `['root', 'middle', 'other']`，仍占 3 块。如果序列在 END 之后不是 other 而是回到 root，会话策略将未命中、必须重算，前缀策略则直接命中。**END 释放赌的是"这个会话不会再回来"；赌赢了换来容量，赌输了付出重算。** Agent 场景里工具循环频繁回来，会话保活得长；一次性问答则结束即放。

由此，会话状态要分清三类：业务对话记录、可重建的模型 KV、正在运行的请求。业务记录可以长久保存在引擎外；KV 可以被淘汰后重算；活动请求需要超时和取消处理。不要把"保留聊天历史"实现成"永不释放 GPU 块"。

## 机制讲解：LRU 的账——容量、工作集与命中率

前缀缓存和会话缓存都没有天然的容量上限承诺：块太多时必须有逐出规则。站内模拟器实现了容量为 3 的缓存，对比两种逐出策略：**LRU**（淘汰最久未访问的块）与**前缀优先**（满时优先淘汰 tail 这类会话增长端的块，它们最不像会被别人共享的前缀）。同一序列、同一容量，命中率可以差出一截。

**第 6 步：工作集大于容量时，LRU 全空手。** 先把**工作集**定义清楚：一段时间窗口内会被再次访问的不同块的集合。它不是"总共有多少数据"，而是"重访模式实际覆盖多少块"。前缀缓存的特殊之处在于共享：4 个会话都用同一段系统说明时，那段块在工作集里只算一份——这正是前缀缓存值得做的根本原因，它把工作集从"每会话全量"压缩到"共享前缀一份 + 各会话私有尾部"。回到序列：前 7 个访问（不含 END）涉及 4 个不同的块 root、middle、tail、other，而容量只有 3。`cachePolicy(6, 'lru')` 的结果是命中 0 次、未命中 7 次。原因值得逐个看：other 进来时容量已满，LRU 逐出最早的 root；轮到 root 回来（第 5 个访问）时它刚被挤出去，未命中，挤掉 middle；middle 回来又挤掉 tail……每个块轮到重访时都恰好不在缓存里。这是经典的**抖动**：循环访问的工作集只要比容量多一个块，命中率就能从满格掉到零。**命中率不是"缓存大小"的平滑函数，而是容量相对工作集的台阶函数。**

同样到第 6 步，`cachePolicy(6, 'prefix')` 命中 2 次、未命中 5 次（session 策略此时与 prefix 相同，END 还没到）。差别只在满时的那一次选择：other 进来时，前缀优先逐出的是 tail 而不是 root，于是 root 和 middle 活到了各自的重访，第 5、6 个访问各命中一次。**逐出策略的本质，是对"谁更可能被重访"下注**；知道块的身份（哪些是共享前缀、哪些是会话私有尾部）就能下得更准。

**第 7、8 步的完整对照**（命中/未命中/结束时的缓存）：

| 策略 | 第 6 步 | 第 7 步（END） | 第 8 步（other） |
| --- | --- | --- | --- |
| lru | 0 命中 / 7 未命中，缓存 3 块 | 不响应 END：0 / 7，缓存 3 块 | 0 / 8，缓存 `[middle, tail, other]` |
| prefix | 2 / 5，缓存 3 块 | 不响应 END：2 / 5，缓存 3 块 | 2 / 6，缓存 `[root, middle, other]` |
| session | 2 / 5，缓存 3 块 | END 释放：2 / 5，缓存 `[]` | 2 / 6，缓存 `[other]` |

三行读法：lru 输在工作集超容量；prefix 赢在逐出押对了块；session 用第 7 步的一次释放，换到第 8 步时只占 1 块的容量。没有一行在所有维度上最优——这正是缓存的常态。

还有一层容量之外的账：上面所有策略的比较都在 3 块容量下进行。把容量加到 4——刚好盖住工作集——三种策略的命中率差距会立即抹平。**逐出策略的价值，恰恰只在工作集放不下的那段区间存在**；容量充足时策略无关紧要，容量越紧策略越值钱。这也是为什么容量规划失败的服务，最后总是先在缓存策略上吵起来。

工具返回顺序、消息模板、隐藏的系统提示和 tokenizer 版本，也会改变实际 token 前缀。先记录规范化后的 ID 与长度，再解释命中率。跨租户共享还要考虑信息暴露和计时侧信道；本课程的默认工程实验只在同一可信租户内比较，避免让缓存身份变成隐式共享接口。

## 策略组合：一张失效条件对照表

三种缓存不是三个独立系统，而是同一批 GPU 块上的三层所有权。一个会话缓存的块，同时也可以是前缀缓存里的共享块；区别只在**谁有权释放它、什么事件触发释放**。把失效条件排成一张表：

| 事件 | 请求级 KV | 会话缓存 | 前缀缓存 |
| --- | --- | --- | --- |
| 新请求到达 | 新建一份，随生成增长 | 属同一会话则接上；否则无关 | 可能命中其共同前缀 |
| 请求结束 | 确定性释放 | 保留，等下一轮 | 保留（引用计数归零后才可逐出） |
| 会话结束（END） | 已随最后一次请求释放 | 确定性释放（session 策略） | 不释放，别的会话仍可复用 |
| 容量逐出 | 活动请求不可丢，只能换出或抢占后重算 | 可被逐出，之后重算 | 可被逐出（LRU 或前缀优先） |
| 前缀身份改变 | 新请求本来就是新的 | 旧块不命中，需重算 | 不命中——这是"没匹配上"，不是"失效" |

最后一行值得强调：换掉前缀中间一个 token、切换 LoRA、更换 tokenizer，效果是缓存**不命中**，缓存里的数据并没有"坏掉"。真正的失效只有两类：生命周期事件（请求结束、会话结束）和容量逐出。

把这张表落到一个块的生命周期上更好读。一个承载系统说明前 4,000 token 的块，可能经历这样的旅程：

1. **出生**：第一个请求 Prefill 时算出，拥有者是该请求（请求级 KV），同时以身份链登记进前缀缓存，供后来的请求查。
2. **被共享**：第二个请求命中它，引用计数加一——此刻它同时是请求 2 的输入历史和前缀缓存的一个条目。
3. **渡口**：两个请求都结束了。会话还在（Agent 在等工具），会话缓存让它留在原处或换到 CPU 层；换出后如果某轮命中要搬回 GPU，先过一遍上一节的加载账。
4. **两种死法**：会话 END 到来，它被确定性释放；或者容量压力下被逐出（LRU 或前缀优先挑中它）。死后不留墓碑——下次需要时重算一遍，数值逐位相同。

整个旅程里块的内容一个字节都没变过，变的只是所有权和住址。**缓存管理的全部复杂度，都在所有权和住址的簿记上。**

再看位置。请求级 KV、会话缓存、前缀缓存和 CPU 换出层，都住在**推理引擎内部**，由块管理器统一分配和释放——失效条件才能落到代码上。会话的业务对话记录、完整回答缓存、检索结果的 embedding 缓存，住在**引擎外**，属于业务状态或业务缓存。两者容易混淆的地方是"会话"这个词：

<aside class="concept-note">
<strong>关键区别：为什么不是直接缓存完整回答？</strong>

完整回答缓存绕过模型执行，适用于允许返回同一结果的业务；KV 缓存保存的是计算中间状态，后面仍然可以输入不同问题或进行不同采样。二者的失效规则、安全边界和命中条件不同。不能用"都是缓存"推导出同一种产品行为。

</aside>

组合策略有没有用，最终要靠对照实验说话：构造两组相同请求分布，一组禁用前缀缓存、一组启用；固定模型、输入长度、输出上限和到达模式；分别测冷启动、预热后和容量压力下的结果；至少记录 TTFT、输出 token 间隔、吞吐、命中 token 数、被逐出与重算数量。如果只反复发送一个完全相同的提示词，你证明的是极端场景能命中，尚未证明生产会话能受益——把共同前缀占比从 80% 降到 10%，或在前缀中间插入一个 token，观察命中边界怎样移动，才是对策略的真正检验。

选哪种组合，则取决于流量形状。短问答服务轮次少、系统说明统一：前缀缓存拿满收益，会话缓存基本用不上，容量优先留给活动请求。Agent 平台轮次多、轮间等待长：会话缓存是主角，配上 CPU 换出层和上一节的加载账。多租户平台共同前缀少、隔离要求高：宁可命中率低也不要跨租户共享块，前缀缓存按租户分池。三种流量，同一套机制，不同的所有权配置——这也是为什么缓存问题最终是策略问题，而不只是数据结构问题。

## 动手：把命中率折进平均 TTFT，再判一个"命中更慢"的场景

缓存的收益从来不落在单次请求上，而是落在**流量分布 × 单次差值**的乘积上。这道题把本章的两笔账——前缀缓存的时间账和加载对重算的判据——串成一次完整的决策：先算单次，再折平均，最后换条件重判。全程只需要加减乘除，但每一步的数字都要有出处。

沿用本章的数字：共同前缀 4,000 token（KV 4 GB），新问题 500 token，Prefill 0.25 ms/token，命中加载带宽 8 GB/s 加 20 ms 开销，固定开销 80 ms。已知线上流量中 60% 的请求能命中前缀。

1. 先写出单次命中与单次未命中的 TTFT（直接复用对比表的两行账，写出各段的加法）。
2. 用命中率把两个数折成**开缓存后的平均 TTFT**，并与完全不开缓存（1,205 ms）比较，写出平均省了多少毫秒；再解释为什么这个节省恰好等于"命中率 × 单次节省"。
3. 现在换一个存储层：同样的 4 GB 前缀 KV，有效带宽只有 1 GB/s，其余条件不变。先判断单次命中还值不值得（写出判据两边的数），再算这种情形下的平均 TTFT，最后回答：这个场景该不该开缓存？如果答案是否定的，指出至少一个可能让它重新变得划算的改动。

<details>
<summary>展开核对：三问的数字</summary>


第 1 问：命中 TTFT = `520 + 125 + 80 = 725 ms`；未命中 TTFT = `1000 + 125 + 80 = 1,205 ms`。两处差别只在共同前缀那段：加载 520 ms 对重算 1,000 ms。

第 2 问：平均 TTFT = `0.6 × 725 + 0.4 × 1205 = 435 + 482 = 917 ms`。相比不开缓存的 1,205 ms，平均省 `1205 − 917 = 288 ms`——正好是 `0.6 × 480`：只有命中的那部分请求拿到 480 ms 的节省，未命中的请求原样承担冷路径。

第 3 问：判据两边：`loadMs = 4/1×1000+20 = 4020 ms`，重算 `1000 ms`；`4020 < 1000` 不成立（即 `cacheBenefit(4, 1, 1000, 20)` 的 `worthwhile = false`），单次命中反而多花 3,020 ms。平均 TTFT = `0.6 × (4020+125+80) + 0.4 × 1205 = 0.6 × 4225 + 482 = 2535 + 482 = 3017 ms`——比不开的 1,205 ms 还差 1.8 倍。**不该开。** 可能翻盘的改动：把前缀 KV 挪到更快的层（提高有效带宽，让加载回到重算以下）；缩小需要搬运的体积（只缓存最常共享的前缀段）；或改判据本身——如果目标是省 GPU 算力而不是延迟，加载虽慢但占用的是搬运路径，结论可能反过来。

自查两处常见错：如果你在第 2 问写"平均省 480 ms"，那是把未命中的 40% 也当成了命中；如果你在第 3 问得出"平均 TTFT = 917 ms 不变"，那是忘了命中路径的加载时间已经换成 4,020 ms——缓存慢了，命中者先受害。

</details>

容量还可以通过降低每个数的存储成本来改善。下一章讨论量化，但必须同时把质量纳入验收。
