极小模型反复看一个句子，数据管道几乎没有成本。真实训练会读取大量文件、解码、分词、随机采样、组装批次，再把输入送入设备。数据错误会影响模型学什么，数据等待则直接影响 GPU 能否持续工作。

## 先明确每条样本教模型什么

语言模型预训练常把文本组织成 token 序列，用当前位置预测下一项。监督微调则可能只对回答部分计算损失，让模型学习怎样响应给定输入。两者都执行前向与反向，但哪些位置是目标，必须由任务定义。

数据集中有 `prompt` 与 `answer` 字段，并不意味着训练器自然知道只优化 answer。经过聊天模板与分词后，需要建立与实际 token 对齐的 labels；不参与损失的位置常用库约定的忽略值。对齐错一位、把 padding 当目标、误把用户问题也当答案，都可能让训练“损失下降，但行为不对”。

先打印两条处理后的样本：原始字段、完整 ID、目标 ID、忽略位置和解码后的目标。这个小检查比直接跑一小时训练更容易发现问题。

## 切分数据必须早于会造成泄漏的处理

训练数据参与参数更新，验证数据用于调整方案，最终测试用于独立评估。相同文档切出的相邻片段、近重复内容、同一来源的模板变体，若落在不同集合，可能让评估看起来很好。

因此切分不应只理解为最后对所有短片段随机取 10%。应按任务判断独立单位：文档、用户、时间、来源或其他真实边界。保存切分规则与数据版本，才能复现实验结果。

清洗也需要与目标相容。去重、格式修复和长度过滤会改变分布；如果只保留短样本，后续长上下文性能评估就不再代表训练负载。

## 一个批次是怎样形成的？

<Term id="batch"/> 是本次一起处理的样本集合。长度不同的序列可以补齐到共同长度，padding 位置通过遮罩和目标忽略规则处理；也可以按框架支持方式组织变长或打包输入。

假设三条序列长度为 100、100、1000，一起补到 1000，会处理最多 3000 个位置，而真实内容只有 1200。按长度分组可能减少无效工作。但过度按长度排序会改变随机性，必须在效率与采样分布之间设计。

Sequence packing 把多个短样本放到较长序列里，可以减少填充，却需要检查样本边界、位置与注意力规则。两个独立样本是否允许互相看见，不能因为拼在一个数组里就失去定义。

## 数据加载器负责哪些等待？

可以把管道看成存储读取、CPU 处理、主存排队、设备传输、GPU 计算五段。若 GPU 每批算 50 ms，准备下一批却要 120 ms，GPU 可能在数据到来前空等。

增加 worker 是让更多 CPU 进程或线程准备数据；预取让准备与当前计算并行；固定页内存可以帮助某些主机到 GPU 的异步传输路径。但它们消耗 CPU、主存和存储带宽，不是越多越好。

先测“只读数据不训练”每秒能提供多少样本，再测“已在内存的固定数据训练”速度，最后测端到端。三个结果能把瓶颈拆开。

## 训练中断后，下一批是谁？

只恢复模型参数与 step，数据加载器可能重新从头或产生不同顺序。要精确继续，需要知道采样器、数据游标和随机状态。多 worker 的预取队列又会使“已经读取”与“已经用于更新”不同。

先明确恢复语义：要求数值路径完全重现，还是允许重新采样但保证没有漏掉关键训练流程？两种目标都可能合理，必须在项目记录里说清楚。

单机实验中先固定样本顺序验证恢复，再逐步加入随机采样和并行加载。后面进入多卡时，每个 rank 还要得到正确的数据分片，不能把这层复杂性一次全塞进来。

## 练习：判断是数据慢，还是模型慢

保持模型、批次与序列长度不变，把数据换成提前准备好的张量。如果 GPU 时间差不多但端到端明显加速，说明减少了 GPU 之外的等待；如果仍然慢，就继续检查模型计算与同步。

还要确认“加速”没有偷偷缩短输入、改变标签或减少样本。只有计算目标一致，对照才有意义。
