上一章把 KV 的账算清了：每个位置多少字节、怎样分块、何时释放。服务已经能跑，单个请求的数字也测过了。现在把镜头从一条请求移到一队请求——中午十二点，一百个请求同时到达，系统必须连续回答四个问题：谁先进来？空位补给谁？满员时新请求在哪里等？用户等不及关掉页面之后，正在算的那份工作怎么办？

这四个问题都没有“自然”的答案，只有被策略决定的答案。策略选错的表象很一致：单个请求不慢，用户却都在等。本章把排队、补位与取消放进同一条时间线，让你能指着某个数字说“这一段是等待，不是计算”。

## 这一章解决什么问题

先看三种真实会发生的判断失误，本章逐一给出机制。

第一种，把排队当成计算。压测里单请求 P50 很好，并发一拉高 p95 却急剧变差，第一反应往往是“模型变慢了”。翻开时间线，模型 kernel 的耗时一点没变——多出来的时间都在排队。诊断若不先把队列与执行分开，就会在错误的方向上优化：改 kernel、换精度、加卡，唯独没动排队。

第二种，把吞吐当体验。系统的每秒输出 token 数不低，用户却在抱怨卡：短请求排在长请求后面进不了场，正在流式输出的请求被一次超长 Prefill 按了暂停。GPU 一直忙，不等于任何一个用户被及时服务。

第三种，以为断开就是取消。客户端关掉连接，用户那边已经结束了；服务端若不把取消信号传到引擎，GPU 还在逐个 token 生成无人接收的内容，KV 也迟迟不还给池子。

把这三种失误放进同一句问话，就是本章开头的思考题：单个请求更快了，但高并发下 p95 更差，可能说明什么？答案几乎从来不是“计算变慢了”，而是调度、公平性、资源预算或到达率改变了排队——优化的收益被别的请求多付的等待吃掉了。

三个失误对应本章的四段机制：时间线拆解（哪一段是等待）、补位语义（空位给谁）、排队策略与资源预算（谁能进场）、取消生命周期（怎么干净地离开）。教学算例沿用站内演示的模型：每步只算一个 token，忽略 Prefill 与硬件竞争——这个模型是简化的，但补位的因果关系是真的；真实引擎多出来的检查在每一节末尾单独标注。

读完的检验标准：不看正文，能把 10 步、2 并发的补位时间线逐秒画出来，说清 C 为什么在第 2 步进场、静态批里它要等多久；并且能写出“接纳一个请求等于承诺什么”。

## 机制讲解：一条时间线、一队请求与一次取消

### 首个 token 之前不只有模型计算

客户端发起请求后，依次可能经历网络传输、输入处理、排队、Prefill、输出处理，然后才收到第一个结果。<Term id="ttft" context="本章从客户端发出请求量到首个非空正文，强调必须写明起点与终点的系统边界。"/> 必须先钉死从哪个起点到哪个终点，否则两个人的数字不可比较。

客户端的首个非空正文时间是实用指标，但不一定精确等于引擎的第一个 token：服务可能先产生控制事件、思考内容，或把多个 token 聚合进一个事件再发出。报告要保留这一差别——这是 <Term id="sse"/> 流式接口特有的坑：一个事件可以没有文本，也可以一次携带多个 token。

先用恒定时间模型算一遍。设排队 Q=800 ms，Prefill P=600 ms，其他开销 O=50 ms，后续每 token D=40 ms，总输出 N=32。首 token 时间为 `Q+P+O=1450 ms`，全部完成约为 `1450+(32−1)×40=2690 ms`。N−1 是因为首 token 已包含在前面的阶段里。

模型假设每步耗时恒定，不描述真实服务的抖动、并行与网络细节，但已经能回答一个诊断问题：如果排队增加一秒，模型 kernel 可能完全没有变化，用户还是慢了一秒。性能诊断必须把队列与执行分开——这是 profiling 一章“先分层、再测量”在服务场景的翻版。

拆开的实用之处在于定位“并发一高谁先动”。恒定模型里 P、O、D 都只依赖计算与网络，Q 是唯一随负载自由伸缩的项：并发翻倍、TTFT 涨了 600 ms 而 P 与 D 不变时，多出来的几乎全在排队；若 D 本身变大了，才是执行侧的问题——batch 变大让每步变慢，或者长 Prefill 在挤占 Decode。两种病因的药方完全不同，先用数字分开再动手。

第一个 token 之后，衡量“输出顺不顺”还有三个容易混用的口径：<Term id="tpot"/> 是首 token 之后的平均每 token 时间；<Term id="itl"/> 是相邻输出 token 时间戳之差，分布才能暴露停顿；网络 chunk 的间隔又是另一层，不能冒充 ITL。平均值 40 ms 的流里可以藏着一次 500 ms 的停顿——只有看分布才看得见。三个口径在后面的取消实验与压测走读里都会再次出现，因为流式输出是观察调度行为最直接的窗口。

这页讲义把一条流式请求从网关串到引擎，再用时间窗与设备标签关联 GPU 侧指标。它用来练习读证据的顺序：先定边界，再分区间，最后才解释空隙。跨组件的 Trace 之所以必要，是因为每一段时钟都有自己的口径——客户端记的是“发出到首个非空正文”，网关 span 记的是转发区间，引擎 span 记的是排队加执行；不靠请求标识把同一条请求的各段对齐，就无从知道总时间里每段的份额，剩下的只能靠猜。

也不要用其中一次请求的数字定义所有模型的正常表现——那是观测条件下的一个样本，不是规范。观测本身还会扰动被观测的对象：采样率过高、日志刷得太密，都可能改变调度节奏。把讲义的数字当练习材料，把方法（对齐口径、分开区间、解释空隙）当成可带走的东西。

### 补位发生在迭代边界：逐秒对账

传统整批（静态批）方式凑齐一批后，可能要等这批全部结束才开始下一批。批里一条需要 100 步、另一条只需 10 步时，短请求算完后留下的执行位置长期空着——位置空了，账还按整批算。

连续批处理（continuous batching）在迭代边界更新活跃请求集合：结束的请求当轮退出，资源允许时等待中的请求立刻补位。它不是把所有请求合并成一条上下文——每个请求仍有自己的状态与 KV，共享的只是每一轮的执行。

补位之所以发生在迭代边界，是因为那是唯一安全的同步点：一步 Decode 是“给活跃集合里每条序列各算一个 token”，步与步之间请求集合才允许变化；步中间插入或移除请求，注意力读取与输出对应关系都会乱。这也意味着补位的粒度是一步，不是即时——请求最长可能等满一步才真正进场。

勾选开关（连续批，结束即让位）：

| 步 | 本步执行 | 等待中 | 已完成 |
| --- | --- | --- | --- |
| t0 | A、B | 无 | 无 |
| t1 | A、B | C | B |
| t2 | A、C | 无 | B |
| t3 | A、C | D | B |
| t4 | A、C | D | A、B、C |
| t5 | D | 无 | A、B、C |
| t6 | D | 无 | A、B、C、D |
| t7–t10 | 无 | 无 | 全部完成 |

关闭开关（静态批，整批结束才换人）：

| 步 | 本步执行 | 等待中 | 已完成 |
| --- | --- | --- | --- |
| t0 | A、B | 无 | 无 |
| t1 | A、B | C | B |
| t2 | A | C | B |
| t3 | A | C、D | B |
| t4 | A | C、D | A、B（整批结束） |
| t5 | C、D | 无 | A、B |
| t6 | C、D | 无 | A、B、D |
| t7 | C | 无 | 全部完成 |

三处对照值得逐格看：

- B 的计算过程两种模式完全相同，价值不同。B 都在 t1 算完自己的第 2 个 token；连续批里它的位置 t2 就让给了 C，静态批里这个位置一直空转到 t4——批没有散，空位就没人能进来。
- C 是补位的主角。连续批：t1 到达，只等 1 步，t2 补进 B 的位置，t4 完成。静态批：C 必须等第一批整体结束（A 直到 t4 才算完），t5 才进场，t7 完成——同样 3 步的工作，完成时间晚 3 步，排队时间从 1 步变成 4 步。
- D 是补位救不了的那类等待。两种模式里 D 都在 t5 进场：它 t3 到达时，连续批的两个位置正被 A、C 占着。补位消除的是“有空位却不用”的浪费，不是“位置真的满了”的排队。
- 竖着加总：连续批 t6 干完全部工作，静态批要等到 t7；而两种模式在负载清空后同样空转（t7 或 t8 之后无活可干）。补位改善的是批内的空转，救不了负载本身的间隙——没有请求到达时，再好的调度也无事可调度。

真实引擎在同一个边界做更多检查：本轮 token 预算、序列数上限、KV 块余量，任何一项不满足，请求就继续在队列里等。还有一个演示刻意抹掉的差别：新请求进场的第一步不是 Decode，是 Prefill——把整个输入一次算完，成本与输入长度成正比，远重于“一个 token”。所以真实引擎的补位决策还要回答“这一轮塞得下一个 Prefill 吗”，塞不下就整轮推迟，这正是后面公平性问题的来源之一。

### 两种排队都会制造牺牲者

补位解决“空位给谁”，不解决“队头是谁”。设执行位每 40 ms 出一个 token：一条请求要生成 2000 个 token，约 80 秒；它后面排着两条各只要 50 个 token、约 2 秒的请求。严格的先来先服务（FCFS）下，两条短请求的等待时间里始终压着这 80 秒——2 秒能做完的工作，等了 40 倍的时间。这叫队头阻塞：排队位置由到达顺序决定，与工作长短无关。

反过来，把规则改成“某种请求永远优先”，牺牲者换成另一边。取 1 个执行位、每个请求占 8 步、高优先级请求每 8 步到达一个，另一个低优先级请求在 t2 就排进了队。逐回合对账：

| 时刻 | 事件 | 等待队列 |
| --- | --- | --- |
| t0 | 高 1 号进场，将算到 t8 | 空 |
| t2 | 低优先级请求入队 | 只有它——它是队头 |
| t8 | 高 2 号恰好到达，越过队头被接纳，算到 t16 | 低优先级请求仍在等 |
| t16 | 高 3 号到达，同样插队进场，算到 t24 | 同上 |
| t24 | 高 4 号……模式无限重复 | 等待时间无上界 |

每次空位出现，刚到达的高优先级请求都越过已经在排队的低优先级请求。低优先级请求没有违反任何规则，只是永远轮不到——等待时间随时间无限增长，这就是饥饿。注意此刻高优先级自己的到达率已经把执行位占满（每 8 步到达、每个占 8 步）；现实里的高峰时段就是这个相位的放大版：系统看似满负荷在服务，某类请求的等待在无声地涨。

两个失败对称存在，工程答案是折中而非站队：让优先级随等待时间上升（老化，aging），或按类别留配额、按权重分配名额。同理，“短请求先跳队”也只解决了 FCFS 的队头阻塞、又制造了对长请求的饥饿——任何单一维度的绝对优先都有牺牲者，老化的本质是给“已经付出的等待”也记成一种优先级。

同样的结构问题也出现在长度维度：一个 8000 token 的 Prefill 若一步算完，本轮 token 预算被它吃满，已在流式输出的请求这一步全部停顿，ITL 分布出现长尾。Chunked prefill 把长输入切成若干轮分摊，Decode 不再整步等待——代价是调度边界变多、单请求的 Prefill 拉长。公平是有账要付的，只是付的位置不同。

这也解释了为什么 <Term id="throughput"/> 与延迟经常被同时提出却不是同一目标：吞吐最大化想要大 batch、GPU 永远忙；每请求低延迟想要尽早进场、均匀输出。排队策略必须写明服务的是哪个目标。而当到达率持续超过处理能力时，任何排队策略都救不了，队列只会无限增长——限流、接纳控制与背压是“告诉上游别再发了”的机制，不是服务能力不足时可有可无的装饰。

### 排队位置与 KV 占用是一笔联动的账

现在把上一章的显存账接进来。示例配置下每个位置 128 KiB：一条上限 8192 位置的请求，KV 承诺是 1 GiB；若引擎留 8 GiB 做 KV 池，同时在场最多 8 条这样的请求。于是调度器看 Waiting 队列头部的请求时，要同时回答两个问题：有没有空执行位（排队位置），以及 KV 池接不接得住它继续增长（资源承诺）。“调度”与上一章的“分配”不能分开想：接纳一个请求，就是当场承诺它的 KV 上限，不管它最后实际用多少。

承诺的粒度本身是个策略选择。一次承诺到上限最保守——短请求也按 1 GiB 扣账，为 2 秒的工作占住一个名额，进场名额被浪费。按块逐次承诺更激进——请求边长边要块，池满了才处理。但推迟承诺并没有把账消掉，只是把风险改了形状：池满时引擎要么让 Running 的请求中途停下（抢占：回收它的块，之后重算或换出），要么让所有人一起变慢。抢占救的是“不崩”，代价是被抢请求的延迟翻倍——尾延迟的剧烈抖动常常来自这里。

把两个账合起来看一次接纳决策。KV 池 8 GiB，已在 Running 的四条请求各自承诺到上限后共占 5.5 GiB，剩余 2.5 GiB。此刻队头依次排着三条等待请求：

| 等待请求 | 输入＋输出上限 | 所需承诺 | 能否接纳 |
| --- | --- | --- | --- |
| E | 2,000 位置 | 约 250 MiB | 能，还剩约 2.25 GiB |
| F | 4,000 位置 | 约 500 MiB | 能，还剩约 1.75 GiB |
| G | 24,000 位置 | 约 2.93 GiB | 不能——放不下，继续等 |

注意两点。其一，G 被挡不是因为计算忙，GPU 可能正闲着——是承诺接不住；它继续留在队里，还可能挡住后面更小的请求（取决于引擎是否跳过队头，这又是一个调度策略选择）。其二，接纳 E 与 F 之后池子只剩 1.75 GiB，之后到达的任何大请求都要等在场请求离开。排队的深浅由“何时能进”决定，池子的松紧由“承诺了多少”决定，而这两本账在同一个调度器手里。

由此得到一个判断服务容量的纪律：GPU 利用率低、但 KV 池满——增加并发没有用，瓶颈在承诺；GPU 利用率低、KV 也空——才谈得上扩并发。只看一边都会误诊。

### 取消要走完三层

进场有策略，离开也有生命周期。一次客户端取消要穿三层才算完成。

第一层，客户端断开：连接关闭、流中断。客户端能做的只有这一层——发起断开，仅此而已。

第二层，服务端感知并传递：网关或协议层注意到连接断了，把取消（abort）传给引擎。这里有一个容易被忽略的物理事实：已经提交到设备的 kernel 不会瞬间中断，引擎在回合边界统一处理取消——这正是站内源码走读篇追过的路径。

第三层，块回收：请求状态结束、引用计数减一，与其他请求共享的前缀块不能删，最后请求计数与 KV 使用指标回落。只有这层完成，资源才真正回到池子里。

三层断在哪一层，故障形态不同：断在第二层，GPU 继续生成无人接收的内容；断在第三层，显存被已经死掉的请求慢慢吃掉，负载越重泄漏越快。还有一个容易忽略的细节：取消发生在 Waiting 还是 Running，代价完全不同——还在排队的请求没有 KV，取消它只是从队列里摘除一行记录；正在执行的请求已经持有块，取消必须走完回收。所以“排队超时”作为一种自动取消，成本结构上是最便宜的防御。

验收要覆盖五种结束方式——成功结束、长度上限、客户端取消、排队超时、执行错误——并且以“请求计数与 KV 使用是否回落”作为共同的观察点。只在成功分支检查回收的系统，故障负载会逐渐耗光资源。

### 把四个决定放回同一条时间线

现在可以把本章拆开的机制装回一条请求的完整生命周期：到达之后进 Waiting 队列（排队位置由策略决定，FCFS、优先级还是带老化）；队头被调度器检查（执行位、token 预算、KV 承诺三个闸门全过才转 Running）；在场期间每轮迭代边界接受体检（结束让位、新请求补位、Prefill 是否分段）；最后以五种方式之一离开，离开必须走完回收。

```text
到达 ──► Waiting 队列（策略：先来先服务／优先级／老化）
            │ 队头检查：执行位？本轮 token 预算？KV 承诺接得住？
            ▼
          Running（迭代边界：结束让位、新请求补位、长 Prefill 分段）
            │ 五种出口之一
            ▼
          成功／长度上限／客户端取消／排队超时／执行错误 ──► 块回收、指标回落
```

每个阶段都有对应的可观察量：排队看 TTFT 的分布与队列深度，执行看 ITL 的停顿，接纳看 KV 使用与并发数的关系，离开看请求计数与显存是否回落。诊断高并发下的 p99 时，先判断请求卡在哪一段，再进对应的小节找机制——这也是本章四个部分共享同一条时间线的原因。

下一节把这套观察量交给一个真实的脚本：它的每个参数都是拧动这条时间线上某个旋钮的把手。

## 代码走读：measure_stream.py 的并发参数怎样当实验用

机制讲完，拿什么做实验？`labs/serving/measure_stream.py` 的每个参数都是一个实验变量：`--requests` 是总请求数（默认 20），`--concurrency` 是同时在飞的请求数（默认 1），`--max-tokens` 是输出上限（默认 64），`--repeat-input` 把一段中文重复拼接拉长输入、加重 Prefill（默认 1），`--output` 把每个请求的完整记录写成 JSONL，每行都带当时的 `config`，事后可复查。

读数口径先钉死。`first_content_seconds` 是客户端从发出请求到首个非空正文 chunk 的时间——它接近但不等于引擎首 token，因为一个 SSE 事件可以没有文本也可以携带多个 token；`total_seconds` 量到 `[DONE]`；`ok` 要求既有内容又收到 `[DONE]`。统计只对 `ok` 的行做：输出中位数与最近邻法 p95，而脚本自己打印的警告值得原样抄进报告——

```text
Closed-loop fixed concurrency; chunk timing is not token ITL. p95 unstable with small sample.
```

第一句点破了这个脚本最容易被误读的属性。第 29 行：

```python
with concurrent.futures.ThreadPoolExecutor(max_workers=a.concurrency) as pool,open(a.output,'w') as f:
```

`--concurrency` 是线程池大小，每个线程做完一个请求才发下一个——这是闭环负载：系统变慢时，客户端发新请求的速度也跟着慢下来，永远复现不了“外部持续到达”时队列无界增长的样子。开环压测按计划到达率发送，更适合研究过载，但要记录客户端自身能否维持住速率。两种方式各有用途，但“闭环并发 8”与“开环并发 8”不是同一个实验，报告必须注明是哪一种。

把参数直接翻译回前几节的机制，实验设计就有了着落：

| 参数 | 拧动它 | 对应的机制问题 |
| --- | --- | --- |
| `--concurrency` | 1 → 2 → 4 → 8 → 16 | 排队账：Waiting 何时开始堆积，`first_content` 在哪个并发档开始跳变 |
| `--repeat-input` | 1 → 8 → 32 | 公平账：长 Prefill 让同时在线的流式请求付出多少停顿 |
| `--max-tokens` | 64 → 512 | 长度维度：短请求与长生成混跑时，前者的等待被后者拉长多少 |
| `--requests` | 给足样本 | 统计口径：p95 至少需要几十个样本才站得住 |

单变量是纪律：一次只拧一档，其余固定，跑完把 `first_content` 的中位数、p95 与 errors 三列放在一起看——中位数抬升而 errors 为零，是排队在涨；errors 出现，是容量或超时已经击穿。每个结论都落在 JSONL 里，可复查。

这些客户端数字背后的服务端结构，站内源码走读 <a href={asset('code/vllm-request/')}>《一个请求怎样获得本轮 token 与 KV？》</a> 沿 vLLM v0.29.0 的 V1 引擎走了一遍，结论与本节互为表里：调度器维护 Waiting 与 Running 两个集合，每个回合在 token 预算内让 Running 续算、从 Waiting 补位；KV 由 `allocate_slots` 按本轮新计算的位置要块，容量不足时向上返回而不是硬塞；取消在回合边界处理。那篇还钉住了一个计数口径——“请求已计算多少、本轮新安排多少、输出了多少”是三个不同的数。压测脚本在门外量时间线，走读篇在门内看队列，两边对得上，排队的数字才解释得动。

两篇可以拼成一个练习：那篇的交付是用 4 个提示 token、最多 3 个输出 token 做纸面跟踪，列出每轮的新计算、总历史、已分配块与是否结束。做完本章的时间线再去做那张表，你会发现它就是本章逐秒表的引擎内视图——只是把“执行 A、B”细化成了“每条请求本轮算到第几个位置、要了哪块 KV”。

## 动手：把并发推过显存上限，先出问题的是什么

预测题。沿用上一章的账：每个位置 128 KiB，一条上限 8192 位置的请求承诺 1 GiB KV，引擎的 KV 池共 8 GiB。现在把 `measure_stream.py` 的 `--concurrency` 从 8 提到 16（`--requests` 给足 32 条）：你预测先出问题的是什么——显存 OOM，还是排队时间暴涨？

先写下推理链再展开核对。提示：客户端的“16 条在飞”与引擎的 Running 集合是不是同一个东西？接纳控制挡在哪里？被挡住的请求去了哪里？写完后可以用两臂实验验证：

```bash
python labs/serving/measure_stream.py --url http://127.0.0.1:8000 --requests 32 --concurrency 8
python labs/serving/measure_stream.py --url http://127.0.0.1:8000 --requests 32 --concurrency 16
```

<details>
<summary>展开核对</summary>


排队时间涨，一般不会 OOM。推理链分五步：

1. 客户端的 16 条在飞不等于引擎的 16 条在算。接纳控制在 KV 承诺处挡人：Running 最多 8 条，另外 8 条留在 Waiting 队列。
2. 留在 Waiting 的请求，多出来的时间全部落在 `first_content_seconds` 的排队项上：第 9–16 条的等待约等于排在它们前面的请求的全程时间，p95 随并发线性抬升；吞吐封顶在容量点，不再增长。
3. GPU 利用率大概率也没涨——因为瓶颈本来就不在计算。这正是上一章末尾那句“空闲计算能力存在，但 KV 块不足时也无法接纳”的实测形态：扩并发只加等待，不加产出。
4. 真会 OOM 的路径不是并发本身，而是配置错误：KV 池或每请求上限按超过物理显存设置、引擎没有做接纳检查。还有一种“半途出事”：若实现按块逐次承诺，池满时可能抢占 Running 请求——回收块、之后重算或换出——表现是尾延迟剧烈抖动而不是崩溃。
5. 验证方法：`--requests 32` 固定，`--concurrency 8` 与 `16` 各跑一遍，比较两次的 `first_content_median` 差值——它应当约等于一批请求的全程时间；errors 应保持为 0。若看到的是崩溃或 errors 暴涨，先查配置，再查抢占。


</details>
