我们已经能启动服务，也知道 KV 占多少资源。现在多个请求同时到来，系统必须决定谁先执行、每轮做多少工作、什么时候接纳新请求。这些选择决定用户感受到的速度。

## 首个 token 之前不只有模型计算

客户端发起请求后，可能经历网络、输入处理、队列、Prefill、输出处理，再收到第一个结果。Time To First Token，简称 TTFT，必须说明从哪个起点到哪个终点测量。

客户端的首个非空正文时间是实用指标，但不一定精确等于引擎的第一个 token 时间；服务可能先产生控制事件、思考内容或聚合多个 token。报告需要保留这一差别。

第一个结果之后，每次输出之间的间隔影响流畅度。平均后续 token 时间与逐个 token 间隔分布不是同一概念，网络 chunk 间隔又是另一层。

## 先用恒定时间模型算一遍

设排队 Q=800 ms，Prefill P=600 ms，其他 O=50 ms，后续每 token D=40 ms，总输出 N=32。首 token 时间为 `Q+P+O=1450 ms`，全部完成约为 `1450+(32−1)×40=2690 ms`。

N−1 是因为首 token 已包含在前面的阶段。这里假设后续耗时恒定，不描述真实服务的抖动、并行与网络细节。

## 连续批处理为什么能让短请求离开？

传统整批方式可能等一组请求全部结束，再开始下一组。若一条需要 100 步，另一条只需 10 步，短请求结束后留下的执行位置可能长期空着。

连续批处理在迭代边界更新活跃请求集合，允许结束请求退出、新请求在资源允许时补位。它不是把所有请求合成一条上下文；每个请求仍有自己的状态与 KV。

## 长输入与持续输出为什么会互相影响？

一个很长的 Prefill 可能占用较多本轮计算，让已有 Decode 请求等待。Chunked prefill 把长输入分段安排，试图改善调度和延迟，但也会增加调度边界并改变执行形状。

吞吐最大化与每个请求低延迟不总是同一目标。排队策略、优先级和公平性需要结合服务目标，而不是只追求 GPU 始终忙碌。

当到达率超过可持续处理能力，队列会增长。限流、接纳控制和背压是告诉上游系统已经不能无限吸收工作，不是“服务能力不足时可有可无的装饰”。

## 压测也可能掩盖排队

固定并发客户端往往等一个请求结束后才补新请求，属于闭环负载。系统慢下来时，新请求发得也慢，可能掩盖外部持续到达时的队列增长。

开环压测按计划到达率发送，更适合研究过载与排队，但要记录客户端自身能否维持速率。两种方式各有用途，报告必须注明，不把同样“并发 8”当成完全相同实验。

## 取消也属于调度职责

客户端断开后，网关、服务层与引擎需要传递取消信号，清理仍在执行或等待的请求及资源。若只关闭网络连接，GPU 可能继续生成无人接收的内容。

验收应包括：成功结束、长度上限、客户端取消、排队超时和执行错误。观察请求计数与 KV 使用是否回落，再判断生命周期管理是否正确。
