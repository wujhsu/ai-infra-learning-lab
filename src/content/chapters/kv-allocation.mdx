上一章把 <Term id="kv-cache"/> 的显存账算到了单个请求：按 28 层、8 个 KV 头、头宽 128、fp16 的设定，每 token 112 KiB，4096 的上下文约 0.44 GiB，并发 64 时 KV 反超权重。但那笔账只回答了"数据本身要放多少"，没有回答引擎怎么把这笔账落到显存上。

这一章把剩下的三个问题补齐：

- **计数**：每 token 的账怎样从模型结构逐项推出来，为什么不能拿查询头数乱代；
- **分配**：为什么生产引擎按固定大小的块分页，而不是给每个请求划一段连续显存——这笔碎片账要算出具体的 GiB 数；
- **回收**：请求结束、被取消、前缀被复用，各自收回什么；块不够时被抢占的请求是搬走还是重算。

这三个问题合起来，就是服务容量问题的另一半。调度章会看到"GPU 还有算力却接不了新请求"，卡住的地方通常正是这里的 KV 块池。

## 这一章解决什么问题

先摆出要解释的现象，再谈机制。

**现象一：同样的显存，有人只能跑 4 条并发，有人能跑 18 条。** 上下文长度事先不知道，请求有长有短、有先有后。如果按"每个请求一段连续显存、按最大长度预留"来分配，浪费会大到具体可算；如果按固定小块分配，浪费会小到几乎可以忽略。差别不是实现细节，而是两种内存组织方式的本质不同。

**现象二：请求早就结束了，显存却没回落。** 客户端断开连接、请求超时、前缀被下一条请求复用——每种情况下"回收"发生的时机和回收的对象都不一样。只在"成功返回"的分支里写释放逻辑，故障负载会一点点把块池吃光。

**现象三：两条请求共享 100 个前缀 token，省下的显存却不是整整 100 个 token 的字节。** 这是章首的问题，答案藏在块的组织方式里：共享的最小单位是块，不是 token。

三个现象对应三条路线，每条都会落到一个能复算的数上：

- 计数——每 token 112 KiB 从哪里来，GQA 怎样把这笔账砍半；
- 分配——同一个 2 GiB 池，连续预留浪费 1.32 GiB、分页只浪费约 0.015 GiB，两笔账差在哪；
- 回收——结束、取消、复用三个时机的对照表，以及块不够时 swap 与 recompute 的取舍。

本章全部算例沿用站内模拟器的同一个公式 `kvBytes(layers, heads, dim, tokens, batch, bytes)`：

```text
KV 字节数 = 2 × 层数 × KV头数 × 头宽 × token数 × 并发 × 每元素字节数
```

所有数字都是纸面算术，不是测量；每个数都值得你自己重算一遍。

## 机制讲解：从每 token 的账到块池

### 第一步：每 token 值多少字节，GQA 为什么改变这笔账

从第四章的教学例出发：单层、单头、每个 K 和 V 有 D 个分量、每元素 s 字节，一个位置这一小份是 `2×D×s` 字节。真实模型只是把几个明确的维度一项项乘上去，而不是背一个现成公式：

| 因子 | 含义 | 0.6B 算例取值 |
|---|---|---|
| 开头的 2 | K 与 V 两份 | — |
| L | 层数，每层各存一份 | 28 |
| $H_{KV}$ | KV 头数（不是查询头数） | 8 |
| D | 头宽 | 128 |
| T | 每条序列已保留的位置数 | 随生成增长 |
| N | 并发且互不共享的序列数 | 由调度决定 |
| s | 每元素字节（fp16 = 2） | 2 |

$$M_{KV}=2\times L\times H_{KV}\times D\times T\times N\times s$$

表里特意把 H 写成 KV 头数。Qwen3-0.6B 模型卡列出 28 层、16 个查询头、8 个 KV 头——两个数不相等，这不是印刷错误。多头 Attention 允许若干个查询组共用同一组 K/V：查询组数多于 KV 组数叫分组查询注意力 <Term id="gqa"/>，全部查询共用一组 K/V 是 MQA。它们是结构设计，改变的是每 token 要保存多少份 K/V；计算缓存容量时必须读实际配置里的 KV 头数，把查询头数代进去会把账算大一倍。

同一个 0.6B 骨架（28 层、头宽 128、fp16）下，KV 头数这一项对每 token 字节的影响一目了然：

| 结构 | KV 头数 | 每 token 字节 | 4096 上下文每条 |
|---|---|---|---|
| 无分组（KV 头 = 查询头） | 16 | 224 KiB | 896 MiB |
| GQA（Qwen3-0.6B 实际结构） | 8 | **112 KiB** | 448 MiB |
| MQA | 1 | 14 KiB | 56 MiB |

分组每砍一半，KV 账就砍一半——这不是运行时"删了几个缓存头"，而是模型出厂时的结构选择。引擎能做的只是准确读它。

代入 0.6B 规模的真实结构（28 层、8 个 KV 头、头宽 128、fp16）：

- 每 token：2 × 28 × 8 × 128 = 57,344 个数；× 2 字节 = 114,688 字节，**即 112 KiB**。
- 上下文 4096 跑满：112 KiB × 4096 = 448 MiB，约 0.44 GiB。
- 这与上一章的数字逐位一致——本章后面所有块大小的账，都从这 112 KiB 出发。

### 第二步：为什么按块分配——两笔碎片账

有了每 token 的账，最直接的分配方式是：每个请求到达时，按它的最大上下文长度划一段**连续**显存。这在纸面上最简单，在实践中浪费最大。

浪费分两笔，各算一个具体的数。

**第一笔：预留了没用（内碎片）。** 设 KV 池共 2 GiB，每条请求按上限 4096 预留，即 448 MiB；实际跑完平均只用 1000 token，即 112,000 KiB ≈ 109.4 MiB。

| 项目 | 连续预留方案 | 分页方案（块 16 token） |
|---|---|---|
| 每请求占用 | 448 MiB（按上限一次划走） | ceil(1000/16) = 63 块 = 110.25 MiB |
| 2 GiB 能容纳 | 2048 ÷ 448 = 4 条 | 2048 MiB ÷ 1.75 MiB = 1170 块 ÷ 63 = 18 条 |
| 池内浪费 | 4 × (448 − 109.4) ≈ **1354.5 MiB ≈ 1.32 GiB（66%）** | 18 条 × 尾块 8 个空位 × 112 KiB = **15.75 MiB（0.77%）** |

同样的池、同样的平均上下文：4 条对 18 条。连续方案的浪费不是工程没做好，而是"按上限预留"这个决定本身的代价——长度事先未知，预留大了浪费、预留小了溢出。

**第二笔：空出来了却用不上（外碎片）。** 连续方案下，请求长短不一、先后结束，池会被切成不连续的空洞。仍设 2 GiB 池，把局面按时间排开：

| 时刻 | 池内布局（区间单位 MiB） | 空闲显存 |
|---|---|---|
| R1、R2 到达，各按上限 6144 预留 | R1 占 [0, 672)，R2 占 [672, 1344) | 尾部 704 MiB，连续 |
| R1 结束并释放 | R2 占 [672, 1344) | 空洞 [0, 672) + 尾部 704，共 1376 MiB，**最大连续段 704 MiB** |
| R3 到达，上限 8192，需 896 MiB 连续 | 放不下，排队 | 1376 MiB 空闲中，672 MiB 因不连续而卡死 |

这 1376 MiB 空闲里有 672 MiB（约 **0.66 GiB**）纯粹因为"不连续"而卡死；池越大、负载越杂，这笔账越难看。而分页方案把同一局面改写成块账：空闲 1376 MiB = 786 块，R3 需要 512 块——从空闲池里任取 512 块即可，无论它们物理上在哪里。

分页方案就是这样把两笔账同时改写的。KV 池被切成固定大小的块（block），一条序列的逻辑位置通过块表映射到若干物理块，块在显存里的位置任意：

- **外碎片结构性为零**：按块分配只要求"块内连续"，不要求"请求连续"，空闲块总能被任何请求使用；
- **内碎片只剩尾块**：一条序列只用得上最后一个块的一部分，浪费不超过一个块。块 16 token、平均上下文 1000 时，全场内碎片 15.75 MiB ≈ 0.015 GiB，且只随并发数增长、不随上下文增长。

用一个更小的例子看懂这张图：每块放 4 个 token，长度 6 的序列占 2 块、尾块空 2 个位置；长到 9 时补第 3 块。PagedAttention 把这种内存组织与注意力读取接起来：逻辑上历史连续，不要求物理地址连续；注意力 kernel 按块表逐块取 K/V。代价是每块一份块表与引用计数元数据——块不能太大也不能太小，这个权衡留到下面量化。

### 第三步：分配的账——块 16 token 时能装多少并发

把 0.6B 的每 token 账换算到块粒度，块大小取 16 token（vLLM 的默认值量级）：

- 每块字节：112 KiB × 16 = 1792 KiB = **1.75 MiB**。
- 上下文 4096 的请求：4096 ÷ 16 = 256 块 = 448 MiB——与连续方案满跑时相同，分页在"人人都跑满"时没有优势。
- 给一张 80 GiB 级别的卡留出全部 KV 预算：80 × 1024 ÷ 1.75 = **46,811 块**；每条 256 块，46,811 ÷ 256 = 182.86，**最多 182 条并发**，剩 219 块（约 383 MiB）。

再看块是**什么时候**加上来的。一条 prompt 2000 token 的请求，Prefill 一结束就有 2000 个位置，此后 <Term id="decode"/> 每步加 1 个位置、块数按 16 的整数倍阶梯式跳涨：

| 时刻 | 已保留位置 | 块数 | 尾块状态 |
|---|---|---|---|
| Prefill 完成 | 2000 | 125 | 恰好装满 |
| Decode 第 1 步 | 2001 | 126 | 尾块 1 个占用 |
| 又生成 16 个 token | 2017 | 127 | 尾块 1 个占用 |
| 跑满上限 | 4096 | 256 | 恰好装满 |

大多数 Decode 步不申请新块，每跨过一次 16 的边界补一块——"何时给请求加块"在时间轴上就是这张锯齿表，代码走读一节会看到它对应引擎里每个调度回合的分配调用。

三个观察。第一，"能装多少并发"这道题的答案由三个数完全决定：预算、块大小、每条请求的块数——没有玄学，调度器接纳请求时做的就是这道除法。第二，剩下的 219 块是**池级**的零头：还够再装一条 2048 上下文的请求（128 块 = 224 MiB），装不下第二条——块池不会像连续池那样把零头锁死。第三，上下文不满时按实际块数线性缩减，所以上一节"平均 1000 token"的例子里 2 GiB 能挤进 18 条，而不是按 4096 上限算的 4 条。

块大小本身是一道两端权衡的题。固定池 2 GiB、平均上下文约 1000（长短不齐）、并发 18 条时：

| 块大小（token） | 每块字节 | 每条块数 | 期望尾块空位 | 空位占比 | 块表条目（18 条合计） |
|---|---|---|---|---|---|
| 16 | 1.75 MiB | 63 | ≈ 8 个 | ≈ 0.8% | 1134 |
| 64 | 7 MiB | 16 | ≈ 32 个 | ≈ 3.2% | 288 |
| 256 | 28 MiB | 4 | ≈ 128 个 | ≈ 12.8% | 72 |

长度不齐时，尾块平均半满：块越小，浪费越少、块表越多；块越大，管理越省、浪费越涨。生产引擎取 16 这个量级，是在两端之间偏向省显存的一侧。

还有一笔演示里看不到的账要补：块表本身、每块的引用计数、以及部分实现为推测解码预留的候选位置。容量算术回答"数据本身要放多少"，监控里看到的已分配显存还包括这些管理结构——这就是"公式与监控对不上"的常态来源。

多卡切分会再加一层偏差：各 rank 各持一份 KV，部分结构复制而非均分，不能先算总字节再无条件除以 TP 卡数。

### 第四步：回收的时机三问

分配讲完了，钱什么时候还？三个时机，回收的对象各不相同。先给一张速查表，再逐条展开：

| 时机 | 回收对象 | 易错点 |
|---|---|---|
| 请求正常结束 | 独占块归还空闲池；共享块引用减一 | 不判共享就删，提前释放别人在读的块 |
| 客户端取消 / 异常退出 | 同上，但须经引擎的一致边界 | 只在成功分支写释放，故障负载逐渐耗尽块池 |
| 前缀被新请求复用 | 暂不回收——块转为缓存资产 | 复用条件不匹配，读到错误数据 |

**一问：请求正常结束，回收什么？** 该请求**独占**的块全部归还空闲池；**共享**的块只把引用计数减一。这正是引用计数存在的原因：两个请求复用同一前缀时引用同一批物理块，一个先结束，块还被另一个读着，必须等引用归零才能进空闲池。

若共享的完整块将被写入或扩展，还要靠写时复制、不可变完整块等策略避免改掉别人正在读的数据。这也回答了章首问题：共享 100 个前缀 token，能直接省下的是其中**落进完整共享块**的部分；跨在块边界上的零头要么重算、要么复制整块，所以节省不等于整整 100 个 token 的字节。逻辑上的重复，不自动等于物理上的等量节省。

**二问：请求被取消，回收什么？** 表面上和正常结束一样——独占块归还、共享块减引用——但触发路径完全不同。客户端断开只是关掉了连接，取消信号要经服务层传进引擎，在调度回合的一致边界上处理；已提交到 GPU 的 kernel 不会瞬间停，引擎仍要在回合末尾统一释放。

这条路径的观察方法在<a href={asset('read/scheduler/')}>调度章</a>的取消实验里：对推理服务发起流式请求、半途断开，然后看服务端显存与请求计数是否回落。"取消之后显存确实回落、该会话的块可被复用"需要真实 GPU 服务端验证，客户端脚本只能制造触发条件。漏掉取消与异常分支的释放逻辑，是推理引擎"显存泄漏"的典型形态。

**三问：前缀被复用，回收什么？** 这条的答案最反直觉：**当下什么也不回收，反而要阻止回收**。新请求命中已有前缀时，引擎让它引用现成的块（引用计数加一），省掉这部分 <Term id="prefill"/> 计算；这些块在原请求结束后不进空闲池，而是留给后续命中。只有缓存策略判定不再值得保留（超时、逐出）且引用归零时，它们才真正被回收。

复用改变的是块的生命周期归属——从"某个请求的私产"变成"缓存池的资产"。

这也在上一章的复用条件上再加一层系统约束：命中要匹配影响计算的完整条件（模型、适配器、位置处理、租户边界），相同可见文字不代表相同实际输入 ID 与上下文。

### 第五步：块不够时——swap 还是 recompute

所有请求都活着、块池却见底了，怎么办？引擎可以**抢占**：暂停若干请求，把它们的块让给优先级更高的（典型如新到的交互式请求）。

被抢占的请求有两种保存方式，取舍一句话：**上下文短的用 recompute（重算比搬运便宜），上下文长的用 swap（搬运比重算便宜）**。

| | swap（换出） | recompute（重算） |
|---|---|---|
| 抢占瞬间释放的 GPU 块 | 该请求全部块 | 该请求全部块 |
| 额外占用的存储 | CPU 内存一份，与该请求 KV 等大（2048 token 即 224 MiB） | 零 |
| 恢复时的代价 | PCIe 往返搬运 224 MiB | 对全部上下文重新 Prefill 一遍 |
| 适合谁 | 长上下文（重算很贵） | 短上下文、前缀便宜（搬运不值得） |

两列在"抢占瞬间腾出多少 GPU 显存"上完全相同——区别全在恢复路径上花的是带宽还是算力。引擎通常按请求长度和运行模式逐请求选择，也可以两者都不做：直接让新请求排队。

排队与抢占的完整调度逻辑是下一章的主场，这里只需要记住：**抢占不是失败，是块池压力下的正常调度动作；选 swap 还是 recompute，是一道可以算出来的性价比题。**

## 代码走读：vLLM 何时给请求加块

机制讲完，问题变成：这套故事在真实引擎里从哪里验证？站内的<a href={asset('code/vllm-request/')}>vLLM 请求路径源码走读</a>（固定 v0.29.0，V1 引擎）按 EngineCore.step → Scheduler.schedule → KVCacheManager 的顺序组织了这条路径。这里不重复该篇的行号级细节，只把它的四个结论与本章机制对号入座。

**加块发生在每个调度回合，不是请求到达时一次到位。** [KVCacheManager.allocate_slots](https://github.com/vllm-project/vllm/blob/v0.29.0/vllm/v1/core/kv_cache_manager.py#L343) 接收本轮要处理的新 token 数、已计算前缀、lookahead 与外部缓存信息，换算成"还差几个块"，能补就补。请求数量不变、位置在长，也会持续申请新块——上一节"分配的账"在代码里的形态就是：每回合做一次小小的除法和取整。

**接纳与否由容量判定先行。** 调度器对等待中的请求先判断现有块池能否放下它的 prompt 加首批输出位置（can_allocate 一类的判定），放不下就让它继续等，或触发上一节的抢占。这就是"GPU 还有算力却接不了新请求"在代码里的位置：卡住的不是计算资源，是块池除法的结果。

**前缀命中改变的是引用，不是拷贝。** allocate_slots 的参数里带已计算前缀——命中的块被新请求引用（计数加一），只有未命中的尾巴才需要新块。对应本章"回收三问"的第三问：复用是引用层面的操作，也解释了为什么取消一个请求不一定立即销毁它访问过的所有块。

**取消与结束走同一条释放路径。** EngineCore.step 在模型执行后处理本回合到达的 abort，经 finish_requests 到 free，把独占块归还、共享块减引用。"只在成功分支回收"的 bug 在这份代码里没有藏身之处，但自己写引擎时是最容易漏的地方；该篇末尾的纸面跟踪练习（4 个提示 token、最多 3 个输出 token，逐轮列已分配块）正是把本章的块账放进这个循环。

最后把观察工具接上。要拿真实请求数据复核本章的账，`labs/serving/measure_stream.py` 在流式响应里记录的 usage 字段（prompt_tokens 与 completion_tokens）给出每条请求的实际 token 数：乘以 112 KiB 就是它的逻辑 KV 占用。

拿它和服务端报告的已分配 KV 显存对比，差值里就有块对齐、尾块与管理结构的成分——纸面账与实测账的差距，本身就是块系统在工作的证据。

## 动手：给定预算，算最大并发与内碎片

纸面算一遍完整的容量题。设定：KV 总预算 8 GiB，块大小 32 token，平均上下文 700 token，模型仍是 0.6B 规模的每 token 112 KiB（fp16）。按顺序算四步：

1. 每块多少字节？由块大小乘每 token 字节得到。
2. 全池共多少块？预算除以每块字节，向下取整。
3. 每条请求占几块？平均上下文除以块大小，向上取整——这一步的"向上"就是内碎片的来源。
4. 最大并发是多少？总块数除以每条块数，向下取整；再算每条请求浪费几个空位、全场内碎片占已分配的百分比。

算完再回答一个追问：把块改成 256 token，并发和内碎片各变成多少？哪一头变了、哪一头没变？

<details>
<summary>参考答案（先自己算完再看）</summary>

1. 每块 = 32 × 112 KiB = 3584 KiB = 3.5 MiB。
2. 总块数 = 8 × 1024 MiB ÷ 3.5 MiB = 2340.57，取 2340 块（池尾 2 MiB 凑不齐一块，这本身就是块对齐的浪费）。
3. 每条请求 = ceil(700 ÷ 32) = 22 块，即 22 × 32 = 704 个槽位，比 700 多 4 个。
4. 最大并发 = floor(2340 ÷ 22) = 106 条（用 2332 块，剩 8 块）。每条浪费 4 个空位 × 112 KiB = 448 KiB；内碎片占已分配 = 4 ÷ 704 ≈ 0.57%；全场共浪费 106 × 448 KiB ≈ 46.4 MiB，同样约占预算的 0.57%。

追问：块 256 token 时，每块 = 256 × 112 KiB = 28 MiB，总块数 = 8192 ÷ 28 = 292 块；每条 = ceil(700 ÷ 256) = 3 块 = 768 槽，浪费 68 个空位（内碎片 68 ÷ 768 ≈ 8.9%）；并发 = floor(292 ÷ 3) = 97 条。对比：内碎片从 0.57% 涨到 8.9%，并发从 106 降到 97——块变大，省下的是块表等元数据与批量管理的开销，付出的是尾块浪费；"并发下降不多、浪费涨了十几倍"说明这个尺寸已经偏大。两头都没变的是每 token 112 KiB：那是模型结构决定的，块大小动不了它。

</details>

这道题就是调度器每回合对块池做的除法。做熟了，回到章首的三个现象：4 条对 18 条是预留方式的差别，显存不回落是回收路径的漏洞，省不满 100 个 token 是块边界的零头——KV 显存的计数、分配与回收，至此闭环。
