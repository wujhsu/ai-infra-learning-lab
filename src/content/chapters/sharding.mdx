DDP 的每个 rank 都保留完整训练状态。如果一份状态已经超过单卡容量，复制更多份并不能解决。现在让不同 rank 分别负责一部分状态。

## 先分清哪些状态必须同时存在

假设两张卡，各自负责一半参数的更新。优化器状态可以只为自己负责的一半保存；梯度也可以在归约后只保留对应片段。真正执行某一层计算时，却可能需要这一层完整参数。

由此出现两个不同概念：长期归哪个 rank 持有，以及计算时临时需要哪些数据。分片系统在二者之间安排通信与释放。

ZeRO 的常见阶段逐步分片优化器状态、梯度和参数。它提供理解节省来自哪项的思路；具体框架的接口、峰值和通信路径仍要单独核对。

## FSDP 怎样把参数临时拼起来？

<Term id="fsdp"/> 的一种典型路径是：计算某组模块之前，AllGather 参数分片；执行前向或反向所需计算；随后按策略重新分片或释放完整参数；梯度通过 ReduceScatter 留给负责的 rank。

```text
常驻：每人一部分参数 / 梯度 / 优化器状态
        ↓ 计算即将需要该组参数
AllGather → 临时完整参数 → 该组计算
        ↓ 按策略释放或保留到后续需要
反向梯度 → ReduceScatter → 各自更新负责的分片
```

完整参数只在需要的窗口出现，有机会降低峰值。但参数组太大、预取太积极或同时保留多组，也可能产生很高临时峰值。因此不能把总状态简单除以卡数就当作实际最大显存。

## 为什么要决定分片粒度？

整模型作为一组，通信次数可能少，但临时收集范围很大。按层或更小模块分组，可以降低同时完整存在的参数量，也会增加调度和通信边界。

预取下一组参数可能把通信藏到当前计算后面，但同时增加内存占用。这里再次出现同一个取舍：为了更多重叠，需要提前准备更多数据。

FSDP2 的接口采用可组合的模块分片方式。阅读教程时要区分 FSDP1 与 FSDP2，不把旧封装的参数直接套给新接口。

## 用小数组理解 ReduceScatter 的位置

假设两个 rank 的完整局部梯度分别为 `[1,2,3,4]` 与 `[5,6,7,8]`。求和结果为 `[6,8,10,12]`。若前两项由 rank 0 负责，后两项由 rank 1 负责，ReduceScatter 后两者各持有自己的部分，再按损失语义做归一化和更新。

下一次计算若需要完整参数，再从各 rank 收集更新后的分片。这个周期解释了为什么分片优化器只更新自己持有的片段，仍能共同推进同一个模型。

## CPU offload 不是免费增加显存

把部分状态放到 CPU 主存可以降低设备常驻量，但计算时需要传输，还要考虑 CPU 优化器执行与主机内存容量。若 PCIe 传输成为关键路径，GPU 可能等待得更多。

应记录每步状态迁移量和等待，比较能否运行更大模型，以及总训练时间的代价。不能只展示“显存减少多少”就宣布整体更好。

## 分片检查点怎样保存？

每个 rank 只持有部分状态，直接把 rank 0 的 state_dict 当作完整模型文件可能遗漏数据。分布式检查点工具需要记录分片与元数据，协调保存和加载。

恢复到不同 world size 可能要求重新分布状态，支持范围由具体 API 与格式决定。不要假定“文件扩展名相同”就能任意跨框架、跨并行策略加载。

项目保留一条小规模 FSDP2 运行路线，并要求比较训练前后结果、峰值显存和通信。GPU 实测状态单独记录；这里的数组例子只验证数据关系。
