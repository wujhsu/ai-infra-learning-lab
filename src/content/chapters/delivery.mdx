诊断章收在一个悬而未决的局面上：新版本的调度配置不合适，长输入在 Prefill 里挤压短请求，TTFT 尾部明显抬升。重启可以暂时清空队列，但真正要回答的是三个连在一起的问题——坏版本怎么停下来（撤回）、怎么确认停对了（验证）、修复怎么重新走完全程（发布）。serving 章问过"为什么今天回答变差"，那时我们把注意力放在请求经过的每一站；本章把同一个问题移到时间轴上：变差往往不是服务自己坏掉，而是一次发布换进来的。

一次可靠的交付管理的不是"把新代码放到线上"这一个动作，而是完整的行为——权重、tokenizer、镜像、配置与路由共同决定用户拿到什么结果。本章把这条链拆成四段：先说清 AI 服务的发布比普通服务多出哪一层；再讲机制——发布轨道、观测信号、回滚决策的四字段与 fail-closed 校验；然后走读本库的三个文件，看一个"健康但坏"的假服务怎样被制造出来；最后把决策练习留给你。

## 这一章解决什么问题

普通服务的发布看两类信号就够：错误率和延迟。一个版本要么报 500，要么不报；要么慢，要么不慢。AI 服务多出一层：质量回归。它不出现在任何常规仪表盘上——每个响应都是 HTTP 200，流式输出正常结束，JSON 可以解析，但回答变差了。四种具体形态，都是教学算例但每种都有对应的真实场景：

- 摘要变短：输出字段齐全，平均句数从五句掉到三句，关键实体开始漏；
- 代码开始出错：固定任务集上语法错误率从 2% 涨到 11%，业务方先于监控发现；
- 拒绝率上升：安全阈值调紧后，昨天正常回答的请求今天被拒，状态码仍是 200；
- 延迟的尾巴：均值几乎不动，p99 TTFT 翻倍——诊断章那个长输入挤压短请求的案例，在均值上根本看不见。

这一层的麻烦在于信号不是免费的。错误率由网关顺手统计；质量抽评需要固定任务集和判定规则，延迟的尾巴需要保留分位数而不是只看均值。多出来的这一层，就是 AI 发布与普通发布的全部区别所在。

在这一层上，三种典型的失败方式反复出现：

第一种，只看健康检查。readiness 探活 `/health` 返回 200，副本标记 Ready、开始接流量——但业务路径在 500。健康检查量的是"进程活着"，不是"服务可用"，两个概念在 AI 服务里离得尤其远：一个把模型加载坏了的引擎照样可以健康地返回错误。

第二种，把无数据当成功。指标查询返回空序列，错误率算出来是"0%"——没有证据被当成了有利证据。0 个样本和"10 个样本 0 个错误"是完全不同的两件事：前者连"候选版被观测到了"都不能确认。

第三种，无证据的回滚与修复。回滚一个没弄清为什么坏的版本，和赌博的区别只在于动作更贵；让 Agent 给出一段听起来合理的解释就直接执行修复，则连赌注是什么都看不清。"服务暂时恢复"从来不构成"修复正确"的证据。

本章的主线就是把这三个洞逐个堵上。读完的检验标准：不看正文，能说出 AI 发布比普通发布多看哪些信号、为什么空结果不是 0%；能写出一个能通过 fail-closed 校验的回滚决策，并指出拿掉哪个字段它就会被拒；能解释为什么校验器永不执行修复。

## 机制讲解：轨道、信号、决策与校验

### 轨道：让新旧版本同时在场

蓝绿、灰度、金丝雀是同一个问题的三种粒度：怎样让"新版本在场"和"全部用户承受新版本"不是同一个时刻。

- 蓝绿：两套完整环境并存，切换是改路由指向，一瞬间完成；代价是双倍资源，回滚等于再切一次。
- 灰度（渐进发布）：按比例逐步放量，每一步之间设分析门，过门才继续。
- 金丝雀：<Term id="canary" /> 灰度在最小比例端的特例——先用极少量真实流量试探，错了只伤极少量请求。

三条轨道共享一个前提：候选版本必须有独立、完整、可服务的运行实例。不能让同一个 TP 组的一半 rank 加载新权重、另一半保留旧权重，然后指望路由层解决——模型内部一致性与服务版本分流是两个层次，前者坏了后者救不回来。

还有一个容易被高估的保证：副本比例不等于流量比例。5 个副本里 1 个跑新版本，并不精确等于 20% 的请求到达新版本——没有真正的按权重路由时，这只是近似。比例是给分析门看的近似值，不是对流量分布的承诺；判断证据时按业务、长度与负载分层比较，别让"最容易的请求都进了金丝雀"制造偏乐观的结论。

### 信号：普通发布看错误率，AI 发布还要看质量漂移

| 信号 | 普通服务 | AI 服务要多看的 |
| --- | --- | --- |
| HTTP 错误率 | 主要信号 | 仍要看，但只是地基 |
| 延迟 | 均值或 p95 | 分布：TTFT 的 p99，按输入长度分层 |
| 质量 | 没有这一层 | 固定任务集抽评：可解析性、必要字段、明确判定规则 |
| 拒绝率 | 没有这一层 | 同一请求集上拒绝比例的变化 |

质量抽评的三个设计要点：固定任务集，让"退化"成为可复现的对照实验而不是两次随机抽样；明确判定规则，结构化输出能否解析、必要字段是否正确，往往比 HTTP 200 更接近业务成功；保留重复评估，随机生成存在波动，一次 82 分一次 79 分说明不了任何事。

一条可复查的质量抽评记录长这样（教学算例）：

```text
任务集：summarize-200（固定 200 条输入，任务集 revision 固定）
判定：JSON 可解析；必填字段 summary 非空；实体覆盖率不低于 0.9
结果：候选 197/200 通过，稳定版同任务集 199/200；不通过样例 id 已附
口径：每版本跑 3 次，报告最差一次
```

每一行都在把"我觉得变差了"翻译成别人能重算的数字。缺了任务集 revision，三周后没人知道当时评的是哪些输入；缺了重复次数，候选 197 对稳定 199 的差别就无法与波动区分。

分析还要区分三种结局：成功、失败、无数据。设目标为候选错误率不高于 1% 且 TTFT 不显著恶化——只观察 5 个请求全部成功，证据仍然太弱（最少样本没到）；指标查询返回空值，更不能按 0 错误处理（这是无数据）。分析需要第四个去向：暂停或不确定，先补观测再下结论。[Argo Rollouts 分析机制](https://argoproj.github.io/argo-rollouts/features/analysis/)

### 回滚决策的四字段

把"撤回"从聊天记录里的一句"回了吧"变成一条可校验的记录，需要四个字段：

| 字段 | 约束 | 作用 |
| --- | --- | --- |
| action | hold / rollback / propose_fix 三选一 | 要做的事，封闭名单 |
| reason | 非空字符串 | 人能读懂的因果叙述 |
| evidence | 非空字符串列表，每条非空白 | 可复查的事实，一条是一条 |
| patch_ref | 字符串；propose_fix 时必须非空 | 可审查的补丁引用 |

为什么 evidence 必须非空？先看回滚的代价：它扔掉候选版本携带的修复、改变在途请求的去向、可能留下双写过的外部状态。付出这个代价，买到的应该是两样东西——回到已知良好状态，以及知道为什么离开。第二样恰恰由 evidence 承载：evidence 为空的回滚只买到前一样。更实际的是，空 evidence 无法回答事后必然被问的三个问题：是发布本身坏了，还是观测坏了？是权重问题还是配置问题？下次发布前要加什么检查？每个答案都藏在证据里。

这也是本章开头那道判断题在决策层的投影：指标空结果时执行回滚，可能是拦住了坏版本，也可能是替采集故障背了锅——没有 evidence，事后分不开这两种情形。

把同一件事的两种写法摆在一起。能通过校验的：

```json
{
  "action": "rollback",
  "reason": "canary 业务路径 10 请求 6 个 500，远超 1% 阈值；稳定版同窗口 0.2%",
  "evidence": [
    "analysis business-path-check: 6/10 HTTP 500",
    "stable error rate 0.2% in same window"
  ],
  "patch_ref": ""
}
```

通不过的，只需把 evidence 换成空列表——同样的 action、同样具体的 reason、同样急迫的现场，校验器一律拒。两条记录在事故当时看起来没有差别，差别在四周后的复盘会上：前者能回答"当时凭什么回"，后者只能回答"当时很慌"。

回滚还有容易被忽略的另一半：在途请求。停止新流量后，已经在候选版本上生成的请求仍占用着 KV；可以等待完成，也可以按预算取消，两种行为都需要记录。路由回到稳定版并不会自动清空候选引擎的活动请求。排空完成后再缩容，确认工作组、设备声明、缓存和临时数据按策略回收；若新制品改变了存储或外部状态格式，还要事先确认旧版本能否读取——镜像回退不覆盖所有副作用。

### fail-closed：校验器永不执行修复

<Term id="agent" context="这里的 Agent 是辅助收集证据、提出补丁和运行检查的程序；发布权限与验收规则仍需明确约束。" /> 可以把错误日志关联到源码，生成修复建议，编写补丁并运行测试——但它的输出到这里只是一份提案。提案进入执行之前，要过一道独立的校验。本库的校验器 `labs/rollouts/validate_decision.py` 全文 13 行，核心是这 8 行（第 3–10 行）：

```python
def validate(value):
 if not isinstance(value,dict) or set(value)!={'action','reason','evidence','patch_ref'}:raise ValueError('Unexpected decision schema')
 if value['action'] not in ['hold','rollback','propose_fix']:raise ValueError('Unsupported action')
 if not isinstance(value['reason'],str) or not value['reason'].strip():raise ValueError('Missing reason')
 if not isinstance(value['evidence'],list) or not value['evidence'] or not all(isinstance(x,str) and x.strip() for x in value['evidence']):raise ValueError('Missing evidence')
 if not isinstance(value['patch_ref'],str):raise ValueError('Invalid patch reference')
 if value['action']=='propose_fix' and not value['patch_ref'].strip():raise ValueError('A fix proposal needs a reviewable patch reference')
 return value
```

逐行看每一行在堵哪个洞：

- 第 4 行，schema 封闭：字段集合必须恰好等于四字段，多一个（比如夹带 `execute`）直接拒。这不是洁癖——一份能顺手夹带执行动作的决策记录，迟早会被夹带。
- 第 5 行，动作封闭名单：`deploy` 不在其中。校验器的世界里没有"直接部署"，部署必须走完整的发布流程。
- 第 6 行，reason 必须是非空字符串：没有任何叙述的决策无法被人事后理解。
- 第 7 行，evidence 必须是非空列表，且每条是非空白字符串。空列表、空串、纯空白串，全部拒——上一小节论证的"为什么"，落在这里就是一行条件。
- 第 8–9 行，patch_ref 必须是字符串；propose_fix 时还必须非空。"我要修复"却不给出可审查的补丁，等于让审查落空。
- 第 10 行，`return value` 原样返回：校验器对通过者的全部动作就是放行——不改写、不补全、不执行。

CLI 入口（第 11–13 行）把"拒"变成流程上的停止：任何 ValueError 都打印 `HOLD:` 原因并以退出码 1 结束，调用它的流水线在这里停下。这就是 fail-closed 的字面语义——校验失败时系统关死，而不是敞开。放行名单里最激进的动作是 propose_fix：提议修复。连它也不执行修复，只保证提议带上了可审查的补丁引用。执行修复要走另一条路：审查、测试、候选发布、重新分析——原路再走一遍。缺失指标、测试失败或无法确认影响范围时，流程停在明确状态；无限重试和自动放宽阈值会掩盖问题，不算自愈。

### 制品身份贯穿发布

回滚的完整语义是：回到"已验证的制品加配置"。不是"把代码改回去"，也不是"重启一下"。<a href={asset('read/artifacts/')}>artifacts 章</a>讲过，权重 revision、tokenizer、镜像 digest、配置共同构成一次发布的身份——所以发布系统必须始终知道"当前稳定版是哪组制品"，否则 rollback 这个 action 没有落点。

配置是制品身份的一等公民。本章代码走读会看到，连 `FAIL` 和 `LATENCY_SECONDS` 这样的故障注入开关也是部署清单的一部分：改清单就是改行为。把期望状态保存在版本控制里、由控制器把集群向声明收敛（修复通过 PR、审核与合并改变声明，而不是直接改集群），是这套做法的名字——GitOps。它和四字段决策是同一原则的两面：任何改变都有可复查的身份与理由。

## 代码走读：一个可控的坏版本

### app.py：健康，但坏

`labs/rollouts/app.py` 全文 11 行，没有模型、没有 GPU；Dockerfile 只是把 python:3.12.11-alpine 加上这一个文件。核心是 Handler 类（第 4–10 行）：

```python
class Handler(BaseHTTPRequestHandler):
 def do_GET(self):
  if self.path=='/health':status=200
  else:
   time.sleep(float(os.getenv('LATENCY_SECONDS','0')))
   status=500 if os.getenv('FAIL','false')=='true' else 200
  self.send_response(status);self.end_headers();self.wfile.write(str(status).encode())
```

三条路径，三条语义：

- `/health` 永远 200：readiness 探针看到的是"进程活着"。
- 其他路径先睡 `LATENCY_SECONDS` 秒：延迟注入，模拟"慢但不错"的候选版本。
- 然后看 `FAIL`：为 true 时业务路径一律 500——"活着但坏"。

两个开关都是环境变量：故障可以从清单里注入，也可以从清单里撤掉。这正是"配置是制品身份一部分"的最小示范。

为什么要造一个假服务，而不是拿真模型注入故障？因为要验证的是发布与决策这条链——分析能否发现业务路径失败、放量能否停止、决策能否通过校验——而不是模型本身。用真模型做这件事，每次实验都要烧 GPU 加载几十亿参数，故障注入还得想办法可靠地"只坏质量不崩进程"；这个假服务把"进程活着但业务失败"做成两个环境变量，测试就能在任何 CPU 上、几秒内制造判例。

判例本身记录在 `tests/test_rollouts.py` 的 FixtureTest（第 16–30 行）：以 `FAIL=true` 启动 app.py，先轮询 `/health` 直到 200——这是发布系统眼中的"副本就绪"；再请求业务路径，断言抛出 500。健康 200 而业务 500，两条路径在同一个进程里分道扬镳：本章开头第一种典型失败的机器复刻。

### render.py：渲染一份渐进交付清单

`labs/rollouts/render.py` 不部署集群，只打印一份 JSON 清单（`kind: List`）——期望状态的声明。给它一个镜像名，它输出四段：

第一段，命名空间与两个 Service（第 19–21 行）：`fixture-stable` 与 `fixture-canary`，两个 Service 的 selector 完全相同（`app: fixture`）。这是刻意声明出来的近似：没有真正的按权重路由器，stable 与 canary 两条 Service 只是名字分开，请求实际打到哪个副本由副本比例近似决定——文件 docstring 自己写明"replica proportions only approximate request distribution"。教学清单不假装自己有它没有的保证，这条边界声明本身就是清单的一部分。

第二段，AnalysisTemplate（第 22 行）：`business-path-check`。它起一个一次性 Job 运行 probe 脚本（第 7–17 行）——连续 10 次请求 `http://fixture-canary:8000/`。注意请求的是业务路径 `/`，不是 `/health`：分析探的就是业务质量，探活探不来这个。probe 统计成功数，达到 9 个以上以退出码 0 通过，否则退出码 1 判失败；配合 `failureLimit: 0`，一次分析失败就中止放量。10 个样本、9 个成功——"最少样本加失败阈值"这两个分析要素，在这里是两个具体的数字。

第三段，Rollout（第 23–26 行）：5 个副本，`revisionHistoryLimit: 2`，canary 策略引用两条 Service，四步走：

```text
setWeight 20   →  5 个副本里 1 个换成新镜像（近似 20% 流量）
analysis       →  跑 business-path-check，失败即中止
pause          →  人工暂停：空的 pause 块表示"等人来决定"
setWeight 100  →  全量
```

第四段藏在容器定义里：新镜像带着 `FAIL=false`、`LATENCY_SECONDS=0` 部署——坏不坏由清单控制。readinessProbe 只查 `/health`，所以哪怕把 FAIL 改成 true，副本照样 Ready、照样被 Service 选中分流；能拦住它的只有 analysis 那一步。这份清单把"健康检查守不住业务质量"写成了可运行的证明：改一个环境变量，看分析门在第几步拦住发布。

边界要说清：这套清单在本库没有对真实集群运行过（见文末验证说明）。决策链的 CPU 部分——app.py 的健康但坏、validate_decision 的 fail-closed——由测试覆盖；集群侧语义（副本比例怎样近似流量、Service 后端怎样切换、排空行为）以 Argo Rollouts 文档为准。

## 动手：三组证据，三个决策

对下面每组观测，写出完整的四字段决策，并预言 `validate_decision.py` 会放行还是拒绝。先全部写下自己的答案，再展开核对。写完可以直接用 CLI 验证：

```bash
echo '{"action":"rollback","reason":"...","evidence":["..."],"patch_ref":""}' | python labs/rollouts/validate_decision.py
```

放行时原样打印决策 JSON；拒绝时 stderr 打印 `HOLD:` 加原因，退出码 1。

组一：setWeight 20 之后。

```text
canary 业务路径 10 个请求：6 个返回 500
稳定版同窗口错误率 0.2%
TTFT p99 两边接近（940 ms 对 955 ms）
analysis 已判定 Failed（failureLimit 0 被触发）
```

组二：指标查询返回空。

```text
canary 的指标查询返回空序列（0 个样本）
监控目标页：canary 的 scrape 目标 down
稳定版指标正常；服务本身同窗口无告警
```

组三：Agent 的修复提案。

```text
action:    propose_fix
reason:    "疑似调度配置不匹配，长输入挤压短请求"
evidence:  []
patch_ref: ""
```

<details>
<summary>展开核对</summary>

组一：rollback。evidence 放可复查的事实，例如 `['canary business path 6/10 HTTP 500', 'stable error rate 0.2% same window', 'analysis business-path-check Failed']`；patch_ref 留空——回滚不携带补丁。校验放行。注意校验器只检查"有据"，不检查"回滚是否最优"：最优与否是分析门和人的事，四字段管的是这条决策能不能被复查。

组二：hold，而不是 rollback。这是本章开头判断题的实操版：0 个样本不是"0% 错误率"，是没有证据。此刻支持回滚的解释（候选坏）与反对的解释（观测坏——scrape 目标 down 时，空结果可能只是采集故障）同时成立，分不开。hold 的 evidence 写 `['canary metrics query returned empty', 'scrape target for canary down']`——证据链恰好说清"为什么只是暂停"：先修观测，再重跑分析。校验放行 hold；此时若写 rollback 同样会放行，但那是用动作代替判断：回滚会掩盖采集故障，而第二天同样的问题还会再来一次。

组三：两处拒绝。第一处：evidence 是空列表，第 7 行抛 `Missing evidence`——"疑似"不是证据。补上 `['analysis job log: timeouts on long inputs', 'stable/canary scheduling config diff']` 之后还有第二处：propose_fix 而 patch_ref 为空，第 9 行抛 `A fix proposal needs a reviewable patch reference`。要过校验，Agent 必须给出可审查的补丁引用，例如 `branch/fix-scheduling-config`。放行也只是放行：validate 原样返回提案，没有任何一行代码去检出那个分支、跑测试或部署——执行要走审查、测试、候选发布、重新分析的原路。

三组合起来就是本章的判例表：有据的撤回放行，无据的观望也放行（hold 本来就是合法动作），无据的修复关死。
