诊断发现新版本使用了不合适的调度配置，导致长输入挤压短请求。现在需要恢复服务，同时保留能解释问题的证据。一次可靠交付管理的是完整行为：权重、tokenizer、镜像、配置与路由共同决定用户拿到什么结果。

## 先定义候选版本的边界

候选版本必须有独立、完整、可服务的运行实例或工作组。不能让同一个 TP 组的部分 rank 加载新权重、另一部分保留旧权重，再期待路由层解决问题。模型内部一致性与服务版本分流是两个层次。

<Term id="canary" /> 将少量代表性流量送到候选版本，比较错误、延迟、资源与质量，再逐步扩大比例。若只把最短、最容易的请求送过去，会得出偏乐观结论。需要按业务、长度与负载分层比较，避免流量组成不同造成误判。

## 成功、失败、无数据要分开

设目标是候选的错误率不高于 1%，且 TTFT 不显著恶化。只观察 5 个请求全部成功，证据仍很弱；指标查询返回空值，更不能按 0 错误处理。分析应设置最少样本、观察窗口、失败阈值和不确定处理。[Argo Rollouts 分析机制](https://argoproj.github.io/argo-rollouts/features/analysis/)

质量回归也要参与。结构化 JSON 是否能解析、必要字段是否正确、固定任务集是否退化，往往比 HTTP 200 更接近业务成功。随机生成存在波动，应保留重复评估与明确判定规则。

## 回滚时，旧请求怎么办

停止新流量后，已在候选版本生成的请求仍可能继续占用 KV。可以等待完成，也可以按预算取消；两种行为都需要记录。路由回到稳定版并不自动清空候选引擎的活动请求。

排空完成后再缩容，检查工作组、设备声明、缓存和临时数据是否按策略回收。若新制品改变了存储或外部状态格式，还需事先确认旧版本能否读取，不能认为镜像回退覆盖了所有副作用。

## Agent 可以参与哪些步骤

<Term id="agent" context="这里的 Agent 是辅助收集证据、提出补丁和运行检查的程序；发布权限与验收规则仍需明确约束。" /> 可以把错误日志关联到源码，形成修复建议，编写补丁并运行测试。但“服务暂时恢复”不能证明补丁正确，自动生成的解释也需要可追溯证据。

本库的修复流程保留审查、测试、候选发布和重新分析。缺失指标、测试失败或无法确认影响范围时，流程应停在明确状态。无限重试和自动放宽阈值会掩盖问题，不能算作自愈。

## 用故障演练证明发布流程

准备稳定版与可控失败的候选版，先验证路由确实到达两者，再注入已知错误或延迟。检查分析能进入失败状态、候选停止接流量、稳定版恢复，并验证正在运行的请求按既定策略结束。最后确认旧资源被清理。

另一轮故意让指标源无数据，结果应是暂停或不确定，而不是成功放量。再做一次质量失败但 HTTP 正常的场景，确认评估门能拦住。配套 CPU 状态机测试只能验证决策逻辑；真实路由与集群演练仍需要实际执行。

发布的最终报告应写清变更身份、比较条件、样本、判定、回滚用时及遗留问题。下一章把同样的证据意识用于容量与成本规划。
