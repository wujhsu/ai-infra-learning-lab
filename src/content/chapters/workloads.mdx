主线始终围绕语言模型，因为它能把计算、训练、缓存、通信与服务串成一条完整路径。现在尝试迁移：一个图像分类服务是否也需要不断增长的 KV？一个扩散模型是不是每次输出一个 token？如果答案仍然只是套用 LLM 术语，就需要重新画数据流。

## 不变的是数据、计算与状态

对任何负载，都先问：输入如何编码，参数在哪里，临时数据多大，一次输出需要哪些重复步骤，哪些状态可复用，哪个指标代表业务成功。这些问题比项目名称更稳定。

| 负载 | 典型执行单位 | 主要变化因素 | 不宜直接套用的 LLM 结论 |
|---|---|---|---|
| 图像分类 | 一批图像的一次前向 | 分辨率、预处理、模型结构 | 不必逐 token Decode，也未必有历史 KV |
| 视觉语言模型 | 图像编码与文本生成 | 图像数、分辨率、视觉表示长度 | 文本 token 数未必覆盖全部计算成本 |
| 扩散生成 | 多轮去噪状态更新 | 分辨率、步数、采样器 | 迭代状态不等同于追加 token 的 KV |
| 推荐 | 特征查询与打分 | 稀疏表容量、访问分布、候选数 | 权重读取与跨节点特征通信可能占主导 |

这张表描述常见机制，不覆盖每一种架构。遇到新模型，应先查它实际的前向过程。

## 视觉：预处理也在服务链里

图像从压缩字节到张量，需要解码、缩放和归一化。模型输入可能是 `[批次,通道,高度,宽度]`，算子可以是卷积或视觉 Attention。增加分辨率改变激活与计算，不只是多传几个网络字节。

因此，图像服务也应拆开输入处理、主机到设备搬运、模型执行与后处理。缓存可以复用预处理或特征，但必须固定图像内容、变换配置与模型版本。分类质量用准确率等任务指标，不能用输出 token/s 衡量。

## 多模态：一条请求包含不同成本段

视觉语言模型往往先把图像变成模型可使用的表示，再与文字共同参与后续计算。即使两条请求文本长度相同，图像数量和分辨率也可能让 Prefill 成本相差很大。

跨请求复用时，除了文本 ID，还需要把图像身份、编码器版本与处理配置纳入依赖。调度预算需要理解实际视觉表示与执行阶段。是否缓存编码结果、是否共享文本 KV、是否拆分编码实例，都是可独立测量的问题。[vLLM 多模态输入](https://docs.vllm.ai/en/latest/features/multimodal_inputs/)

## 扩散：重复执行的是去噪过程

扩散生成通常从噪声状态出发，多次运行模型，按调度规则更新状态，最后解码成图像等结果。时间步是算法状态，不是自然语言位置。减少步骤可能提速，但会影响输出质量或要求特定模型与采样方法。

可以复用的文本条件、模型权重和中间数据需要分别判断。不要把某种实验性特征缓存直接视为数学上完全等价。对照应同时记录分辨率、步数、随机种子、采样方法、延迟、显存与质量。[Diffusers 原理与组件](https://huggingface.co/docs/diffusers/using-diffusers/write_own_pipeline)

## 推荐：大表与不均匀访问

推荐模型经常通过 ID 查询大量 Embedding 表，再组合稠密特征进行排序。这与第一阶段的词向量查表有共同基础，但词表规模、访问模式与分片压力不同。热门 ID 与长尾 ID 的访问分布会影响缓存命中和负载均衡。

表分片可以省单机容量，也会引入查询路由与跨设备通信。增加 GPU 算力未必解决内存、网络或特征新鲜度瓶颈。训练与在线服务还要保证特征定义一致。[TorchRec 官方介绍](https://docs.pytorch.org/torchrec/)

## 用一个新问题结束主线

现在接到任务：“部署一个接收两张图片并生成中文说明的服务。”先画输入解码、视觉编码、文本生成、输出四段；为每段标注输入形状、状态、存储和计时点；再决定批处理、缓存与扩容单位。不要先列一串熟悉的软件名。

你应能给出最小实现、基线、瓶颈假设、优化对照、部署与恢复方式，并说明没有验证的部分。五个项目分别训练这些能力。阅读结束不是掌握证明；能修改实现、解释新输入下的行为，并用证据处理异常，才是本库的实践终点。
