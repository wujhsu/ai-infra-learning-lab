三十八章走完，主线只剩最后一个问题：把这些章拆开时你都答得上来，合在一起还答得上来吗？一个真实系统里，分词、调度、KV 分配、量化、观测、计费是在**同一条请求**上同时发生的——单独每章的账你都会算，现在要沿一条请求和一次训练把它们连起来算。这是终章复盘，不引入任何新机制；它的价值全在"串联"，引用的每个数字都来自前面的章节。

本章的结构对应它的四件事：两条"一生"（请求与训练）各一节，把散落各章的账按时间线重排成两张总表；一节讲负载形态怎样决定哪本账最重要——那是"经验是否仍然成立"的边界问题；最后一节给检验标准与继续路径，动手环节只留一道综合三种负载的终局练习。

## 这一章解决什么问题

先数一数手上有过什么。五个项目是一条递进的弧线：

- **项目一（极小模型实验室）**：亲手实现并训练一个 7 token 的两层模型——计算、复用与学习循环从此不是黑箱；
- **项目二（单机训练与微调）**：让数据、显存与恢复形成可靠流程，显存账从 16 字节/参数算起；
- **项目三（分布式训练）**：多卡通信、分片与故障恢复，扩展效率有了解释框架；
- **项目四（推理性能实验室）**：部署、测量并理解一个完整服务，从 TTFT 分解到缓存与投机解码；
- **项目五（AI 平台综合项目）**：把训练任务和推理服务纳入同一资源体系——准入、设备、观测、发布与成本。

但项目与章节都是**纵切**的：每章深挖一个机制。真实负载是**横切**的：一条请求同时压在五个机制上，一个配置改动同时改写几本账。终章要补的正是这个维度——

1. **一条请求的一生**：从 tokenize 到计费，九个站点逐站对账，每站挂回它所属的章与核心数字；
2. **一次训练的一生**：从数据到发布回滚，同样格式串第二遍；
3. **负载形态怎样改变设计**：长上下文、高并发短请求、离线批处理各压哪一环；
4. **检验标准**：15 个不看正文应当能回答的问题，以及读完之后的下一条路。

复盘不是复习。复习检验记忆，复盘检验的是**接力能力**：上一站的输出怎样变成下一站的输入，一本账的改动怎样波及另一本。章首那个问题——图文请求文本长度相同、处理成本为什么不同——正是接力能力的试金石：你必须先知道"成本由哪些站构成"，才能指出哪一站被图像改变了。

因此本章的用法和前面的章不同：它没有新的 Lab，两张总表就是教具。建议的读法有三步——先通读两条"一生"，把每站挂回你还记得的机制；再遮住表格的"关键账"一列自测；最后带着第④节的负载视角重读一遍，体会同一站在不同负载下权重的升降。文中引用的所有数字都是各章的教学算例，不是实测成绩；它们的用途是让"哪一站大概什么量级"有据可依，替换成你自己的负载数字后，这套框架就是你的容量规划草稿。

两条时间线也能挂回五个项目，看清楚每个项目在整条弧上的位置：项目一给的是**心智模型**——两条线上的每一站，拆到最小都是那个 7 token 模型里的张量与循环；项目二、项目三走的是训练的一生（单机账到分布式账）；项目四走的是请求的一生（从部署到投机解码）；项目五把两条线汇进同一个资源体系，并补上观测、发布与成本这最后三站。终点回到起点的含义正在于此：最后你用来分析真实系统的每一个抽象，都是第一周亲手写过的某行代码的放大。

最后交代本章的证据边界，与 frontmatter 的验证声明一致：这是综合复盘，无新增实验。引用的数字里，一部分来自 CPU 上已测的实验（极小模型、流式客户端、取消脚本、清单与回滚逻辑），一部分是各章明确标注的教学算例（服务端毫秒、KV 字节、投机与缓存账），还有一部分涉及 GPU 与集群、本环境从未运行。复盘不产生新证据，它重组旧证据——所以每笔账都标了出处章，你可以随时回查它的假设条件。

## 复盘：一条请求的一生

用户按下回车。一条请求从进入服务到被计费，要经过九个站点。先把整条线走一遍，再对总表。

在九站之前还有个第零站，它不耗时却决定一切数字的意义：服务启动时被钉死的身份——模型 revision（40 位提交哈希）与镜像 digest。身份没钉死，后面每一站的毫秒都无从比较。

**第①站，输入处理。** 聊天模板拼接消息，<Term id="tokenizer"/> 把文字转成 token ID。这一步有两个来自前文的结论：其一，同一个 token ID 查同一张嵌入表，初始向量必然相同——让表示不同的是位置处理与上下文计算（<a href={asset('read/representations/')}>representations 章</a>）；其二，可见字数与 token 数不是一回事，多轮历史把输入撑过 `max-model-len`（本服务线固定 4096）时请求直接被拒（<a href={asset('read/serving/')}>serving 章</a>）。

**第②站，调度与排队。** 请求进入引擎，等批次位置与 KV 预算。排队是时间线里唯一随负载自由伸缩的项：并发翻倍、TTFT 涨了而 prefill 与 decode 耗时不变时，涨幅几乎全在排队（<a href={asset('read/scheduler/')}>scheduler 章</a>）。连续批处理在迭代边界补位：同一算例里请求 C 在连续批下等 1 步进场，静态批下等 4 步。

**第③站，KV 分配。** 引擎按块给这条请求划显存。按 Qwen3-0.6B 的结构（28 层、8 个 KV 头、头宽 128、fp16），每 token <Term id="kv-cache"/> 是 112 KiB——GQA 把无分组时的 224 KiB 砍了一半；块取 16 token 即 1.75 MiB。同一个 2 GiB 的池，连续预留只装得下 4 条，分页装得下 18 条（<a href={asset('read/kv-allocation/')}>kv-allocation 章</a>）。

**第④站，prefill 与 decode。** <Term id="prefill"/> 一次处理整段输入并交付第一个新 token；此后 <Term id="decode"/> 每轮只推进一个新位置。首字时间因此分解为 `queue + prefill + network`——serving 章的算例是 40 + 180 + 20 = 240 ms——总时长再叠 <Term id="tpot"/> × (tokens − 1)。

**第⑤站，缓存。** 如果下一条请求以同一段系统说明开头，<Term id="prefix-cache"/> 让它免于重算：cache-hierarchy 章的算例里，重算 4,000 token 花 1,000 ms、命中加载只要 520 ms，省 480 ms；但有效带宽低于约 4 GB/s 时，命中反而比重算更慢。

**第⑥站，量化与投机。** 引擎可能用量化压每个数的成本，用投机解码改执行结构。W4A16 只把权重主体压到四分之一，KV、尺度与工作区不跟着缩；投机解码在 γ=0.7、k=4 时期望每轮 2.77 个 token，γ 跌到 0.3 反而比串行慢 26%。

**第⑦站，SSE 返回。** 增量以 <Term id="sse"/> 事件写回。一个事件可以没有文本、也可以一次携带多个 token——测试里"1 个 chunk、7 个 token"可以是同一次请求；token 数只认服务端 usage。

**第⑧站，观测。** 客户端与服务端的指标按请求标识对齐成跨组件 Trace。两个纪律：p99 不能对每个实例求平均得到服务的 p99（<a href={asset('read/observability/')}>observability 章</a>）；平均 40 ms 的流里可以藏着一次 500 ms 的停顿，要看 <Term id="itl"/> 的分布而不是均值。

**第⑨站，计费与容量。** 这条请求最终折进成本账：Little 定律 L=λW 估在途（20 个在途不等于 GPU 每轮处理 20 个 token）；4 单位/小时产出 72 万个合格 token，约折 5.56 单位/百万 token（<a href={asset('read/economics/')}>economics 章</a>）。SLO 在这一站从工程指标变成容量与商务承诺：分位数写清请求范围、时间窗口与成功条件，容量结论才可迁移。

九站是 serving 章那张五站流水线的细分版：那里的①输入处理、②调度排队、③前向计算、④输出处理、⑤网络协议，在这里展开成了 tokenize、KV 承诺、缓存、量化投机与观测计费——终点章把中途每一章的成果插回它当年被抽象掉的槽位。九站排成一张总表。**读法：先遮住"关键账"一列，沿站点自问每站的核心数字，再对照。**

| 站点 | 对应章 | 关键账 |
|---|---|---|
| ① tokenize | representations、serving | 同 ID 同初始向量，上下文再改表示；可见字数 ≠ token 数，超 4096 上限直接拒 |
| ② 调度与排队 | scheduler | 排队是唯一随负载自由伸缩的项；连续批补位 C 等 1 步、静态批等 4 步；队头阻塞让 2 秒的工作等 40 倍 |
| ③ KV 分配 | kv-allocation | 每 token 112 KiB（GQA 自 224 砍半）；块 16 token = 1.75 MiB；同一 2 GiB 池，连续预留 4 条、分页 18 条 |

| ⑥ 量化与投机 | quantization、speculative-pd | W4A16 只压权重主体，KV 与尺度不跟缩；γ=0.7、k=4 期望每轮 2.77 token，γ=0.3 慢 26% |

三个接力点值得单独点破，因为它们跨了表的行：

- **接纳即承诺。** 第②站与第③站不能分开想：调度器接纳一条请求，就是当场承诺它的 KV 上限。GPU 利用率低、块池却满时，加并发没有用——瓶颈在承诺，不在计算。
- **命中不救 decode。** 第⑤站省的只是 prefill 的重复计算；decode 每一步仍要读全部可见历史的 K/V，前缀缓存一格都省不掉。缓存把账推迟到生成阶段，不取消它。
- **优化要组合后重算。** 第⑥站内部：KV 每元素从 2 字节降到 1 字节，PD 分离的传输账（该章示例：8192 token × 128 KiB = 1 GiB，25 GiB/s 下下界 40 ms）直接减半到 20 ms——两个优化的收益相加没有意义，要合起来重算。
- **口径贯穿九站。** 客户端还是服务端的 TTFT、chunk 还是 token、单实例还是服务的 p95——每一段边界不写清，跨站的加减法就都白做。这不是第⑧站独有的要求：从第①站"可见字数与 token 数不是一回事"起，这条纪律就在每一站重复自己。

### 沿九站倒查一次故障

总表除了正着读，还可以倒着用。给一个综合诊断的样例：某次配置变更后，p95 TTFT 从 240 ms 涨到 600 ms，吞吐不变。沿站倒查的顺序是：

1. **第⑧站先钉口径。** 600 ms 是客户端还是服务端口径？分位数怎样聚合的？两个口径混用会让后续所有比较失真。
2. **服务端口径也涨，进入第②站。** 看等待队列深度与调度延迟是否同涨。若模型每步耗时没变、队列深度翻倍，涨幅在排队。
3. **排队涨了，进第③站问承诺。** 这次变更把 `max-model-len` 从 4096 调到了 8192：每条请求的 KV 承诺翻倍，同一块池能接纳的请求数减半——GPU 利用率一个点没动，排队却上去了。这正是"GPU 闲、池满，瓶颈在承诺"的实测形态。
4. **若队列没涨，才轮到第④⑤⑥站**：输入分布是否变长（prefill 变重）、命中率是否下降（缓存身份变了）、新精度是否改变每步耗时。

注意这次故障里没有任何 kernel 变慢、没有任何硬件变化——变的只是一行配置写进承诺账的数字。九站总表的价值就在这里：它把"服务变慢了"这句模糊的话，变成"哪一站的哪本账变了"的可检验问题。这套"先定位、再深挖"的倒查次序，就是 diagnostics 章三个性能故障的方法论在推理线上的复用——那里对分布式训练的要求，同样是先比较所有证据再下结论，而不是抓住最先出现的报错。

## 复盘：一次训练的一生

同一个夜里，另一个进程在跑：一次微调训练。它的一生同样按站点对账，读法与上一节相同——先沿叙事走一遍，再对总表，最后盯着"接力点"看跨行的联动。与请求线不同的是，训练线的时间尺度以小时和天计，中途还要跨越"进程死亡"这道坎，所以检查点与恢复在这里的分量，相当于请求线里的取消与回收。

**数据与流水线。** 样本从存储到 GPU 要经过 Dataset、worker、预取缓冲、固定页内存。data-pipeline 章的三数法：只读数据 25 样本/s、纯计算 40 样本/s，端到端被拉到接近 25——数据侧的改进只在"准备时间超过计算时间"时才直接兑换成吞吐；情形二与情形三差出的约 100 s，恰好是 1,000 步 × 每步空转 100 ms，一行乘法。

**单机显存账。** 混合精度 AdamW 下每参数 16 字节：fp16 权重 2 + fp16 梯度 2 + fp32 主副本 4 + 一阶动量 4 + 二阶动量 4。0.6B 的模型训练态约 23.3 GB，是推理权重 1.2 GB 的约 19 倍；batch 8 × 序列 1024 的激活另计 13.7 GB，其中注意力分数约占每 token 元素的 47%。显存曲线呈锯齿状：锯齿的底由 16 字节/参数决定，高度由 batch × 序列决定。

**数据并行与状态分片。** DDP 的第一问不是快不快，而是"两卡是否真的各见一半样本"——两卡吞吐更高但用了同一批样本，就是重复计算，有效样本量没有扩展。各 rank 局部平均后直接再平均也不等于全局平均：1 条与 3 条样本的两个 rank 必须按样本数加权。状态装不下时换 FSDP 分片，但分片描述的是常驻状态：计算时临时 <Term id="allgather"/> 出完整参数，加上预取组、激活与通信缓冲，峰值仍可能明显大于总状态的四分之一。

**通信重叠。** 把通信和计算放进两个 stream 只是提供调度机会，不自动建立依赖、不保证收益——消费者必须等到它的数据可用，还要核对跨流可见性。通信形态也分层：每层都通信的模型与只在阶段边界通信的模型，同样的跨机带宽下扩展效果可以完全不同。

**检查点。** 一份检查点要装下参数、优化器状态、步数、随机状态与数据进度——缺一项，恢复后的轨迹就与未中断基线分叉。两个纪律直接来自前文：模型重新加载后能生成相同文字，不等于能从中断处正确继续训练；写了一半的截断文件"存在"但"不是任何时刻的模型"。微调用 <Term id="lora"/> 时，r=16、d=4096 只训 2r/d = 1/128 ≈ 0.78% 的参数，每层适配器约 256 KiB 对 32 MiB——省的是状态与制品，不省执行。

**制品。** 只保存容器 tag 和模型名称仍可能无法复现：需要模型 revision（40 位提交哈希）、镜像 digest、tokenizer、数据与评估身份，且三者不可互相替代。

**平台调度。** 空闲 GPU 总数足够，四卡训练仍可能无法开始——配额、整体准入、设备类型、拓扑与节点可达性任何一项都能挡住它。进了集群还有一层：Job 配置自动重试不等于训练恢复，重试只重建执行；程序必须加载一致检查点、优化器与数据进度，否则重新开始或产生不同轨迹。设备侧同理：ResourceClaim 已分配不等于容器已可用；四卡工作组里一个 worker 失败、三卡进程还活着，也不等于服务健康。扩容同样不是立刻获得服务能力：新实例要排队拿设备、拉镜像、加载权重、预热，共需几分钟——只按"延迟已经恶化"才扩容，可能来不及接住短突发。

**发布回滚。** 训练产物变成服务变更后：灰度期间指标查询返回空结果，不能按错误率 0% 处理——缺少证据应进入暂停状态；回滚要处理在途请求的排空，而不是直接掐断。

| 流水线 | data-pipeline | num_workers／预取／pin_memory 展示管道位置，不承诺重叠；空转 100 ms × 1,000 步 = 100 s |
| 单机显存账 | training-memory | 16 字节/参数（2+2+4+4+4）；0.6B 训练态 ≈23.3 GB，为推理权重约 19 倍；激活 13.7 GB 随 batch×序列伸缩 |
| 数据并行 | ddp、collectives | 两卡同一批样本 = 重复计算；局部平均须按样本数加权，直接再平均让单样本 rank 权重过大 |
| 状态分片 | sharding、model-parallel | 分片后峰值仍可远超总状态的 1/4：AllGather 临时参数、预取组、激活与缓冲都在 |
| 通信重叠 | nccl、topology | 双 stream 只是调度机会，不建立依赖；频繁小消息受延迟限制，大消息接近带宽主导 |
| 检查点 | checkpoints-finetuning、tiny-training | 状态缺一项即续不上；能生成 ≠ 能继续训练；LoRA r=16 只训 0.78%，省状态不省执行 |
| 制品 | artifacts | tag + 模型名不足以复现；revision、镜像 digest、tokenizer、数据与评估身份缺一不可 |
| 平台调度 | scheduling、kubernetes、dra、lws | 空闲卡总数够仍可能起不来（配额/准入/拓扑）；Job 重试 ≠ 训练恢复；Claim 分配 ≠ 容器可用 |
| 发布回滚 | delivery | 灰度空结果 ≠ 0% 错误率，应进入暂停；回滚要排空在途请求 |

训练线同样有三个跨行的接力点：

- **显存账是分片的基数。** 16 字节/参数既是"第一次 `optimizer.step()` 时显存跳升"的机制根源，也是 FSDP"每张卡分到多少状态"的分子——不对齐精度布局就分片，账从第一步就是错的。
- **恢复要三层语义一致。** 检查点装下哪些状态、Job 怎样重试、加载路径读什么，三层缺一层，恢复就只是"重新开始"：kubernetes 章的重试、recovery 章的故障注入、tiny-training 的中断恢复实验，验证的是同一件事的三个切面。
- **扩展效率是比较条件下的结论。** "两卡 1.8 倍"必须连同样本分片方式、长度分布、硬件拓扑一起报告——ddp 章的重复计算陷阱说明，吞吐数字本身不证明扩展发生了。

训练线同样可以倒查。样例：一次微调从第 3 个 epoch 起"变慢"，每 step 时间涨了 40%。沿站点倒：先看数据站——流水线三个数里"只读数据"的速率是否随 epoch 下降（缓存失效、存储随机读放大是常见病因）；再看显存站——是否因碎片或累积的中间量让分配器开始走慢路径；然后看通信站——梯度里是否混进了不该同步的参数，让 AllReduce 的字节数悄悄变大；最后才怀疑硬件。与请求线一样，倒查的纪律是**先比较所有站的证据，再对最可疑的站深挖**——"所有 rank 都报超时，先别调超时参数"是同一条纪律在另一条线上的措辞。

两条"一生"合起来，才是项目五那句交付——"把训练任务和推理服务纳入同一资源体系"——的完整含义：训练的产物（带 revision 与 digest 的制品）是推理的第零站输入，推理的指标是发布回滚与成本账的证据；它们共享同一批 GPU、同一套准入与观测。

## 负载形态怎样改变设计

前面所有账都算在"某个负载"上。现在反过来：负载本身怎样决定哪本账最重要。三种典型形态，各压不同的环。为了把差异归因于负载本身，三种形态固定同一个模型（Qwen3-0.6B，每 token KV 112 KiB）与同一张 80 GiB 级的卡——变的只有输入输出分布、并发与到达模式、有没有 SLO。这三个量，就是"负载形态"的全部旋钮。

**长上下文：压 KV 与 decode 读取。** 一条 32,768 token 的分析或 Agent 请求，按每 token 112 KiB 仅 KV 就要约 3.5 GiB——同一张 80 GiB 级的卡按 kv-allocation 章的算法留给 KV 全部预算（约 46,811 块），4,096 上下文的请求每条 256 块、能装约 182 条并发；32,768 上下文每条 2,048 块、只剩约 22 条：同一道除法，长度换了数字。更深的账在 decode：每生成一个 token，注意力要读全部可见历史的 K/V，前缀缓存对这一格省不掉。100 个并发 Agent 会话各自再带几百 token 私有历史，每会话约 0.5 GB 就是 50 GB——单张 80 GB 的卡放不下模型加这笔账，会话缓存必须分层。长上下文还放大跨实例结构的传输账：PD 分离的 KV 交接随输入长度线性增长，与它消除的干扰赛跑。

**高并发短请求：压调度与块池。** 输入 500、输出 64 的交互请求，单条 KV 承诺不过几十 MiB，时间线的大头是排队——TTFT 由排队主导时，优化 prefill 或 kernel 都是错方向。并发从 8 提到 16 的那道预测题给出过完整推理链：客户端 16 条在飞不等于引擎 16 条在算，接纳控制在承诺处挡人，多出的请求全部落在等待里，p95 随并发线性抬升而吞吐封顶。这一形态下最锋利的几条结论都来自 scheduler 章：接纳一个请求等于承诺它的 KV 上限，GPU 利用率低、块池满时加并发只加等待；一条 200 ms 的长 prefill 插队，正在流式输出的请求全部停顿，所以要 chunked prefill；取消要走完客户端断开、引擎传递、块回收三层，只在成功分支写释放的系统，故障负载会逐渐耗光资源。SLO 要按分位数写（p95、p99），并写明客户端还是服务端口径。

**离线批处理：压吞吐经济性。** 海量语料、没有交互 SLO，延迟预算可以全部换成吞吐：大批连续调度让 GPU 一直忙，指标从 TTFT/p95 换成有效吞吐与每百万 token 成本——4 单位/小时产出 72 万合格 token 约折 5.56 单位/百万，产出减半单位成本就翻倍。这个形态下有些在线优化会反向：GPU 已被连续批处理喂饱时，投机解码的验证批次挤占的是真实请求的算力——它把闲置的串行延迟换成吞吐，不创造算力；量化则仍然划算，因为 decode 是访存受限工作，压权重直接压每步要搬的字节。

三种形态收进一张速查表，行是负载，列是"先动哪里、先别动哪里"：

| 负载 | 压的环 | 第一杠杆 | 先别急着做的事 |
|---|---|---|---|
| 长上下文 | KV 容量与 decode 读取 | 前缀缓存、KV 量化、分层换出 | 投机解码（开放分析类 γ 低） |
| 高并发短请求 | 调度与块池承诺 | 接纳策略＋chunked prefill | 一味加并发（池满时只加等待） |
| 离线批处理 | 吞吐经济性 | 大批连续调度＋有效吞吐口径 | PD 分离（没有交互延迟要保护） |

这张表的用法不是照抄，而是**先判断自己站在哪一行**。判断错的代价是双重的：在长上下文流量上抄了高并发的配置，会为不存在的排队做优化，而放任每条 3.5 GiB 的 KV 承诺把池子吃光；反过来，在交互流量上抄离线的配置，会为了吞吐牺牲 p95，SLO 先崩。判断依据都在前文的账里：输入输出分布、并发与到达模式、SLO 的有无——量出这三个量，行就选定了。

三种形态摆在一起，结论只有一句：**没有一种配置对所有负载最优。** cache-hierarchy 章的三种流量（短问答、Agent 平台、多租户）对应三套缓存所有权配置；speculative-pd 章的要求是"先选问题，再选组合"；economics 章的要求是把"在 A 条件下可支持 B"与"任何场景都能支持 B"严格分开。这也是本章标题的答案：经验仍然成立的是**方法**——画数据流、列账本、先测量再优化；会失效的是**数字**——112 KiB、480 ms、2.77 个 token 都只在它们被测量的条件下成立，换一种模型、换一种负载，第一件事是重新量，而不是套用。

这个答案也直接回应了章首那道图文问题。两条"文本长度相同"的请求，只是第①站的 token 数恰好相同；图像数量与分辨率改变的是视觉编码的 prefill 账、视觉表示拉长的是后续每一站的 KV 与读取账——成本从来不由某一站单独决定，而由九站各自被负载改写的程度共同决定。能这样逐站拆开回答，38 章的方法就迁移过去了；只会报一个"多模态更贵"的总量判断，则说明账还没有立起来。

## 学完的检验标准

15 个问题，每条来自一章的核心账。评分口径只有一条：能**独立**回答并给出数字或机制——翻书答对不算。答不出的那一章，值得回去读；全答对的话，你拥有的不是 38 个知识点，而是两条能随时展开的完整链路。

另外一个诚实的边界：这 15 条检验的是"理解"，项目验收检验的是"动手"。本库各章的验证声明里反复出现"GPU 未运行""集群未运行"——理解链路和在真实设备上复现链路之间还隔着环境、驱动与真实负载，这一步只能在项目里补。

1. 同一个模型，续写 5 个 token 与 50 个 token，会使用不同数量的参数吗？后者为什么通常更贵？（generation）
2. 输入 4 个位置、已输出 2 个新 token，但只把第一个新 token 送回模型处理——完整历史缓存包含几个位置？（kv-reuse）
3. 把后面新增的 token 改掉，会改变前面位置的因果注意力输出吗？如果没有因果遮罩呢？（attention）
4. 混合精度 AdamW 的 16 字节/参数由哪五项组成？为什么梯度累积救不了装不下的常驻项？（training-memory、tiny-training）
5. 增加 DataLoader worker 后吞吐不升反降，先测哪三个数再决定下一步？（data-pipeline）
6. LoRA 适配器文件很小，能单独启动一个完整模型服务吗？0.78% 这个比例省的是什么、不省什么？（checkpoints-finetuning）
7. 两个 rank 分别处理 1 条与 3 条样本，各自求平均再平均，等于对 4 条样本求平均吗？（collectives）
8. 两卡训练吞吐更高，但每张卡都用了同一批样本——实际发生了什么？该检查什么？（ddp）
9. 四卡分片后，峰值显存为什么仍可能明显大于总状态的四分之一？（sharding）
10. 把通信和计算放在两个 stream，足以证明它们正确并行了吗？（nccl）
11. 所有 rank 都报 NCCL 超时，下一步是调大超时时间吗？（recovery、diagnostics）
12. 健康接口正常但首个正文很慢，GPU 一定慢吗？TTFT 由哪几段相加，TPOT 为什么乘 (tokens−1)？（serving）
13. 两条请求共享 100 个前缀 token，一定省下 100 个 token 的 KV 字节吗？命中前缀缓存后，decode 为什么不一定变快？（kv-allocation、cache-hierarchy）
14. 单个请求更快，但高并发下 p95 更差，可能说明什么？取消要走完哪三层？（scheduler）
15. KV 传输要 40 ms、消除的干扰只有 10 ms，该分离吗？平均在途 20 个请求等于 GPU 每轮 20 个 token 吗？（speculative-pd、economics）

这 15 问刻意在两条线上各占一半：1–3 是模型与状态的底账，4–11 走训练的一生，12–15 走请求的一生。哪一半卡壳多，就回哪一半的项目重做验收——清单、总表与项目，三者指向同一套能力。

这 15 问的来历也交代一下：每条都是某一章 frontmatter 里那道思考题的变体，而每一章的思考题，又是该章要解释的现象的浓缩。所以这份清单其实是把 38 个"现象"按两条时间线重排了一遍——如果哪一问让你觉得"从没想过"，说明那一章你记住的是结论，不是它当初要解决的问题。

给自己一个粗略的分档：15 问里能带数字或机制完整答出 12 问以上，可以直奔项目验收；8 到 11 问，先回卡壳章的重做动手题，再进项目；不足 8 问，值得从项目一的重做开始——不是重读，是把当年跳过的动手环节补上。检验标准从来不是"读完"，而是"能独立复算"。

## 动手：终局练习

最后一道题不给新场景，给三种你已经算过每一环的负载——它考的正是"串联"：每份建议都要同时用到 KV 账、调度账与成本账，任何一份只靠某一章的知识都写不完整。设定：一张 80 GiB 级的卡，Qwen3-0.6B（权重约 1.2 GB，每 token KV 112 KiB，块 16 token），引擎可配 KV 池比例、块大小、前缀缓存、chunked prefill、量化、投机解码与 PD 分离。

为三种负载各写一份建议，每份三行：**资源配置**（KV 池比例、并发上限的粗账）、**优化优先级**（最多三项，按序）、**明确不做的事**（一件，附理由）。三种负载是：

- **A 长上下文分析**：输入约 32,000 token，输出约 500，同时在场约 10 条，TTFT 放宽到数秒；
- **B 高并发短请求**：输入约 500，输出 64，p95 TTFT 有 SLO，闭环并发 16 起；
- **C 离线批处理**：固定语料海量请求，无交互 SLO，按每百万 token 成本考核。

先写，再展开对照。写的时候给自己立三条规矩，它们都是前面章节反复出现过的纪律：

- **每个数字要有出处**：3.5 GiB 来自 32,768 × 112 KiB 的乘法，61 MiB 来自 (500+64) × 112 KiB——写出算式，不要写"大概几十 G"；
- **每项优先级要指回一张账**：说"先做前缀缓存"，就要说清省的是哪段时间（重算 8,000 ms 级）、付的是什么（块身份表与容量占用）；
- **"不做的事"必须有理由**：这条检验的是你能否识别收益条件不成立的优化，而不是知识面。

**A 长上下文分析。** 资源：每条 KV 约 3.5 GiB，10 条在场约 35 GB——KV 池比例给到 0.7 以上（80 × 0.7 = 56 GB，容纳 10 条 32k 请求与共享前缀仍宽裕），并发上限按"预算 ÷ 每条块数"那道除法设，宁可低于物理上限。优先级：①前缀缓存钉住共享的系统说明与分析模板（命中省的是 8,000 ms 级的重算，量级远超短请求场景）；②KV 量化或分层换出——每 token 从 112 KiB 压到 56 KiB，同一池并发翻倍；③验证取消与 END 的块回收（长请求被掐断的代价最大）。不做：投机解码——开放分析类输出接受率 γ 低，γ=0.3 时比串行还慢 26%；PD 分离先算传输账再议（32k 输入的 KV 交接是 4 GiB 级，没有高带宽互联时下界可观）。

**B 高并发短请求。** 资源：每条承诺约 (500+64) × 112 KiB ≈ 61 MiB，KV 池不用极大，瓶颈大概率在排队与调度而不是显存——按目标 p95 反推接纳上限，别按池子最大值设。优先级：①排队与接纳策略连同 SLO 一起定（GPU 闲、池满时加并发只加等待）；②chunked prefill 保护正在流式输出请求的 ITL（一条长 prefill 插队，全场停顿）；③取消三层与五种结束方式的回收验证（故障负载耗光块池是最常见的隐性故障）。不做：投机解码——高并发下 GPU 已被连续批处理喂饱，验证批次挤占的是真实请求的算力。

**C 离线批处理。** 资源：无 SLO，并发拉到块池除法允许的上限，让 batch 尽量大、GPU 一直忙；显存优先留给大 batch 的激活与 KV。优先级：①有效吞吐与每百万 token 成本作为唯一口径（分母必须扣掉失败与不合格 token）；②量化压 decode 的访存（decode 是访存受限工作，压权重直接压每步字节）；③前缀缓存仅当语料确有共同前缀才开——共同前缀占比低时，命中收益付不起块身份表的固定税。不做：PD 分离——它的收益是消除干扰、保护交互延迟，离线场景没有这项目标，只剩传输与协调的净支出。

三份建议放在一起看，正好是上一节的结论：同一张卡、同一个模型，资源配置与优化排序完全不同——能按负载写出这三行，38 章的账就真的串起来了。

如果写的时候发现某一行的账拿不准——比如 A 的 KV 量化后并发到底翻不翻倍、C 的共同前缀占比到底够不够付缓存税——那就回到对应章的动手题重做一遍。终局练习答不出的地方，就是这条 38 章路径上你真正的下一站。
