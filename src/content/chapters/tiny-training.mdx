现在已经有了两条完整的计算线：生成时，根据已有内容选下一项；<Term id="training"/> 时，根据目标计算损失，再用梯度更新参数。本章把它们放进同一个程序，串成一个真的训练循环，并且让这个循环能停下来、把状态存盘、再从中断处继续。

目标不是训练一个好用的聊天模型，而是让你能指着 `labs/tiny_model/train.py` 的每一行，说出它在循环里担任的角色，并用一次真实运行的数字验证它确实工作。这个规模足够在 CPU 上运行。

## 这一章解决什么问题

前五章各解决一段计算：怎么把文字变成 <Term id="token"/>、怎么让位置之间交换信息、怎么算<Term id="loss"/>、怎么求<Term id="gradient"/>、怎么让推理复用 KV。每一章都只动一段。真实的训练是把这些段落反复执行的过程，于是问题从“一次计算对不对”变成“一个循环对不对”：

- 循环的每一步读什么状态、写什么状态？
- 中途停掉再启动，怎么保证接下来的更新和从未中断时完全一样？
- 怎么证明“损失在降”不是恰好打印出来安慰你的？

项目 `labs/tiny_model` 用一个极小 Transformer 回答这三问：2 层、2 个注意力头、宽度 32、七项教学词表，随机初始化参数。训练数据固定为一句教学文本“北京是中国的首都。”再接结束标记。我们故意让模型反复学习这一个句子——这叫小样本过拟合检查：模型如果连一个极小样本都学不好，数据、目标或更新流程可能有问题；反过来，学会这个句子不证明它具备语言理解能力，也不构成独立验证集评估。

前面的章节用二维小矩阵手算；这里把表示扩大到 32 维、2 个注意力头、2 层，参数随机初始化。我们仍然沿着同样的数据流走，只是数值不再假定是手工填的 0 和 1。

证据是一次真实运行（macOS arm64，Python 3.12.14，torch 2.14.0，CPU，1 线程，2026-09-13），100 步把训练损失从 2.5985586643218994 降到 0.0008747270912863314，从提示 `[0,1,2,3]` 生成出 `[[0,1,2,3,4,5,6]]`，缓存与全量重算两种生成方式结果相同，5 项机制测试全部通过。本章的代码走读就对照这次运行展开，数字记录在 `docs/runs/tiny-model-cpu.json`。

## 训练循环总览

先用一张表把循环说清楚，再进代码。这个模型的数据是固定的——每次迭代都是同一句话——所以循环里没有“取下一批数据”这一步。这恰恰使它适合当教学基线：状态最少，每一项都能点名。真实训练里替换成“从数据加载器取下一批”，循环骨架不变。

| 阶段 | 读入 | 写出 | 说明 |
|---|---|---|---|
| ① 固定数据 | 词表 | `INPUT` / `TARGET` | 程序启动时执行一次，循环内不变 |
| ② forward | `INPUT`、参数 | <Term id="logits"/> | 一次前向，得 `[1,6,7]` 候选得分 |
| ③ loss | logits、`TARGET` | 一个数 | 6 个位置的交叉熵平均 |
| ④ backward | loss、计算图 | 每个参数的 `.grad` | 沿图反向应用链式法则 |
| ⑤ step | `.grad`、优化器状态 | 新参数、新优化器状态 | 参数真正改变的位置 |
| ⑥ 重复②–⑤ | — | — | 100 次 |
| ⑦ 保存 | 参数、优化器状态、步数、随机状态 | 检查点文件 | 循环结束后执行 |

表里有三个容易看漏的区分：

**forward 和 backward 都不改参数。** 前向算出“当前参数下有多错”，<Term id="backprop"/> 算出“每个参数微调一点会怎样”。真正把变化落到参数上的只有⑤的 `optimizer.step()`——整个循环里唯一一行修改参数的代码。把“算出梯度”和“完成更新”混为一谈，是初读训练代码最常见的错位。

**循环的状态分三份，寿命不同。** 参数由模型持有，跨步存活；梯度每步清零重算，只活一步；<Term id="optimizer"/> 状态（下一节的主题）跨步累积。一份状态属于“这一步”还是“跨步累积”，决定了它要不要进检查点：参数和优化器状态要存，梯度不用存。

**损失数字是“改之前”的。** 循环打印的第 N 步损失，是用第 N−1 步更新后的参数算出的，先报告再更新。读损失曲线时要知道每个点对应哪一刻的参数。

再把一圈摊开成状态变化，以从零开始的那次真实运行为例：

1. 循环前：参数是种子 7 下的随机初始化；所有 `.grad` 为空；AdamW 的矩为零。用这套参数先算一次损失，得 2.5985586643218994。
2. 第 1 圈：`train_step` 先清空 `.grad`（此时本来就没有），再前向、算损失、反向写出全部梯度、step 修改参数并更新矩。
3. 第 2–100 圈：同样三拍。参数和优化器状态逐圈演化；`.grad` 每圈以清零开始、以写满结束，从不满一圈。
4. 循环后：切到 eval，用训完的参数重算损失，得 0.0008747270912863314；再生成、存盘。

看清楚“谁跨圈存活、谁只活一圈”，下一节的检查点清单就不再需要背。

## 代码走读：train.py 从头到尾

两个文件分工明确：`labs/tiny_model/model.py` 定义计算（嵌入、注意力层、前馈、输出投影），`labs/tiny_model/train.py` 组织循环。走读顺序是先找到 `TinyLM.forward` 的输入输出，再进单层 `Block.forward`，最后回到训练循环。本章重点在后者；前者只保留一条数据流在脑子里：

```text
[1,6] 输入 ID
  ↓ 词嵌入 + 位置嵌入
[1,6,32] 表示
  ↓ 第 1 层：Attention + 前馈，含残差和归一化
[1,6,32]
  ↓ 第 2 层：同样的结构，独立的参数
[1,6,32]
  ↓ 最终归一化 + 输出投影
[1,6,7] 候选得分
```

每个 token 先查出 32 维词向量，再加同维度的位置向量，让相同 token 出现在不同位置时得到不同输入表示。每层先归一化输入、算 Q/K/V、按因果规则汇总、投影回模型宽度并与输入相加；再经另一段归一化与前馈网络（32 维扩到 128 维、过 GELU、回到 32 维），加一次残差。残差要求形状一致，所以注意力投影和前馈最后一层都回到 32 维——这些形状约束能直接帮助阅读模型源码。这是一种常见结构的教学实现，不是 Qwen 的完整复制；真实工程模型在归一化、位置处理、多头结构等细节上会有不同。

下面按执行顺序引 `train.py`（以及一处 `model.py`）的四段原文，逐行对照上面的表。

**第一段（train.py 第 8–10 行）：数据在循环外就固定好。**

```python
TOKENS = ['北京','是','中国','的','首都','。','<结束>']
INPUT = torch.tensor([[0,1,2,3,4,5]], dtype=torch.long)
TARGET = torch.tensor([[1,2,3,4,5,6]], dtype=torch.long)
```

- `TOKENS`：七项教学<Term id="vocabulary"/>，ID 就是列表下标——“北京”是 0，结束标记是 6。
- `INPUT`：把句子前六项编码成 `[1,6]` 的整型张量——1 条序列、6 个位置。
- `TARGET`：同样是 `[1,6]`，每一项是“对应输入位置应当预测出的下一个 token”。

注意 `TARGET` 不是 `INPUT` 的复制品，而是整体右移一位：

| 输入位置 | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| 输入 token | 北京 | 是 | 中国 | 的 | 首都 | 。 |
| 目标 token | 是 | 中国 | 的 | 首都 | 。 | 结束 |

每一个输入位置负责预测它后面的那项。如果把输入和目标设成完全相同，模型会学到“复制当前 token”，目标与续写任务不一致。这里的“错开”是训练目标的构造，不是把序列弄乱。

**第二段（train.py 第 12–19 行）：train_step 的四行主课。**

```python
def train_step(model, optimizer):
    model.train()
    optimizer.zero_grad(set_to_none=True)
    logits, _ = model(INPUT)
    loss = F.cross_entropy(logits.reshape(-1, len(TOKENS)), TARGET.reshape(-1))
    loss.backward()
    optimizer.step()
    return loss.item()
```

一次调用就是上表的一圈②–⑤。逐行看：

- `model.train()`：切换训练模式。它与 `model.eval()` 控制某些层（如 Dropout）的训练/推理行为，是和“是否记录梯度”不同的开关——调用 eval 不会自动关闭求导，`torch.no_grad()` 也不会自动切换所有层的行为。本模型没有 Dropout，两种模式下前向相同；仍明确调用，是为了形成正确习惯。
- `optimizer.zero_grad(set_to_none=True)`：清掉上一圈的梯度。不清零的话，<Term id="autograd"/> 会把新梯度累加到旧值上（这个语义对梯度累积有用），这里要的是每步只用本步梯度。`set_to_none=True` 直接把 `.grad` 置空而不是写零，省一次无谓的写回。
- `logits, _ = model(INPUT)`：<Term id="forward"/>，对应上表②。返回形状 `[1,6,7]`——1 条序列、6 个输入位置、每个位置对 7 个词表候选各给一个原始得分。第二个返回值是各层的新 K/V，训练时用不上，用 `_` 丢弃。
- `loss = F.cross_entropy(...)`：对应③。`reshape(-1, len(TOKENS))` 把前两维摊平成 6 个“样本”，与 `TARGET.reshape(-1)` 的 6 个目标 ID 对齐，逐位置算交叉熵再平均——6 个位置各问一句“你给正确下一项的得分够不够高”，损失是六句的平均。
- `loss.backward()`：对应④。沿前向记录的计算图反向应用链式法则，把损失对每个参数的梯度写进各自的 `.grad`。此时参数还没有变。
- `optimizer.step()`：对应⑤，唯一修改参数的一行。AdamW 按自己的规则读 `.grad` 和自身状态决定更新量。
- `return loss.item()`：把单元素张量取成 Python 数返回。注意这个数是用本步更新前的参数算的——它报告“改之前有多错”。

顺带解释 `_` 丢弃的东西：forward 的第二个返回值是这 6 个位置在每层新产生的 K/V。生成路径会把它作为缓存传回下一轮，只算新位置（前一章的内容）；训练路径用不上——每步都对完整 6 个位置重新前向。KV 缓存是生成时的省算手段；训练的前向本来就要算所有位置，因为每个位置的预测都要进损失。

对照真实运行：进入循环前，用初始参数算出的损失是 2.5985586643218994。七个候选完全均匀时的交叉熵是 ln(7)≈1.95，初始损失比它还高——随机初始化的参数给正确答案的得分低于均匀分布，这是正常起点，不是异常。跑满 100 圈后，损失为 0.0008747270912863314：模型对六个位置的下一项几乎全对。这两个数分别是证据文件里的 `training_loss_before` 和 `training_loss_after`。

**第三段（model.py 第 87–89 行）：检查点里存了什么。**

```python
def save_checkpoint(path, model, optimizer, step):
    torch.save({'config':asdict(model.cfg),'model':model.state_dict(),
                'optimizer':optimizer.state_dict(),'step':step,'rng':torch.get_rng_state()}, path)
```

一个字典，五个键：结构配置，加上上表⑦要读走的全部跨步状态——

- `config`：结构配置（词表 7、宽度 32、头 2、层 2、上下文 32），用 `asdict` 转成普通字典。恢复时先按它重建同样结构，再填数值——检查点不是“打印模型对象”存下来的，`state_dict` 只提供参数和持久缓冲区的“名字到张量”映射，不含结构信息。加载报维度不匹配时，应检查配置与词表，而不是随手忽略错误。
- `model`：全部<Term id="parameters"/>。只为了重新加载并生成，有 config 加 model 加词表就够了。
- `optimizer`：AdamW 的状态。为了继续训练，它非存不可——为什么，是下一节的主题。
- `step`：已完成步数，resume 时决定循环从哪里继续。
- `rng`：PyTorch 的 CPU 随机状态。本模型没有 Dropout，前向没有随机性，这一项目前是“为含随机的模型预留的正确习惯”；真实训练里数据顺序、Dropout 掩码等都吃这份状态。更复杂的数据加载器还要保存采样顺序与数据游标，后面的训练恢复章节会扩展这份清单。

**第四段（train.py 第 23、31–39 行）：resume 分支与 `--steps` 的语义。**

```python
    ap.add_argument('--steps', type=int, default=100, help='Total target steps, not extra steps')
```

```python
    if args.resume:
        model, optimizer, start = load_checkpoint(args.resume)
    else:
        model = TinyLM()
        optimizer = torch.optim.AdamW(model.parameters(), lr=0.01)
        start = 0
    before = F.cross_entropy(model(INPUT)[0].reshape(-1, 7), TARGET.reshape(-1)).item()
    for step in range(start, args.steps):
        train_step(model, optimizer)
```

- `--steps` 是累计目标步数，不是“再跑多少步”——help 字符串原文就写着 `Total target steps, not extra steps`。所以循环是 `range(start, args.steps)`：恢复时 `start` 来自检查点里的 `step`，训练恰好从断点续到目标值；全新开始时 `start=0`。一条命令两种起点，循环本体一个字不用改。
- `before` 在进循环前算一次，就是证据文件里的 `training_loss_before`。恢复运行时，它是“刚从检查点加载的参数”的损失——所以 2.5985586643218994 这个数只属于从零开始的那一次。
- 分支之前有两行铺垫值得注意：`torch.set_num_threads(1)` 把线程数固定为 1（证据文件环境栏的 “1 thread” 即此，让记录的数字可对照），`torch.manual_seed(7)` 固定随机种子使从零开始的初始化可复现——测试的 `setUp` 也用同一个种子。resume 时 `load_checkpoint` 末尾会 `torch.set_rng_state` 覆盖成检查点里保存的随机状态，两条路径各得其所。
- 保存时写的是 `max(start, args.steps)`：如果你 resume 一个已到 100 步的检查点却传 `--steps 80`，`range(100, 80)` 为空、一步不训，检查点步数保持 100——步数只增不减。

循环结束后的收尾（第 40–50 行）不再整段引用：`model.eval()` 加 `torch.no_grad()` 下重算一次损失得 `training_loss_after`，用提示 `[0,1,2,3]` 分别以开缓存和关缓存两种方式生成并比较（`cache_generation_equal`），保存检查点，最后把全部结果打成 JSON 打印。程序打印的键逐个对照：

- `torch` / `device`：版本与设备（证据记录里是 torch 2.14.0、cpu）；
- `start_step` / `end_step`：本次从第几步到第几步，resume 时两者不同；
- `training_loss_before` / `training_loss_after`：循环前、后各算一次的同一损失；
- `generated_ids` / `text`：生成的 ID 序列和按词表拼回的文本；
- `cache_generation_equal`：两种生成方式是否逐位相同；
- `evaluation`：一句自我声明——单句过拟合的机制检查，不构成留出集评估。

`docs/runs/tiny-model-cpu.json` 就是在这份输出基础上，补记了日期、环境、命令和 5 项机制测试的通过数。

## 为什么要保存 optimizer 状态

现在单独回答检查点里最不直观的一项。设想一个具体故障：参数已经训练了 8 步，存了盘，但只保存了 `model` 没保存 `optimizer`。重新加载后参数数值一字不差，生成结果也正常——看起来一切完好。然后做一次 `optimizer.step()`：这一步的更新和未中断的基线不一样了。

原因在 AdamW 的工作方式。它不是拿学习率乘梯度就完事，而是为每个参数维护两份跨步累积的统计：梯度一阶矩（按 β1=0.9 的指数平均，反映近几步梯度的持续方向）和二阶矩（按 β2=0.999 的指数平均，反映近几步梯度的典型幅度），实际更新量由两者相除缩放（另有与矩无关的解耦权重衰减项）。这两份统计就是优化器状态。只恢复参数、新开一个 AdamW，矩从零开始：数学上可以推出，冷启动后第一次更新里梯度项的缩放退化为梯度的符号函数，几乎不反映梯度大小，更不反映历史；而正确恢复的版本由八步积累的矩缩放。两者一般不相等——参数对了，下一步更新仍然错。

这一差别有测试盯着。`tests/test_tiny_model.py` 的 `test_checkpoint_resume_preserves_next_updates` 判据是：

1. 固定种子训练 8 步，`save_checkpoint` 存下 model 加 optimizer 加 step=8。
2. 让原模型原地继续跑 3 步，记录每步损失——这是未中断基线。
3. `load_checkpoint` 到新对象，同样跑 3 步。
4. 断言三条：恢复出的 `step` 等于 8；两组三步损失逐项完全相等；三步之后两组参数逐位相同（容差为零）。

容差为零的浮点相等之所以成立，是因为两边走的是同一条确定性计算路径：本模型无 Dropout、数据固定、单线程、随机状态随检查点恢复，同样的输入与状态必然得到逐位相同的浮点结果。若路径里有不可复现的随机性或并行归约顺序差异，就要改用带容差的比较——那本身也是一个要回答的问题。

判据的关键在第 2、3 步的设计：不比较“能加载”“能生成”，而比较恢复后的下一次与后续参数更新是否与基线一致。这正是本章开篇问题的答案——重新加载后能生成相同文字，不说明能从中断处正确继续训练：生成只需要部分状态；继续训练还依赖优化器、步数、随机状态和数据顺序。应比较恢复后的下一次或多次参数更新与未中断基线。

<Term id="checkpoint"/> 恢复只是 5 项机制测试之一，证据文件里的 `mechanism_tests_passed: 5` 指的是这五条，各回答一个独立问题：

| 测试 | 回答的问题 |
|---|---|
| `test_cached_incremental_and_chunked_match_full_causal_logits` | 逐 token 增量与分块续算的 logits，是否都等于全量因果 logits |
| `test_future_tokens_cannot_change_prefix` | 修改未来 token，是否不影响已算好的前缀表示 |
| `test_gradient_matches_finite_difference` | 自动求导的梯度，是否与中心有限差分一致 |
| `test_checkpoint_resume_preserves_next_updates` | 恢复后的参数更新，是否与未中断基线逐位一致 |
| `test_training_reduces_loss_and_generation_matches` | 训练是否把损失降到首步的二十分之一以下，生成命中目标，缓存开关等价 |

恢复后能加载只检查文件格式，继续更新一致才能验证优化器与状态恢复正确。

完成这些检查后，你已经把第一章的黑箱打开为一条可实现的循环路径。下一阶段把数据放到真实设备上，解释为什么同样正确的计算可能有完全不同的时间与空间代价。

## 动手

进入仓库并激活项目的 PyTorch 环境后，先跑一条从零开始的训练：

```bash
python labs/tiny_model/train.py --steps 100 --output /tmp/tiny-checkpoint.pt
```

再跑一条恢复的：

```bash
python labs/tiny_model/train.py --resume /tmp/tiny-checkpoint.pt --steps 120 --output /tmp/tiny-resumed.pt
```

第二条从 100 继续到 120，不是再跑 120 步。观察按顺序做三件事：先看 `training_loss_after` 是否远小于 `training_loss_before`；再对照词表检查 `generated_ids`——从提示 `[0,1,2,3]` 出发，贪心选每步最高分，期望补出 4、5、6 并停在结束标记；最后确认 `cache_generation_equal` 为 true。若只看输出文字合理，却没有验证缓存开关的数值一致性，仍不能证明缓存实现正确。恢复那条命令里，还可以看 `start_step` 是不是 100——它是检查点里 `step` 键的直接体现。
