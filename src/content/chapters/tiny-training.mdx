现在已经有了两条完整的计算线：生成时，根据已有内容选下一项；训练时，根据目标计算损失，再用梯度更新参数。本章把它们放进同一个程序。

目标不是训练一个好用的聊天模型，而是让你能指出每一项数据在哪里产生、代码为什么按这个顺序执行，并能验证参数确实改变了。这个规模足够在 CPU 上运行。

## 先规定我们要验证什么

项目使用七项教学词表，训练句子是“北京是中国的首都。”再接结束标记。我们故意让小模型反复学习这一个句子，以检查训练机制能否工作。

这叫小样本过拟合检查：模型如果连一个极小样本都学不好，数据、目标或更新流程可能有问题。但学会这个句子，不证明它具备语言理解能力，也不构成独立验证集评估。

前面的二维小矩阵用于手算；这里把表示扩大到 32 维、2 个注意力头、2 层，并随机初始化参数。我们仍然沿着同样的数据流，但数值不再假定为手工填的 0 和 1。

## 把输入和目标错开一个位置

完整序列的 ID 是 `[0,1,2,3,4,5,6]`。模型读取前六项，目标是后六项：

```text
输入：北京  是  中国  的  首都  。
目标：是    中国 的  首都 。   结束
```

每一个输入位置负责预测它后面的那项。这里“错开”是训练目标的构造，不是把序列弄乱。如果把输入和目标完全相同，模型就可能学习复制当前 token，目标与续写任务不一致。

一次正向会返回形状 `[1,6,7]` 的 logits：1 条序列，6 个输入位置，每个位置对 7 个词表候选给分。为了计算每个位置的交叉熵，我们把前两维合成 6 个样本，对应 6 个目标 ID。

## 这次把一个完整层的部件接起来

每个 token 先查出 32 维词向量，再加上同维度的位置向量。位置向量也来自参数表，按位置编号查找，让相同 token 出现在不同位置时能够得到不同输入表示。

一个层按如下顺序处理：先归一化输入，计算 Q/K/V，按因果规则汇总；再把注意力结果投影回模型宽度，与进入本段前的输入相加；然后经过另一段归一化与前馈网络，再加一次残差。

这里的归一化使用 LayerNorm。它按每个位置的表示分量计算均值和方差，调整尺度，再应用可学习的缩放与偏移。它不使用其他请求的统计，也不会让当前位置看见未来 token。

前馈网络先将 32 维扩到 128 维，经过 GELU 非线性，再回到 32 维。GELU 是对数值逐项执行的平滑非线性函数；你现在需要知道它让整段加工不等价于单次线性变换，不需要先推导其函数形式。

残差相加要求形状一致。因此注意力投影和前馈最后一层都回到 32 维，才能与原输入相加。这些形状约束能直接帮助阅读模型源码。

```text
[1,6] 输入 ID
  ↓ 词嵌入 + 位置嵌入
[1,6,32] 表示
  ↓ 第 1 层：Attention + 前馈，含残差和归一化
[1,6,32]
  ↓ 第 2 层：同样的结构，独立的参数
[1,6,32]
  ↓ 最后归一化 + 输出投影
[1,6,7] 候选得分
```

这是一种常见结构的教学实现，不是 Qwen 的完整复制。真实工程模型会在归一化、位置处理、前馈、多头结构和其他细节上有所不同；后面的源码阅读会明确做对照。

## 在项目里找到每一段代码

下载项目代码后，主要阅读两个文件：`labs/tiny_model/model.py` 定义计算，`labs/tiny_model/train.py` 组织训练。先找到 `TinyLM.forward`，再进入单层 `Block.forward`，最后回到训练循环。

`qkv(...).chunk(3)` 把同一次线性投影的输出分成 Q、K、V；把形状拆成 `[batch,heads,time,head_width]` 后，每个头独立完成注意力。`transpose` 改变维度顺序；回到模型宽度前调用 `contiguous`，让后续重排具有所需连续布局。下一阶段专门讲这些内存操作。

如果有旧缓存，层先连接旧 K/V 与新 K/V，并用“历史长度 + 新位置偏移”建立正确的遮罩。不能每次把新位置当成位置 0，否则位置向量和因果边界都会错。

## 运行与观察

完整环境创建、下载、验证和清理步骤在关联项目中。这两条命令假定你已进入仓库并激活项目的 PyTorch 环境：

```bash
python labs/tiny_model/train.py --steps 100 --output /tmp/tiny-checkpoint.pt
python labs/tiny_model/train.py --resume /tmp/tiny-checkpoint.pt --steps 120 --output /tmp/tiny-resumed.pt
```

`--steps` 是目标累计步数，因此第二条从 100 继续到 120，不是再跑 120 步。输出包含训练损失前后值、生成 ID，以及使用缓存和全量重算时生成是否相同。

先检查损失是否下降，再检查生成 ID 能否与词表对应。若只是输出文字合理，却没有验证缓存开关的数值一致性，仍不能证明缓存实现正确。

## 保存的不只是权重

只为了重新加载并生成，模型配置、权重和词表就已经很重要。为了继续训练，还应保存优化器状态、已完成步数和影响后续随机选择的状态。

本项目检查点包含模型参数、结构配置、AdamW 状态、步数和 PyTorch CPU 随机状态。在更复杂的数据加载器中，还要考虑采样顺序、数据游标及其他随机来源；后面的训练恢复章节会扩展这份清单。

检查点不是通过“打印模型对象”保存的。`state_dict` 提供参数和持久缓冲区的名称到张量映射；恢复时先根据配置建立同样结构，再加载数值。输入输出维度不匹配时，应检查配置与词表，而不是随便忽略加载错误。

## 为什么还有训练模式和推理模式？

`model.train()` 与 `model.eval()` 控制某些层的训练/推理行为；`torch.no_grad()` 控制是否记录梯度相关计算。它们是不同开关。调用 eval 不会自动关闭求导，关闭求导也不会自动切换所有层的行为。

我们的小模型不使用 Dropout，所以两个模式下的前向没有随机丢弃变化；仍明确调用模式切换，是为了形成正确习惯。真实模型若含 Dropout 等结构，这个区别就会直接影响结果。

## 项目怎样防止“看起来能跑”的错误？

项目测试比较：全量因果 logits 与逐位置缓存 logits；分块输入与全量输入；修改未来 token 后的前缀不变性；自动求导与有限差分；保存恢复后的下一步更新；训练前后损失。

这些测试各回答一个独立问题。缓存生成相同只检查最终选择，logits 对比还能发现尚未改变最高分位置的细微错误。恢复后能加载只检查文件格式，继续更新一致才能验证优化器和状态是否恢复正确。

完成这些检查后，你已经把第一章的黑箱打开为一条可实现的计算路径。下一阶段把数据放到真实设备上，解释为什么同样正确的计算可能有完全不同的时间与空间代价。
