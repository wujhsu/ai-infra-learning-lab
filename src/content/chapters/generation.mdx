## 这一章解决什么问题

你已经熟悉这样的后端服务：接收请求，读取数据，做一些计算，返回响应。语言模型服务也有这层外壳。但当响应是逐渐出现的一段文字时，里面的工作与查询一条数据库记录很不一样。

差别在一次响应被拆成多少次计算。查一条记录，一次计算就够；生成一段文字，服务要反复执行“根据已有内容决定下一个 token”，每轮只前进一小步。你在终端里看着文字一个个冒出来，看到的就是这个循环的节拍。

我们先只做一件事：**把“输入一段文字，得到一段续写”拆成可追踪的步骤。** 学完本章，你不必知道模型内部的全部运算，但应该能画出循环，说清每次循环的输入与输出，并且能回答一个后端工程师马上会问的问题：把 `max_tokens` 从 5 调到 50，多花了什么，没花什么。

后面几章一直使用同一个例子：输入“北京是中国的”，希望服务接着写下去。这里选择续写而不是多轮聊天，是为了先看清最基本的数据流。聊天所需的角色标记和历史消息，后面再加回去。

本章的数字都来自同一份手工构造的教学数据（`src/data/toy-model.json`），不是真实模型的预测。它们的作用是让每一步可以纸笔复核，而不是报告性能；文中会一直标明“教学设定”。

## 文字不是直接送进计算函数的

假设你设计一个接受整数数组的函数。用户给它一句中文，你首先需要规定：这句话怎样变成数组？语言模型也需要这样的对应关系。

<Term id="token" context="在这一段里，token 是把中文输入转为整数数组时使用的单位。先关注切分和编号，不必把它理解成一个完整单词。"/> 中文常译为“词元”。<Term id="tokenizer"/> 负责按配套规则把文字转换成 token ID；<Term id="vocabulary"/> 保存 token 与编号之间的对应关系。三者分别是单位、转换工具和对应表。

为了手工追踪，我们约定一个只有七项的教学词表：

| ID | token | 在例子中的用途 |
|---|---|---|
| 0 | 北京 | 输入的一部分 |
| 1 | 是 | 输入的一部分 |
| 2 | 中国 | 输入的一部分 |
| 3 | 的 | 输入的一部分 |
| 4 | 首都 | 可能的续写 |
| 5 | 。 | 可能的续写 |
| 6 | 结束标记 | 表示这段生成可以停止 |

于是，“北京是中国的”在**这套教学规则**下变为 `[0, 1, 2, 3]`。这个数组的长度是 4，表示有四个 token。它不表示四个字节，也不表示只有四个汉字。

真实模型的词表大得多，分词规则也不一定按中文词语切分。“北京”可能对应一项，也可能拆成多项；空格、标点和特殊标记也要处理。不能用这里的七项表估算真实服务的输入长度。重要的是流程：**先使用与模型配套的规则得到 ID，再让模型计算。**

ID 本身没有语言意义。“首都”的 ID 比“北京”大，不代表它更重要、更可能出现或在语义上更远。这一点下一章会变得关键：模型还会把编号查成另一组数字。

<details>
<summary>聊天接口中的 role 和 content 放在哪里？</summary>


聊天接口通常先通过模型配套的聊天模板，把系统指令、用户消息和角色边界等组织成模型所需的输入形式，再转换成 ID。因此，只有 `content` 的可见文字长度还不等于实际输入 token 数。这里先研究续写循环；模板是送入循环之前的处理，不会改变“依据上下文选择下一项”的基本问题。


</details>

<span id="model-box"></span>
## 模型先给候选打分，不会直接返回一个汉字

现在把数组 `[0, 1, 2, 3]` 交给模型。为了理解外围流程，我们暂时把内部运算写成一个函数：

```python
scores = model(context_ids)
```

这是一行表示数据关系的伪代码，不是可直接调用的库接口。`context_ids` 是当前已有内容的 ID；`scores` 是用于选择下一 token 的候选得分。模型内部怎样算出它们，会在第二、三章展开。

这个函数并不是一张“输入整句 → 查出整句答案”的表。它使用训练得到的 <Term id="parameters"/>，对输入做数值计算。参数可以先理解为函数内部反复读取的数值配置：同一个模型处理不同请求时，通常读取同一套参数，但输入不同，计算结果便可能不同。这套教学数据里最小的一块参数，是下一章要读的一张 7 行 2 列的表——7 个 token 各占一行，每行 2 个数，一共 14 个数。生成 5 个还是 50 个 token，读取的都是这同一份表。

“参数”与我们在 HTTP 请求里填写的 `max_tokens` 也不是一个概念。前者是模型学到的大量数值；后者是服务调用的生成设置。不要因为中文都叫参数，就把两者放在同一个位置理解。

我们的词表有七项，因此为了决定下一个位置，模型要区分七个候选，`scores` 的相应位置就有 7 个数。原始结果叫 <Term id="logits"/>。它是一组分数：可以为负，不要求总和为 1，也还不是“选到每个候选的概率”。下一节给出一组具体的数。

<span id="scores"></span>
## 从候选得分到一个具体选择

为了能按概率选择，生成程序通常会把得分转换成一组非负且总和为 1 的数。比如 0.8 可以写成 80%，表示相应候选在这次选择中的概率。

转换使用的 <Term id="softmax"/> 计算会在第三章一步步展开。现在先理解它在流程中的作用：得分告诉我们候选的相对倾向，归一化后的概率让我们能够定义选择规则。

下面是一组**手工设置的示意概率，不是真实模型的预测，也不是下一章小矩阵算出来的结果**。我们先用它观察生成循环；后面用小矩阵研究内部计算，两种教学简化会明确区分。

<CandidateTable />

这组概率和 logits 之间可以搭一座能复核的桥：对每个概率取自然对数，就得到一组“经过归一化后恰好还原出这张表”的得分。这是教学构造，不是模型真的这样算，但它让“得分 → 概率”不再是黑箱：

| 候选 token | 本轮概率 | 能产生它的得分（取自然对数） |
|---|---|---|
| 北京 | 2% | −3.91 |
| 是 | 2% | −3.91 |
| 中国 | 4% | −3.22 |
| 的 | 2% | −3.91 |
| 首都 | 80% | −0.22 |
| 。 | 8% | −2.53 |
| 结束标记 | 2% | −3.91 |

两个可以直接检查的事实：这组得分总和约 −21.62，既不是 0 也不是 1，可见“logits 总和不必为 1”不是一句空话；而“首都”与“。”的得分只差约 2.3（−0.22 对 −2.53），换算后却是 80% 对 8% 的十倍差距——归一化计算会放大得分间的距离。

得到这组数字后，可以使用不同规则：

- **贪心选择**：每次选当前概率最大的候选。在这张表中是“首都”，也就是 ID 4；同一输入下每次都选它，结果确定。
- <Term id="sampling"/>：按概率抽取候选。80% 的候选更容易被抽到，但某一次也可能选中其他项。

把第一轮的数字拆开看：采样时有 80% 选到“首都”，8% 选到“。”，剩下 12% 分给北京、是、中国、的、结束标记五项。也就是说，同样跑 100 次独立采样，大约 80 次第一轮落在“首都”上，但没有任何一次保证——这正是不确定性的来源。贪心则是 100 次全选 ID 4。

因此，同样的模型和输入，在使用随机采样时可能产生不同输出。这并不要求模型参数发生变化。你可以把它理解为“得到了同一组抽取权重，但抽取动作不同”。

还要区分两件事：模型对某个候选的概率，与这句话在现实世界里正确的概率。前者是在当前生成机制下选择文字的倾向，不能直接作为事实真实性的置信度。

<aside class="concept-note">
<strong>易混点：这里有 80%，是不是每五次必定有四次选中？</strong>


不是。概率描述抽样机制，不规定每一小组结果的精确比例。就像抛公平硬币，连续两次也可能都是正面。生成里的随机选择还会受随机种子、候选过滤等设置影响；这些暂时不影响我们理解基本循环。


</aside>

<span id="one-step"></span>
## 选到“首都”之后，为什么还要再执行？

第一轮选中 ID 4，对应“首都”。这时我们只决定了一个新 token，还没有决定后面是句号、更多描述，还是立即结束。

要继续，就把刚生成的 ID 接回已有数组：`[0, 1, 2, 3, 4]`。下一次选择的依据，已经从“北京是中国的”变成“北京是中国的首都”。

这叫 <Term id="autoregressive"/>：输出的一部分回到后续输入中。这里的“自”表示利用自身已经生成的结果，不是服务在自动训练自己。

<LearningFigure kind="generation" />

按教学设定，我们跟踪三轮。第一轮的选择由上面的概率表决定；后两轮的路径来自教学数据里预写的续写序列 `[4, 5, 6]`（数据文件中的 `scriptedContinuation` 字段），没有为它们手工另设概率表。重点不在路径本身，而在每轮的输入如何变成下一轮的输入：

| 轮次 | 本轮送入模型的 ID | 数组长度 | 本轮选中 | 选中后的数组 |
|---|---|---|---|---|
| 第 1 轮 | `[0, 1, 2, 3]` | 4 | 4（首都，概率表最高项 80%） | `[0, 1, 2, 3, 4]` |
| 第 2 轮 | `[0, 1, 2, 3, 4]` | 5 | 5（。，教学设定路径） | `[0, 1, 2, 3, 4, 5]` |
| 第 3 轮 | `[0, 1, 2, 3, 4, 5]` | 6 | 6（结束标记） | 停止，正文为“首都。” |

逐列读这张表能看出三件事：送入模型的数组每轮长 1；新增的恰好是上一轮选中的那一个 ID；最终数组有 7 项，但正文只有 2 个 token——结束标记让循环停止，它本身不作为普通文字显示。若改用采样，第 2、3 轮的概率表会随上下文重新计算，我们不在本章手工设定它们；无论选择到哪一项，循环要处理的问题不变：保存已经选出的内容，判断是否结束，决定是否继续计算。

服务还可以因为达到输出长度上限、匹配停止条件，或客户端取消而结束。因此，“这次没有生成结束标记”不代表服务会永远运行。

```python
# 流程伪代码：展示先后依赖，尚未加入缓存。
context_ids = tokenize("北京是中国的")
output_ids = []

for step in range(max_new_tokens):
    scores = model(context_ids)       # 根据目前已有内容计算
    next_id = choose(scores)          # 本轮只决定一个新 ID
    if next_id == end_id:
        break
    output_ids.append(next_id)
    context_ids.append(next_id)      # 新输出成为下一轮的上下文

text = detokenize(output_ids)
```

这段伪代码里，`max_new_tokens` 限制新生成多少项，不包括最开始那四项输入。`detokenize` 表示用配套规则把 ID 转回可显示的文本。把 token 还原为文字，也常被叫做“解码”；第四章会介绍另一个同样叫 Decode 的执行阶段，届时我们会明确区分。

你可以只盯住一处依赖：`context_ids.append(next_id)`。如果删除它，每一轮模型看到的输入都相同，程序就不再按已经产生的结果继续这段文字。这比记住“自回归”四个字更重要。

现在回答开头埋下的问题：`max_tokens` 从 5 调到 50，多花了什么？参数一个没变——还是同一份权重，教学数据里最小那张表始终是 14 个数。变的是循环次数的上限。在这段无缓存伪代码下，每轮都重算全部输入：生成 5 个新 token 要处理 4+5+6+7+8 = 30 个位置，生成 50 个要处理 4 到 53 共 1,425 个位置，约 47 倍。第五章的 KV 缓存会把每轮压回只处理新增的一个位置，到那时差距回到接近 10 倍；排队和执行方式仍会带来出入，所以“十倍 token”从不等于“十倍时间”。

<span id="service"></span>
## 再放回你熟悉的后端服务

现在可以把一次响应分成三段来看：输入处理把文字准备成 ID；生成循环反复决定新的 ID；输出处理把它们转换成文字，发送给客户端。

流式接口可以在生成尚未结束时发送已经得到的内容。但网络响应的一小块不必恰好对应一个 token，拿本章的例子数一遍：正文只有“首都”和“。”两个 token，结束标记不计入正文。同一次生成，服务可以先发一个只含角色信息的空事件，再分别发出两个含正文的事件——客户端数出 3 块；也可以把两个 token 合并成一个事件——客户端数出 1 块。token 数都是 2。所以“浏览器一共收到了十个数据块”不能直接推出“模型生成了十个 token”。<Term id="sse"/> 的事件只承诺“一段逐步送达的文本”，不承诺事件边界与 token 边界对齐。

同样，用户看见第一个字之前的时间，也不只是第一轮模型计算。请求可能在等待资源，输入还要处理，输出还要经过网络。我们以后测量 <Term id="ttft"/> 时，会把这些环节放回时间线；此刻先不要把尚未出现的性能指标背进来。

在本章的基本逐 token 生成方式下，一段回答通常需要多轮模型计算。后面还会遇到可以尝试一次验证多个候选的优化方法，它们需要更多机制，不用现在就推翻刚建立的基本流程。先掌握普通执行方式，才有办法解释优化到底改变了哪里。

## 代码走读：生成循环在 labs 里长什么样

上面的伪代码在仓库里有一个能跑的对应物：`labs/tiny_model/model.py` 中的 `generate` 方法。它只多了一个“缓存”开关，其余结构和伪代码一一对应。

```python
# labs/tiny_model/model.py:73 —— TinyLM.generate
@torch.no_grad()
def generate(self, ids, max_new_tokens=8, eos_id=6, use_cache=True):
    self.eval()
    result = ids.clone()
    cache = None
    for _ in range(max_new_tokens):
        model_input = result if cache is None or not use_cache else result[:, -1:]
        logits, new_cache = self(model_input, cache if use_cache else None)
        next_id = logits[:, -1].argmax(-1, keepdim=True)
        result = torch.cat((result, next_id), dim=1)
        cache = new_cache if use_cache else None
        if (next_id == eos_id).all():
            break
    return result
```

逐行对应本章的循环：

- `@torch.no_grad()` 与 `self.eval()`：生成是推理，不更新参数。生成 50 个 token 也不会把这段对话“训练进”模型。
- `result = ids.clone()`：复制输入而不是改动调用方的数组；`result` 从这里开始一路持有“提示 + 已生成”的全部 ID，就是伪代码里的 `context_ids`。
- `for _ in range(max_new_tokens)`：与伪代码同名同义，默认 8。这个 lab 的词表同样只有 7 项（`Config` 里 `vocab_size: int = 7`），所以每轮 logits 沿词表方向也是 7 个数。
- `model_input = result ... else result[:, -1:]`：两种喂法。`use_cache=False` 时整段重喂，正是本章的无缓存伪代码；`True` 时只喂最后一个新 token，为什么可以这样留到第五章。
- `logits, new_cache = self(...)`：一轮一次 <Term id="forward"/>。返回值里除得分外还有供下一轮使用的缓存状态。
- `next_id = logits[:, -1].argmax(-1, keepdim=True)`：只取最后一个位置的 7 个得分，`argmax` 选最大项——这就是贪心选择。对照概率表，最大项是 80% 的“首都”，选出的就是 ID 4。这个 lab 没有实现随机采样；把这一行换成按概率抽取，就是本章的 sampling，循环其余部分一个字不用改。
- `result = torch.cat((result, next_id), dim=1)`：`context_ids.append(next_id)` 的张量写法。删掉它，循环同样立刻退化。
- `if (next_id == eos_id).all(): break`：结束标记检查，`eos_id` 默认 6；`.all()` 是为了兼容一次处理多条序列的批量维度。
- 返回的是 ID 数组，不是文本。把 ID 变回文字发生在调用方（`train.py` 里用 `''.join(TOKENS[i] ...)` 拼出）。

训练脚本 `labs/tiny_model/train.py` 还专门验证了两件本章说过的事。其一，缓存只省计算、不改结果：

```python
# labs/tiny_model/train.py:43
cached = model.generate(torch.tensor([[0,1,2,3]]), use_cache=True)
full = model.generate(torch.tensor([[0,1,2,3]]), use_cache=False)
```

两次生成的结果会被逐 ID 比较，以 `cache_generation_equal` 写进输出的 JSON；期望为 `true`。其二，训练本身教的就是“每个位置预测下一个 token”：`INPUT = [0,1,2,3,4,5]` 对 `TARGET = [1,2,3,4,5,6]`，整体错开一位——生成循环和训练目标是同一件事的两面。

你可以自己跑一遍：

```bash
cd labs/tiny_model && python train.py --steps 100
```

输出的 JSON 里看两项：`generated_ids` 期望以 `[0,1,2,3,4,5,6]` 结尾，也就是教学路径“首都、。、结束标记”（脚本只在一句话上过拟合，属于 sanity check，以实际输出为准）；`cache_generation_equal` 期望为 `true`。

## 动手：纸笔推演
