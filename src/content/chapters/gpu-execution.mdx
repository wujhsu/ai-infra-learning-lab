## 这一章解决什么问题

前两章弄清了数据放在哪一层存储、搬一次要多久。但“谁来算”还没有展开：一次 <Term id="kernel"/> 启动之后，GPU 内部究竟是谁在执行这些乘加？为什么同样一张卡，跑大矩阵乘能接近满速，跑小批次生成却大量空转？

这一章把 GPU 的执行组织讲清楚：线程怎样分层、硬件一次真正容纳多少线程、访存模式怎样决定带宽利用、寄存器与共享内存怎样限制并行规模。所有算例都标明假设，可以用纸笔复核；本章没有在 GPU 上运行实验，属于机制讲解与源码阅读。

阅读提示：每个结论旁边都有可复核的算例，假设写在算例前；只想抓主线的读者可以先看“喂得饱与喂不饱”两个算例和最后的动手练习，再回头补 warp 与 occupancy 的细节。

先用最小的例子热身。两个长度 1024 的数组逐项相加，最直接的分工是让逻辑线程 i 计算 `out[i] = a[i] + b[i]`：不同元素之间没有依赖，可以同时进行。若每块 256 个线程，1024 ÷ 256 = 4，正好 4 块。若长度是 1000，仍然启动 4 块（1000 ÷ 256 = 3.9，向上取整），但最后一块覆盖下标 768 到 1023，其中只有 1000 − 768 = 232 个下标有效，其余 24 个线程必须做边界检查，不读也不写数组之外的数据。

```text
元素索引 = 块编号 × 每块线程数 + 块内线程编号
若元素索引 < 数组长度：执行加法
否则：不读取、不写入
```

这个五分钟能算完的小例子，已经包含了本章全部要素的雏形：工作量怎样切给块、块内线程怎样编号、边界怎样掩码。接下来只是把它放大到真实硬件的规模，并问出更深的问题：块放到哪里执行？多少块能同时执行？什么会让“同时”变少？

先把结论的形状说出来：GPU 快不是因为单个线程快，而是因为它用一套层级把百万量级的独立小计算组织起来，并让访存等待与计算重叠。理解了这套层级，“线程越多越快”这类说法哪里对、哪里错，就能逐条判断，而不是凭感觉。

带着四个问题往下读，本章结束时应该能各自给出有数字支撑的回答：

- 一张 GPU 同时最多容纳多少线程？我的问题规模是它的几倍或几分之几？
- 相邻线程的访问地址是否相邻？差多少带宽利用率？
- 每个线程、每个块各占多少寄存器和共享内存？最紧的限制让多少块同时驻留？
- 长度不整除块大小时，边界由谁、用什么条件保护？

## 机制讲解：SM、线程块与线程的层级

CUDA 的组织方式是三层：一次 kernel 启动一个网格（grid），网格由许多线程块（block）组成，块内的线程再按 warp 分组调度。编程时你决定“每块多少线程、一共多少块”；硬件决定“每个块放到哪个 <Term id="sm"/> 上，何时执行”。

一个定量的对比帮助建立直觉：一颗典型服务器 CPU 同时运行的硬件线程是几十条量级；一张 GPU 同时在场的是几十万条。差了四个数量级，这意味着 GPU 的线程必须“多而轻”——启动一条线程几乎零成本，但每条线程能用的寄存器和本地资源也很有限，靠数量而不是靠单条线程的复杂逻辑取胜。

以 NVIDIA H100 SXM 为例做算例。假设与规格：132 个 SM，每个 SM 最多同时驻留 2048 个线程（取自公开资料的常见值；其他卡数字不同，但推理方法一样）。那么整卡同时驻留的线程上限是：

```text
132 个 SM × 2048 线程/SM = 270,336 个线程同时在场（约 27 万）
```

注意这是“同时在场”的容量，不是每秒完成的计算量。线程块一旦分配到某个 SM，就驻留在那里直到执行完；后续的块在有空位的 SM 上启动。若每块 256 个线程，则单个 SM 最多驻留 2048 ÷ 256 = 8 块，整卡最多 132 × 8 = 1056 块。

把层级和数量汇总成一张表（数字均为 H100 SXM 假设下的示例）：

| 层级 | 规模 | 由谁决定 |
| --- | --- | --- |
| 网格 grid | 一次 kernel 的全部块 | 程序按问题规模指定 |
| 线程块 block | 如每块 256 线程；每 SM 同时驻留至多 8 块 | 程序选块大小，硬件分配到 SM |
| warp | 32 线程，每 SM 至多 64 个 | 硬件的调度与执行单位 |
| 线程 thread | 每 SM 驻留上限 2048 | 线程数上限与资源限制取最紧 |

还要区分“逻辑线程”与物理执行：逻辑线程是编程模型里的工作身份，GPU 并不会为它保留一个独占的算术单元。硬件以 warp 为单位调度，用大量线程之间的切换来掩盖访存延迟——某个 warp 在等数据时，SM 切去执行别的 warp，让计算与访存重叠。这套层级是 NVIDIA CUDA 路径的具体实现，其他加速器的分组与调度规则可能不同；学它是为了掌握一套真实机制，再辨认可迁移的并行原则。

两个容易被忽略的推论。其一，块与块之间没有隐含的先后顺序，硬件可以用任意顺序、在任意 SM 上执行它们，也不提供块间同步原语——所以划分必须让每个块不依赖其他块的进度，块内归约可以用同步完成，跨块汇总就要另起一个 kernel 或用其他机制。其二，块大小通常取 32 的倍数（常见 128、256），否则最后一个 warp 会被凑不满：256 = 8 × 32 恰好整除；1000 线程的块要按 32 个 warp 分配，最后一个 warp 只有 8 条有效通道。

“驻留”与“排队”也要分开：超过驻留容量的块不会被丢弃，它们排队等待，SM 上每完成一块就补一块。所以后面算例一里“工作量是容量 62 倍”不是问题，反而是好事——SM 永远有下一块可补；真正的问题是反过来的情形（算例二），队列本身就是空的。

还有一类开销与线程组织无关但常一起出现：kernel 启动本身有固定的提交与调度成本（微秒量级，量级假设）。若用 Python 循环逐元素提交成千上万个小 kernel，每个 kernel 只做一点计算，启动开销就会淹没实际工作。这正是上一章看到“框架把许多小算子融合成一个 kernel”的动机之一：融合既减少搬运，也减少启动次数。

### 算例：喂得饱与喂不饱

**算例一：为什么 4096×4096 矩阵乘喂得饱。** 矩阵乘 [M,K]×[K,N] 的可并行输出有 M×N 个，因为每个输出元素只依赖自己的那行与那列。当 M=N=4096 时：

```text
输出元素数 = 4096 × 4096 = 16,777,216 个（约 1677 万）
相对硬件容量 = 16,777,216 ÷ 270,336 ≈ 62 倍
```

就算乐观地假设“一个线程算一个输出”，工作量也是硬件一次能容纳的 62 倍，意味着 SM 要连续接收许多波线程块，始终有事可做。换成分块视角也一样：若每个块负责 128×128 的输出小块，需要 (4096÷128)² = 32² = 1024 块；132 个 SM 即使每次各只驻留一块，也要约 1024 ÷ 132 ≈ 8 轮才能做完。并行度远超硬件容量，这是“喂得饱”的算术含义。

**算例二：为什么 7-token 教学模型喂不饱。** 本课程的教学模型每 token 只有 2 维，一层的关键计算是 [7,2]×[2,2]，可并行输出 7 × 2 = 14 个。14 个线程连一个 warp 的 32 个位置都填不满，更不用说 27 万个驻留槽位——GPU 几乎整个空转。

把维度换成真实规模再看：假设隐藏维 d=4096 的层，一次前向处理 7 个 token，输出也只有 7 × 4096 = 28,672 个，约占驻留容量的 28,672 ÷ 270,336 ≈ 11%，不足一波。而生成阶段每步只处理 1 个新 token，输出 1 × 4096 = 4,096 个，约占 4,096 ÷ 270,336 ≈ 1.5%。

这两组数字解释了一条经验规律：训练和大 batch prefill 是“计算多到要排队”，适合 GPU；小 batch decode 是“线程槽位大量空着”。空着不代表不要读数据——每一层权重仍要从 <Term id="hbm"/> 完整读一遍，所以小 batch decode 常常回到上一章说的带宽瓶颈：算术强度低、并行度也低，双重不利。同一段模型代码快慢悬殊，根源常常就在这两个比例，而不是代码“写得好不好”。

补一笔计算量，说明算例一不仅“块数够”，每块里也有实打实的工作：每个输出元素要算一条长度 4096 的点积（4096 次乘加），总浮点运算约 2 × 4096³ ≈ 1374 亿次。可并行度高、每个线程的计算也不单薄，两者叠加才是矩阵乘能吃满 GPU 的完整原因；反过来，若只把 16,777,216 个输出摊给线程而每个只做一次加法（就像向量加法），它立刻变成上一章的带宽问题。

这两个比例也是许多推理引擎设计的驱动力：continuous batching、增大批规模、Prefill/Decode 分离，本质上都是在把更多可并行的工作塞进同一波，让 27 万个驻留槽位有更高的有效占用。本章先把“有多少槽位、为什么空着”算清楚，这些机制留到后面的章节展开。

### warp 与合并访存：相邻线程读相邻地址

CUDA 中一个 warp 通常包含 32 个线程（32 个执行通道，常称 lane），它们一起提交访存请求。硬件不逐个线程处理请求，而是把一个 warp 的请求合并（coalesce）成少量内存事务，这直接决定上一章的带宽利用率。合并的判断单位是 warp 而不是整块：内存系统每次面对的是 32 条通道的一组地址，与其他 warp 无关；一维连续编号下，块大小从 256 改成 512，每个 warp 读哪 32 个相邻元素并不变。

算例（假设元素为 4 字节 float32，内存以 32 字节 sector 为最小搬运单位）。warp 0 处理下标 0..31，两种索引写法：

```text
情形 A（相邻线程读相邻元素 a[i]）：
  线程 0..31 的地址：0, 4, 8, …, 124 字节，连续 128B
  落在 4 个 sector → 搬运 128B，实际需要 128B → 利用率 100%

情形 B（按列读行主序 4096 列矩阵 a[row + col×4096]，相邻线程递增 col）：
  相邻线程地址差 = 4096 × 4B = 16,384B
  32 个线程散落在 32 个不同 sector → 搬运 32 × 32B = 1024B
  实际需要 128B → 利用率 12.5%，流量放大 8 倍
```

同样是“每线程读一个数”，情形 B 让 <Term id="bandwidth"/> 有效吞吐降到八分之一。这正是“跨步读取”的代价：它不是让每个字节变慢，而是让每次搬运夹带大量用不上的字节。转置、按列归约、布局不当的批量查表，都可能落入这种模式。

因此索引写法不只是正确性问题：`线程 i 读元素 i` 与 `线程 i 读元素 i×4096` 在正确性上都对，在带宽上差 8 倍。看 kernel 时应养成习惯——先问这 32 个相邻线程的地址是否相邻。

也有天然合并不了的访问：embedding 查表里相邻线程查不同 token 的行，行间距离由词表宽度决定，不是重排索引就能变连续的。这类模式的出路是改变分工（例如多个线程合作搬一整行）或接受它、靠足够多的并发请求把带宽填满——合并访存是工具，不是每类算子都能直接满足的条件。

二维的情形更有代表性。给矩阵乘的分块加载 A、B 两个小片时，A 片沿 K 维连续（相邻线程读相邻地址），B 片沿 N 维排列、在行主序存储里却隔了一整行——直接按“数学上自然”的分工去读，两个片一个合并、一个跨步。常见的解法不是改变数学，而是改变分工：让线程沿存储连续的方向各读一段，先写进共享内存，再让块内线程从共享内存按需要的任意模式去读。共享内存没有合并限制，跨步的代价只出现在片内一次，而不是每次参与运算都付一次。这也是“分块提高算术强度”之外，共享内存的第二重作用：给访问模式解耦。

顺带一个与掩码相关的执行细节：同一 warp 的 32 个线程一起执行同一条指令路径；若块内不同线程走了不同分支（例如只有部分线程满足掩码条件），warp 内才需要分批串行执行，这称为分支发散。整块、整网格的分支差异不会这样逐条串行——发散的代价单位是 warp，不是块。这也是边界掩码通常代价不大的原因之一：它只影响最后一个不完整的 warp 附近的线程。

### occupancy：资源怎样限制驻留的线程数

一个 SM 能驻留多少线程，不只看 2048 这个线程数上限，还要看寄存器和共享内存这两类资源的消耗。概念性地看（不背公式，只看“谁先耗尽”）：

寄存器算例（假设 H100 每 SM 有 65,536 个 32 位寄存器，分配粒度等细节先忽略）：

```text
每块 256 线程，每线程 64 个寄存器：
  每块占用 256 × 64 = 16,384 个 → 65,536 ÷ 16,384 = 4 块可驻留
  4 × 256 = 1024 线程 → 占线程上限 2048 的 50%

每线程 128 个寄存器：
  每块占用 256 × 128 = 32,768 个 → 只能驻留 2 块 = 512 线程 → 25%
```

共享内存同理：若每块申请 200KB 共享内存，即使线程数远没用满（H100 每 SM 共享内存上限约 228KB），一个 SM 也放不下第二块，因为 2 × 200KB = 400KB 超过上限。线程数、寄存器、共享内存几项限制取最紧的那个，才是实际驻留规模。

这些上限不必背：真实卡的 SM 数、每 SM 的线程/寄存器/共享内存上限，可以用 CUDA 自带的设备查询工具或 Nsight Compute 的 occupancy 报告读到，编译工具链也提供按资源计算驻留块数的接口。本章用 H100 SXM 的数字，只是为了让算例落在真实规格上，方法比数字重要。

Occupancy 常指实际驻留 warp 相对硬件上限的比例（上例分别是 50% 与 25%）。驻留 warp 多，某个 warp 等待访存时，硬件更有机会切换到别的 warp，让计算与访存重叠；驻留太少，延迟藏不住。但它不是越高越好，这就回到本章开头的问题：

增加每线程寄存器，可能让性能变差（如上例从 4 块降到 2 块，掩盖延迟的能力下降），也可能让性能变好（更多数据留在寄存器里复用，减少对较慢存储的重复读取）。两种效应方向相反，孰大孰小取决于算子的数据复用结构和实际访存行为，要靠基准测试判断，不能只看占用率一个数字。把“占用率低”直接写成故障结论，是性能分析里的常见误判。

事实上，高性能矩阵乘 kernel 常常主动选择低占用：每线程用更多寄存器保存分块数据、每块申请大块共享内存，驻留块数因此下降，但每次访存搬来的数据被复用得更充分，总耗时反而更短。占用率 90% 的朴素写法输给 25% 的分块写法，在真实基准里并不罕见——占用率回答的是“能藏住多少延迟”，不回答“需要藏多少延迟、总共搬了多少字节”。

驻留规模还带来“波次”与尾巴的概念：若每 SM 每次只完成 1 块（简化假设），391 块在 132 个 SM 上要分 3 波，最后一波只有 391 − 2×132 = 127 块，132 个 SM 中 5 个空着。这个例子尾巴很短，但同样的机制放大就很伤：若总共 133 块，第二波只剩 1 块在跑、131 个 SM 空等近一半时间。块数不是 SM 数的整数倍、或驻留块数受资源压制时，都会产生尾部空转；把问题切得足够大（如算例一的 62 倍），尾部占比就变得不重要。

最后把数据复用说完：矩阵乘中同一输入元素参与多个输出的计算，分块（tiling）先把一小片数据搬进共享内存供块内多次使用，提高上一章 <Term id="roofline"/> 说的算术强度。但共同使用一片数据需要知道“写入何时完成”：一个线程开始读之前，负责加载的线程必须已写完，块内同步（如 `__syncthreads()`）用来建立这条依赖。同步范围不要扩大理解——块内同步不会同步整张 GPU 上的所有块，跨块的顺序由流与事件等其他机制保证。

## 代码走读：一个 Triton kernel 长什么样

下面是 `labs/kernel/triton_add.py` 中 masked 向量加法的核心部分（源码阅读，未在 GPU 上运行）。Triton 让你按“块”而不是按单线程写程序：你描述一个程序实例怎样处理一段 BLOCK 大小的数据，编译器再把它落到线程层级上。

```python
@triton.jit
def add_kernel(X, Y, Z, N: tl.constexpr, BLOCK: tl.constexpr):
    offsets = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK)
    mask = offsets < N
    x = tl.load(X + offsets, mask=mask, other=0)
    y = tl.load(Y + offsets, mask=mask, other=0)
    tl.store(Z + offsets, x + y, mask=mask)

def add(x, y):
    assert x.is_cuda and y.is_cuda and x.is_contiguous() and y.is_contiguous()
    assert x.shape == y.shape and x.dtype == y.dtype and x.device == y.device
    z = torch.empty_like(x)
    if x.numel():
        add_kernel[(triton.cdiv(x.numel(), 256),)](x, y, z, x.numel(), 256)
    return z
```

逐行对应本章的层级概念：

- `BLOCK` 是每个程序实例处理的元素数（这里 256），对应线程块的概念——Triton 把一个程序实例映射到一个块，`tl.arange(0, BLOCK)` 生成块内 256 个并行位置，相当于每条通道各自拿到自己的块内偏移。
- `tl.program_id(0)` 是这个程序实例的编号，即块编号；`program_id(0) * BLOCK + tl.arange(0, BLOCK)` 正是热身例子的公式：块编号 × 每块元素数 + 块内偏移。相邻实例处理相邻数据段，天然满足合并访存。
- `mask = offsets < N` 是边界检查：长度不整除 BLOCK 时，最后一块的一部分位置会拿到越界偏移；`tl.load/tl.store` 的 `mask=` 让这些位置既不读也不写，`other=0` 只给被掩码的读一个占位值。
- 启动处的 `triton.cdiv(x.numel(), 256)` 是向上取整的块数，方括号里的元组就是网格形状——一维网格，块数由数据长度决定（长度 100,003 时即 `(391,)`，下文核对）。
- `if x.numel()` 是空数组保护：长度为 0 时 cdiv(0, 256) = 0，网格形状成为 (0,)，而零块的启动在 CUDA 中不被允许；主程序测试列表里开头的 0 就是对这条路径的检查。

用一个数字核对这个映射：N = 100,003 时，cdiv(100003, 256) = 391 块（因为 390 × 256 = 99,840 < 100,003 ≤ 391 × 256 = 100,096）。最后一块编号 390，覆盖偏移 99,840 到 100,095；其中有效的是 100,003 − 99,840 = 163 个位置，其余 93 个被掩码置空。上一节的“尾巴”算例用的正是这 391。

`tl.constexpr` 的标注也值得停一下：被标成 constexpr 的参数在编译期固定，编译器按这些值专门生成一份代码。N 也标了 constexpr，意味着每个不同长度各有一份编译产物——对以固定长度反复调用的训练算子合适，对长度频繁变化的调用则要付出重复编译的成本；这类取舍属于后续实验的观察点。

另外注意启动的异步性：Python 侧的 `add(x, y)` 返回后，GPU 上的 kernel 可能还没执行完，它只是把启动提交进了流；后面真正的计时用 CUDA event 在流内对齐，而不是靠 CPU 的时钟。这与上一章“张量 runtime 调度算子”的视角衔接：CPU 负责提交与组织，设备侧按流推进。

`add()` 里的断言值得留意：`is_contiguous` 保证 `offsets` 直接对应底层存储位置（回想上一章的 stride），形状与 dtype 检查保证两个输入的元素一一对应。这些是“正确性基线先于性能”的最小形态——主程序因此敢于在 0、1、255、256、257、100003 这些边界长度上逐一断言结果等于 `x + y`。文件其余部分用 CUDA event 对比 Triton 版与 `x + y` 的耗时，属于后续 GPU 实验内容，此处不展开。

为什么从向量加法而不是矩阵乘开始读？因为它把本章的三件事——块划分、索引公式、边界掩码——压缩在十行里，又有 `x + y` 这个现成的正确性基线；先在最小算子上把这些机制看顺，再去读带归约、分块和共享内存同步的矩阵乘 kernel，每一层新机制才有落脚点。

提交这次启动时，操作进入一个 <Term id="stream"/>——按序执行设备操作的队列。同一流内的操作按提交顺序执行；不同流之间有并行机会，但数据依赖不会自动建立。例如流 A 写一个缓冲区、流 B 读它，就需要事件等同步机制显式连接，仅凭 CPU 先调用 A 再调用 B 不能推断依赖已建立。后面的 NCCL 流水线会把这一点变成关键：通信未完成就读结果，错误偶发难复现；处处全局同步虽稳妥，却可能失去重叠收益。

本章不要求你会写 kernel，只要求看到 kernel 时能把它放回层级里：这段代码的一个实例是什么（块）、实例里有多少并行位置（warp 与通道）、越界由谁挡（掩码）、资源由谁限制（寄存器与共享内存）。后面的分布式章节反复用到的“计算与通信重叠”，落到硬件上也是这套层级加流的结果。

## 动手：纸笔划分线程块

不写代码，只用纸笔把划分做一遍。假设：数组长度 N = 1,000,000（取十进制一百万，明确标注，避免与 2 的幂混淆），每块 BLOCK = 256 个线程，float32 元素，计算 `out[i] = a[i] + b[i]`。

题目故意取十进制长度，让边界掩码真的出现；涉及硬件规模的问题沿用正文的 132 个 SM（H100 SXM 假设）。建议先自己算完七问，再展开核对。

1. 需要启动多少个线程块？写出计算式，并说明为什么不能更少。
2. 最后一个块覆盖哪些下标？其中多少线程有效、多少被掩码？掩码条件怎么写？
3. 若 N 恰好是 1,048,576（2 的 20 次方），上述答案哪些会变？
4. 这次计算一共搬运多少字节的数据？结合上一章的算术强度，判断它更接近带宽瓶颈还是计算瓶颈。
5. 最后一块里有效的 64 个线程，按 warp 怎么划分？有没有凑不满的 warp？
6. 回顾算例一：这些块分配到 132 个 SM 上，按“每 SM 同时只驻留一块”的简化假设大约分几波执行完？这个估计忽略了什么？
7. 若把 BLOCK 从 256 改成 1000（先不管 Triton 的限制，按 CUDA 规则想），块数、warp 利用和驻留情况各会怎样变化？

<details>
<summary>展开核对</summary>

1. 块数 = 向上取整 N ÷ BLOCK = 1,000,000 ÷ 256 = 3906.25，向上取整为 **3907 块**。任何更少都会漏元素：3906 × 256 = 999,936 < 1,000,000。

2. 最后一个块编号 3906（从 0 数起），覆盖下标 3906 × 256 = 999,936 到 3907 × 256 − 1 = 1,000,191。有效下标必须 < 1,000,000，共 1,000,000 − 999,936 = **64 个有效线程**，其余 256 − 64 = **192 个被掩码**。掩码条件即 `offsets < 1_000_000`，与代码走读中 `mask = offsets < N` 完全一致。

3. 1,048,576 = 256 × 4096，整除，所以是 **4096 块**，且最后一块 256 个线程全部有效——掩码条件仍然要写，只是在这个长度下恒为真。这解释了实验代码为什么专门测试 255、256、257 这些边界长度。

4. 读 a 与 b 各 4MB、写 out 4MB（按 1,000,000 × 4 字节计算）：3 × 4,000,000 = 12MB；浮点运算约 1,000,000 次加法。算术强度 ≈ 1,000,000 FLOP ÷ 12,000,000 B ≈ 0.08 FLOP/B，远低于任何 GPU 的计算/带宽比，向量加法是典型的带宽瓶颈算子——它的优化方向是少搬字节和高效合并访存，而不是减少加法次数。

5. 64 = 2 × 32，恰好是 **2 个完整 warp**；其余 192 = 6 × 32 个位置构成 6 个整 warp，全部被掩码。整 warp 被掩码时硬件直接跳过，不产生发散代价，所以这个尾巴主要浪费的是“占着块名额”，而不是串行执行。

6. 3907 ÷ 132 ≈ 29.6，约 **30 波**：29 × 132 = 3828 块占满前 29 波，最后一波只剩 3907 − 3828 = 79 块，大部分 SM 空闲收尾。注意两个方向的忽略：一是每 SM 同时驻留的块不止一个（向量加法每线程资源占用很小，可能驻留满 8 块，真实“波数”约为 3907 ÷ 1056 ≈ 3.7）；二是忽略了启动开销与访存竞争。所以“波数”只是工作量为硬件容量多少倍的另一种说法，不是严格的时间分段。

7. 块数变为 1,000,000 ÷ 1000 = **1000 块**，恰好整除、无需掩码，但每块 1000 线程要按 ceil(1000 ÷ 32) = 32 个 warp 分配，最后一个 warp 只有 8 条有效通道、24 条空闲；总通道数 1000 × 32 × 32 = 1,024,000，比元素数多 2.4%。驻留上，2048 ÷ 1000 向下取整只剩 **2 块/SM**（2000 线程，线程占用率仍有约 98%，但块粒度变粗：从 8 块变 2 块，掩盖延迟与均衡负载的粒度都变差），而且 1000 已逼近每块 1024 线程的上限。在 Triton 里这条路直接走不通：`tl.arange` 要求 2 的幂长度，这正是实验代码选 256 的原因之一。

</details>

做完这个练习，再看任何 kernel 都可以问同一组问题：多少工作量、分多少块、边界怎么掩、每线程耗多少资源、相邻线程的地址是否相邻。

这一章带走三句话：

- 饿不饿看比例：可并行工作量 ÷ 约 27 万驻留槽位，决定 GPU 是排队还是空转。
- 快不快看地址：相邻线程读相邻地址，有效带宽利用率可以从 12.5% 到 100%。
- 驻留看最紧的资源：线程数、寄存器、共享内存谁先用完谁说了算；占用率是手段的度量，不是目标本身。

现在看一张 GPU 的图时，你已经可以追问：数据放在哪层？由哪些线程读取？哪些线程共享一片数据？什么依赖必须同步？性能分析需要这些具体问题，而不是只看一条 GPU 利用率曲线。
