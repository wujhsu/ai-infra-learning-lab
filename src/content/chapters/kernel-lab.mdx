我们先优化一个足够小、结果容易核对的表达式：`relu(2*x+1)`。relu 把负数变为零，非负数保持不变。它是纯数值加工，不涉及模型结构的复杂性——但训练里到处是这类逐元素链（缩放、偏置、激活、掩码），它们身上的搬运问题是一样的。

## 这一章解决什么问题

前两章的账都记在"时间"上：profiling 一章教我们测，gpu-execution 一章教我们看一个 kernel 在硬件上怎么跑。这一章换一个记账单位：**字节**。

一个 kernel 的快慢，大多数时候不取决于它做了多少次乘加，而取决于它搬了多少数据。乘加在寄存器里几乎不要钱；数据一旦要进出设备内存，每一字节都要按带宽交税。所以"优化一个算子"的第一问不是"怎么算得更快"，而是"**哪些搬运本来可以不发生**"。

"搬运"其实是两个可分开优化的量：**搬了多少字节**（流量），和**搬运了多少次**（启动次数）。后面会看到，融合优化的是前者，AdamW 的 foreach 路径优化的是后者——把这两个量分开记账，是本章最重要的思维工具。

本章沿一条主线走完三段：先在纸面上算清内存层级的账，弄明白融合到底省了哪几笔；再逐行读两个 Triton kernel，把"融合"从概念落到代码；最后看 AdamW 优化器的 single/foreach/fused 三种实现——同一个"减少搬运"的故事，在另一个方向上重演。

动手前先说破一个警告：PyTorch 的 eager 模式下，`2*x`、`+1`、`relu()` 通常各自启动一个 kernel；但一旦启用 `torch.compile` 之类的编译路径，框架可能已经替你融合了其中几步。所以先用上一章的方法看真实执行，再决定优化什么——既不能假设每个 Python 运算一定单独启动一个 kernel，也不能假设它一定被融合了。

还有一条诚实的边界要说在前面：本章所有 Triton 代码都没有在 GPU 上实跑过，正确性靠脚本内置的边界测试与 PyTorch 比对来保证，性能结论靠字节账推理。所以动手环节的定位是"纸面预测 + GPU 核对"，不是"照抄已知答案"。

## 机制讲解：先算内存层级的账

### 数据要经过一条越走越快的路

GPU 不是只有一块"显存"。数据从设备内存到参与运算，要穿过一条层级路径。下面的数字都是教科书量级，具体值随架构变化，但结论只依赖"层级之间差着数量级"这一个事实：

| 层级 | 位置 | 容量（量级） | 延迟（量级） |
|---|---|---|---|
| HBM（设备内存） | 芯片外 | 几十 GB | 数百 ns |
| L2 缓存 | 芯片内，所有 SM 共享 | 几十 MB | 约一两百 ns |
| 共享内存 | 每个 SM 内 | 几十 KB | 数十 ns |
| 寄存器 | 每个线程私有 | 每线程几百个 | 约 1 个时钟周期，不到 1 ns |

<aside class="concept-note">
<strong>量级声明</strong>

这张表只用于建立直觉：寄存器与 HBM 之间差约三个数量级——一次 HBM 访问的时间够做上千次寄存器级运算；HBM 带宽虽大（数据中心 GPU 每秒几 TB），却是整条路上最窄的口子。不同架构的具体数字请查对应手册，不要把这里的值当精确参数用。
</aside>

用"每字节数据配多少次运算"（算术强度）可以判断一个 kernel 卡在哪：把峰值算力和 HBM 带宽相除，得到这台机器的平衡点，量级在每字节十几到几十次运算（fp32、不用张量核心的口径）。逐元素链完全够不着：`relu(2*x+1)` 每元素只做约 3 次运算，却要搬 8 到 24 字节，算术强度不到 0.5——远在平衡点左侧，属于**带宽受限**：算力大量空转，时间全花在等数据。对这类 kernel，优化就等于减字节，这也是为什么本章的账本用字节记账。

eager 执行的问题由此而来：`relu(2*x+1)` 的中间结果被放到了最慢的一层。每个中间张量都要完整写回 HBM、再被下一个 kernel 完整读出——而它本可以在寄存器里生存与消亡。

### 融合为什么省：写一遍算例

取一个有代表性的规模：N = 4096 × 4096 个元素、float32。逐项把账算出来：

```text
N = 4096 × 4096 = 16,777,216 个元素，float32 每元素 4 字节
一个完整张量 = 16,777,216 × 4 B = 67,108,864 B = 64 MiB

eager 三步，每步一个 kernel，各读一个张量、写一个张量：
  t1 = 2*x ：读 x  (64 MiB) → 写 t1 (64 MiB)
  t2 = t1+1：读 t1 (64 MiB) → 写 t2 (64 MiB)
  y  = relu：读 t2 (64 MiB) → 写 y  (64 MiB)
HBM 总流量 = 6 × 64 MiB = 384 MiB

融合成一步，只读 x、只写 y：
HBM 总流量 = 2 × 64 MiB = 128 MiB

省掉 = 384 − 128 = 256 MiB
验算：256 MiB 恰好是两个中间张量各"写一遍 + 读一遍"
     = 2 × (64 + 64) MiB，占非融合流量的 2/3
```

注意融合省下的**不是计算**：乘、加、截断一次都没少。省的是 t1、t2 的搬运——它们留在寄存器里，从未到达 HBM。这就是"减少数据搬运"最具体的形式：**中间结果越靠近寄存器，HBM 流量越少**。

附带收益是 kernel 从 3 次启动变 1 次。这笔账也值得单算：一次 kernel 启动的开销量级在几微秒，来自 CPU 侧的准备、指令下发与 GPU 侧的调度。N = 4096² 时流量占绝对主导，启动费可以忽略；但把 N 缩到几千个元素，一个 kernel 只要几微秒，3 次启动费就可能与总时间同量级——**对小数组，启动次数是第一账本，流量退居第二**。这就是同一项技术在不同规模下"省的名目不同"。

### 什么时候不值得融合

融合不是免费的，概念级有三笔代价：

- **寄存器压力**。两个各自很重的算子合到一个 kernel 里，各自的中间值必须同时存活在寄存器中。教科书量级：每线程可用寄存器至多 255 个，一个 SM 的寄存器文件总量约 256 KB；逐元素链只占十几个，很宽的融合（比如一次加十路输入、或塞进一整个归约）会把中间值推过这条线。寄存器不够时要么溢写到 local memory（物理上又落回了慢层，融合白做），要么编译器降低并行宽度。
- **占用率下降**。每个线程占的寄存器越多，一个 SM 能同时驻留的块就越少，用来掩盖访存延迟的并行度随之下降。融合可能"省了字节、丢了并行"——两个各占 30% 端到端时间的算子，融合后就算把各自流量都清零，也可能因占用率损失追平收益。
- **失去各自的最优解**。合成后无法再给每个阶段单独选块大小、调度或数值实现；有全局依赖的操作（跨块归约、全局同步）也不能按这个模板直接融合。

所以优化问题不是"能不能把所有代码合成一个 kernel"，而是"当前瓶颈里的哪些中间量值得不写回，代价是什么"。

### 融合的近亲：分块复用

逐元素链靠融合省搬运；矩阵乘法靠**分块**省另一种搬运。`C = A×B` 的每个输出是 A 的一行与 B 的一列的点积，相邻输出会重复使用大量相同的输入——如果每个输出都独立地从 HBM 读，重复搬运会大到荒唐。用 N = 1024、float32 记一笔复用账：

```text
A、B 各 1024×1024×4 B = 4 MiB，两个加起来 8 MiB

朴素做法（每个输出独立读自己的一行一列）：
  N² 个输出 × 每个 2N 次元素读取 = 2N³ = 2,147,483,648 次读取
  × 4 B ≈ 8 GiB —— 是真实数据量的 1024 倍

按 32×32 分块（子块载入共享内存后复用）：
  每个元素被读的次数从 N=1024 降到 N/32=32 次
  总流量 ≈ 32 × 8 MiB = 256 MiB —— 缩小 32 倍
```

分块没有改变任何一个乘加，改变的是读取顺序与复用位置：让数据在共享内存里被用够再走。块取得更大，复用更多，但共享内存容量（每 SM 几十 KB 量级）与寄存器占用会反过来限制块大小和驻留块数——和融合一样，是"快层容量"与"并行度"的折中，没有随形状不变的万能配置。

FlashAttention 是同一张地图上的另一个点：把注意力分块并在线归一化，避免把巨大的位置×位置得分矩阵写回慢层存储。训练的反向传播还会带来不同的重计算与存储取舍，所以不能只看前向一张性能图。两者与融合共享一句话：**让数据在快的层级里被用够，再离开**。

## 代码走读：从 triton_add 到 triton_fused

`labs/kernel/triton_add.py` 是一个正确性优先的骨架；`labs/kernel/triton_fused.py` 在骨架上做融合。两个 kernel 的核心体合起来不到 20 行，先看第一个：

```python
@triton.jit
def add_kernel(X, Y, Z, N: tl.constexpr, BLOCK: tl.constexpr):
    offsets = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK)
    mask = offsets < N
    x = tl.load(X + offsets, mask=mask, other=0)
    y = tl.load(Y + offsets, mask=mask, other=0)
    tl.store(Z + offsets, x + y, mask=mask)
```

逐行拆开：

- `@triton.jit` 把这个 Python 函数编译成 GPU 程序；`N` 和 `BLOCK` 标了 `constexpr`，是编译期常量，编译器可以据此特化代码。
- `tl.program_id(0)` 是当前程序实例在第 0 维上的编号，也就是**块编号**。启动时按 `triton.cdiv(N, 256)` 个实例铺满网格，每个实例负责 256 个连续元素——向上取整保证最后一个不满的块也有人管。
- `tl.arange(0, BLOCK)` 生成块内相对位置 0..255；乘上 `BLOCK` 加块内偏移，得到这 256 个元素各自的**全局索引** `offsets`。此后所有操作都是对这 256 维向量的整块运算。
- `mask = offsets < N`：N 不被 256 整除时，最后一个块的索引会越过数组末端；mask 标出哪些通道有效。
- `tl.load(..., mask=..., other=0)`：无效通道**不读内存**，用 0 填充——既不越界访问，也不会污染有效结果。
- `tl.store(..., mask=...)`：同样只写有效通道。读写两头都堵住，边界才算正确。

外层包装 `add()` 断言形状、类型与连续性，`empty_like` 分配输出，`numel()==0` 时干脆不启动。启动发生在这一行：

```python
add_kernel[(triton.cdiv(x.numel(), 256),)](x, y, z, x.numel(), 256)
```

方括号里是**网格**：一个元组，每个分量给出一维上的块数，这里就是 `cdiv(N, 256)`——向上取整的除法，保证不满的块也有实例负责。后面跟普通函数调用的写法，把张量与两个编译期常量传进去。`256` 不是随手选的：GPU 以 32 个线程为一组（warp）调度，块大小取 2 的幂（256 = 8 组）能让块内向量整齐地铺满执行单元；`tl.arange` 也要求 2 的幂。块取得更大，程序实例更少、每实例占用更多寄存器；取得更小，实例多但每个太瘦——没有全局最优，只有随形状与硬件试出来的合适值。

正确性清单里最有含金量的是 `[0, 1, 255, 256, 257, 100003]`：255 和 257 是"差一个元素就整除"的两侧，100003 除以 256 余数非零——越界 bug 最容易藏在这些长度上。计时函数 `timed()` 同样有讲究：先空跑 10 次预热（排除编译与缓存冷启动），再循环 100 次取平均为一个样本，重复 30 个样本取中位数——中位数比均值抗抖动。口径包含输出分配与启动，不是孤立的 kernel 延迟，与上一章的口径一致。

再看融合版，结构完全同构，只是算术换了：

```python
@triton.jit
def fused(X,Y,N:tl.constexpr,BLOCK:tl.constexpr):
    offsets=tl.program_id(0)*BLOCK+tl.arange(0,BLOCK)
    active=offsets<N
    values=tl.load(X+offsets,mask=active,other=0.)
    result=tl.maximum(values*2.+1.,0.)
    tl.store(Y+offsets,result,mask=active)
```

与 `add_kernel` 逐行对比，只有两处不同：输入从两个减到一个；中间那行从 `x + y` 换成 `values*2.+1.` 再套 `tl.maximum(..., 0.)`。几个值得停下来看的细节：

- `other=0.` 带小数点——填充值要和数据类型（float32）一致；
- `values*2.+1.` 是对整块 256 维向量的一次乘、一次加，产出的 `t1`、`t2` 是寄存器里的临时向量值，不是张量：没有形状、没有存储地址，下一行立刻用掉；
- `tl.maximum(..., 0.)` 逐通道取最大，就是 relu 的定义。

关键正是 `t1`、`t2` 的身份变化——eager 里它们是各占 64 MiB、要在 HBM 走一个来回的张量；这里它们从未落进 HBM。一次 load、一次 store，账面上就只剩输入和输出。

两个文件也示范了"只有核心函数还不够完成一个实验"。kernel 体之外，`run()` 要断言输入合法、分配输出、处理零长度；主流程要先过正确性（多个边界长度、与 PyTorch 基线比对误差），再进计时（预热、CUDA 事件、多样本取中位数），最后把版本号、GPU 名称、口径说明一并打进 JSON 输出——**口径说明尤其不能省**：读者拿到 `median_ms` 时必须同时知道它含不含分配与启动，否则数字之间没有可比性。这一整套"外壳"在两个脚本里几乎逐行对应，读懂一个就读懂了另一个。

### 两个 kernel 的访存账

把四个版本放进同一张表（float32，N = 4096² = 16,777,216 元素）：

| 版本 | kernel 数 | 每元素 HBM 读 | 每元素 HBM 写 | 总流量 |
|---|---|---|---|---|
| eager `x+y` | 1 | 8 B（两个输入） | 4 B | 192 MiB |
| `triton_add.add` | 1 | 8 B | 4 B | 192 MiB |
| eager `relu(2*x+1)` | 3 | 12 B（每步各读一个） | 12 B（每步各写一个） | 384 MiB |
| `triton_fused.run` | 1 | 4 B | 4 B | 128 MiB |

两个诚实的读法。第一，`triton_add` 与 eager 加法的访存**完全相同**（每元素 12 B）——它的价值是那副可复用的骨架：索引、mask、网格、包装、计时，融合版正是在它上面长出来的，而不是因为它更快。第二，融合的正确对照组是三步 eager，收益是 384 MiB → 128 MiB；拿融合版去比单步 eager 加法，是比错了对象。这也回答了本章开头的问题背景：kernel 数量变少只是表象，字节数才是账本。

这张表也有它不覆盖的东西：它是 HBM 口径的理论账，没算 L2 命中——若输入或中间张量恰好还在 L2 里，eager 的实际 HBM 流量会小一些（几十 MB 的 L2 装不下 64 MiB 的张量，但装得下小规模测试的）；也没算输出分配与启动次数。所以表给出的方向与量级是可靠的，精确倍数要靠 GPU 实测——这正是动手环节要做的核对。

## 优化器的同款故事：single / foreach / fused

训练每一步都要更新参数，AdamW 是最常见的更新规则。它比"梯度直接减到参数上"多维护两份与参数同形状的状态：一阶动量 m（梯度的指数滑动平均）与二阶动量 v（梯度平方的滑动平均），一个定方向、一个自适应步长，再加上 weight decay、学习率与偏差校正的组合。状态正是这里的麻烦所在：**每步要碰的张量不是参数一个，而是参数、梯度、m、v 四个**——优化器天生就是字节大户，这也是它值得单独拿出来看的原因。

同目录的 `labs/kernel/optimizers.py` 用同一个随机种子、同样的 1024×1024 参数，对比 PyTorch 暴露的三条路径：

```python
for name,kwargs in [('single',{'foreach':False,'fused':False}),
                    ('foreach',{'foreach':True,'fused':False}),
                    ('fused',{'fused':True})]:
```

- **single**：逐张量的 Python 循环。一次 `AdamW.step()` 被拆成十几个小 kernel——更新一阶动量、二阶动量、偏差校正、缩放、写回参数……每个临时张量都要写回 HBM 再被下一个 kernel 读出，和张量版的"三步往返"同一个病，只是链更长。
- **foreach**：多张量批量路径。把许多张量并进同一次 kernel 启动。它减少的是**启动与 Python 循环开销**——搬运的"指令"变少了，但每个数学子步的临时张量仍在 HBM 往返，每字节的税没变。
- **fused**：整条更新公式（动量、方差、weight decay、学习率）进一个 kernel。梯度、两个动量状态、参数各读一遍，参数与状态各写一遍，中间量全在寄存器。它减少的是**访存字节**。

给单步更新粗略记一笔字节账（概念级，具体拆分数随 PyTorch 版本变化）。一次 AdamW 步必须触碰的张量：参数 p、梯度 g、一阶动量 m、二阶动量 v——脚本的参数是 1024×1024 float32，各 4 MiB：

```text
必要流量（任何实现都省不掉的）：
  读 p, g, m, v  = 4 × 4 MiB = 16 MiB
  写 p, m, v     = 3 × 4 MiB = 12 MiB
  合计 28 MiB

fused：一个 kernel，流量 ≈ 必要流量 28 MiB
single：十几个小 kernel，每个临时张量（分母、更新量…）再写回读出，
        每个临时多付 2 × 4 MiB，总流量成倍超出必要值
foreach：临时张量仍在 HBM 往返（流量接近 single），launch 数降到每类操作一次
```

这是同一个标题"减少搬运"下的两个不同方向：**foreach 减的是搬运次数（launch），fused 减的是搬运体积（字节）**。一大堆小张量时 launch 开销主导，foreach 先救场；单个大张量时流量主导，fused 收益最大；两者不互斥——fused 模式内部同样按多张量组织。

脚本本身有三个值得学的设计：

- 同种子、同形状：三条路径的 loss 轨迹应当一致（数值路径不同，只允许浮点舍入级差异），`loss_samples` 就是用来核对这一点的；
- 从第 20 步才开始计时：把建图与预热排除在测量之外；
- 同时记录 `peak_bytes`：省下的时间与省下的临时显存，是同一笔账的两面。

## 动手：先在纸上算，再到 GPU 上对

顺序很重要：先纸面、后实测。字节账是这一章最可复用的产出——它不需要 GPU 就能算，算错了立刻能发现（对不上"中间张量 × 写一遍读一遍"的结构），而 GPU 数字只有对着预测看才有意义。GPU 命令在下方实验卡片里；动 GPU 之前，先把四道纸上题算出来，跑到机器上才有得对：

1. N = 1000、BLOCK = 256：网格是多少个块？最后一个块有多少个有效元素？（算完对照：第 4 个块覆盖索引 768..1023，其中有效的是 768..999，共 232 个。）
2. N = 1,048,576（即 1024×1024，与优化器脚本的参数同规模）：融合 `relu(2*x+1)` 比三步 eager 省多少字节？（每张量 4 MiB，两个中间张量各写一遍读一遍：2 × (4+4) MiB = 16 MiB = 16,777,216 B。）
3. 把 `fused` 的 BLOCK 从 256 改成 1024：每元素 HBM 流量变吗？（不变——总元素数没变；变的是块数和每块的并行宽度。这就是"流量"与"并行度"是两笔账。）
4. `triton_add.add` 和 eager `x+y` 的每元素流量都是 12 B。那跑基准时两者时间差说明的是什么？（不是流量差，而是实现质量差异——启动路径、向量化效率等，数量级通常不大。）

四道题各自埋了一个常见错的疫苗：第 1 题防"忘了向上取整的最后一个块"；第 2 题防"把省下的流量记成一遍而不是写+读两遍"；第 3 题防"把流量与并行度混成一笔账"；第 4 题防"把 kernel 数量本身当收益"。都在纸上错一遍，比在 GPU 的输出里猜要便宜得多。

纸面账算清后，跑卡片里的两条命令。两个脚本都输出 JSON：`triton_add.py` 给出 eager 与 triton 的 `median_ms`/`min_ms`/`max_ms`；`triton_fused.py` 按多个规模各给一行，能直接看到规模变小时"流量优势"如何被启动开销稀释；`optimizers.py` 给出三条路径的 `step_ms` 与 `peak_bytes`。逐项对三件事：

- 融合相对三步 eager 的加速，方向应与 384 → 128 MiB 一致，但比例不会是整 3 倍——时间里有启动、分配等与流量无关的部分；
- 三条 AdamW 路径的 `loss_samples` 应当一致到浮点舍入量级——不一致说明对比的不是同一份数学；
- `peak_bytes` 的差值方向应与字节账一致——fused 的临时显存更省。

当结果变慢时，回到启动次数、内存流量和资源占用这三笔账找原因，而不是直接归因于"编译器不好"。下一章把手工优化与框架编译联系起来——到那时你已经知道，编译器该替你省的正是这一章算过的字节。
