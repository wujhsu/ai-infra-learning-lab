数据管道、张量布局与设备执行，前面几章分别把它们讲成“可能占时间的地方”。现在真有一段“训练很慢”的程序摆在面前：慢只是一个症状，可能是 GPU 在算，也可能是 GPU 在等。猜错方向的优化不只是白费力气——它让代码更复杂，却一点没快。

本章把“猜”换成“量”：建立一套能回答两个问题的测量——瓶颈到底在哪一段？动了它，整体最多能快多少？

## 这一章解决什么问题

先看三种典型的猜错，它们在真实项目里反复出现。

第一种，优化了不占时间的部分。花一周把某个逐元素算子改写成更精巧的形式，profile 一看，它只占端到端时间的 4%：就算快一倍，整体几乎没有感觉。

第二种，量对了对象，量错了口径。想量“GPU 算这一步要多久”，却在 Python 调用前后读 CPU 时钟——异步执行下，这个数字量到的是“提交”，不是“执行”。数字很稳定，但量的是另一件事。

第三种，局部收益没有兑现成整体收益。kernel 快了 10 倍，程序几乎没变快，因为省下的时间被别处的等待吃掉了，或者那个 kernel 本来就不在关键路径上。

三种失败有同一个根源：没有先分层、再测量、再决策。本章按这个顺序组织：先定义测量的三层口径，再用一张教学算例的 kernel 表演练“先优化哪个”的决策，然后读一段真实的计时代码，最后把这个决策过程留给你自己走一遍。

全篇贯穿一个教学算例：假设一段训练程序，一步端到端 168 毫秒。这个数字以及后面所有拆分都是假设的算例，不是实测——目的是让每一步判断都有数字可以落在上面。

读完的检验标准：不看正文，能把这 168 毫秒拆到三层，并对“先优化哪一段”给出带数量的理由。

## 机制讲解：把 168 毫秒拆成三层

### 第一层：墙钟与吞吐——用户感受到的时间

墙钟时间回答“一步多久”“每秒处理多少”。口径必须先说清楚：从哪到哪。训练循环的一步是“取到批次 → 前向 → 反向 → 更新”，这个区间的墙钟就是一步的端到端时间。

教学算例：一步 168 毫秒，即每秒约 5.95 步；若每步处理 16 个样本，吞吐约 95 样本/秒。

这一层的价值是当最终裁判：任何优化的成败，最后都要回到这一层复测。它的局限是什么都混在一起：168 毫秒里哪些是计算、哪些是等待、哪些是日志，它说不出来。拆开它，需要下两层。

先把容易互换的三种时间钉在墙上——异步执行使它们不能直接换算：

| 时间 | 量的是什么 | 正确的量法 |
| --- | --- | --- |
| 端到端（墙钟） | 训练循环感受到的完整一步 | 计时范围覆盖数据、计算与同步 |
| 设备执行 | kernel 在 GPU 上真正运行的区间 | CUDA 事件或 profiler |
| CPU 提交 | Python 发起一次调用花的功夫 | 裸时钟量到的往往就是它（常见误用） |

问题是“这个 kernel 是否变快”，就看设备执行；问题是“训练每秒处理多少有效样本”，就不能丢掉数据加载与更新。没有哪种口径永远最好，只有与问题匹配的口径。

### 第二层：kernel 级——每个 kernel 的时长与占比

用 PyTorch profiler 或 Nsight 采集一步内执行的所有 kernel，得到一张时长表。教学算例（假设的一次采集）：

| kernel | 时长 | 占比 |
| --- | --- | --- |
| gemm（大矩阵乘） | 85 ms | 70.8% |
| elementwise（逐元素运算） | 12 ms | 10.0% |
| 主机到设备的数据拷贝 | 10 ms | 8.3% |
| norm 归约 | 8 ms | 6.7% |
| 索引与切片复制 | 5 ms | 4.2% |
| 合计 | 120 ms | 100% |

读表的第一眼是 80/20：gemm 一项占 71%，五个 kernel 里最热的一个吃掉了七成设备时间。但“最热”不等于“该先做”。把决策写成一棵树：

```text
一步端到端时间里——
├─ 存在大段 GPU 空闲？── 是 ── 先消空隙：预取、流水线、减同步（系统层，见第三层）
│                        否
├─ kernel 表里有非必要的工作？── 是 ── 先消除多余的：融合或删除（不需要更聪明）
│                                否
└─ 剩下必要且最热的工作 ── 优化它：分块、精度、算法（每一点加速都更贵）
```

第一刀不在表内。端到端 168 毫秒，kernel 合计只有 120 毫秒，剩下 48 毫秒去哪了？如果存在大段等待，先处理等待——优化再快的 gemm 也缩短不了 GPU 空闲的时间。

确认没有大段空隙之后，才回到表内，对每一行问两个不同的问题：它是必要的工作吗？它有更快的等价形式吗？两个问题对应两条优化路线。

- 消除多余的：elementwise 12 毫秒加索引复制 5 毫秒，若能融合进相邻 kernel 或干脆删掉，一步省 17 毫秒。消除不需要更聪明，只需要不做。
- 优化最热的：gemm 是必要计算，让它更快需要更聪明——分块、精度、算法选择，而且每一点加速都受硬件上限约束。

用数字对比两条路线（假设 48 毫秒空隙与其他 kernel 都不变）：

```text
消除 17 ms 多余工作：120 → 103 ms，端到端 168 → 151 ms，快 1.11 倍
gemm 加速 1.2 倍：    85 → 70.8 ms，省 14.2 ms，端到端 168 → 153.8 ms，快 1.09 倍
```

一次 1.2 倍的 gemm 改进，收益和“删掉两段多余工作”相当，而后者通常工程代价小一个量级。但两条路线的上限方向不同：消除多余的上限就是那 17 毫秒，做完即止；gemm 占比大，越往上每一点加速越贵，但理论上限也高得多。所以顺序是：先摘掉多余的，再攻坚最热的。

### 局部加速怎样换算成整体收益

上面对比用的是一个可以写在手边的公式。设被优化部分原占比为 f，加速倍数为 s，假设其他部分时间不变：

```text
新时间 / 旧时间 = (1 − f) + f / s
```

三个代入，全部是教学算例：

```text
f = 0.2，s = 2：        0.8 + 0.1  = 0.9    → 整体快 1.11 倍
f = 0.1，s = 10：       0.9 + 0.01 = 0.91   → 整体快约 1.099 倍
f = 0.708（gemm），s 趋近无穷：→ 0.292      → 上限约 3.4 倍
```

第二行就是本章开头的问题：占总时间 10% 的 kernel 快 10 倍，整体最多快约 1.099 倍——不到一成一。两点警告随之而来。其一，“其他部分不变”经常不成立：优化可能改变缓存命中、执行重叠和排队关系，所以公式只用于排序候选，结论必须端到端复测。其二，f 很小时，再大的 s 也救不了整体——这是“先看占比再动手”的数学理由，也是第一种猜错的解剖图。

### 第三层：系统级——等待：数据、通信、调度

回到那 48 毫秒。教学假设它的构成是：数据等待 30 毫秒（取批次慢于计算），同步与调度 18 毫秒。这段时间 GPU 空闲，时间线上表现为空隙。

系统层的结论经常反直觉：如果一步里有 48 毫秒空隙，正确动作是预取数据、流水线化、减少同步——而不是碰任何 kernel。反过来，GPU 一直忙也不等于没事可做：它可能在做大量不必要的拷贝，而不是有效数值计算。所以口诀是“先找空隙，再找最贵的工作”。

工具层次跟着问题走，不要一次全开：PyTorch profiler 把算子、形状和部分内存事件联系起来，适合回答“哪个算子占时间”；Nsight Systems 看 CPU、CUDA、通信的整体时间线，适合找空隙和重叠机会；更细的 kernel 分析（存储访问、指令、硬件限制）再交给 Nsight Compute。分析本身有开销，详细记录可能改变调度——探索时可以多开，最终的性能数字要在干净的测量配置下复核。

### 同步误差：异步执行下的墙钟会撒谎

张量运行时一章讲过：Python 调用把 kernel 放进设备的队列就立刻返回，GPU 在后面异步执行。于是这段看似合理的计时是错的：

```python
t0 = time.perf_counter()
for _ in range(100):
    fn(x)
t1 = time.perf_counter()   # 循环返回时，GPU 可能才刚开始算
```

教学算例：假设 CPU 每次提交只要 0.05 毫秒，GPU 每次实际执行 1.2 毫秒。循环跑完时墙钟只走了约 5 毫秒，而真实执行需要 120 毫秒——相差 24 倍，而且这个错误的方向永远是“偏快”。

修复有两种。简单的一种是让墙钟等到设备真正做完：

```python
for _ in range(20):
    fn(x)                       # 预热（见下一小节）
torch.cuda.synchronize()        # 队列清空，起点干净
t0 = time.perf_counter()
for _ in range(100):
    fn(x)
torch.cuda.synchronize()        # 等最后一次执行真正结束
t1 = time.perf_counter()        # 这才是“执行”的墙钟
```

更精确的一种是用 CUDA 事件在设备侧计时——下一节的代码走读用的正是事件。两种口径量到的都是“执行”，区别在事件由设备打点，不受 Python 循环里提交顺序的干扰。

### 预热与稳态：把一次性工作分开

第一次执行往往包含设备初始化、内存分配、算法选择，以及编译——torch.compile 的第一次调用尤其慢，编译一章会展开。这些是一次性成本，混进采样会让“稳态下每步多久”的答案失真。

所以量稳态：先跑若干次预热，再开始采样。冷启动是另一个问题，需要另开实验刻意包含这些成本。两者不能混着比：把编译的第一次调用计入 compiled 的成绩、却只测 eager 的稳定阶段，是不公平对照；反过来完全忽略编译时间，也无法回答“只运行几次的任务值不值得编译”。

一次性成本该不该忽略，取决于任务会跑多少次。还是教学算例：假设首步含 300 毫秒编译，之后每步稳态 168 毫秒——

```text
只跑 10 步的任务：  (300 + 10 × 168) / 10  = 198 ms/步   稳态数字低估了近 18%
跑 1000 步的任务：(300 + 1000 × 168) / 1000 ≈ 168.3 ms/步  稳态数字基本成立
```

同一个稳态 168 毫秒，对长任务是有意义的答案，对短任务是系统性偏快的答案。“量稳态才有意义”这句话的完整版本是：先问任务跑多少次，再决定一次性成本怎么算。

### microbenchmark 的坑：缓存让重负载偏快

单独反复测一个 kernel（microbenchmark）还有一个系统性偏差，概念上要心里有数：反复执行同一负载时，输入数据会驻留在 GPU 的 L2 缓存里，后续执行从更快的缓存读取，而不是像真实训练那样每步处理新数据、从高带宽内存搬入。比如 2048×2048 的 float32 张量约 16 MB，而数据中心 GPU 的 L2 通常是几十 MB 量级——同一输入的重复执行恰好是最容易命中缓存的情形。

这不是禁止 microbenchmark，而是要求报告时写清楚：输入是否复用、测量的是不是“缓存命中情形”。下一节的脚本里，eager 与 compiled 两边同样反复使用同一输入，作为相对比较仍然公平；但它的绝对数字会偏乐观，不能直接外推为真实训练的每步耗时。

## 代码走读：benchmark.py 怎样计时

`labs/kernel/benchmark.py` 对同一个 `relu(2*x+1)` 比较 eager 与 `torch.compile` 的稳态设备耗时——编译章的 Lab 卡片会真正运行它。本章没有在 GPU 上运行过这个脚本（见文末验证说明），下面是方法走读。计时骨架节选自文件第 9–17 行：

```python
for name,fn in [('eager',baseline),('compiled',compiled)]:
 for _ in range(20):fn(x)
 torch.cuda.synchronize();samples=[]
 for _ in range(30):
  start=torch.cuda.Event(enable_timing=True);end=torch.cuda.Event(enable_timing=True)
  start.record()
  for _ in range(100):fn(x)
  end.record();end.synchronize();samples.append(start.elapsed_time(end)/100)
 results[name]={'median_ms':statistics.median(samples),'samples_ms':samples}
```

每一行都能在前面的机制里找到对应：

| 代码 | 对应机制 |
| --- | --- |
| `torch.testing.assert_close(compiled(x),expected)`（第 7 行） | 正确性检查在性能结论前面 |
| `for _ in range(20):fn(x)` | 预热：把编译与一次性成本留在采样外 |
| `torch.cuda.synchronize()` | 消同步误差：确保预热真正完成 |
| `start.record()` / `end.record()` | CUDA 事件在设备侧计时，量的是执行不是提交 |
| 30 个样本，每个含 100 次调用 | 稳态采样；`elapsed_time(end)/100` 折算为每次毫秒 |
| `median_ms` 与 `samples_ms` 一起保存 | 报分布，不只报一个数 |
| 输出 torch 版本、设备名、形状、dtype | 结论写成别人能复查的记录 |

还有两个设计值得指出。其一是对照实验的结构：两个候选只有“是否 compile”一个变量，输入是同一个 `x`——单变量修改正是测量闭环图里的一环。其二是正确性在前：第 7 行先用 `assert_close` 确认 compiled 与 eager 输出一致，才允许进入计时。更快的代码可能漏算了一部分、换了精度或改了归约顺序；判定前要先定误差容限，接近零的数值只用相对误差会不稳定，而浮点归约顺序造成的合理差异也不该一律判错。只在恰好整除块大小的输入上验证过，同样不足以宣布正确。

没有 GPU 也能在 CPU 上练习同一套方法。`python -m timeit` 对小循环做的就是“预热加重复采样”：

```bash
python -m timeit -s "x = list(range(1000))" "sum(x)"
python -m timeit -s "x = list(range(1000))" "total = 0
for v in x:
    total += v"
```

`-s` 后面是只执行一次的准备语句，相当于固定输入与预热；后面是要反复计时的语句。注意一个口径差异：timeit 默认报告多次重复里最好的一次，它回答的是“这段代码最快能做到多快”；要看稳定性，得看它同时打印的各轮数字。这与本章“报告中位数、保留波动”的建议并不矛盾——前者是代码能力的口径，后者是系统运行的口径，你要哪个，取决于问的是哪个问题。

无论哪种测量，把结论写成别人能复查的记录：输入形状与分布、精度、版本、硬件、预热方式、采样次数、计时范围、正确性误差、原始样本。如果结论是“某型号 GPU、某种形状下少 15% 时间”，就按这个范围写，不要从一个小数组外推所有模型与所有负载。

4. 最该先验证的是那 28 毫秒等待是否真实存在、能否被重叠。它决定第一优先级的成立与否：如果实测等待只有 5 毫秒，整个排序就要重来。占比最大的 allreduce 反而不是最急的数字，因为即便量准了，它的改进路径（减通信量、重叠）也更贵。
