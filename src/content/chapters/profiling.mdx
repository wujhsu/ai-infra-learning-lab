数据管道、张量布局与设备执行都可能占时间。现在有一段“训练很慢”的程序，第一步不是选择一种优化，而是建立能回答问题的测量。

## 你量的是哪一段时间？

至少区分三种时间：CPU 提交一项工作的时间，设备执行这项工作的时间，以及用户或训练循环感受到的端到端时间。异步执行使它们不能直接互换。

如果只在 Python 调用前后读时钟，可能量到提交；如果在 GPU 事件之间计时，可以观察流中对应设备工作的区间；如果量完整一次更新，则还包含数据、同步、日志等额外环节。

没有哪种口径永远最好。问题是“这个 kernel 是否变快”，就先看设备执行；问题是“训练每秒处理多少有效 token”，就不能丢掉数据加载与更新。

## 预热是为了把一次性工作分开

第一次执行可能包含设备初始化、内存分配、算法选择或编译。稳态性能需要先预热，再收集多次样本；冷启动性能则需要另开实验，刻意包含这些成本。

把编译第一次调用计入 compiled，却只测 eager 的稳定阶段，会产生不公平对照。反过来完全忽略编译时间，也无法回答一个只运行几次的任务是否值得编译。

```python
# GPU 环境，比较同一函数与输入的稳态设备耗时。
for _ in range(20):
    fn(x)
torch.cuda.synchronize()
start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
start.record()
for _ in range(100):
    fn(x)
end.record()
end.synchronize()
print(start.elapsed_time(end) / 100)  # 毫秒/调用
```

这是一段特定流中的平均区间测量，不包含整个服务的网络与排队。多流并发、图回放与内存复用也需要与测量目标相容。重复实验报告分布，不能只挑最快的一次。

## 正确性检查必须在性能结论前面

更快的代码可能漏算了一部分、越界、使用不同精度或换了目标。先对同一输入与可信基线比较，再定义误差容限。

绝对误差关心差了多少，相对误差关心相对参考值差多少；接近零的数只用相对误差会不稳定。浮点归约顺序改变也可能造成合理差异，因此不能把“不是逐位相同”一概判为错误，也不能无限放宽容限掩盖问题。

对不同形状、边界长度和数值范围检查。只在恰好整除块大小的输入上正确，不足以说明通用 kernel 正确。

## 先找空隙，再找最贵的工作

时间线里大段 GPU 空闲，可能来自数据准备、CPU 控制、同步或通信等待。GPU 一直忙，也可能在做大量不必要的复制，而不是有效数值计算。

PyTorch profiler 可以把算子、形状和部分内存事件联系起来；Nsight Systems 用于看 CPU、CUDA、通信等整体时间线；更细的 kernel 分析再观察存储、指令和硬件限制。工具层次应跟着问题走。

不要把所有采样工具一起打开就认为证据更多。分析本身有开销，详细记录可能改变调度；最终性能数字应在明确的测量配置下复核。

## 一个小优化能影响整体多少？

若某部分占总时间 20%，把它加速两倍，原来 100 ms 会变成 `80 + 20/2 = 90 ms`，整体只快约 1.11 倍。局部巨大的加速并不自动变成系统同等收益。

一般可写为 `新时间/旧时间=(1−f)+f/s`，f 是被优化部分原先占比，s 是它的加速倍数。这个估算假设其他部分不变；实际优化可能改变缓存、重叠和排队，需要端到端再测。

## 把结论写成别人能复查的记录

至少保存输入形状与分布、精度、版本、硬件、预热方式、采样次数、计时范围、正确性误差和原始样本。报告中位数或分位数，并保留波动。

如果结果是“某型号 GPU、某种形状下少 15% 时间”，就按这个范围写。不要从一个小数组外推所有模型与所有负载。
