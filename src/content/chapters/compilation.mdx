上一章手动合并了几个算子。真实模型有许多算子，编译系统尝试分析整段计算，再生成更适合设备执行的实现。你需要理解它看见了什么，以及哪些工作仍留在 Python 或运行时。

## 编译先需要看见一段可分析的计算

Eager 执行随程序逐项派发运算。图捕获则将一段可表示的张量运算收集成计算图，使后续阶段能够分析依赖、消除重复、融合或选择实现。

`torch.compile` 是这条流程的用户入口之一。常见路径涉及 Python 执行捕获、面向自动求导的图处理，以及后端代码生成。TorchDynamo、AOTAutograd、Inductor 分别参与这些环节；它们不是三个可以任意互换的推理引擎。

初次调用可能触发编译，随后符合条件的输入可以复用结果。判断收益时同时考虑冷启动与重复次数，而不只看稳态 kernel 时间。

## 图中断是什么意思？

当一部分程序无法按当前路径纳入同一计算图，系统可能结束当前图，回到普通执行，再继续捕获后面的部分。这个边界常称 graph break，即图中断。

例如依赖张量数值决定 Python 分支、把设备数值取回 Python、某些不支持的操作或副作用，都可能影响捕获。具体能力随版本变化，因此要看诊断信息，不能仅凭一段旧教程判断某种写法永远不支持。

图中断不必然导致结果错误，但可能降低融合机会、引入额外边界或重复编译。优化前先确认它是否在热点路径，以及消除它会不会改变原有语义。

## 为什么换一种输入长度会再次变慢？

编译结果通常受输入形状、类型、设备或其他条件约束。系统用 guard 等检查确定结果是否仍可复用。新输入不满足条件时，可能走新的编译路径。

动态形状支持能够覆盖一定变化范围，但并不意味着完全没有条件或额外开销。为所有请求强行使用同一填充长度，也可能浪费计算；为每个长度独立编译，又可能产生大量冷启动成本。

服务中的形状分桶是在两者之间取舍：把相近输入组织到有限的形状集合中。需要结合输入长度分布、缓存和延迟目标评估，不能只按“编译命中率高”判断。

## CUDA Graph 与计算图编译有什么区别？

CUDA Graph 关注把一组设备操作及其依赖捕获后回放，减少重复提交等开销。它并不自动等同于融合所有算子，也不是 `torch.compile` 的同义词。

回放通常要求满足相应的内存地址、形状或执行约束，具体支持由框架管理。改变输入时，可能是向可复用缓冲区写入新值，再回放已建立的工作图。

编译与 CUDA Graph 可以在某些路径中配合，也可以独立讨论。先分清“改写运算实现”与“减少反复提交的工作”，才知道应该观察哪个指标。

## 做一个完整对照实验

项目提供 `labs/kernel/benchmark.py`，对同一个 `relu(2*x+1)` 比较 eager 与 compiled。脚本先比较正确性，再分别预热，使用设备事件采样，输出版本、设备、形状、类型和原始样本。

```bash
python labs/kernel/benchmark.py
```

这需要 CUDA GPU。脚本不会在没有 GPU 时伪造一组“演示性能”。CPU 可以理解计算图和运行其他正确性例子，但不能据此推断 CUDA kernel 的实际加速。

接下来可以尝试多种形状，分开记录第一次调用和稳态。若编译后没有收益，先看原算子是否已高效、计算量是否太小、图是否中断、形状是否不断变化。

## 回到模型训练与推理

训练还包含反向与优化器；推理有队列、KV 管理和动态请求生命周期。编译某个模型函数，并不会自动优化所有周边系统。

因此源码阅读会从实际热点入口出发，追踪哪些段被捕获、生成代码落在哪里、运行时又做了什么。你不必先写一个编译器，但应该能解释一次改动影响了哪一段执行。
