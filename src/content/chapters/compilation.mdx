上一章我们用 Triton 手工把 `relu(2*x+1)` 写成一个 kernel，并数了省下的数据往返。真实模型有几百个算子，逐个手写既不可能也不必要——`torch.compile` 尝试让程序自己完成这件事。问题随之而来：**它到底改变了哪些工作，哪些工作原样留在了 Python 里？** 本章用一个表达式、一份源码走读和几个算例回答，不引入“编译器很智能”这类不可检验的断言。

路线分四步：先划定编译器改变与不改变的工作；再讲 capture 与 lowering 两阶段的机制，并用算例数清重编译次数；然后沿源码走读任务验证这条路径；最后把计数规则变成你自己能完成的练习。

## 这一章解决什么问题

先回到没有编译器的世界。Eager 执行下，Python 逐行解释你的模型代码：每个 `x * 2` 都要走一遍 Python 解释、张量派发、kernel 启动的完整路径。上一章已经在这条路径上数出两笔浪费：

- **派发与启动开销**：算子再小，Python 对象包装、调度和 kernel launch 的固定成本也要照付；
- **中间数据往返**：`2*x` 的结果写回设备内存，`+1` 再读出来，`relu` 又写一次——最多三次全局内存读写，只有最后一次是必要的。

把这笔账落到 `relu(2*x+1)` 的一次调用上：

```text
eager（完全未融合时）：
  kernel 1：读 x   → 写回 t1 = 2*x
  kernel 2：读 t1  → 写回 t2 = t1 + 1
  kernel 3：读 t2  → 写回 y  = relu(t2)
设备内存：3 次读 + 3 次写；kernel 启动：3 次；每次都经过一遍 Python 派发
```

框架可能已经融合其中一部分，所以上一章强调先看真实执行再谈优化；这里展开的是未融合的最坏形态，用来界定问题的规模。

手工融合解决第二个问题，但你自己就成了编译器：读代码、找相邻算子、写 Triton。`torch.compile` 把这件事自动化——在程序运行时分析一段 Python 执行，生成一份替代代码。所以它改变的工作是：

| 工作 | eager 下 | torch.compile 后 |
|---|---|---|
| 决定执行哪些运算 | 每次调用时逐行解释 | 捕获成图，一次分析 |
| 相邻算子的融合 | 没有（除非手写 kernel） | lowering 阶段自动融合 |
| 每次调用的固定开销 | 每行 Python 都付 | 只剩 guard 检查与生成代码入口 |
| 分析与生成代码的成本 | 不存在 | 首次遇到新工况时一次性付出 |

最后一行是编译的代价：分析和代码生成本身要时间，这正是“第一次调用更慢”的来源，也是本章要算的账。

同样要看清**没有改变**的：图外的 Python（取数据、循环控制、日志）照旧执行；缓存、队列、KV 管理这些系统组件与编译无关。编译某个模型函数，不等于优化了整个服务。

## 机制讲解：torch.compile 的两阶段故事

把 `torch.compile(f)` 想成给 `f` 换一个入口。调用它时，实际发生的事可以讲成两幕：先把 Python 执行**捕获**（capture）成计算图，再把图**lowering** 成设备代码。两幕之间还有一个不认清就读不懂日志的角色：guards，守卫。

### 第一幕 capture：把 Python 执行追踪成图

`torch.compile` 不解析你的源代码文本。它在运行时接管 Python 的帧执行——入口在 `torch/_dynamo/eval_frame.py` 的 `compile_wrapper` 与 `optimize`（TorchDynamo 组件）——让解释器在执行 `f` 的同时，把执行的每个张量运算记录成一张图。执行一遍、记录一遍：控制流这次走了哪个分支、`x.shape` 这次是多少，都被“烙印”进这张图。

具体记下了什么？还是那个表达式：

```python
def f(x):
    return torch.relu(x * 2 + 1)
```

捕获的产物是一张算子图（示意）：

```text
placeholder x
t1 = mul(x, 2)
t2 = add(t1, 1)
y  = relu(t2)
```

图里没有 Python：没有函数调用、没有属性查找，只有算子与依赖，这是后面能做融合分析的前提。但也因此，图只对“捕获时成立的条件”负责——`x` 的形状、dtype、设备，以及这次执行走过的分支，都作为条件被一并记录下来。

这带来一个根本约束：**Python 是动态的，而图是一次具体执行的快照。** 捕获时 `if x.max() > 0:` 走了 True 分支，图里就只有 True 分支的运算，下次输入走 False 分支时这张图是错的；捕获时输入形状是 `[4, 2048]`，图里的形状假设也随输入改变而失效。无法纳入图的操作（依赖张量数值的分支、把设备数值取回 Python、不支持的调用）会导致**图中断**（graph break）：系统结束当前图、回到普通执行、再继续捕获后面的部分。图中断不一定造成错误，但会降低融合机会、增加边界，还可能带来重复编译。

### 为什么需要 guards：失效检查与重编译

不能每次调用都重新捕获（那比 eager 还慢），也不能盲目复用（结果可能错）。系统的做法是：捕获的同时生成一组**守卫**——一组关于本次执行条件的廉价检查：“输入形状是 `[4, 2048]`”、“这个维度是 64”、“闭包里的开关还是 True”。此后每次调用先跑 guards：

- 全部通过 → 复用已编译结果，直接执行生成代码；
- 任一失败 → 这份快照不再适用，触发**重新编译**（recompile）：以当前输入重新捕获、重新生成。

guards 覆盖的也不只是形状。粗略按失效原因分类：

| 检查对象 | 什么时候失效 | 典型场景 |
|---|---|---|
| 张量形状 | batch 或序列长度变化 | 服务中来了不同长度的请求 |
| dtype / 设备 | 换精度、换卡 | 量化切换、多卡训练 |
| Python 标量与全局状态 | 超参、开关改变 | 训练阶段切换标志位 |
| 对象身份与属性 | 换模块实例、容器内容变化 | 动态组装的层列表 |

分类不必背。遇到“为什么又编译了”，先在日志里找是哪一类 guard 失败，而不是猜。

所以“换一种 batch size 就变慢一次”的机制是：新形状让 guard 失败，第一次遇到它要付一次编译。而关键在**缓存按“已见过的形状”记账，不按“形状变化次数”记账**。下面用一个算例把这条规则数清楚。

### 算例：同一模型三种 batch size 触发几次编译

模型就用 benchmark.py 的那个表达式：`f(x) = relu(2*x+1)`，`compiled = torch.compile(f)`。调用五次，batch 维依次为：

```text
调用序号：   1    2    3    4    5
batch：     4    4    8    8    4
```

按“每个首次出现的形状触发一次编译”计数：

| 调用 | batch | guard 结果 | 发生什么 | 累计编译次数 |
|---|---|---|---|---|
| 1 | 4 | 无缓存条目 | 编译 #1 | 1 |
| 2 | 4 | 通过 | 直接复用 #1 | 1 |
| 3 | 8 | 失败（形状不再是 4） | 编译 #2 | 2 |
| 4 | 8 | 通过 | 直接复用 #2 | 2 |
| 5 | 4 | 对 #2 失败，命中 #1 | 复用旧条目 #1 | 2 |

答案是 **2 次编译、5 次调用**。第 5 次最容易数错：对最新条目 #2 这确实是一次 guard 失败，但缓存里 #1 的条目还在——每个被编译的函数可以挂多条缓存记录，系统回退到仍匹配的那条即可，**不需要**再编译。“形状变回来了”不等于“再编译一次”。

一个必须交代的边界：PyTorch 默认的 automatic dynamic shapes 会在重编译时比较前后两次的差异，把变化的维度标成符号（动态）形状，生成对一批形状都成立的图。于是第 3 步的编译可能直接产出“batch 任意”的版本，让累计编译停在 1 次；代价是图内多一些符号形状的处理。某次调用到底重不重编译，由动态策略与版本共同决定——所以本章的动手环节和源码走读任务都要求**看日志**，而不是背口诀。

动态形状也并非“没有条件”：它扩大复用范围，图仍有自己的约束与开销。服务端把所有请求 pad 到同一填充长度是另一端的取舍——换来完全复用，付出无用计算；形状分桶把相近输入收拢到有限的形状集合，落在两者之间。这笔账留给推理服务章节，这里只需要知道它在机制层的根源：guard 按 shape 记账。

### 第二幕 lowering：图变成什么代码

capture 产出图之后，lowering 把图变成适合设备的实现。常见路径上，AOTAutograd 面向自动求导处理图（捕获前向、生成反向），Inductor 做代码生成：融合相邻算子、规划内存，在 GPU 上产出 Triton kernel，在 CPU 上产出 C++/OpenMP 代码。

融合的账不必重算——上一章已经数过：`2*x`、`+1`、`relu` 三个算子，eager 最多三次读三次写加三次启动；融合后一次读一次写一次启动。`torch.compile` 的 lowering 做的就是这件事的自动化版本，而且看得比手写更远：跨更多算子找融合机会、消除检查与派发、规划中间量的存放。<a href={asset('read/kernel-lab/')}>kernel-lab 章的融合账</a>在这里有了第二重身份：它是 lowering 阶段对每个点都在做的计算的纸上样本。

那一章同样数过融合的代价——寄存器压力、不能随意合并的依赖、块大小的权衡——编译器的搜索也受这些约束，可能放弃融合或改选分块。所以结论仍是看生成代码和 profiler，而不是假设“编译过等于全融合”。

训练还要多问一层：反向怎么办？AOTAutograd 在处理前向图的同时准备好反向的图，所以第一次 `backward` 也可能触发一轮编译——首步慢的不只是前向。优化器的 `step` 同样可以被独立编译：它与模型前向是不同的函数，各有各的缓存条目，也各有各的首次编译成本。

两幕加上运行期，收进一张表：

| 阶段 | 输入 | 产物 | 出问题时的表现 |
|---|---|---|---|
| capture | 一次 Python 执行 | 算子图 + guards | 图中断，回退普通执行 |
| lowering | 算子图 | Triton / C++ 代码与调度 | 保守实现或放弃融合 |
| 运行期 | 新的一次调用 | guard 通过则复用生成代码 | guard 失败，重新编译 |

后面读日志时，先把每条输出归到这三行之一，就不会迷路。

### 首步慢、稳态快：曲线的形状

把 100 次调用的时间画出来，eager 是一条平线，compiled 是一个尖峰加一条更低的平线。用教学数字摆出形状（**教学算例，非实测**；设 eager 每次调用归一为 1.0）：

| 调用 | 第 1 次 | 第 2 次 | 第 10 次 | 第 100 次 |
|---|---|---|---|---|
| eager | 1.0 | 1.0 | 1.0 | 1.0 |
| compiled | 55.0（含分析与代码生成） | 0.6 | 0.6 | 0.6 |

单次稳态从 1.0 降到 0.6，但首次多付了 54。回本点是一次除法：54 ÷ 0.4 ≈ 135，即大约第 135 次调用后累计时间才追平 eager。三个直接推论：

- **只跑几次的函数不值得编译**：训练循环里跑几千次的 step 函数值得，一个请求只走一次的冷路径不值得。重复次数决定编译是否划算，这正是章首问题的答案——第一次更慢不能证明编译没用，要分开量冷启动与稳态，再按真实重复次数算总账。
- **评测必须区分冷与热**：混在一起的计时要么高估收益（把编译成本摊没了）要么低估（只用首次计时）。
- **稳态的 0.6 里还剩什么**？guard 检查、生成代码的入口、kernel launch。`mode="reduce-overhead"` 针对最后这项：把编译后的整段设备工作捕获成 CUDA Graph 再回放，消掉逐次提交开销。一句话定位：它减少的是“反复提交”，不是融合，是与本章两幕正交的第三种优化。

CUDA Graph 的回放要求内存地址、形状等条件稳定，具体约束由框架管理。把它当成“自动消除一切 GPU 启动开销”的开关，会掩盖它和图编译在层次上的区别——源码走读任务也把这一点单列。

## 代码走读：compile-path 的阅读路径

机制讲完，问题变成：这套故事在 PyTorch 源码里从哪里验证？站内的<a href={asset('code/compile-path/')}>源码走读任务</a>按 PyTorch v2.14.0 组织了这条路径，这里按它的结构串一遍关键结论。

1. **入口**。从 `torch/_dynamo/eval_frame.py` 的 `compile_wrapper`（v2.14.0 约第 1147 行）和 `optimize` 入口（约第 1775 行）建立阅读范围。走读的第一课在这里：区分用户函数、捕获上下文与后端处理——**这些层不是同一个 kernel**。`@torch.compile` 换掉的是帧执行方式，不是换了一个推理引擎。
2. **guards 与重编译**。走读任务的最小实验：

   ```python
   import torch
   @torch.compile
   def f(x):
       return (x.sin() + x).relu()
   for n in [16, 16, 32, 32]:
       x = torch.randn(n)
       torch.testing.assert_close(f(x), (x.sin() + x).relu())
   ```

   把它存成文件，以 `TORCH_LOGS=recompiles,graph_breaks` 运行：先看重复形状的两次调用，再看形状变化的那次。任务特意强调**不预先断言某次一定重新编译**——automatic dynamic 策略与版本都会改变结果，日志才是裁判。上一节的算例要求用日志验证，原因相同。正确性对照来自 eager 表达式，与计时分开。
3. **图中断怎样继续读**。遇到断点时，先定位断点附近的代码，再判断它是否位于热点循环；减少断点不应以改变模型语义为代价。判断融合是否真的发生，要检查算子数量、内存读写和实际 profiler，而不是看到一段生成代码存在，就推断整个函数都被融合。
4. **CUDA Graph 是另一个层次**。它复用设备执行提交结构，`torch.compile` 处理程序捕获与后端生成；二者可以组合，但内存地址、形状和运行约束不同——对应本章 `mode="reduce-overhead"` 的定位。

任务的交付要求值得抄下来当习惯：固定版本、输入变化序列、正确性结果、日志与冷/热计时。若没有硬件，就完成捕获与日志观察，并明确写出 GPU 部分尚未验证——本章的 verification 字段正是这样记录的。

计时怎么落到代码？`labs/kernel/benchmark.py` 对同一个 `relu(2*x+1)` 比较 eager 与 compiled。计时骨架节选如下（**未运行**，需要 CUDA GPU；脚本先对拍正确性再计时）：

```python
for name, fn in [('eager', baseline), ('compiled', compiled)]:
    for _ in range(20): fn(x)                        # 预热：把首次编译挡在计时外
    torch.cuda.synchronize(); samples = []
    for _ in range(30):                              # 30 个样本，取中位数
        start = torch.cuda.Event(enable_timing=True) # 设备事件计时，避开主机视角偏差
        end = torch.cuda.Event(enable_timing=True)
        start.record()
        for _ in range(100): fn(x)                   # 100 次调用摊薄单次抖动
        end.record(); end.synchronize()
        samples.append(start.elapsed_time(end) / 100)
```

骨架的每个结构都对应本章一个论断：预热 20 次对应“冷启动与稳态分开量”；设备事件而不是 `time.time()`，因为异步的 GPU 执行只有事件和 `synchronize` 能给出真实完成时刻；每个样本 100 次调用再取中位数，避免把单次抖动当成收益。脚本在没有 GPU 时直接报错而不是伪造演示数字——CPU 上可以验证捕获与正确性，但不能据此推断 CUDA kernel 的实际加速。

## 动手：三种输入模式各触发几次编译

先不运行代码，按本章的计数规则推理，再用日志验证。设 `g` 是固定的小模型，`f = torch.compile(g)`；三次互相独立的运行，输入序列分别为（数字是 batch size）：

1. 模式 A：`8, 8, 8, 8`；
2. 模式 B：`8, 8, 16, 16, 8`；
3. 模式 C：`8, 16, 32, 64`（四个互不相同的 batch）；
4. 追问：把模式 C 的输入全部 pad 到 16 的倍数再送入，编译次数怎么变？省下的编译是用什么换来的？

前三问各给出次数和理由；第四问把机制接到服务端的真实取舍上。记录时给每次调用留一行：

| 调用 | 输入形状 | 我的预期 | 日志实际 |
|---|---|---|---|
| 1 | 8 | … | … |
| 2 | 8 | … | … |

先写下你的答案，再展开对照。

<summary>参考答案（先推理，再用 TORCH_LOGS=recompiles 验证）</summary>

按“每个首次出现的形状触发一次编译、缓存条目可回退复用”计数：

- **模式 A：1 次。** 第 1 次调用编译；后三次 guards 通过，直接复用。这是编译收益的理想工况：形状稳定，一次成本摊给全部调用。
- **模式 B：静态计数 2 次。** 8 首次出现编译 #1；16 首次出现时 #1 的形状 guard 失败，编译 #2；最后的 8 虽然对 #2 失败，但命中仍在缓存的 #1 条目，不再编译。常见错答是 3 次——把“guard 失败”与“重新编译”划等号，漏掉了缓存按形状记账、可回退到旧条目这一层。
- **模式 C：静态计数 4 次。** 每个新形状各触发一次，且中间没有任何复用机会——这是编译最差的工况：每次调用的稳态收益只覆盖它自己，净付出四次编译成本。
- **追问**：pad 到 16 的倍数后，形状集合从 {8, 16, 32, 64} 收拢为 {16, 32, 64}（8 被 pad 成 16），静态计数从 4 次降到 3 次。省下的编译用两样东西换来：pad 出来的位置要白算，且多了一次 pad 操作本身。这就是服务端形状分桶的最小版本——用受控的冗余计算，换有限的形状集合与更少的重编译。

但要把“静态计数”四个字当真：默认的 automatic dynamic shapes 在重编译时比较前后形状，把变化的维度符号化。模式 B 里 16 触发的那次重编译，很可能生成“batch 任意”的动态图，让累计停在 1 次；模式 C 同理可能远少于 4 次。策略与版本都会改变结果，所以最终裁判是日志：把三个模式分别在 CPU 上跑一遍（重编译行为可以在 CPU 上观察；性能结论不行），数 `TORCH_LOGS=recompiles` 输出的条目，与你的推理对照。

</details>

做完这个练习再回头看第一节的表：编译改变的是“每次调用的固定开销与融合机会”，付出的是“每个新工况的一次性成本”。输入分布的形状决定了哪边占上风——这也是推理服务要用形状分桶，把开放的长度分布收拢到有限形状集合的机制层原因。
