现在我们知道通信算什么、数据走哪里。最后一个问题是时序：必须等所有数据到齐才能计算吗？哪些计算可以提前开始，而不会读到未完成的结果？

## 从正确但完全串行的方案开始

假设有 4 个独立数据块，每块通信 3 ms，计算 5 ms。串行方案依次完成每块的传输与计算，总时间为 `4×(3+5)=32 ms`。

如果传输与计算使用足够独立的资源，第 1 块传完即可开始算；与此同时传第 2 块。后面的块按相同方式进入流水线。

关键条件是：计算第 i 块必须等第 i 块的数据可用，但不必无条件等所有块。这是依赖的细化，不是取消同步。

## 先建立数据可见，再讨论并行

CPU 调用返回、通信操作入队、设备数据可用，是不同阶段。具体 API 的返回语义要按所用 NCCL/PyTorch 接口核对，不能用一个“异步”词概括全部。

<Term id="stream"/> 与事件帮助声明某条设备执行流需要等待另一条流中的条件。正确依赖通常是“数据块写入完成后，消费者才能读”，而不是任意两个函数的文本先后顺序。

如果每次都执行全设备同步，容易保证一部分顺序，却会迫使无关工作也等待。若完全不等待，则可能偶发读取旧值或未完成数据。优化要找到准确的依赖边界。

## 理想流水线为什么还需要填充和排空？

本例的第一个计算要先等 3 ms 通信；之后计算阶段更慢，每 5 ms 才能推进一块。总时间为 `3 + 5 + (4−1)×5 = 23 ms`。

一般化为 n 块、每块通信 c、计算 p：

$$T_{serial}=n(c+p),\qquad T_{pipeline}=c+p+(n-1)\max(c,p)$$

n 无单位，c/p/T 使用同一时间单位。这是两阶段独立资源、每块成本恒定的教学模型。它不包含资源争用、同步开销或额外数据依赖。

把块数增加并不保证真实系统持续加速。块太小会放大启动和同步开销；块太大又可能降低重叠机会。真实通信还会与计算争用 GPU、设备内存或互连资源。

## NCCL 在训练和推理里出现的方式不同

训练的数据并行常在反向过程中逐步得到梯度。梯度 bucket 就绪后可以启动通信，与后面层的反向重叠。bucket 太大可能开始得晚，太小可能启动过多。

张量并行推理则常在层内出现结果交换，有些下游计算必须等 collective。能否切块、是否有独立工作、调用顺序是否一致，要按具体模型路径判断。

Device-initiated communication 等进阶接口进一步让设备端参与通信发起与同步。它们有版本、平台和编程语义要求，应在理解主机发起的基本路径后阅读，不宜把示例中的同步原语随意替换成另一种 barrier。

## 三个有用的诊断问题

第一，某个 rank 是否先发生异常，让其他 rank 只表现为通信超时？第二，各 rank 的 collective 类型、顺序与形状是否相容？第三，时间线中的等待是数据依赖、资源争用，还是过度同步？

只提高超时时间可能掩盖前两类错误。只增加 stream 也不会自动消除真实依赖。先恢复正确执行，再设计性能对照。

项目中先做最小 AllReduce 正确性，再做同机/跨机基准，最后追踪模型中的重叠。每一步都有独立的失败定位范围。
