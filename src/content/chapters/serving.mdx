## 这一章解决什么问题

到前面的章节为止，"模型"对我们来说是仓库里的一组文件：权重、配置、分词器。但用户从不直接消费文件——他们向一个地址发 HTTP 请求，看着文字一段段流回来。从"模型文件"到"可测量的服务"，中间隔着一段工程距离：谁把文件加载进显存？请求进来先经过什么？"第一个字很慢"该怪谁？

先把三个经常被混着说的词分开：**模型**定义数值计算与参数；**推理引擎**安排模型怎样在设备上执行，管理批次、缓存与并行；**API 服务**接收用户请求，处理协议与结果返回。三者可以住在同一个进程，也可以拆开。vLLM 是我们主要观察的实现：它同时提供引擎与 OpenAI 兼容的 API 层。极小模型用来学习机制；本章的工程线加载稳定受支持的 Qwen3-0.6B，逐项对照真实结构。

本章把这段距离拆成可以逐段指认的对象。读完你应该能：

- 说清一次流式请求从进入到返回要过哪几站，每一站各自会怎样失败；
- 用一个分解公式把"首字时间"与"总时长"算成具体毫秒，而不是一句"感觉慢"；
- 解释为什么动手之前要先跑一个不碰 GPU 的 `prepare.py`——它在替我们钉死什么。

引擎内部仍然是 <a href={asset('read/generation/')}>generation 章</a>建立的逐 token 循环：依据已有内容选下一个 <Term id="token"/>，把新输出接回输入，直到停止条件。区别在于，那一章的循环住在一段可以直接阅读的 Python 函数里，本章的循环住在一个真实引擎里，中间隔了 HTTP、调度和批次。

先交代本章的证据边界：**服务端需要 GPU 与 Docker，本环境没有运行**。文中所有毫秒数字都是标注过的算例（假设输入），作用是建立分解框架，不是实测成绩；能本地验证的部分——准备脚本与流式客户端——已由仓库内测试覆盖，覆盖到哪一层会在代码走读里逐一说明。

与前置章节的分工也说清楚：机制部分站在 <a href={asset('read/kv-reuse/')}>kv-reuse 章</a>的肩膀上——那里已经算清 prefill 处理整段输入、decode 每轮只进一个新位置的时间账，本章把这些阶段装回一条带排队与网络的端到端时间线；服务启动时的显存规划，用的是 <a href={asset('read/gpu-memory/')}>gpu-memory 章</a>建立的显存住户分类的推理侧版本——权重常驻、KV 池按比例划分，`--gpu-memory-utilization 0.8` 就是那套账的旋钮。

这也直接指向本章的核心问题：进程在运行、健康接口正常，但首个正文很慢，能不能说明 GPU 计算慢？读完分解账你会看到这个推理缺了中间环节——首字时间至少由三段相加，GPU 只拥有一段。

## 机制讲解：服务与前向的边界

### 一条请求要过哪几站，每站怎样失败

把"`/v1/chat/completions` 收到请求"到"客户端读到结束事件"的路径画直，是一条五站流水线：

| 站 | 做什么 | 一个具体的失败样子 |
|---|---|---|
| ① 输入处理 | 聊天模板拼接消息，<Term id="tokenizer"/> 转成 token ID | 多轮历史把输入撑过 `max-model-len`（本服务固定 4096），请求直接被拒；可见字数与 token 数不是一回事 |
| ② 调度与排队 | 请求进入引擎，等 KV 预算与批次位置 | 并发升高后新请求在队列里等待，TTFT 变长，但 GPU 此刻在忙别的批次——"首字慢"不等于"算得慢" |
| ③ 前向计算 | 引擎把多个请求的 prefill/decode 组织成 <Term id="batch"/> 执行 | 一条长输入的 <Term id="prefill"/> 占满本轮计算，其他请求的 <Term id="decode"/> 被推迟一个回合 |
| ④ 输出处理 | 新 token ID 反查词表，增量拼成文本 | 一个数据块可以携带多个 token 的文字，也可以是只含角色信息的空增量——按块计数会数错 |
| ⑤ 网络与协议 | 以 <Term id="sse"/> 事件持续写回，末尾附 usage 与 `[DONE]` | 中间代理把响应整个缓冲再转发，"流式"退化为一次性到达，TTFT 被假性放大 |

表里最重要的分界是第③站与其余各站：**前向计算只是五站之一**。健康接口探到的是最外层进程活着，它既不推进第①站，也不证明第②站没有排队。这是开篇问题的答案骨架，下一小节用公式补上数字。

失败定位因此有了抓手：不要问"服务为什么慢"，问"慢在哪一站"。每站至少有一个便宜的确认动作——第①站用服务端日志里的实际输入 token 数对照 4096 上限；第②站看引擎指标里的等待队列长度与调度次数；第③站看每步耗时和批次构成；第④站直接数客户端收到的块并对照 `usage`；第⑤站绕过代理直连，或对比同一请求在内网与外网的 TTFT。先定位站，再谈优化。

<details>
<summary>为什么第④站会让"块数"与"token 数"错位？</summary>

两个机制。其一是打包：SSE 的每个事件携带一段增量文本，服务端可以攒几个 token 再发一个事件，也可以为角色信息先发一个空事件——事件边界是协议实现的选择，不承诺与 token 边界对齐。其二是增量反查词表：token ID 转回文字按词表项拼接，增量 detokenizer 在字节序列确认完整之前可能持有 token 暂不输出，客户端看到正文的时间因此晚于 token 产生的时间。结论都指向同一处：客户端数块只能证明"收到了几段文本"，证明不了"模型生成了几个 token"；token 数只有服务端 `usage` 可信。

</details>

第③站内部是 generation 章那个循环的多请求版本：

<Diagram id="engine" caption="真实推理引擎的主循环：请求 → 调度与缓存预算 → 模型执行 → 输出与状态更新 → 下一轮或释放" />

这个循环不是"每个请求各自独占一个 for"。调度器每轮决定哪些请求参加、各推进多少；模型执行器统一跑一步；输出和完成状态再交回调度器。一次 HTTP 调用会跨过很多轮这样的循环——这个判断在源码里怎么落地，本章代码走读的最后一节会接上一篇专门的源码走读。

服务启动本身是第零站，同样不能用"进程在跑"代替：权重读取、设备初始化、按 `--gpu-memory-utilization 0.8` 规划显存、编译或图捕获，都发生在第一个请求之前。就绪检查因此有顺序：先看启动日志确认模型、revision、精度与设备分配，再查 `/v1/models`，最后发一个输入输出都定小的请求。健康接口通过，不等于业务延迟达标。

### TTFT 与 TPOT 的分解账

"慢"必须先拆成两个不同的指标。<Term id="ttft"/>（首 token 时间）回答"用户多久看到第一个字"；TPOT（每输出 token 时间）回答"之后每个字隔多久"。站内模拟器 `src/lib/simulations.ts` 的 `latency()` 用的正是这套口径：

```ts
ttft  = queue + prefill + network
total = ttft + tpot × (tokens − 1)
```

公式与五站流水线逐一对应，这是它值得背下来的原因：

| 公式项 | 对应的站 | 含义 |
|---|---|---|
| `queue` | ② 调度与排队 | 等批次位置与 KV 预算的时间 |
| `prefill` | ③ 前向计算（输入段） | 处理整段输入并产出第一个新 token |
| `network` | ⑤ 网络与协议 | 首个正文事件从服务端到客户端 |
| `tpot × (tokens − 1)` | ③ 前向计算（输出段） | 生成其余每个 token 的每步耗时 |

三个注脚，每个都对应一个容易算错的地方：

- **首 token 住在 prefill 里。** Prefill 的定义就是"处理整段输入，并用最后一个位置的输出决定第一个新 token"，所以公式没有单独的"首 token 解码"项——那一步是 prefill 的一部分，已经计入 `prefill`。
- **network 只加一次。** 这是教学口径的简化：TTFT 在首个正文事件到达客户端时测得，之后各 chunk 的网络时间被并进 TPOT，不逐段相加。
- **tokens 是输出 token 数**，且公式按"恰好生成这么多"计算；真实请求可能在到达上限之前命中停止标记提前结束。
- **TPOT 乘的是 (tokens − 1)，不是 tokens。** 第一个 token 已经由 prefill 交付，decode 只负责其余的；若误写成乘 tokens，64 token 的算例会多算整整一个 TPOT（25 ms），恰好等于把 TTFT 里的 prefill 又计了一次。TPOT 本身的来历在 <a href={asset('read/kv-reuse/')}>kv-reuse 章</a>：有 KV 缓存后，decode 每轮只处理一个新位置，这一轮的耗时就是 TPOT 的物理本体。

给一组假设数字算一遍（算例，非实测）。设排队 40 ms、prefill 180 ms、网络 20 ms、TPOT 25 ms，输出上限 64 个 token：

| 量 | 算式 | 结果 |
|---|---|---|
| TTFT | 40 + 180 + 20 | **240 ms** |
| 总时长（64 token） | 240 + 25 × (64−1) | **1815 ms** |
| 反解 TPOT | (1815 − 240) ÷ 63 | 25 ms（口径自洽的检查） |

这张表立刻给出三个诊断动作。TTFT 超标，先查排队与 prefill——是并发挤爆了队列，还是输入太长；TPOT 超标，查 decode 每轮——批次构成、显存带宽或引擎调度。两个指标对同一句"慢"开出的药方完全不同，这就是 <Term id="slo"/> 要分开写的原因。

再算一组，看"同一句慢"怎样指向完全不同的项。保持 prefill 180 ms、network 20 ms、TPOT 25 ms 不变，把并发加上去，排队从 40 ms 涨到 400 ms：

| 量 | 低并发 | 高并发 |
|---|---|---|
| TTFT | 240 ms | 400 + 180 + 20 = **600 ms** |
| 总时长（64 token） | 1815 ms | 600 + 1575 = **2175 ms** |

TTFT 涨到 2.5 倍，而模型计算本身一个毫秒都没变——全部涨幅来自排队。反过来，若两个场景的引擎侧指标（服务端口径的 TTFT）几乎相同、客户端口径差很多，涨幅就在 network。没有分解，这两种"变慢"无法区分。

还能看出一个结构性事实：**`tokens` 只出现在第二项里**。在该口径下，把 `max_tokens` 调大不碰 TTFT，只拉长总时长——这个结论留到动手环节做成预测题。

<aside class="concept-note">
<strong>易混点：TTFT 还分客户端口径与服务端口径</strong>


`latency()` 把 `network` 计入 TTFT，这是**客户端口径**——用户视角"发出请求到看见第一个字"。引擎指标面板里的 TTFT 通常是服务端口径，从请求进入引擎或完成输入处理起算，不含客户端网络。两个数字都合法，但不能放进同一张对比表。术语表里 TTFT 的定义专门强调"必须明确客户端还是服务端口径"；本章与 `measure_stream.py` 一律使用客户端口径，起点是发请求前，终点是第一个非空正文到达。


</aside>

最后回到开篇问题：健康接口正常，但首个正文慢。分解账说明"首个正文慢"至少有三种 GPU 无辜的情形：排队 200 ms 也慢、代理缓冲了响应也慢、prefill 本身长也慢（长输入是请求方自己发的）。不下结论先拆账，是本章想留下的习惯。

### 身份钉死：为什么动手前先跑 prepare.py

测量之前还有一个前提：**你测的确实是"那个"服务**。"我们都用 Qwen3-0.6B"这句话的信息量比看起来少：模型仓库的默认分支会移动，`v0.29.0` 这样的镜像 tag 可以被重新推送覆盖，分词器与配置还可能和权重取了不同版本。三个松动的身份，任何一个都能让两次"同一实验"的数字失去可比性。

所以本项目的第一步不是起服务，而是 `labs/serving/prepare.py` 把身份写死：模型固定为 `Qwen/Qwen3-0.6B` 的 revision `c1899de289a04d12100db370d81485cdf75e47ca`（40 位提交哈希），引擎镜像固定为 `vllm/vllm-openai:v0.29.0`。tag 便于人读，真正不可变的是拉取之后记录的 digest——`serve.sh` 会把实际的 `RepoDigests` 写进 `image-digests.json`，让"我以为在测 v0.29.0"变成一条可核对的记录。

三个松动的身份，各自咬人的方式不同。模型 revision 漂移：仓库默认分支更新后，同名模型的权重、分词器或配置变了——最隐蔽的情形不是报错，而是分词悄悄变了，同样的文字换了一组 token ID，输入长度与输出风格都跟着漂，测量对比悄然失效。镜像 tag 被覆盖：引擎行为（调度、内核、默认参数）变了，数字不可比。分词器与权重取了不同版本：模板对不上特殊 token，输出可能直接错乱。钉住一个 revision，等于让权重、分词器、配置整套取自同一提交。

还有一条边界要说死：实际 GPU、驱动与镜像的兼容性，必须在目标环境检查——CPU 上的极小模型测试不构成这套 CUDA 环境的验证。镜像能携带用户态程序，设备与驱动仍由宿主机管理；容器内看到某个 CUDA 版本，不单独证明宿主驱动能跑这个构建。这就是 `environment.json` 里 `hardware_verified` 单独成一个字段的原因。

这套语义不是本章独创。<Term id="artifact"/>（制品）的完整定义——可发布、可验证、可追踪版本的一组运行产物，以及"源码 commit、模型 revision、镜像 digest 三者不可互相替代"——在 <a href={asset('read/artifacts/')}>artifacts 章</a>展开。本章只取它的最小实践：先把身份钉死，再谈数字。

## 代码走读：prepare、measure 与一次请求的引擎路径

三个脚本各守一段：`prepare.py` 钉身份，`serve.sh` 起服务并记录 digest，`measure_stream.py` 测时间线。逐个看它们各自承诺了什么、没有承诺什么。

### prepare.py 的产物逐行

脚本只有两个实质动作，各写一个文件，全程不碰 GPU（docstring 第一句就声明了这一点——所以它可以在任何机器上运行和测试）：

```python
# labs/serving/prepare.py（固定值节选）
MODEL='Qwen/Qwen3-0.6B'
revision='c1899de289a04d12100db370d81485cdf75e47ca'
image='vllm/vllm-openai:v0.29.0'
```

- 第 6 行的校验：revision 必须恰好 40 个十六进制字符，否则抛 `ValueError`。防的是手滑把短哈希或分支名当 revision 写进去。
- 第 8 行写出 `experiment.env`，三个键各有消费方：

| 键 | 固定值 | 谁读它 |
|---|---|---|
| `MODEL` | `Qwen/Qwen3-0.6B` | `serve.sh` 的容器参数，决定加载哪个模型 |
| `MODEL_REVISION` | `c1899de…47ca` | `serve.sh` 转成 `--revision`，下载时钉住仓库内容 |
| `IMAGE` | `vllm/vllm-openai:v0.29.0` | `serve.sh` 的 `docker pull` 与 `docker run` |

- 第 9 行写出 `environment.json`：同样三个身份，加一个 `"hardware_verified": false`。最后一项是诚实的自白——这套身份**还没有**在真实 GPU 环境验证过；谁在哪台机器上跑通了，谁再去改它。

产物是给后续步骤的合同：`serve.sh` 只消费 `experiment.env`，人与后续章节读 `environment.json`。分成两个文件不是重复：`.env` 是 shell 能直接 `source` 的键值对，但机器可读、人不可审计；JSON 多出 `hardware_verified` 这样的运行状态字段，供之后的章节与报告引用。写完即打印下一步提示——`prepare.py` 管到此为止，起不起服务、在哪台机器起，是下一段脚本的事。

### serve.sh 怎样消费这份身份

`serve.sh` 开头 `source experiment.env`，然后一行哨兵：`MODEL_REVISION` 未设置就直接报错退出，提示先跑 `prepare.py`——身份没钉死，服务不许起。随后 `docker pull` 镜像、把实际 digest 存进 `image-digests.json`，再启动容器。启动参数里有三个和本章直接相关：`--served-model-name lab-model`（对外的模型名，请求里的 `model` 字段要填它而不是 `Qwen/Qwen3-0.6B`）、`--max-model-len 4096`（输入加输出的总上限，对应第一站的失败例子）、`--gpu-memory-utilization 0.8`（划分给引擎的显存比例，进而决定 KV 池大小，下一章展开）。端口只绑定 `127.0.0.1:8000`；模型文件缓存到实验目录的 `model-cache/`，第一次启动包含下载与加载时间。完整清理说明在推理项目（项目四）中。

这一段需要 GPU 与 Docker，本环境未运行——验证声明里"GPU 服务端未运行"指的就是这一步。

### measure_stream.py 的测量口径

客户端只用标准库，但对"测到了什么"极其较真。四个口径决定数字的含义：

**一、chunks ≠ tokens。** 脚本遍历 SSE 行，只把 `delta.content` 非空的帧记进 `chunks`，每条存 `{seconds, text}`：空增量（比如只带角色信息的事件）跳过，一个携带多个 token 文字的帧只算一条。所以 `len(chunks)` 既不是事件数，也不是 token 数——第五站的失败例子在这里被正面处理。

**二、token 数以服务端 usage 为准。** 请求带 `stream_options: {'include_usage': True}`，服务端在最后一个数据帧附上 `usage`；`completion_tokens` 才是 token 数的权威来源。仓库测试 `tests/test_stream.py` 用一个本地假 SSE 服务把两者钉在一起：服务端发 1 个非空内容帧、`completion_tokens` 为 7——**1 个 chunk，7 个 token**，同一次请求。

**三、成功与截断的判定。** `ok` 要求"见过非空正文"且"读到 `[DONE]`"同时成立；流被掐断会得到 `Stream ended before [DONE]` 而不是半份成绩。同一测试还覆盖了 HTTP 503 与截断两条错误路径。

**四、起点与汇总。** 计时起点在发请求前（`time.perf_counter()`）；`first_content_seconds` 是第一个**非空正文**的时刻，不是第一个网络事件。汇总输出中位数与 nearest-rank p95——对 20 个样本，p95 取排序后第 `ceil(0.95 × 20)` = 第 19 个值，nearest-rank 的含义是"至少 95% 的样本不慢于它"；脚本自带注记"chunk 计时不是 token 间隔、小样本 p95 不稳定"。

**五、负载的形状是参数。** 固定并发由线程池闭环维持：`--concurrency 4` 表示任意时刻最多 4 个在途请求，一个结束才补发下一个，这是"闭环"与开环压测的区别；`--repeat-input` 把一句固定中文重复 N 次再接一个问题，输入长度可控且内容不变；每行结果连同完整配置（`vars(a)`）写进 JSONL，先低并发验证功能与结束事件，再谈容量。`temperature=0` 与 `enable_thinking=False` 关掉两个噪声源——前者固定选择规则，后者不让 Qwen3 的思考内容混进正文计时（否则"首字"测到的可能是思考的第一个字，这正是本章 frontmatter 里提醒的口径问题）。

覆盖边界如实说明：**解析逻辑已由 `tests/test_stream.py` 在本地假 SSE 服务上验证**（正常流、503、截断），**真实 GPU 服务端未运行**——所以本章拿不出实测 TTFT，只有算例。

### 一次请求在 V1 引擎里的路径

第③站内部发生了什么，站内有一篇专门的源码走读：<a href={asset('code/vllm-request/')}>《一个请求怎样获得本轮 token 与 KV？》</a>，固定 vLLM v0.29.0 的 V1 引擎。这里按它的结论复述，给不马上读源码的读者对齐图景：

- 入口是 `EngineCore.step`：有请求就调用调度器，提交模型执行并取回输出，处理**执行期间到达的取消**，再更新调度状态。
- `Scheduler.schedule` 决定本轮的 token 预算、运行与等待集合；`KVCacheManager.allocate_slots` 按新 token、已计算前缀与 lookahead 分配块。"已计算 token 数"与"输出 token 数"不是同一概念——prefill 推进的是输入位置。
- 一次 HTTP 调用不等于一次引擎回合。生成跨很多轮，每轮可能与其他请求合批，直到结束或取消。
- 取消不是瞬时的：已提交给设备的工作可能无法立刻中断，引擎要在一致边界处理输出与请求状态。配套的 `labs/serving/cancel.py` 只负责在首个非空正文后关掉客户端流，并明确打印"后端回收必须在引擎指标/日志里另行验证"——它创建触发条件，不证明回收发生。

想把这条路径读扎实，那篇源码走读留了一个最小交付：以 4 个提示 token、最多 3 个输出 token 做纸面跟踪，列出每轮的新计算数、总历史、已分配块与是否结束；再把输入改成部分前缀命中，观察哪些字段改变。做完这个练习再看下一章的 KV 显存账，衔接是平滑的。

## 动手：固化身份，再预测一次测量

进入 Lab 之前，先做一道不花一分钱 GPU 的预测题——它检验你是否真的记住了分解账，而不是背下了公式。

**预测：** 同一个请求，只把 `max_tokens` 从 64 改成 512，两次都恰好生成满。TTFT 会变吗？总时长按什么比例涨？用算例数字（TTFT 240 ms、TPOT 25 ms）给出 512 时的具体毫秒数。

<details>
<summary>对答案</summary>

TTFT 不变，仍是 240 ms：公式里 `tokens` 只出现在第二项，排队、prefill、网络都不依赖输出上限。总时长 = 240 + 25 × (512−1) = 240 + 12775 = **13015 ms**，对比 64 时的 1815 ms。总时长比值约 7.2 倍，而纯 decode 段是 511 ÷ 63 ≈ 8.1 倍——总比例被不变的 TTFT 稀释了。两点保留：这是单请求、开环的教学口径，真实并发下更长的 decode 会占用引擎更久，可能反压后续请求的排队时间；其次"生成满"是上限口径，真实请求可能提前命中停止标记。

</details>
