某个周一早上你接手三个现场：一条训练任务里两份“应当相同”的参数差了 1.49e-08；一次故障恢复后 loss 突然跳回初始量级；一个服务健康检查全绿、用户却全部拿到 500。三件事领域不同，但要的是同一种能力：把“我看到了什么”一步步变成“根因是什么”，并且每一步都留下别人能复查的证据。本章用站内真实留下的运行记录当证据，把这套推理完整走三遍——三个案例的证据分别是 `docs/runs/ddp-cpu.json`（数值）、`docs/runs/dcp-cpu.json`（恢复）、`tests/test_rollouts.py` 加 `docs/runs/online-http.json`（服务），你可以在读推理的同时打开记录逐字段核对。

## 诊断是证据链，不是猜

直觉给出的第一个解释几乎总是最可及的解释，而不是最可能的解释：看到 NCCL 超时就怀疑网卡，看到 loss 突跳就怀疑数据脏了。诊断的方法论是把这件事流程化地反过来——先承认自己不知道，然后用实验把可能性一块一块砍掉。

具体是一条收缩路径：

1. **钉住症状。**哪个指标、什么时刻、影响多少请求或多少 rank；“TTFT 变差”不够，“重启后 15 分钟内 p50 TTFT 从 180 ms 升到 360 ms，输入长度分布不变”才是一个可以被攻击的陈述。
2. **列出候选假设。**通常三个就够覆盖大部分空间；每个假设必须写明机制——“数据解码让 GPU 等待”，而不是“数据有问题”。
3. **给每个假设设计判别性实验。**判别力的来源是预测差异：两个假设对同一个实验给出不同预测，这个实验才有资格裁决它们；预测相同，做了也是白做。
4. **先写下期望输出，再看结果。**看到 1e-08 再解释成“大概是舍入吧”，与预测了“舍入应当是 1e-8 量级”然后看到 1e-08，是两种可信度完全不同的推理——后者才是证据。
5. **让结果杀死假设。**每轮砍掉至少一个候选，剩下的假设空间越来越小，直到只剩一个能同时解释全部证据，或者证据不足、明确说不足。

还有一条贯穿三个案例的提醒：**症状在哪里被观察到，不等于根因在哪里。**rank 3 报通信超时，可能只是它在等待一个早已异常退出或走错调用顺序的同伴——报错位置是观察点，不是病因；健康检查在服务进程里被观察到 200，用户却在网关之外经历 500——观测点与故障点隔着整整一条请求路径。收缩法因此总是双向的：既要沿着调用链往下钻（从症状到机制），也要横向核对观察口径（这个症状本身可不可信、在哪个位置测的）。

假设从哪里来？从机制来，不从关键词来。“数据有问题”是关键词联想，“解码让 GPU 等待、供应跟不上计算”是机制——机制能推出可检验的预测（替换数据源后 GPU 空白应当缩短），关键词不能。三个案例的假设清单都长成“三条、各指向一段明确的因果链”的形状，这不是巧合：少于三条容易过早锁定在第一个解释上，多于五条说明症状还没钉清楚、该回到第一步。

上一章（<a href={asset('read/observability/')}>observability 章</a>）给了三种信号与最小证据包；本章的三个案例分别发生在训练、恢复、服务三种现场，但裁决手段是同一个：对照实验。

## 案例A（数值类）：DDP 误差 1.49e-08，是 bug 还是舍入

**症状。**<Term id="ddp" /> 的承诺是“多份模型学成同一份参数”。`labs/distributed/ddp_check.py` 跑完，两条路径的最大参数误差不是 0，而是 `1.4901161193847656e-08`（`docs/runs/ddp-cpu.json`，2026-09-13，torch 2.14.0，gloo，world_size 2）。一个非零的误差摆在面前，三种解释都说得通：

- **假设 A1：梯度同步有逻辑错误**——忘除以进程数、样本分片重叠、或者梯度根本没同步；
- **假设 A2：初始状态就不一致**——两个 rank 的初始参数或环境不同，误差从第 0 步就存在；
- **假设 A3：浮点舍入路径不同**——数学上等价的两次计算，在 fp32 里走了不同的舍入路径。

**判别实验的设计。**这一步的关键动作是**对照全局批次基线**：让单进程一口吃下全部 4 条样本走一步 SGD，与两个进程各吃 2 条、梯度经 <Term id="allreduce" /> 同步后各走一步，对**同一批数据**各走一次更新，再逐参数比较。脚本把两条路径放进同一份代码、同一次运行——`copy.deepcopy(model)` 保证基线与 DDP 从逐位相同的参数出发，环境、种子、数据张量完全相同，唯一的差别就是执行路径本身。这个“唯一差别”是整件事的支点：如果误差只在切换执行路径后出现，它就只可能来自执行路径（A1 的逻辑，或 A3 的舍入），不可能来自初值（A2）。

复现这条基线的命令与全部环境字段都在运行记录里：

```bash
torchrun --standalone --nproc-per-node=2 labs/distributed/ddp_check.py
```

`docs/runs/ddp-cpu.json` 的 `command` 字段就是这一条。读记录时先读 `scope`：“equal local batch sizes; one SGD update; not a GPU performance result”——它声明了这条证据只支持“一次更新的等价性”，不支持任何性能结论。scope 字段是每条证据自带的适用范围声明，读结论之前先读它，这一习惯后面每个案例都要用。

**每个假设的预测，先写下来。**

- **A1 预测：误差与梯度本身同量级。**逻辑错误的家族——忘除以进程数、分片重叠、漏同步——改变的是“平均”的数学，不改变数字的量级。<a href={asset('read/ddp/')}>ddp 章</a>用整数算过一例：3+1 分片的错平均得到 (3+7)/2=5 而非 4，错 25%；忘除以 2 则梯度整体翻倍。梯度量级 0.1–1、乘学习率 0.01 后，参数误差应落在 1e-3–1e-2。
- **A2 预测：误差 O(0.1–1) 且出现在第一次前向。**初始参数不同，第 0 步的损失值就已经不同，误差不可能小到 1e-8。
- **A3 预测：误差恰好一格表示精度。**fp32 机器精度 ε = 2⁻²³ ≈ 1.2×10⁻⁷，单次加法舍入以 u = ε/2 ≈ 6×10⁻⁸ 为界；聚合涉及十几次加法、<Term id="gradient" /> 量级记为 G ≈ 0.1–1，两条路径的梯度差上界约 10⁻⁸–10⁻⁷。乘学习率 0.01 后是 10⁻¹⁰–10⁻⁹——已经小于参数本身的一格表示精度，于是最后一层是量化：参数落回 fp32 网格，多数参数舍到同一个数，恰好跨过舍入分界线的参数差整整一格（一格 ULP）。

**证据。**实测 `1.4901161193847656e-08` 比任何逻辑错误的预测小六个数量级——A1 死。同环境重跑（单线程、固定种子、固定数据）逐位复现同一个数，误差出现的位置在更新之后而非前向——A2 死。而这个数有一个精确的身份：`1.4901161193847656e-08` 恰好等于 2⁻²⁶，正是数值落在 [0.125, 0.25) 区间的参数的一格 ULP；本模型宽度 32 的线性层初始幅度约 ±0.177（≈1/√32），正好在这一档。预测被逐位命中——A3 是唯一活着的解释。

把三个假设的账并成一张判决表——预测写在左边的实验才配拥有这张表：

| 假设 | 预测量级 | 实测 | 判决 |
|---|---|---|---|
| A1 同步/缩放逻辑错 | 1e-3–1e-2（错平均 25%、忘除 2 则翻倍） | 1.49e-08，小六个数量级 | 杀死 |
| A2 初值或环境不一致 | O(0.1–1)，且第一次前向就错 | 误差在更新后才出现；重跑逐位复现 | 杀死 |
| A3 舍入路径差异 | 10⁻⁸–10⁻⁷ 的梯度差，量化后 0 或 1 格 ULP | 恰为 2⁻²⁶ = 一格 ULP | 支持 |

**结论。**`docs/runs/ddp-cpu.json` 记录 `matches_global_batch: true`：误差是舍入的量化，不是逻辑差异的信号。注意这里用的是误差的**形状**而不只是大小——1.49e-08 是 2 的精确幂次、恰好等于某一档数值的一格 ULP、且落在该档参数确实存在的区间上。数值类故障的指纹常常这样藏在数的身份里：不是“很小所以没事”，而是“小得恰好、小得可解释”。反过来，如果哪天有人向你报告一个“说不清来历”的非零误差，第一个问题应当是：这个量级对应哪一类机制？

这个案例还有一层方法论收益：脚本里的断言 `torch.testing.assert_close(a, b, atol=2e-6, rtol=2e-5)` 本身就是一个预先写好的判别实验——它比舍入量级（1e-8）宽约两个数量级（atol 是实测误差的约 134 倍），又比逻辑错误（1e-2）窄四个数量级，恰好落在“容纳舍入、拦住逻辑错误”之间的判别带上。若某天断言失败而误差只升到 1e-6 量级，先查环境（线程数、后端、torch 版本）再查逻辑；涨到 1e-2 量级，几乎必然是归一化或分片错了——**误差的量级本身就指向假设**。而换到 GPU 与 NCCL 之后，具体的数会变、判别带不动：断言写成量级判断，而不是把 1.49e-08 硬编码成期望值——这是“不可复现时降级”的提前演练，方法论一节会回到它。

## 案例B（恢复类）：恢复后 loss 突跳

**症状。**训练夜间中断，从检查点恢复。注意症状里两个细节的分量：“恢复脚本正常退出、没有任何报错”——加载链路自己声明了成功，所以故障（如果有）在声明的覆盖之外；“loss 跳回 2.5 量级”——接近随机初始化的水平（量级参照：随机初始化的模型对词表近似均匀猜测，loss 应在 −ln(1/词表) 附近或更高——<a href={asset('read/tiny-training/')}>tiny-training</a> 项目词表 7，−ln(1/7)≈1.95，实测初始 loss 2.5986，同一档）。第二个细节已经悄悄偏向“参数错了”一边，但量级特征只是先验，不是证据——判别要靠实验。三种解释：

- **假设 B1：检查点根本没加载上。**DCP 的 `dcp.load` 是就地填充——按 `.metadata` 往预制的容器里填数，加载被跳过或读空时未必大吵大闹；模型可能还是随机初始化的值。
- **假设 B2：加载发生了，但状态不全。**优化器动量、step 计数、rng 状态、数据进度——<Term id="checkpoint" /> 里跨步存活的每一类状态，漏掉任何一样都可能让训练走岔。保存侧的 state 有三键（model、optimizer、step），漏掉哪一键，症状不同。
- **假设 B3：状态是全的，loss 突跳是训练的真实现象。**数据分布变化、调度策略，或者本来就该跳。

**怎么区分“没加载上”和“加载了但状态不全”——这是本案例的核心判别问题。**答案是问一个时机问题：**恢复后第一次前向的 loss 对不对？**参数错了，第一次前向就错；参数对了、更新后走岔，问题在更新所依赖的状态里。`labs/distributed/checkpoint_check.py`（<a href={asset('read/recovery/')}>recovery 章</a>逐行走读过）把两种情形都做成了可控的实验：

- **判别“没加载上”：换种子对照。**恢复用的模型在加载前用 `torch.manual_seed(99)` 重新初始化——与基线毫无关系的随机值。若 `dcp.load` 静默失效，参数还是这批随机值，误差是 O(0.1–1)；若加载真的发生，随机初值被整体覆盖，误差回到 0。这一个设计把“静默失效”从不可见变成响亮：大误差 = 没加载上，零误差 = 加载发生了，两种结果都有明确解读。这也是“失败也要能杀假设”的范本——对照的两种结局各有名字。
- **判别“状态不全”：非张量探针 + 破坏性验证。**state 里的 `step` 故意填错误值 0，加载后断言它必须变成 1——加载若真的发生，错误值必然被覆盖，这一条同时验证了非张量状态随检查点走。再主动做一次破坏：把 state 里的 `'optimizer'` 键删掉重跑——加载依然成功、不报错，但恢复后的第一次更新就与连续基线分岔（AdamW 的一阶/二阶矩被清零，第一步的方向与步长都是错的）。这亲手验证了“状态不全”的指纹：**加载时不报错，更新后走岔。**没有这次破坏，你只是相信断言有牙齿；破坏之后，你知道它有。
- **判别“本来就是训练现象”：连续基线对照。**基线不停机，原地多走一步并把参数克隆成独立副本当答案（克隆是把“基线答案”冻结成谁也动不了的参照）；恢复路径从检查点重放同一步。固定数据、无 dropout、同一 world size 下，两条路径是**同一个确定性函数在同样输入上的两次求值**——输入相同、状态相同、函数确定，输出应当逐位相同。确定性不是口号，是可以逐项清点的：输入固定（同一句 x/y，没有数据管线）、没有随机消费者（无 dropout，种子 99 的初始化被加载整体覆盖）、执行确定（单线程压掉归约顺序抖动）、状态完备（跨步存活的参数、优化器状态、步数三样全在检查点里）。

**证据。**`docs/runs/dcp-cpu.json` 记录 `next_step_max_error: 0.0`：恢复后走出的下一步，与从未中断的连续训练完全一致。B1、B2 在这个受控环境里都被排除，B3 也被排除——对照证明了突跳不是训练的固有行为。判据本身由“加载没报错”升级成了“**下一步等价**”，这是恢复类故障最重要的一个方法论动作。这个判据的严格性还是双向的：清单里任何一项漏存，0.0 立刻保不住；反过来，正因为随机流不参与，0.0 才敢要求。

用本案例的判据反推真实现场的操作顺序：生产上 loss 突跳时，你多半没有现成的连续基线，但同样的推理可以落地成三问——恢复后第一次前向的 loss 与中断前最后一个日志点接得上吗（接不上 → B1 方向）？接得上但几步内走岔（→ B2 方向，按指纹表定位缺哪类状态）？受控重放（固定数据、无 dropout、小步数）能复现突跳吗（能 → 真实故障可复现，进入修复；不能 → 环境或数据前提不同，先查前提）？三问的答案组合直接指向下一跳实验。

受控重放的参考命令同样有记录可查：

```bash
torchrun --standalone --nproc-per-node=2 labs/distributed/checkpoint_check.py --directory /tmp/ai-infra-dcp-lab
```

把 B2 展开成一张指纹表——缺失的状态不同，最早可见的症状出现在不同的时机，这正是区分它们的办法。症状出现得越早，缺的东西越基础：

| 缺失的状态 | 最早可见症状 | 判别手段 |
|---|---|---|
| 参数 | 恢复后第一次前向 loss 就错 | 换种子对照，误差应为 O(1) |
| 优化器动量 | 前向对，第一次更新后参数走岔 | 删键的破坏性验证 |
| step 计数 | 数值近似正确，日志与 lr 调度错位 | step 填 0，加载后必须变 1 |
| rng / 数据进度 | 第一个随机消费者处才分岔（dropout 前向、下个 epoch 的 shuffle） | 带 dropout 重放、跨 epoch 观察 |

**结论与边界。**“loss 突跳”不是单一故障，而是一族故障共享的症状；分岔出现的时机就是缺失状态的指纹——回到症状本身：“跳回初始量级”这个形状已经先验地偏向 B1（随机初始化的 loss 正是那个量级），而实验把它变成了结论。同时注意判据的适用范围：`dcp-cpu.json` 的 `scope` 字段写明 fixed data、no dropout、same world size——换到 GPU 与 NCCL、真实数据管线、弹性重分片之后，逐位相等不再可预期，判据必须降档为“数值近似”，并且把降档声明出来。若受控对照是 0.0 而生产环境仍在突跳，结论不是“判据错了”，而是生产的某条前提被打破了——去查前提，别去改容差。

## 案例C（服务类）：健康检查 200，业务却 500

**症状。**发布之后监控全绿：健康检查 200、进程数正常、CPU 内存正常；用户报告所有请求拿到 500。三种解释：

- **假设 C1：服务还没就绪。**health 过早返回 200，业务路径还在初始化（权重没加载完、依赖没连上）——一个启动竞态。
- **假设 C2：业务路径坏了。**健康与业务是两条代码路径，health 不经过的那部分（模型加载、处理逻辑、下游依赖）坏了。
- **假设 C3：服务本身是好的。**错误出在其他层——网关、客户端口径，观测看到的是假象。

三个假设各配一个便宜的判别动作：C1 用**时间**判别——等 health 稳定返回 200 之后症状是否仍在（竞态会自愈，稳态故障不会）；C2 用**直连**判别——绕过一切中间层，直接向服务本机发一个真实业务请求；C3 用**位置**判别——比较“直连的结果”与“经过网关的结果”，不一致才指向中间层。三个动作共用一次受控启动，成本几乎为零。

这三条假设不用停留在猜测：站里有一条可执行的判例——`tests/test_rollouts.py` 的 `test_health_success_does_not_hide_business_failure`。逐步读它怎么区分三者：

1. 用 `FAIL=true` 启动 `labs/rollouts/app.py`——注意这个环境变量只影响业务路径，是故意种下的“坏版本”；
2. 轮询等待 `/health` 返回 200——**C1 被控制住**：health 已经绿了，症状仍然存在，排除“还没就绪”；
3. 向 `/` 发一个真实请求，断言抛出 HTTP 500——**支持 C2**：业务路径确实坏了；
4. 请求直接打 `127.0.0.1` 的服务端口，不经过任何网关——**C3 被杀死**：故障在服务本身，不在网关层。

`app.py` 只有十几行，把“health 为什么会骗人”写成了机制：handler 里 `if self.path=='/health': status=200`——health 分支无条件返回 200，`FAIL` 只写在 else 分支。**健康与业务是两条代码路径**；探活绿只证明“进程活着、能 accept 连接、能执行 handler”，不证明“请求路径可用”。这正是 <Term id="metrics" /> 类证据的天花板：它度量的是你埋点的位置，不是用户经历的位置。同一个 fixture 还支持 `LATENCY_SECONDS` 注入延迟而不是错误——把 `FAIL=true` 换成 `LATENCY_SECONDS=2`，health 依旧秒回 200，业务每个请求慢 2 秒：错误与延迟共用这条“health 盲区”，判别手段也共用（打业务路径、量真实耗时）。

**该看哪层。**症状在客户端报告，就从客户端往下找第一跳——直接对服务发一个真实业务请求。把“验证一个服务”拆成分层清单，每层回答一个问题、只回答一个问题：

| 层 | 探什么 | 证据 | 站内判例 |
|---|---|---|---|
| 进程 | 活着吗、能执行 handler 吗 | `/health` 200 | 判例的等待循环 |
| 业务路径 | 请求路径可用吗 | 真实路径的状态码与耗时 | 判例的 500 断言 |
| 业务面 | 部署的版本对吗、资产齐吗 | 一组代表性路径的 200/404 | `online-http.json` |
| 因果链 | 断在哪一层、谁等谁 | 带 traceparent 的请求 | `trace_request.py` |

站内“业务面”一层的判例是 `docs/runs/online-http.json`：部署后打的不是 health，而是 13 条真实路径——9 条应当存在的（首页、生成/Attention/DRA 章节、极小模型项目、vLLM 源码阅读、pagefind 脚本、webp 图片、labs.zip 下载）全部 200，4 条旧路由（`/learn/01-request/` 等）确认 404。每条路径各测一件事：内容页验证构建产物正确，静态资源验证资产在，下载验证打包在，旧路由 404 验证旧版本确实没上线——404 在这里是**预期的正面证据**，这提醒我们判别性实验里“什么算失败”是要预先定义的，不是看到非 200 就算坏。一个 `/health` 200 提供不了其中任何一条：如果部署了错误版本，health 照样 200，而业务面会以 404 的形式喊出来。

再往上一步，**业务探活也要带身份**。`labs/observability/trace_request.py` 把 W3C `traceparent` 头注入发往 vLLM `/v1/chat/completions` 的真实请求，trace_id 能在 Jaeger 里检索到。这样探活失败的那一刻，<Term id="trace" /> 已经在系统里，诊断从“哪个请求、断在哪一层”直接开始，而不是从零猜起。脚本 docstring 老实写了边界：不虚构网关或 GPU <Term id="span" />，检索到的是真实返回的那条——探活脚本自己也要遵守“不造证据”的纪律。

**结论。**health 是第 0 层证据，适合回答“要不要重启”，回答不了“服务是否可用”。发布或重启后的验证要在业务面上做——真实路径、真实负载形状；并且失败样本要能接上 trace。同一个测试文件里还有一条量方面的纪律：`test_rejects_unreviewed_deploy_and_missing_evidence` 要求证据只有 “2 requests” 时动作必须是 hold——健康绿加两个样本，不够放行一次 deploy。判别与决策共用同一条证据标准。

最后把这一层与 <Term id="slo" /> 对齐：SLO 定义的是用户视角的成功（例如“p99 TTFT < 300 ms 的请求占比 ≥ 99.9%”），那么验证发布也必须在用户视角的路径上度量——health 绿不进 SLO 的分子，也不该进发布检查单的通过条件。观测口径离用户越近，证据越贵也越硬；分层探活的意义就是用最便宜的一层守着“要不要重启”，用最贵的一层裁决“能不能算好”。

## 方法论：设计能杀死假设的实验

三个案例走完，把可复用的部分压成四条设计原则、一座证据金字塔和一条复现纪律。

**判别性实验的四条原则。**案例之间领域不同，但把每个实验拆开，反复出现的是同一组设计决策：

1. **一次只变一个。**案例A 把基线与 DDP 放进同一进程、同一次运行，唯一差别是执行路径；案例B 的恢复路径与连续基线共用同一份数据与同一个 step 函数；案例C 的 A/B 只切换实例新旧，负载与输入固定。变量多于一个，结果无法归因——“改了三个参数后变快”不是任何参数的因果证据。这条原则也是对照实验成本的主要来源：钉住“其余一切不变”需要环境管理、种子管理、数据管理，三个案例的脚本里 `torch.set_num_threads(1)`、`manual_seed`、固定张量这些看似啰嗦的准备段，全部在为它服务。
2. **期望输出先写下来。**案例A 在看结果之前先写下两个量级：逻辑错 1e-2、舍入 1e-8，然后看到 1e-08 恰好落在舍入档、还等于 2⁻²⁶。预测写在前面，结果是判决；预测写在后面，结果只是素材——事后总能找到一个能解释任何数字的故事，这正是“事后合理化”能毁掉整条证据链的原因。写预测时尽量写成可比较的数（量级、区间、精确值三档，能写多细写多细），而不是“应该差不多”。
3. **失败也要能杀假设。**好实验的每种结果都有解读：换种子对照里，大误差意味着没加载、零误差意味着加载了；全局批次对照里，误差落在舍入档意味着数值机制、跳到 1e-2 档意味着逻辑错误。设计实验时先自问：如果结果是 X，我会改变哪个判断？如果结果是 Y 呢？哪种结果都不改变判断的实验，不值得跑——它只是在收集故事。
4. **主动破坏一次。**删一个键、换一个种子、填一个错误值——验证判据本身有牙齿（案例B 的删键重跑、填 0 探针）。一个从未被弄碎过的断言，通过不构成证据：你不知道它是因为正确而通过，还是因为永远都会通过。破坏性验证是给判据做的“反向测试”，成本低（通常是把已有实验改一个参数重跑），信息量大。

**证据金字塔。**从弱到强：

| 层 | 回答什么 | 案例 |
|---|---|---|
| <Term id="logs" /> | 发生了什么事件 | C 里 500 的访问日志只说“坏了” |
| 指标 | 何时开始、影响多大 | C 里全绿的监控恰恰是误导源 |
| trace | 事件串成的因果路径 | trace_request.py 定位“断在哪层” |
| 对照实验 | 因果归因 | A 的全局批次基线、B 的连续基线、C 的直连业务请求 |

用法是自下而上收集、自上而下裁决：金字塔顶缺一块时（案例C 初期只有 health 指标），结论只能停在“证据不足”，而证据不足本身就是可行动的结论——它告诉你下一个实验该补在哪一层。还要当心塔底的证据**主动说谎**的可能：案例C 的全绿监控不是“缺少证据”，而是“给错了证据”；遇到观测与用户报告冲突时，先怀疑观测的埋点位置，再怀疑用户。

**杀假设的顺序。**三个候选不必轮流各做一个实验——按“信息量 ÷ 成本”排序：优先做一次采集能同时裁决多个假设的实验（TTFT 的时间线分解一次服务三个假设；两个进程各打印一条 JSON 的 DDP 记录同时含有样本分片与误差两个字段）；把只能裁决一个假设、且成本高的实验（例如跨机 A/B）留到候选已收敛之后。每杀掉一个假设就重新排序一次，因为剩下的假设决定了哪些实验还有判别力——上一个实验的结果会改变下一个实验的性价比，这也是“收缩”二字的含义。

**“先复现再修”，与不可复现时的降级路径。**理想路径是修复前先在受控环境复现——1.49e-08 在单线程、固定种子、固定数据下逐位可复现，复现了才有资格说“修好了”，也才有办法证明“修好了”（同样的实验再跑一遍）。但训练与服务现场常常给不出这种确定性，此时逐档降级，且每一档都要声明降到了哪一档：

| 档 | 复现什么 | 例子 |
|---|---|---|
| 逐位复现 | 同环境重跑得到同一个数 | ddp 的 1.49e-08（单线程、固定种子、固定数据） |
| 量级复现 | 具体数字变、量级不变 | 换 GPU 与 NCCL 后误差仍应在 1e-8 档，断言写成量级判断 |
| 统计复现 | 复现分布而非个体 | 真实流量下比较分位数与直方图，不是单点对单点 |
| 机制复现 | 用小模型把机制单独复现 | `docs/runs/tiny-model-cpu.json` |

机制复现那一档的判例值得整句读：`tiny-model-cpu.json` 记录 100 步 loss 2.5986→0.000875、`mechanism_tests_passed: 5`、`cache_generation_equal: true`，但 `limitation` 字段写明“单句过拟合 sanity check，不是 held-out 评估或 GPU 性能测量”。它复现的是“因果/缓存/梯度/恢复这些机制在该实现里成立”，不是“这个模型有用”。每条 `docs/runs` 记录都带 scope 或 limitation 字段；读结论先读边界，没有声明降档的“复现了”三个字会骗人。

**最后写一份能被推翻的诊断记录。**模板如下，用案例A 实填一遍做示范：

| 项目 | 案例A 的实填 |
|---|---|
| 症状 | 两路径最大参数误差 1.4901161193847656e-08（torch 2.14.0，gloo，world 2） |
| 假设 | A1 同步/缩放逻辑错；A2 初值不一致；A3 舍入路径差异 |
| 对照 | 单进程全局批次基线，同进程同次运行，仅执行路径不同 |
| 预测 | A1 → 1e-3–1e-2；A2 → O(0.1–1) 且前向即错；A3 → 0 或 1 格 ULP |
| 结果 | 实测恰为 2⁻²⁶（[0.125, 0.25) 档一格 ULP）；重跑逐位复现 |
| 结论 | 支持 A3；证据记录 `docs/runs/ddp-cpu.json` |

通用的空表是：

| 项目 | 应写内容 |
|---|---|
| 症状 | 哪个指标、何时、影响多少请求或 rank |
| 假设 | 一个明确机制，例如“数据解码让 GPU 等待” |
| 对照 | 仅替换数据源，保持模型与批次一致 |
| 预测 | 若假设成立，GPU 空白与 step 时间应降低 |
| 结果 | 原始样本、环境、重复次数与误差 |
| 结论 | 支持、否定或证据不足；下一步是什么 |

注意实填示范里“预测”一行是在看到结果**之前**就定型的三档量级——这正是这张表能被推翻的原因。业务需要紧急缓解时，可以先降流量或回滚——但缓解与根因是两件事，事后仍要补做能区分原因的实验，否则下一次还是同一个事故。

## 动手：给“重启后 TTFT 变差 2 倍”设计诊断

三个真实案例的推理结构，现在轮到你套到一个新症状上。先把口径钉进一张清单——每一行都是“变差 2 倍”这个说法背后必须先回答的问题：

| 口径项 | 要回答什么 |
|---|---|
| 定义 | 首字节、首个 SSE 数据块，还是首个模型 token？ |
| 统计 | 哪个分位数？多少样本？直方图长什么样，还是只有平均？ |
| 输入 | 前后输入长度分布、到达速率是否相同？ |
| 身份 | 前后模型 revision、实例配置、节点是否相同？ |
| 时间 | 变差是重启后立即、渐进、还是延迟出现？持续还是暂态？ |

然后按顺序做：

1. **先钉口径。**上表逐行填空——口径不钉住，后面全部是沙滩上的房子。特别提醒两件 <a href={asset('read/observability/')}>observability 章</a>讲过的坑：平均值会把“一半没变、一半翻倍”藏成一个 1.5 倍，先看直方图；各实例的分位数不能求平均当全服务的数，比较前先统一口径。
2. **写下三个候选假设。**每个假设必须是一个明确机制，并附一个判别实验和**双向预测**——什么结果支持它，什么结果杀死它。
3. **把实验按成本排序，先跑最便宜的。**提示：几个假设常常共用同一条证据采集，一次采集能同时服务多个判别。
4. **写完再核对一遍。**对照“四条原则”逐条过：变了几个变量？预测写下来了吗？每个结果都有解读吗？——这四问就是自检清单。

**题**：服务重启后，TTFT 变差 2 倍，且持续不是瞬间。给出三个候选假设与各自的判别实验。

<details>
<summary>展开核对</summary>

三个可用的候选（你的清单不必相同，但每个都应能被某个结果杀死）：

- **H1 前缀缓存被清空。**重启清掉了 <Term id="prefix-cache" />，原本命中的长前缀现在要完整重新 <Term id="prefill" />，而 KV 重建也占用算力。判别实验：对比重启前后**同一组请求**的缓存命中率，并把 TTFT 分解成排队段与 Prefill 段。预测：命中率从原来的水平掉到接近 0，Prefill 段显著变长，排队段基本不变；若命中率没有掉、变长的也不是 Prefill 段，H1 死。附一个时间维度的旁证：若几小时后随缓存重建 TTFT 逐渐回落，支持 H1。
- **H2 配置或版本漂移。**新起的实例用了不同的 revision 或配置——batch 策略变了、编译缓存失效、某项调优参数没进配置管理。判别实验：diff 重启前后实例的镜像 digest 与全部配置项；若旧实例还活着（或能起一个），做单变量 A/B——负载与输入固定，只切换实例新旧。预测：diff 非空，或 A/B 稳定复现差值；逐项相同且 A/B 无差异，H2 死。
- **H3 重启期间的排队积压。**停机窗口内请求堆积，重启后队列先消化积压，排队时间推高了 TTFT。判别实验：把 TTFT 按时间轴分解，看重启时刻附近的等待队列长度与到达速率曲线。预测：增长主要来自排队段，且随队列清空 TTFT 回落——症状是暂态；若队列早已清空而 TTFT 仍持续 2 倍，H3 死。

注意三个假设共用同一条分解时间线（排队 / Prefill / 输出首 token）：一次 trace 采样同时服务三个判别——这就是“先跑最便宜的”的含义，也是三个案例共同的底层结构——**证据采集一次，判别力来自预测的差异**。

核对你的答案时再检查三件事：每个假设是否都写明了“什么结果杀死它”（写不出来的假设是不可否证的，要重写）；H2 的 A/B 是否做到了只变实例新旧这一件事；以及——如果三个实验都做完、假设都还活着或都死了，你的下一步是列第四个假设，还是回到第 1 步怀疑症状口径本身？后一种直觉常常才是资深与否的分界。
