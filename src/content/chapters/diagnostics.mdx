假设服务昨天还能处理目标负载，今天首 token 突然变慢。直接重启可能暂时清空队列，却没有解释原因。我们需要一条可以复查的推理链：看到什么，怀疑什么，做什么实验，什么结果会推翻假设。

## 先把“慢”变成可定位的变化

第一步固定比较对象。模型 revision、长度分布、到达速率、硬件和测量口径是否相同？如果今天输入平均长度翻倍，不能把全部变化归因于发布版本。保存未聚合的样本，避免只剩一个总平均数。

第二步分阶段。TTFT 升高而输出间隔基本稳定，优先看排队与 Prefill；输出间隔也明显升高，继续看活动批次、KV 读取与资源竞争。两者都正常但客户端总耗时增加，检查输出长度、网络和客户端处理。

## 案例一：GPU 常空闲，训练 step 却很长

观察：每个 step 中，GPU 有规律地出现空白区间；CPU 有解压活动；把数据替换为内存中的固定张量后，空白显著缩短。这个对照支持“数据供应不足”，但没有证明是磁盘本身慢。解码、转换、采样或进程间传递都可能参与。

接着分别测读取原始字节、解码成张量、拼批与主机到设备搬运。只增加 DataLoader worker 可能加重存储竞争，也可能因为复制更多缓存而耗尽内存。观察队列与阶段时间，再决定改数据格式、预处理或并发数。

## 案例二：小批次能跑，大批次 OOM

先按训练或推理分账。训练看参数、梯度、优化器状态与保存的激活；推理看权重、KV、临时张量和执行工作区。记录峰值发生在哪一步，而不仅是报错后的占用。

若降低序列长度明显降低峰值，优先分析随 token 增长的数据；若加载模型时就失败，批次调度还未开始，应先检查权重表示与加载峰值。分配器保留内存与活动张量内存也不同，不能把缓存分配器的保留量直接称为泄漏。

验证泄漏需要重复稳定工作负载，检查活动对象与已分配内存是否持续增长。释放 Python 引用、等待异步工作完成、区分缓存保留后，再讨论长期增长。

## 案例三：NCCL 超时发生在 rank 3

报错 rank 是观察到超时的一方，不一定是最早出错的一方。先找所有 rank 时间线上最早的异常：某个数据批次读取失败、某进程提前退出、不同 rank 分支进入不同 collective，都可能让其他进程最终在 NCCL 等待。

先运行小 collective，验证基本连通；再用接近真实消息大小的测试，检查大消息路径；最后放回训练，观察调用顺序与计算重叠。小 AllReduce 通过，只能排除一部分问题，不能证明长时间训练没有网络或应用逻辑故障。

## 案例四：取消请求后容量回不来

区分客户端关闭连接、网关取消、引擎收到 abort、调度器停止推进和块管理器释放引用五个事件。用同一 request_id 追踪后端是否还在生成。缓存中保留可复用的空闲块不一定是泄漏，但活动请求引用不能永久遗留。

实验先记录空闲基线，再发长生成并取消，等待有限时间，看活动请求归零与新请求能否重新获得容量。重复多轮观察是否累积。若只看 HTTP 连接关闭，就无法证明资源释放。

## 写一份能被推翻的诊断记录

| 项目 | 应写内容 |
|---|---|
| 症状 | 哪个指标、何时、影响多少请求或 rank |
| 假设 | 一个明确机制，例如“数据解码让 GPU 等待” |
| 对照 | 仅替换数据源，保持模型与批次一致 |
| 预测 | 若假设成立，GPU 空白与 step 时间应降低 |
| 结果 | 原始样本、环境、重复次数与误差 |
| 结论 | 支持、否定或证据不足；下一步是什么 |

不要把“改了三个参数后变快”写成某个参数的因果证据。若业务需要紧急缓解，可以先降流量或回滚；事后仍要补做能区分原因的实验。
