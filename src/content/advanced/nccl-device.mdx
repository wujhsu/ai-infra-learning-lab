先完成集合通信、拓扑与 NCCL 主线。设备侧通信把部分通信控制放入 GPU 执行过程中，使更细粒度的计算通信组合成为可能，同时也要求更清楚地理解内存可见性与参与范围。

## 先分清三个“完成”

主机已提交操作、数据已经传输、消费者可以安全读取，是不同事件。一个线程写完局部结果，不代表远端 GPU 已可见；一个局部 barrier，也不自动同步所有 rank。

因此，每个同步点都要写出参与者、保证的顺序与受保护的数据。若发送者发出信号后仍会修改数据，接收者可能读到错误版本；若接收方永远等待一个未参与的发送者，系统会死锁。

## 对象范围决定合法操作

NCCL Device API 使用设备通信器、可访问内存窗口、通信成员与协作线程范围等概念组织能力。先查询所需硬件与传输支持，再建立对象；不要把一段适用于特定拓扑的示例当作所有 GPU 都可执行。

大会的流水线图可以帮助理解计算与传输分段，但每个箭头都应附上生产、发送、通知、等待和消费边界。只画重叠区域而不说明依赖，无法判断正确性。

## 一个双缓冲思考实验

生产者交替写缓冲 A 与 B。消费者读 A 时，生产者可写 B；但再次覆盖 A 之前，必须知道消费者已完成 A。至少需要区分“数据就绪”与“空间可重用”两种状态。

如果只用一个布尔标志，多轮操作可能把旧通知误当新通知。序号或代际可以帮助区分轮次，但仍需遵循 API 的内存顺序约束。这里是协议推导，具体实现要按固定 NCCL API 检查。

## 如何研究而不误报性能

先用可预测数据与多轮校验验证可见性，再加入计算；最后比较串行、常规流重叠与设备侧方案。记录拓扑、消息规模、同步开销和资源占用，确认没有通过省略正确同步获得假提速。

本库保留官方 API 与会议案例作为入口，设备侧硬件实验未运行。主线的普通 AllReduce 与 overlap 模型不能代替这一专题的真实验证。
