## 项目地图与边界

交付包括训练 Job、模型制品、推理 Deployment 或 LWS、资源分配记录、持久存储、指标、故障演练与发布复盘。先在独立实验集群执行，明确命名空间与资源预算。所有集群步骤在本次工作站未运行，清单审阅不等于集群验收。

建议以 Kubernetes 1.36 系列为实验基线，记录具体补丁版本、驱动和插件镜像。DRA、Kueue、LWS 与 Rollouts 分别检查其安装版本、CRD 和功能门，不能把滚动文档直接当作已安装功能。

## 第一步：训练任务与持久产出

把项目一源码构建进训练镜像，将 `python labs/tiny_model/train.py` 作为 Job 命令，输出路径挂载到独立 PVC 或可提交的对象存储位置。先用 CPU Job 验证镜像、挂载与退出状态，再增加 GPU 训练路径。

训练结束后，用另一个 Pod 从相同存储加载检查点并继续训练一步。随后删除原训练 Pod，再重复加载，证明结果没有只保存在容器临时层。记录文件摘要、模型配置、完成步数和恢复结果。

配套 `labs/kubernetes/training-job.yaml` 是 PVC 与镜像字段明确标注的模板；`training.Dockerfile` 从仓库根目录构建。先替换镜像仓库地址并检查存储类，再提交，不能把模板占位符当作部署成功。

## 第二步：单 GPU 服务

```bash
kubectl apply --dry-run=server -f labs/kubernetes/vllm.yaml
kubectl apply -f labs/kubernetes/vllm.yaml
kubectl -n inference-lab get pods -w
kubectl -n inference-lab port-forward service/vllm 8000:8000
```

server dry-run 验证当前 API 接收清单，不证明设备足够或容器能运行。观察事件，分别检查镜像、设备、挂载、加载与 readiness；通过项目四的短请求后才记为服务可用。

## 第三步：分清准入与设备实验

Kueue 实验先让两个短 Job 进入同一 LocalQueue，设置只能容纳一个任务的预算，观察第二个等待及前一个完成后的准入。不要直接在共享团队队列调整预算。记录 Workload 状态与首次有效执行时间。

配套 `labs/kubernetes/kueue.yaml` 为 Kueue 0.19.0 的 CPU 准入实验：独立队列只有 1 CPU 预算，两个 Job 各请求 1 CPU，各运行约 45 秒。检查当前集群已安装对应 CRD 后执行：

```bash
kubectl apply --dry-run=server -f labs/kubernetes/kueue.yaml
kubectl apply -f labs/kubernetes/kueue.yaml
kubectl -n queue-lab get workloads,jobs,pods -w
```

预期同一时刻只有一个任务获得该预算；谁先运行由准入策略决定，不以名字承诺顺序。完成后清理 `queue-lab` 以及本次独立的 ClusterQueue、ResourceFlavor。此实验不验证真实 GPU 放置。

DRA 路径使用 `labs/kubernetes/dra.yaml`，把 `example-gpu-class` 替换为真实驱动的 DeviceClass，并核对容器运行时要求。先读 ResourceSlice 库存，再创建声明和 Pod；观察分配、准备、使用和清理。

独立声明不会因为实验 Pod 结束就必然立即消失。结束后明确删除本实验消费者与声明，再提交第二个请求，验证设备可以重新分配。模拟驱动只能验证控制面流程，真实 GPU 使用必须另测。

## 第四步：多节点工作组

```bash
python3 labs/kubernetes/render-lws.py --model-revision c1899de289a04d12100db370d81485cdf75e47ca > lws-lab.json
kubectl apply --dry-run=server -f lws-lab.json
kubectl apply -f lws-lab.json
```

模板为两节点、每节点一 GPU、PP=2 的教学路径，安装 LWS 0.10.0 后再核对 schema。它先运行 collective 检查，再启动固定模型。小模型跨两节点未必提速，目的是理解生命周期与通信。

worker 的 preflight 文件只能说明前置检查通过；完整服务还需 leader 就绪和真实推理请求。检查组内镜像、模型 revision、rank 与地址一致。故障演练让一个 worker 退出，观察组重建、路由与恢复时间。

## 第五步：观测与受控发布

先采集基础指标与事件，再接入追踪。用请求 ID、Pod UID、节点和 GPU UUID 建立关联。注入一次长输入压力，按诊断章形成假设与对照，不把所有变化归因于 GPU 利用率。

`labs/rollouts/` 提供可控失败的 CPU 服务与分析模板生成器。构建并推送自己可访问的镜像后：

```bash
python3 labs/rollouts/render.py --image YOUR_REGISTRY/ai-infra-fixture:VERSION > rollout-lab.json
kubectl apply --dry-run=server -f rollout-lab.json
```

替换两个占位字段并安装对应 Rollouts CRD 后再实际 apply。此实验用副本比例近似流量比例，没有精确百分比路由器；迁移到模型服务时，需要在完整版本工作组之间实现路由与排空。

先验证正常候选，再把候选业务路径配置为失败，确认分析失败和回滚；另测无数据状态与质量失败。CPU 决策单元测试不能替代集群流量演练。

## 最终报告与清理

报告沿同一条链组织：制品 → 任务准入 → 设备与存储 → 工作组 → 请求 → 观测 → 故障 → 恢复。每一步附实际状态与时间，并把未执行项保留为未验证。

清理前导出日志、指标、检查点与分析记录。仅删除本项目创建的命名空间、独立 ResourceClaim 和临时文件；PVC 是否删除要由数据保留计划决定。不要为了清理实验卸载共享集群驱动或控制器。

最终迁移题是把短文本服务换成长上下文图文服务：重新估算输入处理、GPU、KV、存储与启动时间，并设计一轮新基线。能够说明哪些配置需要重做，才算把平台机制用于新问题。
